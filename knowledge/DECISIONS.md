# DECISIONS — архитектурные решения фабрики

Формат: решение → обоснование → следствие в коде. Детальные ADR — в `adr/`.

| ID | Решение | Обоснование | Реализация |
|----|---------|-------------|------------|
| D1 | Controller на Python 3.11 без внешних фреймворков; единственная обязательная внешняя зависимость — `jsonschema` (валидация) и `PyYAML` (инвентарь). | Python 3.11 и PyYAML уже есть в среде (F2.2); минимум зависимостей = минимум supply-chain риска и воспроизводимость. `pydantic` не установлен и не обязателен: семантическая валидация всё равно доменная. | `factory/`, `requirements.txt` |
| D2 | Состояние очереди и job'ов хранится на диске (`var/state/*.json`, `queue/*`), а не в контексте модели. | Требование §7: Claude не является базой данных; worker должен переживать restart. | `factory/state.py`, `factory/queue.py` |
| D3 | Все производственные мутации выполняются только через `factory deploy`, который сам проверяет manifest, allowlist, авторизацию, backup, lock и quality gates. Claude не имеет права на произвольный SSH. | §5.5. Реализовано двумя слоями: PreToolUse-hook (детерминированный запрет) + deny-правила в settings.json. | `.claude/hooks/guard.py`, `.claude/settings.json` |
| D4 | Deployment-слой — декларативный, с двумя целевыми адаптерами: `ssh_ansible` (production/staging по SSH) и `local_disposable` (пилот и тесты). Выбор адаптера — из inventory, не из кода. | §4: «Ansible или другой обоснованный декларативный SSH deployment слой». Ansible в среде отсутствует (F2.4), поэтому playbook'и написаны и синтаксически проверяемы, а исполнение помечается `BLOCKED_ACCESS` до установки Ansible и передачи хоста. | `factory/targets/`, `automation/ansible/` |
| D5 | Атомарные релизы: `releases/<build_id>` + симлинк `current`, переключаемый только после health check; предыдущий релиз сохраняется. | §8.7, требование отката. | `factory/targets/base.py`, `automation/ansible/roles/dle_release` |
| D6 | Секреты только через `secret_ref` (имя переменной окружения или путь в secret-хранилище). Значения секретов никогда не попадают в git, лог, отчёт, скриншот и prompt. | §6. Проверяется юнит-тестами редактора и линтером артефактов. | `factory/redaction.py`, `tests/unit/test_redaction.py` |
| D7 | Пути DLE, требующие записи, НЕ угадываются. Профиль путей — обязательный входной файл `blueprints/dle20/profiles/paths.yaml`, заполняемый из официальной документации/дистрибутива. Без него установка даёт `BLOCKED_INPUT`. | §3.8 прямо запрещает угадывание; официальная документация заблокирована egress-политикой (F3.3). | `blueprints/dle20/profiles/paths.template.yaml`, `factory/blueprint.py` |
| D8 | Проверка лицензии — по домену второго уровня (eTLD+1 по встроенному списку публичных суффиксов проекта), до любой production-мутации. Нет покрытия → `BLOCKED_LICENSE`, установка не начинается. | §3.4 и F5.2. | `factory/licensing.py`, `inventory/dle-licenses.yaml` |
| D9 | SEO-контур — часть архитектуры: матрица индексируемости строится ДО шаблонов и является входом для рендера и для acceptance gates. Шаблон, тип страницы которого отсутствует в матрице, не рендерится. | §9A. | `knowledge/SEO_INDEXABILITY_MATRIX.yaml`, `factory/seo/` |
| D10 | Пагинация: серверные `<a href>`-ссылки обязательны; «Показать ещё»/infinite scroll — только progressive enhancement поверх них; каждая страница имеет self-canonical; page 1 имеет один канонический URL. Детерминированный порядок с tie-breaker по `id`. | §9A. Проверяется краулером и E2E. | `themes/*/templates/`, `factory/seo/lint.py` |
| D11 | Контент никогда не генерируется фабрикой. Отсутствующий обязательный контентный факт (в т.ч. `alt`) блокирует публикацию конкретного материала, а не заменяется значением по умолчанию. | §9, §13. | `factory/validation.py` (`BLOCKED_INPUT`, `BLOCKED_RIGHTS`) |
| D12 | VK-плеер и рекламный контур реализованы как адаптеры с явным contract-ref. Без переданного contract доступен только `mock`-адаптер и только для `environment: staging`; в production он технически недоступен. | §9, §11. | `factory/vk.py`, `factory/ads.py`, `tests/unit/test_vk_ads_gating.py` |
| D13 | Пилот выполняется на disposable local target (PHP built-in server), потому что staging-хост не передан, а Docker-демон недоступен (F2.5). Пилот проверяет весь SEO/QA-контур на реальном HTTP. | §11.10. | `factory/targets/local_disposable.py` |
| D14 | Fixture-пакеты помечаются `fixture: true` и отвергаются валидатором при `environment: production` — тестовые данные не могут попасть в production. | §10 «в production попали test/demo данные». | `schemas/site-package.schema.json`, `factory/validation.py` |
| D15 | CDN Video Hub не интегрируется. Создана версионируемая extension point и место под knowledge pack, обе — no-op до второго change request. | §11. | `plugins/cdnvideohub/`, `knowledge/cdnvideohub/.gitkeep` |
| D16 | Идемпотентность достигается контентной адресацией сборки (`build_id` = SHA-256 от нормализованного пакета + blueprint) и проверкой уже применённого релиза перед мутацией. | §3.11, §7. | `factory/build.py`, `factory/targets/base.py` |
| D17 | Requirements traceability: каждое нормативное требование мастер-промпта получает ID `REQ-*` и связывается с тестом. | Требование «отчёт не должен утверждать проверку, которая не запускалась». | `docs/MASTER_PROMPT_REQUIREMENTS.md`, `tests/test_traceability.py` |
