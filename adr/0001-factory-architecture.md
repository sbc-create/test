# ADR-0001. Архитектура фабрики

- Статус: принято, 2026-08-21
- Контекст: нужно повторяемое массовое создание сайтов на DLE 20.0 с проверяемым качеством.

## Решение

Фабрика — это **контроллер на Python 3.11 + декларативный слой развёртывания + строгий
входной контракт**. Слои разделены так, что модель никогда не выполняет мутацию напрямую:

```
site package (YAML)
   ↓ validate (JSON Schema + семантика домена)
   ↓ build    (детерминированная сборка, контентный build_id)
   ↓ target adapter (local_disposable | ssh_ansible)
   ↓ verify   (SEO / браузер / security / acceptance / performance)
   ↓ job result (JSON по схеме, с артефактом на каждую проверку)
```

## Обоснование

1. **Минимум зависимостей.** Python 3.11 и PyYAML уже есть в среде; добавлены только
   `jsonschema` (валидация) и dev-инструменты (`pytest`, `playwright-core`, `axe-core`).
   Чем меньше стороннего кода, тем меньше supply-chain риска в контуре, который ходит в production.
2. **Состояние на диске.** `var/state/*.json` + файловая очередь: worker переживает
   restart и продолжает с последнего checkpoint. Модель не является базой данных.
3. **Контентная адресация сборки.** `build_id` = SHA-256 от нормализованного пакета,
   контента, темы, версии матрицы **и исходников фабрики**. Последнее добавлено после
   реального дефекта: изменившийся рендер давал прежний `build_id`, деплой считал релиз
   уже применённым и продолжал отдавать старое содержимое.
4. **Адаптеры целей.** Один контракт (`plan/backup/deploy/health/rollback`) и две
   реализации. `local_disposable` даёт настоящий HTTP для пилота и тестов без внешней
   инфраструктуры; `ssh_ansible` — декларативный выкат на реальные хосты.

## Последствия

- Любая новая цель реализуется как адаптер и обязана поддержать backup, health и rollback.
- SEO-матрица — вход рендера, а не отчёт: новый тип страницы без записи в матрице не рендерится.
- Отчёт задания валидируется схемой, поэтому «проверено» без артефакта технически невозможно.
