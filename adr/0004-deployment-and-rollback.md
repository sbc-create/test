# ADR-0004. Развёртывание и откат

- Статус: принято, 2026-08-21

## Решение

**Атомарные релизы.** `releases/<build_id>` + симлинк `current`, переключаемый
`os.replace` (атомарная замена симлинка). Порядок шагов фиксирован:

```
prepare → backup → upload_release → health(релиз-кандидат) → switch_current
        → health(после переключения) → prune(с защитой точки отката)
```

**Backup до мутации.** Восстановимость проверяется фактическим разворачиванием архива
во временный каталог и сравнением содержимого; `restore_verified` в отчёте задания
ставится только по результату этой проверки.

**Откат.** `current` переключается на предыдущий релиз, затем обязательный health.
Откат кода не откатывает БД: при наличии миграции восстановление выполняется из бэкапа
этого релиза (`rollback_policy.database_rollback: from_backup`).

## Дефекты, найденные на пилоте и закрытые здесь

1. Порт стенда выбирался до остановки прежнего процесса, поэтому занятый им порт
   выглядел недоступным и стенд «переезжал» при каждом деплое. Исправлено порядком шагов.
2. `previous_release_id` перезаписывался самим собой при повторном деплое того же релиза —
   точка отката терялась. Теперь обновляется только при фактической смене `current`.
3. Очистка старых релизов могла удалить релиз, на который ссылается точка отката.
   Теперь и текущий, и сохранённый предыдущий защищены от очистки.
4. Идемпотентность считалась по всем мутациям, включая перезапуск процесса сервера.
   Теперь учитываются только мутации, меняющие содержимое релиза.

## Последствия

- Любой новый адаптер обязан пройти `tests/integration/test_rollback.py` и
  `test_backup_restore.py`.
- `production_authorized: true` необходим, но недостаточен: `factory deploy` требует
  ещё и явного `--allow-production` от оператора.
