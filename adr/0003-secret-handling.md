# ADR-0003. Обращение с секретами

- Статус: принято, 2026-08-21

## Решение

1. В пакете, инвентаре и git находятся только `secret_ref` вида `env:NAME`, `file:/path`,
   `vault:path`. Значение секрета в репозиторий не попадает никогда.
2. Всё, что покидает процесс (лог, отчёт задания, аудит, артефакт), проходит
   `factory.redaction.redact/redact_obj`. Редактируются: значения переменных окружения
   с «секретными» именами, приватные ключи, токены известных форм, credentials в URL,
   пары `key=value` с секретным ключом.
3. `secret_ref` **не** редактируется: это ссылка, и оператору она нужна.
4. PreToolUse-hook запрещает чтение `.env`, `secrets/`, ключей и `~/.ssh`, PostToolUse-hook
   ищет секреты в только что записанных файлах.

## Реальный дефект, найденный тестом

Первая версия правила скрывала любое поле, чьё имя содержит `pass`. Под это попало поле
`passed: true` в результате задания: булево значение превращалось в строку `«REDACTED»`
и отчёт переставал проходить собственную схему. Правило переписано с обязательными
границами слова; регрессия закреплена тестом
`test_redaction.py::test_boolean_fields_are_not_mangled`.

## Последствия

- Добавляя новое секретное поле, добавляй его имя в `SENSITIVE_KEY_RE` **с границами**
  и тест на то, что соседние несекретные поля не пострадали.
- Staging-учётные данные одноразового стенда генерируются локально (`var/.../staging-auth`,
  права 0600) и не публикуются ни в отчёте, ни в git.
