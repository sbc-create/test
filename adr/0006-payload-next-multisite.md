# ADR-0006. Второй blueprint: Payload CMS + Next.js + PostgreSQL для трёх аниме-сайтов

- **Статус:** принято
- **Дата:** 2026-08-22
- **Контекст задания:** Change Request v2.0
- **Заменяет:** ничего. ADR-0001…0005 и DLE blueprint остаются в силе.

## Контекст

Нужны три самостоятельных сайта на общей проверенной базе фактов о тайтлах, с
одной русскоязычной CMS, в которой редактор без доступа к коду управляет
каталогом, текстами, меню, SEO, расписанием, медиа и модерацией комментариев
отдельно по каждому сайту. Три сайта обязаны различаться назначением, дизайном и
индексируемой поверхностью; автоматическое размножение одинаковых страниц по трём
доменам недопустимо.

Существующий blueprint фабрики — DataLife Engine 20.0. Он остаётся пригодным для
других заданий и не удаляется.

## Рассмотренные варианты

### 1. DLE 20.0 (текущий blueprint фабрики)

За:
- уже реализован в фабрике целиком: сборка, деплой, SEO-контур, откат, ворота;
- знакомая редакции панель;
- пилот уже проходит весь QA-контур.

Против (для этой задачи):
- лицензия DLE привязана к домену второго уровня — три домена дают три
  лицензионных и эксплуатационных контура вместо одного;
- нет единой панели с переключателем сайта: три установки — три админки, три
  базы, три обновления;
- общая база фактов о тайтлах между установками требует внешнего слоя синхронизации,
  которого в DLE нет;
- типизированная модель каталога (тайтл → сезон → серия → права → провенанс)
  ложится на DLE неестественно;
- три разные SEO-политики на одном движке требуют набора исключений в шаблонах.

### 2. WordPress Multisite

За:
- зрелая встроенная модерация комментариев;
- domain mapping из коробки;
- большая экосистема.

Против:
- сайты сети по умолчанию хранят контент раздельно: общая база фактов о тайтлах
  требует отдельного плагина или внешнего хранилища;
- темы и плагины связаны на уровне сети — изоляция трёх разных фронтендов слабее,
  чем нужно;
- строго типизированная модель каталога достигается наборами метаполей и
  специальных плагинов, валидация остаётся частичной;
- три разные SEO-политики требуют исключений поверх универсального SEO-плагина;
- контроль над серверным HTML, статусами и кэшем ниже, чем у собственного фронтенда.

### 3. Payload CMS 3 + Next.js + PostgreSQL — **выбрано**

За:
- официальный плагин multi-tenant с переключателем сайта в панели и фильтрацией
  коллекций; изоляция выражается констрейнтом запроса, а не фильтрацией результата;
- типизированные коллекции с серверной валидацией: общий фактический каталог и
  tenant-scoped публикации разделены явно;
- drafts, autosave и запланированная публикация — из коробки;
- официальный SEO-плагин соседствует с нашей матрицей индексируемости, не заменяя её;
- Next.js даёт полный контроль над серверным HTML, метаданными, кодами ответа,
  редиректами и кэшем — то, без чего три разные SEO-модели не сделать честно;
- три оригинальные темы — это три набора токенов и раскладок в одном приложении,
  а не три копии кода;
- PostgreSQL закрывает и каталог, и комментарии, и аудит, и журнал импорта;
- интеграции (CDNVideoHub, Content API, реклама) остаются адаптерами.

Против (принято осознанно):
- собственный фронтенд нужно писать и поддерживать самим — готовых тем нет;
- модерация комментариев реализуется нами, а не берётся готовой;
- команда должна знать TypeScript.

## Решение

Для трёх аниме-сайтов используется blueprint `payload-next-multisite`.
DLE blueprint сохраняется без изменений и остаётся выбором по умолчанию для
заданий, где он уместен. Пакет сайта выбирает blueprint явно полем `blueprint`;
пакет без этого поля считается DLE-пакетом и сохраняет все прежние ворота.

## Обоснование, которое проверяется тестами

| Утверждение ADR | Чем доказано |
|---|---|
| Одна панель переключает сайты и не смешивает данные | `tests/tenant-isolation.ts`, 97 проверок на реальном PostgreSQL |
| Изоляция — констрейнт запроса, а не фильтрация после выборки | те же тесты: `count`, `find`, `findByID`, массовые `update`/`delete` |
| Изоляцию держат два независимых слоя | `tests/tools/mutation_isolation.py`: отключение любого слоя обнаруживается |
| Межсайтовые ссылки невозможны | хук целостности + прямые проверки в наборе изоляции |
| Три сайта различаются индексируемой поверхностью | `tests/seo-matrix.ts` (27 проверок), ворота `cross_site_uniqueness` |
| Редактор публикует без кода, изменение видно только на своём домене | сценарии приёмки пакетов, `frontend_http.py` |
| Интеграция плеера соответствует контракту | `tests/player-contract.ts`, `tests/e2e-multisite/player.spec.js` |
| Лицензия DLE к этим сайтам неприменима и не может «переехать» | схема пакета: `dle_license_ref` для этого blueprint обязан быть null |

## Сосуществование с DLE

- общий конвейер: `validate → plan → build → deploy → verify → rollback`;
- общая машина состояний и общий набор статусов, расширенный тремя новыми;
- общий инвентарь целей; для нового blueprint добавлена цель `payload-local`;
- общая матрица индексируемости `knowledge/SEO_INDEXABILITY_MATRIX.yaml`: её копия
  в TypeScript сверяется с YAML тестом, чтобы политика не разошлась;
- отдельные ворота качества: у динамического сайта нет отрендеренных файлов,
  поэтому проверки идут по живому HTTP с заголовком Host.

## Последствия

- Появляется вторая среда исполнения (Node.js + PostgreSQL) рядом с PHP-контуром.
  Это принято: без неё три сайта на одной CMS не собираются.
- Redis не добавлен: очередь и лимиты частоты решены существующими средствами,
  инфраструктура без назначения не заводится.
- S3-совместимое хранилище пока не подключено — медиа лежит в каталоге стенда
  (`var/media`), путь задаётся окружением. Для production это открытый пункт:
  хранилище должно быть передано владельцем.
