# Объём следующей задачи: SITE-ENGINE-02B

Не начинать без команды владельца.

## 1. Аутентификация и RBAC (обязательное условие всего остального)

Слой сценариев редактирования готов и покрыт тестами, но публичных изменяющих
маршрутов нет и не будет, пока личность не подтверждается по-настоящему.
Нужно: способ аутентификации, срок жизни сессии, привязка личности к области
сайтов, отзыв прав. Только после этого — изменяющие маршруты из списка в
`CMS-DOMAIN.md`, по одному, каждый с сухим прогоном и аудитом.

## 2. Перенос существующих связей на контракты

Классифицировано в `DEPENDENCY-MAP.md`, не сделано намеренно — правило 02A
запрещает смешивать рефакторинг с продуктовыми изменениями:

* `factory.build` ↔ `factory.lords`: заменить импорт витрины на реестр
  рендереров (реестр уже есть и выбирает рендерер по профилю для всех шести);
* `factory.validation → factory.lords`: то же;
* `factory.lords.gate → factory.seo`: требует стыковки с SEO;
* `factory.recs.cli → factory.lords`: обратное ребро идёт только из CLI.

Порядок для каждого: закрепить поведение тестом, минимально перенести, прогнать
целевой тест и гейт границ, посмотреть diff.

## 3. Единая точка входа к поставщику

Сейчас `cdnvideohub` упоминается в семи модулях `lords`, в `verify` и в
`analytics.events`. Каждое место — самостоятельное мнение о том, что умеет
поставщик, и мнения расходятся. Свести к `ProviderAdapter`, у которого уже есть
проверенный запросами перечень возможностей.

## 4. Промышленное хранилище

`InMemoryStore` достаточен для каркаса и тестов. Нужна реализация того же
интерфейса поверх настоящего хранилища, с сохранением права записи по токену
прогона.

## 5. Подключение кэша к витринам

Контракт и эталонная реализация есть. Нужно перевести на них живой кэш Yummy
(сейчас это TypeScript одной витрины) и кэш каталога Lords, не меняя
наблюдаемого поведения и с измерениями до и после, как требует
PERFORMANCE/CACHE GATE.

## 6. Гейт границ на стороне TypeScript

Не начат. Заготовка, написанная было в 02A, убрана: она возвращала пустой список
всегда, потому что витрины Yummy живут в соседнем репозитории, которого нет в
этом дереве. Правило, которое не может сработать, выглядит как покрытие, не
будучи им.

Что проверять там: компонент не читает runtime-файлы напрямую; страница не
обращается к API поставщика; модуль каталога не импортирует внутренности
соседнего.

## 6a. Мелочь, найденная при обзоре и намеренно не тронутая

В `src/lib/cache/ttl-cache.ts` витрины Yummy есть мёртвая строка: `latest = load`
присваивает переменной то, что в ней уже лежит. Вреда нет, но она обозначает
намерение, которого в коде не осталось. Не исправлена в 02A сознательно: этот
репозиторий — источник выкладки, и правка в нём означала бы подготовленное
изменение production, запрещённое условиями задачи.

## 7. Панель массового управления

Только после пунктов 1 и 4. Слой `BulkOperation`, `ChangeSet` и сухого прогона
готов; интерфейса нет намеренно.

## Чего в 02B не делать

Не выкладывать API в production. Не открывать изменяющие маршруты до
аутентификации. Не переписывать работающие витрины ради единообразия.
