## Воспроизведение пробела

Очередь умела записать решение и отменить его. **Записанное решение никуда не
применялось**: вид в каталоге оставался прежним. Первый прогон новых тестов —
ошибка сборки: модуля `kind_overlay` не существовало.

## Решение

Наложение отдельно от каталога поставщика. Каталог перезаписывается
обновлением целиком — приращением раз в десять минут и полным обходом раз в
шесть часов. Решение, записанное прямо в него, исчезло бы при следующем
прогоне.

Наложение действует **только** там, где данные источника противоречивы. Там,
где поставщик сам себе не противоречит, наложение означало бы подмену
источника.

Поток: сверка «было/стало» → утверждение вторым человеком → публикация →
точечный откат.

## Настоящие дефекты, найденные циклом

1. **Каталог не спрашивал наложение** — опубликованное решение не доходило до
   выдачи. Поймано браузерной проверкой, которая сверяет вид **через API
   каталога**, а не строку в очереди. Именно поэтому проверка сделана так.
2. **Действующее лицо всегда было «operator»** — у `Principal` нет поля `name`.
   Запрет утверждать собственное решение и запись в журнал опирались на
   пустоту.
3. **Конфликт состояния отдавался как 400** — «вы прислали ерунду». Оператор
   искал бы ошибку в своей форме. Стало 409.

## Отрицательные и конкурентные сценарии

| Сценарий | Ожидание | Результат |
|---|---|---|
| двое решают по одной версии | второй получает 409 | PASS |
| утверждение собственного решения | 409 | PASS |
| публикация без утверждения | отказ | PASS |
| публикация по устаревшей версии | отказ | PASS |
| отмена решения после публикации | наложение снято | PASS |
| наложение с UNKNOWN | отказ | PASS |
| наложение с видом вне контракта | отказ | PASS |
| откат партии | все наложения сняты | PASS |
| наложение поверх непротиворечивой записи | игнорируется | PASS |
