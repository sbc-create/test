# Security review — путь живого canary

Проверено чтением кода в этой сессии; против живого хоста ничего не
запускалось. Область — ровно тот путь, который исполнится после одобрения
владельца.

## Что держит границу

`privilege.parse_runner_argv` принимает четыре флага и отвергает всё
остальное, включая `--force`, `--shell`, `--command`, `--service`, `--unit`,
`--path`, `--exec` (`privilege.py:22-71`). Произвольной команды, юнита или
домена в root-раннер не передать.

Имя юнита, домены и обработчики берутся из реестра, а не из манифеста
(`privilege.py:80-101`). Обработчики сверяются с `ALLOWED_HANDLERS`;
`HandlerBus.register` отказывает не-allowlisted имени. Произвольного shell нет.

Одобрение связано с манифестом по каноническому digest, по точному списку
`exact_site_ids` и по digest артефакта каждой витрины; `CONSUMED` блокирует
повтор, срок годности проверяется (`approval.py:88-125`). Расширить область
одобрения, не сломав digest, нельзя.

Секретов в `reports/releases/**` нет: поиск по token/secret/password/api_key/
credential/private-key дал ноль совпадений вне имён переменных вида
`*_CREDENTIAL`, которые являются ссылками, а не значениями.

Индексация и DNS: `indexability.assert_transition_allowed` отвергает любой
переход при `mutations_allowed=false`, а `preflight_batch` отдельно валит
манифест с `dns_mutations_allowed=true` или `paid_operations_allowed=true`
(`preflight.py:89-92`). В пакете все три флага false.

## Находки

### SEC-1 (P2) — одобрение не связано с владельцем криптографически

`--manifest`, `--manifest-digest` и `--approval` — произвольные пути, а
`approval.json` это обычный JSON без подписи. Самосогласованная тройка
(поддельные манифест + digest + одобрение) проходит `load_trusted_context`
целиком: digest сверяется с тем, что передал сам вызывающий.

Сегодня ущерб ограничен: обработчики выкладки не реализованы, `HandlerBus`
пуст, и при `mutate=True` реально выполняется только перезапуск юнита, взятого
из реестра. То есть подделка позволяет выбрать, какую *зарегистрированную*
витрину перезапустить, но не подставить свои байты и не назвать чужой юнит.

Как только обработчики выкладки будут реализованы, `artifact_path` из манифеста
станет источником исполняемых байтов, и та же подделка превратится в P1.

Требуется до включения выкладки: каталог одобрений, недоступный на запись
пользователю-планировщику (root-owned), либо подпись одобрения. Узкий sudoers
ограничивает *флаги*, но не *значения* — этого недостаточно.

### SEC-2 (P2) — `OWNER_CANARY_APPROVAL_ID` не проверяется кодом

`approval_id` — свободное поле; ни один тест и ни одна ветка кода не требуют
отдельного идентификатора именно для canary. Требование «живой прогон только по
отдельному `OWNER_CANARY_APPROVAL_ID`» сегодня держится процессом, а не
программой. Пакет это фиксирует и не исполняется, но гарантии в коде нет.

### SEC-3 (P3) — `BATCH_PASS` на завершённом чекпойнте без проверки одобрения

`run_batch` при пустом `todo` ставит `BATCH_PASS`, потребляет одобрение и
возвращается **до** вызова `assert_usable_for_manifest` (`runner.py:98-111`).
Просроченное или несоответствующее по области одобрение даст `BATCH_PASS`.

Мутаций на этом пути нет — он достижим только когда чекпойнт уже говорит, что
всё прошло. Это дефект достоверности отчёта, а не выкладки: отчёт утверждает
успех, не проверив право на него.

### SEC-4 (P3) — `restore_from_backup` удаляет каталог назначения

`rollback.py:107-112` делает `shutil.rmtree(live_root)` перед восстановлением.
В текущем вызове `live_root` собирается оркестратором из `work_root/site_id`,
а не из манифеста, поэтому путь не управляется извне. Отмечено как свойство,
за которым нужно следить при реализации настоящих обработчиков выкладки: туда
нельзя передавать путь из манифеста.

### Изоляция витрин — отдельно

Общий исполняемый файл `/srv/lords/.frontend/lords-frontend.py` обслуживал шесть
витрин трёх семейств: одна выкладка меняла байты всем. Во время этой сессии
другой поток работ заменил его диспетчером, раздающим каждой витрине свой
неизменяемый релиз через `sites/<витрина>/current`. Это снимает основной канал
перекрёстного влияния, но миграция не завершена: lords-03 ещё указывает на
`legacy-b32438c91aaa`, а процесс lords-01 старше диспетчера.

До завершения миграции операция, заявленная для lords-02, не может считаться
изолированной по построению — она изолирована только потому, что у lords-02
уже свой релиз-каталог.

## Вывод

Блокирующих находок, которые делали бы подготовленный пакет опасным *сам по
себе*, нет: он не исполняется. SEC-1 и SEC-2 должны быть закрыты до того, как
живой canary станет регулярной операцией, а не разовым действием под надзором
владельца.
