# Архитектура

## Что измерено, а не предположено

| Величина | Значение |
| --- | --- |
| модулей Python в `factory/` | 141 |
| строк кода в `factory/` | 33 411 |
| хостовых сценариев `automation/host/` | 16 |
| модульных проверок | 122 файла |
| прямых обращений к API поставщика из рендера | 0 |
| секретов в коде | 0 |
| нарушений границ модулей | 0 |

## Движки и их владение

```
Content Engine     → provider adapters, ingestion, нормализация, происхождение,
                     свежесть, события, дедупликация
Site Engine        → SiteProfile, страницы, полки, каталог, контракт рендера
Publishing Engine  → сборка, инкрементальный рендер, релизы, атомарная подмена,
                     canary, откат, происхождение выкладки
Media Engine       → изображения, локальный кэш, stale-while-revalidate,
                     last-known-good, лимиты
SEO Engine         → потребитель нормализованных данных, SeoDocument, canonical,
                     robots, sitemap, schema.org, EditorialOverride
Scheduler Engine   → таймеры, очереди, повтор с задержкой, замки, сторож, SLA
Control Plane      → сайты, команды, состояния, лица, роли, аудит, CMS
```

Это модульная архитектура с независимыми контрактами, а не набор сетевых служб.
Вынести любой модуль в отдельную службу можно позже: границы уже проверяются
автоматически, и импорт внутренностей чужого движка запрещён.

## Поток данных

```
поставщик → Content Engine → нормализованный контент → снимок на диске
                                        │
                    ┌───────────────────┼───────────────────┐
                    ↓                   ↓                   ↓
              Site Engine          SEO Engine         Scheduler Engine
              (страницы)          (SeoDocument)        (таймеры, SLA)
                    │                                        │
                    ↓                                        ↓
            Publishing Engine ←──────────────────── быстрый путь
            (релиз, подмена ссылки)
                    │
                    ↓
              Media Engine (кэш постеров в nginx)
```

Существенное свойство: **SEO не ходит к поставщику**. Он потребляет уже
нормализованные данные. Граница держится правами и проверкой границ модулей, а
не договорённостью.

## Где решения принимаются до работы, а не после

| Решение | Где принимается | Стоимость проверки |
| --- | --- | --- |
| нужен ли рендер | ворота отпечатка входа | 5 с |
| какие страницы переписать | снимок произведений | доли секунды |
| можно ли публиковать | `PLAYER_FREEZE_GATE`, приёмка | секунды |
| можно ли откатывать | закреплённый тег образа, репетиция | секунды |

Прежде идентификатор релиза считался от уже собранной витрины — то есть ответ на
вопрос «менять ли что-нибудь» стоил полного рендера.

## Что осталось несимметричным

Yummy и Lords — разные технологии (Next.js против статического рендера на
Python) и живут в разных репозиториях. Общими у них являются контракты
(`SiteProfile`, `ContentEvent`, кэш-теги), а не код. Это осознанный компромисс:
свести их в один рендер означало бы переписать обе витрины, чего задача прямо
запрещает.
