# Права доступа

## Роли и права

Право именуется по действию (`publish:production`), а не по разделу интерфейса.
Раздел можно переставить или переименовать; право от этого не меняется.

| Роль | Права |
| --- | --- |
| `viewer` | чтение: сайты, контент, задания, аудит |
| `editor` | чтение + `editorial:write`, `editorial:publish`, `shelf:write` |
| `seo` | чтение + `seo:write` |
| `operator` | чтение + `ingestion:run`, `title:refresh`, `cache:invalidate`, `publish:canary`, `rollback:run` |
| `admin` | всё, кроме `publish:production` и `users:manage` |
| `owner` | все права |

## Два ограничения, а не одно

Право отвечает на вопрос «что можно», область — «где можно». Администратор
одного портала не управляет соседним:

```
Principal("admin-site", (Role.ADMIN,), sites={"yummyani-site"})
  profile:write для yummyani-site → разрешено
  profile:write для lords-01      → отказ
```

## Публикация в production принадлежит владельцу

Проверено для всех остальных ролей: `viewer`, `editor`, `seo`, `operator`,
`admin` — ни одна не имеет `publish:production`.

## Граница SEO держится правами

У роли `seo` есть `seo:write` и чтение. Нет ни `publish:canary`, ни
`publish:production`, ни `ingestion:run`, ни `rollback:run`. Это проверяется
тестом, а не соблюдается по договорённости.

## Опасное действие отделено от сохранения формы

`release.publish`, `rollback.run` и `site.create` требуют явного подтверждения.
Без него команда отклоняется с кодом 409 и объяснением, а не выполняется молча.

## Отказ — исключение, а не значение

`require()` бросает `AccessDenied`. Право, возвращаемое значением, легко забыть
проверить; исключение забыть нельзя.

## Чего здесь нет

Паролей. Лицо опознаётся ключом сеанса, который выдаётся при запуске canary и
печатается только в консоль запустившего. Проверено: ключ не появляется ни в
одной странице интерфейса и ни в одной строке журнала сервера.
