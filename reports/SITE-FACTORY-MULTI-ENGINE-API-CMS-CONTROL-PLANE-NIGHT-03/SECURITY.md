| ключ сеанса CMS в разметке (5 страниц) | 0 вхождений |

Учётные данные поставщика лежат вне репозитория (`0440 root:ubuntu`) и приходят
в контейнер монтированием только для чтения. CMS их не видит и не запрашивает.

## Опознание в CMS

Паролей нет. Лицо опознаётся ключом сеанса, который выдаётся при запуске и
пишется в файл с правами `0600` либо печатается в консоль запустившего.

Журнал обращений сервера выключен намеренно: путь `/login?key=…` содержит ключ,
и его запись сделала бы ключ достоянием журнала.

Куки: `HttpOnly`, `SameSite=Strict`. Ответы: `Cache-Control: no-store`,
`X-Robots-Tag: noindex, nofollow`.

## Права

| Свойство | Проверено |

## Изоляция canary

CMS слушает `127.0.0.1` и только его. Публичного домена нет. В production не
выкладывалась и по условию задачи выкладываться не может.

Команды в canary **не исполняются**: они принимаются, проверяются правом,
записываются в аудит и остаются в состоянии `DRAFT`. Изолированный контур не
управляет production.

## Поверхность API

| Свойство | Как обеспечено |
| --- | --- |
| выключен по умолчанию | без `SITE_ENGINE_API_ENABLED` отвечает 404 |
| 404, а не 403, у выключенного | наличие маршрута — тоже сведения |
| 401 отличается от 403 | «кто ты» и «тебе нельзя» — разные события при разборе |
| содержание команды не отдаётся | только имена полей: в нём может оказаться что угодно |
| предел размера страницы | 200 записей, иначе один запрос выгружает хранилище |

## Аудит

Журнал только дописывается: ни изменения, ни удаления в модуле нет. У каждой
записи отпечаток содержимого — подмена перестаёт быть незаметной. Повторная
подача команды не порождает второй записи.

## Чего не проверялось

Устойчивость к подбору ключа сеанса и ограничение частоты запросов. В контуре,
слушающем только loopback и не имеющем публичного адреса, это не первоочередное;
перед любой выкладкой CMS наружу — обязательно.

стоит раньше разбора маршрута. С ключом тот же путь отвечает **404**: API в
контур CMS не смонтирован, это отдельная поверхность. Прежняя строка не была
ложной, но доказывала не то, что я ей приписал.

## Живая проверка разграничения прав, 2026-09-01 05:45 UTC

Раньше здесь стояло, что снять её не вышло: файл ключей основного canary закрыт
даже для меня. Способ нашёлся и не потребовал ни одного чужого секрета — поднят
**второй** экземпляр canary на 127.0.0.1:8711 со своими ключами шести ролей,
проверка снята и экземпляр остановлен, ключи удалены.

### Чтение: различий между ролями нет — и это замысел, а не дыра

Все шесть ролей получают 200 на всех десяти разделах, и тела страниц совпадают
байт в байт с точностью до имени лица в шапке:

```
/users   viewer 3747 байт, 14 строк таблицы | owner 3745 байт, 14 строк
/sites   viewer 2904 байт,  8 строк         | owner 2902 байт,  8 строк
```

Причина видна в матрице: `audit:read`, `content:read`, `jobs:read` и
`sites:read` входят во **все** роли, включая `viewer` (4 права из 17).
Разграничение построено на записи, а не на чтении. Я счёл это дырой, пока не
свёл матрицу — и записываю здесь, чтобы следующий читатель не проделал тот же
путь.

### Запись: различие есть, и оно сработало живьём

`POST /jobs` с командой `release.publish` — правом на неё обладает только
владелец:

```
viewer   403  нет права publish:production
seo      403  нет права publish:production
editor   403  нет права publish:production
operator 403  нет права publish:production
admin    403  нет права publish:production
owner    409  release.publish: требуется отдельное подтверждение
```

Владелец проходит проверку прав и упирается в **отдельные** ворота опасной
команды — 409, а не 403. Три исхода различены живым запросом: 401 без ключа,
403 без права, 409 при недостающем подтверждении.

Обратная проверка — что дело не в «всё запрещено»:

```
operator ingestion.run    → 202
editor   editorial.create → 202
admin    profile.update   → 202
viewer   ingestion.run    → 403  нет права ingestion:run
```

Команды, принятые с кодом 202, остались в журнале **canary**, а не production:
исполнителя у команд пока нет, они лежат в состоянии черновика.
