# Установка быстрого пути в production

Ниже — точная последовательность. Раздел «Ход установки» в конце описывает, что
из неё уже произошло.

## Почему нельзя во время цикла

| Действие | Что произойдёт |
| --- | --- |
| подмена `lords-content-refresh.sh` копированием | bash читает сценарий порциями по мере исполнения; перезапись того же inode ломает работающий цикл |
| переключение ветки в `/srv/site-factory/repo` | перезапишет файлы, которые читает работающий цикл |
| публикация релиза быстрым путём | гонка за символьную ссылку `current` с самим циклом |

Подмена через переименование (`mv`) была бы безопасна для одного файла —
работающий процесс сохраняет открытый inode. Но переключение ветки затрагивает
шесть файлов сразу, и делать половину безопасно, а половину нет — хуже, чем
подождать.

## Последовательность

1. Дождаться настоящего завершения цикла — двух признаков сразу:

```
systemctl show lords-content-refresh.service -p ActiveState --value   # не activating и не active
ps -eo args | grep -c "[l]ords-content-refresh.sh"                     # 0
```

   Проверять оба обязательно: `systemctl is-active --quiet` считает
   `activating` неактивным, и ожидание на нём срабатывает в начале запуска, а не
   в конце. Эта ошибка уже была допущена в этой задаче и исправлена.

2. Переключить рабочий репозиторий:

```
git -C /srv/site-factory/repo checkout deploy/night-03-fast-path
```

3. Дождаться очередного запуска таймера. Первый цикл: снимка произведений нет →
   полный рендер → снимок записан после приёмки.

4. Второй и третий циклы: убедиться, что неизменившийся цикл даёт
   `rendered_pages=0`, релиз не создаётся, символьная ссылка не переключается.

5. Зафиксировать три цикла с временами, кодами возврата и результатами.

## Откат

`LORDS_FAST_PATH=0` в окружении службы возвращает конвейер к полной сборке без
выкладки. Удаление `var/lords/render-state/*.titles.json` возвращает быстрый путь
к «нужен полный рендер».

## Что проверить после установки

| Проверка | Ожидание |
| --- | --- |
| три домена Lords | 200 |

| хранится релизов | 2 на витрину |

| неизменившийся цикл | `rendered_pages=0`, новый релиз не создаётся |

## Ход установки

**00:44 UTC — первое окно открылось и было упущено.** Цикл, шедший с 16:55:29,
завершился в 00:44 (`ActiveState=inactive`, процессов сценария 0). Ожидание я вёл
скриптом, писавшим в файл, а результат прочитал только в 04:52 — к этому моменту
таймер уже запустил следующий цикл в 03:56:06. Окно длилось 3 ч 12 мин и было
потрачено впустую по моей вине: сторожевой скрипт сообщал о завершении в лог,
но ничего не предпринимал.

**04:56 UTC — установка переведена в автоматический режим.** Чтобы не потерять
следующее окно, установка оформлена сценарием `/home/claude/install-fast-path.sh`,
запущенным в фоне. Он:

1. ждёт двух признаков простоя, подтверждённых **дважды с интервалом 30 с**
   (одиночная проверка ловит паузу между шагами цикла, а не его конец);
2. снимает состояние витрин — `current` и число релизов;
3. выполняет `git checkout deploy/night-03-fast-path`;
4. проверяет: SHA равен `788c1a79…`, `bash -n` конвейера, компиляция пяти
   изменённых модулей, импорт `factory.lords.fast_path`, три домена → 200,
   `current` и число релизов не изменились;
5. при любом расхождении — `git checkout deploy/02b` и запись «откат выполнен».

Журнал: `/home/claude/work-night03/install-fast-path.log`.

**Расчёт окна.** Цикл от 03:56:06 при наблюдавшейся длительности 7 ч 49 мин
(16:55:29 → 00:44) завершится около 11:45 UTC. Следующее срабатывание таймера —
14:56 (`OnUnitActiveSec=11h` от 03:56:06). Запас на установку и проверку — около
трёх часов.

**Чего установка не даёт этой ночью.** Быстрый путь вступит в силу на цикле
14:56, то есть первый timer-цикл с ним завершится около 22:45 UTC, а три таких
цикла — только к 1 сентября 12:56. Пункт «три timer-цикла» остаётся закрытым
расписанием, а не кодом; см. блокер 2.
