Только чтение. Ни одного merge, rebase, cherry-pick, push, выката и изменения
production. Файлы между рабочими деревьями не копировались.

Проверка выполнена 31 августа 2026 года.

## Противоречие 1: непубликованные коммиты

Handoff утверждает одновременно `UNPUSHED_COMMITS=0`, `SEO_BRANCH_PUSHED=yes` и
что `a5f6aa6` не опубликован. Противоречие разрешается так:

* фактический SEO HEAD: **`a5f6aa677311cb306b0bbe827ad26f8ebf832ebe`**;
* origin для ветки: **`e4da4315b6d59420b6834705ff9e42dc743757e4`**;
* **непубликованных коммитов: 1** — ровно `a5f6aa6`, сам отчётный коммит;
* **upstream у ветки не задан вовсе** (`@{u}` пуст), поэтому обычный подсчёт
  `git rev-list @{u}..HEAD` в этом дереве не работает.

Это не ошибка отчёта, а самоустаревающее измерение: `UNPUSHED_COMMITS=0` было
верно в момент подсчёта и перестало быть верным, как только отчёт закоммитили.
Такое измерение стоит либо делать после коммита, либо оговаривать.

## Противоречие 2: target не опубликован

Подтверждено: `7ed1631` **отсутствует на всех ссылках origin**. origin знает
ветку `claude/night-yummy-schedule-12` в состоянии `555db001a12482769f9b28ce4cb4aa0e518ea6dc`.

Target впереди origin на **два коммита**, и оба — мои:

```
7ed1631 yummy: проверка различия заголовков перестала брать чужой трёхдневный файл
a4476fd yummy: главная перестала пересобирать одно и то же на каждый запрос
```

**Безопасный способ сохранить ветку без переписывания истории:** `555db001`
является предком `7ed1631`, поэтому публикация будет **fast-forward**.

```bash
cd /srv/sites/yummyani-staging/repo
git push origin claude/night-yummy-schedule-12   # без --force, без -u
```

Проверить до публикации:

```bash
git merge-base --is-ancestor \
  555db001a12482769f9b28ce4cb4aa0e518ea6dc HEAD && echo fast-forward
```

Если проверка не проходит — не публиковать и разбираться, а не давить `--force`.

## Противоречие 3: production revision вне object store Site Engine

Подтверждено: `6fc4d3ed` **отсутствует** в `/srv/sites/yummyani-staging/repo`, но
присутствует в `/home/claude/work-seo/yummy` и на origin.

**Безопасный refspec** — забрать объекты в отдельную ссылку, не трогая ветки, не
сливая и не копируя файлы:

```bash
cd /srv/sites/yummyani-staging/repo
git fetch origin \
  'refs/heads/claude/yummy-seo-release-zero-01:refs/remotes/origin/claude/yummy-seo-release-zero-01'
git cat-file -e 6fc4d3ed95cad53f91214836107bd1aad463b972^{commit} && echo "объекты на месте"
```

Это чтение: рабочее дерево не меняется, HEAD остаётся на месте, ни одна
локальная ветка не двигается.

## Семантический конфликт — главный вывод проверки

**`deploy/staging/verify.sh` в репозитории противоречит фактическому состоянию
production.**

Проверка требует (строки 52–55):

```
X-Robots-Tag: noindex   на каждом тенанте
robots.txt содержит     Disallow: /
```

Фактически на живых доменах:

| Домен | X-Robots-Tag | robots.txt | meta robots |
| --- | --- | --- | --- |
| yummyani.site | **отсутствует** | `Allow: /` | `index, follow` |
| yummyani.org | **отсутствует** | закрыт | `noindex, follow` |
| yummyani.biz | **отсутствует** | закрыт | `noindex, follow` |

Запуск `verify.sh` из репозитория **провалился бы на всех трёх тенантах**.

Причина связная и прослеживается по коммитам:

1. `16d9055` открыл индексацию решением владельца — **входит в образ**;
2. заголовок `X-Robots-Tag` снят с развёрнутого nginx, но
   `deploy/staging/nginx.conf` в репозитории **всё ещё содержит его в четырёх
   местах** — развёрнутая конфигурация разошлась с репозиторием;
3. `7b48464` и `a0b42c9` чинят именно это — сверяют проверку с политикой
   публикации, а не с одним состоянием, — но **не входят в образ**.

Индексация при этом открыта **только на одном домене из трёх**, а не на трёх,
как говорит заголовок коммита: `resolveSiteProfile().indexing` закрывает org и
biz редакционным решением. Формулировка коммита шире действительности.

### Скрытый конфликт двух источников правды

`SiteProfile.seo_profile.indexing_enabled` в профилях Site Engine равен `false`
для всех трёх витрин Yummy. Витрина эти профили **не читает** — решение об
индексации принимает `indexingDecision()` на стороне SEO. Активного конфликта
сегодня нет.

Но источников правды два, и если профили Site Engine когда-нибудь начнут влиять
на витрину, они **закроют индексацию, открытую владельцем**. Это надо решить до
такого подключения, а не после.

## Противоречие 4: происхождение образа при выкладке

`deploy.sh` берёт `git rev-parse HEAD`, а `EXPECTED_SHA` — необязательный
позиционный аргумент. Проверок соответствия работающему образу нет ни одной
(`docker inspect … revision` не встречается в сценарии).

**Риск конкретен и измерен.** Репозиторий витрины стоит на `7ed1631`, работает
образ из `6fc4d3ed`. Выкладка без аргумента собрала бы образ из `7ed1631` и
**молча откатила бы 22 коммита SEO**, включая открытие индексации. Приёмка при
этом прошла бы, потому что старая `verify.sh` как раз и ждёт `noindex`.

**Предлагаемое исправление (fail-closed), сейчас не применяется:**

```bash
# 1. Ревизия обязательна, а не опциональна.
EXPECTED_SHA="${1:?укажите ревизию: deploy.sh <sha>}"

# 2. Сверка с тем, что реально работает, до первой мутации.
RUNNING_REV="$(docker inspect "${PROJECT}-web-site-1" \
  --format '{{index .Config.Labels "org.opencontainers.image.revision"}}')"
if ! git merge-base --is-ancestor "$RUNNING_REV" HEAD; then
  die "работающая ревизия ${RUNNING_REV} не является предком ${SHA}: выкладка откатила бы её"
fi
```

Второе условие — существенное: оно ловит именно нынешний случай, когда дерево
выкладки не содержит работающего состояния.

## Какие SEO-коммиты нужны Site Engine

Для работы движка — **ни один**. Site Engine не читает слой SEO витрины.

Для того чтобы дерево выкладки перестало быть опасным — **все 22**, потому что
любая выкладка из дерева без них откатывает production.

## Порядок создания integration-ветки

Ничего из этого не выполнено, только описано.

1. Опубликовать target fast-forward (`git push`, без `--force`).
2. Забрать объекты SEO указанным refspec (только `refs/remotes/…`).
3. Создать ветку интеграции **от production-ревизии**, а не от target:
   `git switch -c claude/yummy-integration-02 6fc4d3ed95…` — так работающее
   состояние является основанием, а не тем, что придётся защищать при слиянии.
4. Внести в неё единственный коммит target (`7ed1631`) — он правит `verify.sh`
   и с 40 файлами не пересекается.
5. Разрешить конфликт `verify.sh` осознанно: проверка должна сверяться с
   политикой публикации (`7b48464`), а не требовать `noindex` безусловно.
6. Привести `deploy/staging/nginx.conf` в соответствие с развёрнутым.

### Тесты после каждого этапа

| Этап | Проверка |
| --- | --- |
| после 1–2 | `git status` чист, HEAD не двигался, `git cat-file -e 6fc4d3ed` |
| после 3–4 | `npx vitest run` целиком; `npx tsc --noEmit` |
| после 5 | `verify.sh` против живого production проходит без правки его ожиданий под факт |
| после 6 | сверка `nginx -T` с файлом репозитория |
| перед выкладкой | предполётная проверка паролей БД; `EXPECTED_SHA` обязателен |

## Откат

Ничего не менялось — откатывать нечего. Если этапы будут выполняться:

* публикация ветки: `git push origin :refs/heads/…` вернёт удалённую ссылку,
  но лучше её не удалять — она никому не мешает;
* ветка интеграции: удаляется локально, production не затронут;
* образ: прежний digest `sha256:da96069f…` остаётся в docker и годен для
  возврата.
