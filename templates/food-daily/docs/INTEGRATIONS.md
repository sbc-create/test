### seo-engine: фактический контракт (проверено 12.10.2026)

Источник: compose-проект `/home/claude/wt-seo-index-audit-20260930`
(`docker inspect seo-engine-api-1`), `openapi.json` 0.5.1 в нём, живая служба
отвечает версией 0.6.0. Секреты и окружение не читались.

* аутентификация — **сессия**: `POST /api/v1/auth/login` (email + пароль,
  TOTP по желанию) → cookie; `GET /api/v1/auth/me` → роль. В OpenAPI
  `securitySchemes` нет;
* роль пользователя **глобальная** (`user.role`), привязки пользователя к сайту
  нет; по сайту ограничиваются только учётные данные провайдеров
  (`security/credentials.py`: `SCOPE_SITE`);
* сайты — `GET/POST /api/sites`, черновики — `/api/v1/editorial/drafts`,
  ChangeSet — `/api/v1/changesets` с `transition`/`export`.

Следствие: «отдельный доступ food-daily только к своему tenant» средствами
службы сейчас не выдаётся — любая учётка видит все сайты. Подключать food-daily
через общую учётку нельзя (чужие credentials), а добавлять привязку
пользователь→сайт — изменение `seo-engine` (не область шаблона).
Статус: **BLOCKED_ACCESS / handoff**. Локальная реализация метаданных, рубрик
и sitemap продолжает работать; публичное чтение от службы не зависит.
Пример запросов будущего адаптера — `docs/examples/seo-engine-adapter.example.json`
(формы запросов, без учётных данных).

### Handoff в общий контур (не делалось в этой ветке)

1. **seo-engine** (владелец модуля): добавить привязку пользователь/сервисная
   учётка → набор `site_id` с проверкой в каждом маршруте `/api/sites/{site_id}/…`;
   описать `securitySchemes` в OpenAPI; завести сайт `food-daily` и сервисную
   учётку только на чтение. После этого адаптер наполняет снимок через
   `/api/v1/editorial/drafts?site_id=food-daily`. До этого multi-tenant
   разграничение для food-daily не подтверждено.
2. **Qwen**: инструмент моста `food_daily_jobs` (только чтение outbox) и
   `food_daily_submit` (запись ответа в inbox с той же схемой) — тогда Qwen
   пишет черновики сам, а импорт и все проверки остаются прежними.
3. **ChangeSet**: если появится общий контракт, food-daily переводит `versions`/
   `audit` на него адаптером; формат журнала уже содержит actor, версию, причину.

## YouTube для игровых сайтов — контракт (без реализации)

Реализация — в ветке игрового шаблона. Пример данных — `data/youtube-contract.example.json`.

* поиск: официальный YouTube Data API `search.list` с `type=video` и
  `videoEmbeddable=true`; затем `videos.list` (`status.embeddable`,
  `status.privacyStatus=public`, `contentDetails.duration`, `snippet.channelId`);
* отдельно хранятся: `video_id`, `channel_id`, `checked_at`, `embeddable`,
  `availability`, `relevance` (смысловое соответствие гайду проверяется
  человеком или моделью по описанию/субтитрам — не по заголовку);
* таймкоды — только подтверждённые (`timestamps_source`), не по заголовку;
* показ — официальный embed `youtube-nocookie.com/embed/<id>` или ссылка;
  ролик не скачивается; поверх плеера своя реклама и pre-roll не ставятся;
  просмотры YouTube не считаются нашими рекламными показами;
* одна игра закреплена за одним игровым сайтом сети.

## Реклама: режимы

| режим | что это | наша реклама |
| --- | --- | --- |
| собственный ролик (in-stream) | наш файл в нашем плеере | возможен pre/mid-roll по правилам поставщика, после проверки ролика |
| out-stream | рекламный блок вне плеера | места с заранее заданной высотой, не перекрывают ингредиенты, шаги и управление видео |
| YouTube embed | чужой плеер | запрещено накладывать и ставить перед ним |
| лицензированное видео | по условиям лицензии | только если лицензия разрешает |

Семантика события `event 3` из существующего рекламного контракта фабрики
в food-daily не используется: рекламного контракта для этого сайта нет.
Sticky-форматы — только в разрешённом поставщиком режиме.

## Приём ночного прогона Qwen (QWEN-NIGHT-RECIPES-100X5-001)

Проверено 12.10.2026: ветки `qwen/content-food-daily-night-001` на origin нет,
файлов прогона и задач с этими ID на сервере не найдено. Статус —
**не подтверждён**; старая партия FD-CONTENT-001 повторно не запускалась.

Контракт приёма, когда результаты появятся (writer — только `fooddaily.qwen import`
в этой ветке; папку и Git index Qwen шаблон не трогает):

* `LOCKED_RECIPE` = факты записи (`records.facts_json` + `content_hash`): ингредиенты,
  количества, порции, время, порядок шагов. Любая версия текста проверяется
  против них (`qwen.validate`), расхождение — отказ, а не правка;
* до пяти редакционных версий одного рецепта сохраняются как **версии одного
  `content_id`** (один `dedupe_key`), а не как разные материалы; публикуется
  одна выбранная версия, остальные в sitemap и на страницы не попадают;
* повтор того же ответа — noop; ответ на устаревшую `base_version` — конфликт и
  запись в журнал; ошибки схемы — `rejected` с причинами (карантин);
* пересчёт порций — только отображение в браузере, базовые значения и хеш не меняются.
