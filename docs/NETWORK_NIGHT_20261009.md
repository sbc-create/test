## 2. zonafilm.cc: реестр описывал намерение, витрина читала другой каталог

**Измерено.** Издатель кладёт свежий каталог в
`/srv/lords/.frontend/sites/zona-02/data` (60 699 позиций, 2026-10-08 04:01), а
витрина читает `/srv/zonafilm-cc/data` — там снимок от 2026-09-28 на 53 908
позиций. **6 791 произведение, одиннадцать суток.**

**Какой каталог читает витрина — установлено измерением, а не документом:**
включён (ссылка в `multi-user.target.wants`) юнит `nova-zonafilm-cc.service` с
`ExecStart … --data-dir /srv/zonafilm-cc/data`; прежний `nova-zona-02.service`
не включён. Заметка в реестре утверждала обратное и была неверна.

**Исправлено** (коммит `052a8de`): новая штатная операция
`factory cell relocate-data` переносит `data_dir_after_relocation` в `data_dir`
**только по измерению включённого юнита** — нет ссылки, нет `--data-dir` в
`ExecStart` или путь не тот, значит отказ с обоими значениями. Иначе операция
стала бы вторым способом соврать о размещении, только автоматическим. Десять
тестов на отказы и идемпотентность. После правки
`factory cell deliver --site zona-02 --dry-run` нацелен на
`/srv/zonafilm-cc/data` и доставил бы оба файла.

**Остаток — одна root-команда.** Суточный издатель
(`nova-catalog-publish.py` читает `data_dir` из реестра) понесёт снимок по
новому пути, но drop-in `10-cell-data-paths.conf` этого пути не объявляет, а
`ProtectSystem=strict` не даст в него писать:

```bash
sudo bash /home/claude/wt-portable-site-cell-01/automation/host/install-publisher-cell-paths.sh
```

Сухой прогон проверен — список из реестра содержит `/srv/zonafilm-cc/data` и
заодно отсутствующие пути an1mego, animeg0, an1meg0, lordserial101, lordfilm077.
Откат: удалить
`/etc/systemd/system/nova-daily-refresh.service.d/10-cell-data-paths.conf` и
`systemctl daemon-reload`; доставленные данные остаются. Отказы издателя
изолированы по витринам (`except OSError` → запись в отчёт и `continue`),
поэтому до установки команды страдает только zona-02.

**Проверка после прогона издателя (03:30Z) — раздел 7.**

## 3. an1meg0.site: у семейства AnimeGo появился читатель редакционных описаний

**Было.** Мост отвечал «публикация описания на этой площадке не сработает — не
объявлено `deliver` и `display`», и шесть живых заданий на описание у ячеек
AnimeGo выполнить было нельзя (измерено по арендам очереди: два на
an1mego.site, четыре на animeg0.site).

**Сделано.**

1. **Читатель перенесён** (ветка `claude/extract-an1meg0-site-overlay-reader-01`,
   коммит `8cae910`): это тот же `src/seo_overlay.py`, что работает у Animedia,
   с одним изменением — корнем каталогов своего семейства
   (`/srv/sites/animego/runtime/overlays`), ровно тот путь, который реестр
   фабрики уже объявляет для `animego`. Вторая реализация не нужна: пишущая
   сторона одна (`TitleOverlayStore`), схема одна. Проверен на изолированных
   данных: свой файл накладывается, файл с чужим `site` отвергается целиком,
   несошедшийся `content_digest` не применяется, отсутствие файла даёт ноль.
2. **Выпущен** штатным путём: CI `37865454705` success, `cell trigger … --confirm-activation`,
   исход `activated`, `stage: live_verified`, релиз `97cad25b81e7`.
3. **Доставка заработала, отображение — нет.** Публикация через мост записала
   текст (`state: written`, одна позиция в `title-overlays.json`), а
   подтверждение девять раз подряд ответило «полного текста в основном блоке
   страницы нет». Причина измерена: наложение читалось РОВНО ОДИН раз, при
   загрузке подробностей, и текст, записанный позже, не появлялся до следующей
   доставки. Тот же дефект уже измерен у Animedia 2026-10-01.
4. **Примета перезагрузки дополнена** (коммит `6623b32`): путь накладки входит
   в отпечаток снимка, по которому витрина решает перечитывать. CI `37866635085`
   success.
5. **Две заставы фабрики знали только одну форму доставки** (коммит `d727841`).
   Реестр выводил `display` по наличию `editorial_overlay.py` (форма Lords), а
   `путь_доставки` для того же семейства возвращал путь второй формы: искал один
   файл, называл другой. `protected.ЧИТАТЕЛЬ_ПРАВОК` отклонял выпуск словами
   «не несёт читателей защищённых данных — `editorial: src/editorial_overlay.py`»,
   защищая данные, которых в этой форме нет. Теперь обе формы законны и
   проверяются ПО ВЫПУСКУ; возможность остаётся посайтовой — `an1meg0.site`
   объявляет `deliver`+`display`, а `an1mego.site` и `animeg0.site` нет, потому
   что читателя в их выпуске ещё нет.

**Остаток — одна root-команда.** Выпуск `6623b32` отклонён исполнителем старым
правилом: он работает из КОРНЕВОЙ копии пакета
(`/usr/local/lib/site-factory-cell`), и в ней `ЧИТАТЕЛЬ_ПРАВОК` для `animego`
ещё односторонний (сверено построчно с рабочей копией). Обновление копии —
осознанное действие владельца по устройству исполнителя:

```bash
sudo bash /home/claude/wt-portable-site-cell-01/automation/host/install-cell-executor.sh
```

Сухой прогон проверен: сценарий копирует пакет под root-владение, подключает
upstream'ы и проверяет импорт корневой копии. Откат: тот же сценарий из
прежнего коммита рабочей копии; выложенные релизы ячеек он не трогает.

### 5.3 an1meg0.site: проверка ячейки падает на publisher ID в песочнице

`checks/run.sh` этой ячейки даёт один отказ: «открыто: publisher-id прежний —
`''` при ожидаемом `10252`». Отказ **воспроизведён на чистой копии HEAD без
моих правок**, то есть он был до меня. Живая витрина при этом отдаёт
`data-publisher-id="10252"` и публично, и на локальном порту: дефект в
песочничном запуске проверки (она поднимает витрину со своим каталогом данных,
где нет `player-<site>.json`, и `LORDS_PLAYER_CONFIG` не передаёт), а не на
сайте. В CI проверка пропускается по названной причине, потому что
`config/player.json` в git не хранится, — поэтому CI зелёный, а локальный
прогон красный.

Что ещё измерено, чтобы следующий не шёл по моим догадкам. Атрибут зависит от
`source_mode` настройки плеера: витрина, поднятая на изолированной настройке с
`source_mode: provider-id`, отдаёт `data-publisher-id="10252"`, а с
`external-ids` не отдаёт атрибут вовсе (проверено двумя запусками на временных
файлах, рабочая настройка площадки не тронута). Локальная копия
`config/player.json` в репозитории объявляет `provider-id`, живая витрина
атрибут отдаёт — значит и у неё `provider-id`. При этом проверка в том же
окружении видит пустую строку: её собственный запуск отличается и от живого
юнита, и от простого запуска рантайма, и это отличие — остаток. Сама проверка
при этом утверждает атрибут безусловно, то есть площадка с `external-ids`
провалит её по устройству.

Следующий шаг владельцу проверки: сверить окружение открытого запуска с тем,
что собирает `run.py`, и сделать ожидание атрибута зависящим от `source_mode`.
