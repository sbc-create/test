# Runbook оператора

## Ежедневные команды

```bash
./bin/seo-operator probe               # доступность источников
./bin/seo-operator inventory           # read-only инвентаризация
./bin/seo-operator dry-run --fixture   # прогон на синтетическом тенанте
./bin/seo-operator report --out docs/seo-operator/reports/$(date +%F).md
```

## Проверка перед коммитом

```bash
./scripts/verify.sh            # 8 стадий, код возврата = число упавших
./scripts/record-evidence.sh   # обновить docs/verification/latest-run.md
```

## Демонстрации

```bash
.venv/bin/python scripts/demo_canary.py      # canary -> ухудшение -> откат
.venv/bin/python scripts/demo_editorial.py   # анонс -> релиз -> снятие
```

## Запуск ежедневного Routine

Routines в аккаунте доступны. Routine намеренно **не создан**: пока portfolio
registry пуст и источники не подключены, ежедневный прогон выдавал бы один и
тот же отчёт «нет данных». Создаётся одной командой после подключения доступов.

Параметры для `create_trigger`:

| Параметр | Значение |
| --- | --- |
| `name` | `SEO operator — ежедневный прогон` |
| `cron_expression` | `0 6 * * *` (06:00 UTC, после стабилизации суточной статистики) |
| `create_new_session_on_fire` | `true` — каждый прогон стартует с чистого состояния |
| `initiation` | `human_request` |

Текст `prompt` для Routine:

```
Выполни ежедневный прогон SEO-оператора в этом репозитории.

1. ./bin/seo-operator probe — зафиксируй доступность источников.
2. Если gate качества данных = FAIL, не публикуй метрики: выведи «не измерено»
   с причиной. Нули вместо отсутствующих данных запрещены.
3. ./bin/seo-operator dry-run — рассчитай изменения.
4. Обработай редакционный цикл: просроченные обещания, истёкшие пины,
   переходы «анонс → релиз» по подтверждённым источникам.
5. Оцени активные эксперименты; примени keep или откат по политике.
6. Запиши отчёт в docs/seo-operator/reports/<дата>.md и закоммить его.
7. Не выходи за пределы canary. Не трогай main. Блокеры собери одним списком.
```

## Резервный планировщик

Если Routines недоступны — cron на сервере:

```cron
0 6 * * * cd /srv/seo-operator && ./bin/seo-operator report \
  --out docs/seo-operator/reports/$(date +\%F).md >> var/cron.log 2>&1
```

Worker (`seo_operator/scheduler.py`) обеспечивает блокировку, повторы и
checkpoints, поэтому пересечение двух запусков безопасно: второй получит
`LockBusy` и завершится.

## Что делать при сбое

| Симптом | Действие |
| --- | --- |
| `LockBusy` | идёт другой прогон; лок старше часа или от мёртвого процесса снимается сам |
| gate = `FAIL` | проверить `probe`; отчёт всё равно формируется, но без метрик |
| эксперимент в `observing` дольше 30 дней | выборка не набирается — свернуть эксперимент |
| откат прерван `ConflictError` | значение правил человек; разобрать вручную, не форсировать |
| `verify.sh` упал | чинить причину; отключать стадию или тест запрещено |

## Границы

Оператор никогда не выполняет сам: удаление сайтов, доменов, backups;
разрушительные миграции; force push; вывод секретов; расширение прав;
отключение hooks и тестов; DNS вне утверждённого manifest; production-мутации
без точной авторизации. Полный перечень — [`protected-guardrails.md`](protected-guardrails.md).
