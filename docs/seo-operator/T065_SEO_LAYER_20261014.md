# T065 — копии seo_layer и падение indexing-live-switch (для Архитектора), 14.10

## Итог

1. **Причина падения `indexing-live-switch` — порядок шагов в самой проверке, а не устаревший seo_layer.** Прежнее утверждение журнала (NIGHT_20261014 §13) неверно.
   - Исправлено в проверке, выпущено, на сайте ничего не меняется (подробности — ниже).
   - От Архитектора по этому пункту ничего не нужно.
2. **Расхождение версий seo_layer остаётся** — это вопрос Архитектора. Две открытые Lords-витрины работают на копиях без `ПАУЗА_ПУСТОГО_С`. После перезапуска на пустом снимке карта у них пишется через 300 с, а не через 2 с.

**Механизм:**
- `снять()` читает `/robots.txt` сразу после первого ответа стенда.
- `_тело_robots()` (src/lords-frontend.py) ставит `Sitemap:` только при существующем `sitemap.xml`. Карта собирается фоном по 63 тыс. записей — на этот момент её ещё нет.
- Затем проверка ждёт карту до 60 с (карта отдаётся, 200), но сверяет robots.txt из прежнего снимка.

**Прежний «PASS» на урезанном снимке был пустым.** Проверка берёт снимок из `/srv/<имя каталога репозитория>/data`. В рабочей копии с другим именем каталога снимка не было, проверка выходила с rc=0 «пропущено», и run.sh засчитывал PASS.

**Исправление — 6da39f6:** выпущено в lords-05, CI 38556753547, исполнитель ok. Live: robots.txt с `Sitemap:`, `/sitemap.xml` 200, главная 200.
- robots.txt перечитывается после ожидания карты, и требуется точная строка `Sitemap: https://lordserials22.info/sitemap.xml`;
- снимок берётся так: `LORDS_FIXTURE_DIR` → `SITE_DATA_DIR` → `/srv/<repo>/data`;
- без снимка проверка пишет «НЕ ИЗМЕРЕНО» (ПРОПУЩЕНО в run.sh), а не rc=0.

Остальные четыре репозитория с этой проверкой (animedia-icu, animedia-space, an1meg0-site, zonafilm-cc): утверждения про `Sitemap:` в robots у них нет, но молчаливый пропуск без снимка тот же. Перенесу правку пропуска туда следующим шагом.

**Что работает на самом деле.**
- Юниты запускают `/srv/<repo>/current` (`WorkingDirectory` и `ExecStart` в `/etc/systemd/system/nova-*.service`, сверено у lordserials22-info, zonafilm-space, animedia-icu). `current` → `releases/<sha>` последнего выпуска.
- **Расхождение с реестром:** `config/site-cells.json` → `runtime.app_dir` = `/srv/<repo>/app`:
  - у Lords (lordfilm47-space, lordserial33-biz, site-1lordserials1-online, lordserials22-info) — пустой каталог;
  - у zonafilm-space, animedia-icu, animedia-space — старое дерево с seo_layer 8fb0a0bac3f8;

- Сборщик, читающий `app_dir`, увидит не тот код, что работает.

**Разница версий:**
- lords-02 → d6f300: +37 / −5 строк;
- lords-05 → d6f300: +74 / −6;
- d6f300 → шаблон 18f02d: +63 / −1.

Строки, которые есть только в устаревших копиях (то, что меняется):
- цикл сборщика сравнивает `поколение = (revision, len(items))` и при неудаче («не записана») всегда спит `ПАУЗА_КАРТЫ_С = 300`;
- в d6f300 после пустого снимка — `ПАУЗА_ПУСТОГО_С = 2` с опросом;
- в d6f300 нет ветки `режим {состояние}: карта не нужна` в этом месте.

**Влияние на живые сайты:** после перезапуска lords-02 и lords-05, если первый проход сборщика застал пустой снимок, карта пишется с задержкой до 5 минут. Записанная ранее карта на диске остаётся (каталог карты постоянный), поэтому robots.txt и `/sitemap.xml` в это время отвечают по прежней карте. Ущерб — задержка обновления, не пропажа карты.

## Что предлагается Архитектору

1. Довести seo_layer у lords-02 и lords-05 до общей версии: d6f300 или шаблон 18f02d — решает владелец шаблона. Штатно — тем же инструментом переноса из `automation/host`, отказывающим при несовпадении якоря, с пересчётом замка (`pins.lock.json`) и полным run.sh. Затем выпуск через `cell trigger`.
2. Решить, нужен ли каталог `/srv/lords/.frontend` (8fb0a0bac3f8): по путям юнитов витрины его не используют; если он не нужен — архивировать по процедуре Архитектора. Сессия его не трогает.
3. Привести `runtime.app_dir` в реестре к фактическому `/srv/<repo>/current` либо убрать поле. Старые деревья `/srv/<repo>/app` — архивировать по процедуре Архитектора. Это постоянные каталоги площадки: сессия их не трогает.
4. Проверка после переноса: на lords-02/05 после перезапуска первая запись карты в журнале службы — в пределах секунд после загрузки снимка, без паузы 300 с.
