# B016 / T081 — постоянное исправление Yummy: выкатка

Исполняемый сценарий: `automation/host/yummy-b016/yummy-b016-release.py`. Документ его
описывает и **не исполняется**: блоков для копирования в оболочку здесь нет.

## Команда владельца

Выполнять от пользователя `claude`: у него есть доступ к docker, и ему принадлежит `compose.vars`.

```
python3 /home/claude/wt-portable-site-cell-01/automation/host/yummy-b016/yummy-b016-release.py run
```

Длительность — около 1,5–2 ч. Сборка трёх образов занимает ~20–40 мин, выкладка с
приёмкой — ~10 мин, приёмка постоянного исправления — до ~70 мин (ожидание устаревания
инвентаря). Каталог состояния выпуска печатается в конце, это `var/yummy-b016/<время>/`:
- `journal.jsonl` — каждая мутация: время, исполнитель, действие, цель, код;
- `release.json`, `images.json`;
- снимки до и после каждой витрины;
- `accept.json`.

| Код | Значение |
| --- | --- |
| 0 | Выпуск и приёмка пройдены. |
| 3 | Остановка до первой мутации (preflight). |
| 4 | Сборка не удалась; контейнеры не трогались. |
| 5 | Витрина не принята. Её образ откачен и проверен, следующие витрины не выкладывались. |
| 6 | Откат витрины не поднялся — нужен человек. В журнале и выводе — что именно. |
| 7 | Приёмка постоянного исправления не пройдена. Витрины работают на новом образе. Откат: `… rollback --service web-site` (затем web-org, web-biz) или оставить и разбираться. |

Дополнительно:
- `preflight` — только проверки;
- `build` — проверки и сборка без пересоздания;
- `accept --state <каталог>` — повтор приёмки;
- `rollback --service <web-…>` — откат образа одной витрины к записанному в выпуске.

## Что исправляется

| Патч | Дефект | Замер 15.10 07:53Z (прогрев был снят) |
| --- | --- | --- |
| `b016-sitemap-swr.v2.patch` | Инвентарь карт с TTL 3600 с строится синхронно в запросе (35–57 с); параллельные запросы строят каждый свой | `titles.xml` холодный: .site 44 с, .org 48 с, .biz 40 с; yummyani7.* — **504** за 30 с |
| `b016-sitemap-cap.patch` | `walkAnimeListItems(maxPages=80)` × 100 = потолок 8000 | у всех `titles.xml` ровно 8000 `<loc>` |
| `t081-shelf-canonical-href[.4c5796e].patch` | Полки главной ведут на `/anime/<slug>--<uuid>` → 308 | .site 54 из 101 ссылки, .org 36, .biz 54 |

**SWR (v2).** Последний исправный инвентарь отдаётся сразу, перестройка идёт в фоне одним
исполнителем (замок Redis и single-flight). Ждёт сборки только холодный старт без данных.
v2 добавляет заголовок `x-sitemap-inventory: fresh|stale|cold|unavailable; age=<с>` у частей
карты. По нему приёмка видит состояние кеша через публичный домен, без доступа к Redis.

**Потолок.** Поднят до 300 страниц: предел защищает от бесконечного курсора, обход и так
кончается на `has_more=false`. Без SWR это удлинило бы холодную сборку, поэтому раньше было запрещено.

## Почему у каждой витрины своя база (изменения Архитектора, publisher_id)

| Витрина | Работающий образ | База |
| --- | --- | --- |
| yummyani.biz | `rel-4c5796eae24c` | 4c5796e (`claude/contact-mail-biz-01`) |
| yummyani.org | `rel-8be8d8b5bdf2` | 8be8d8b (`claude/contact-mail-org-site-01`) |
| yummyani.site | `rel-054c6170519d` | 054c617 (`claude/yummy-actual-shelf-01`) |

Ветки расходятся. Одна общая база откатила бы чужие коммиты. Прежняя 97c88d2 откатила бы 33,
в том числе c42561b («publisher ID закрепляется за арендатором»). Сценарий собирает для
каждой витрины **её живую базу + те же патчи**.

Источник сборки — отдельная рабочая копия коммита (`git worktree add --detach`). Дерево
`/srv/sites/yummyani-staging/repo` не используется: в нём незакоммиченные правки CR-006 от 20.09.

## Что сценарий проверяет и когда останавливается

**preflight — все условия обязательны; нарушение любого → код 3, ни одной мутации:**
- sha256 всех патчей совпадают с `automation/host/yummy-b016/PATCHES.sha256`.
- Базовый compose (`/home/claude/wt-yummy-mail-biz`): HEAD = 4c5796e, дерево чистое; оба наложения на месте.
- В `compose.vars` ровно по одной строке `WEB_BIZ_IMAGE`, `WEB_ORG_IMAGE`, `WEB_SITE_IMAGE`, каждая в формате `yummyani/web:rel-<12 hex>`.
- Каждый контейнер healthy, работает ровно закреплённый образ, его ревизия начинается с ожидаемой базы.
- **Итоговая конфигурация compose из трёх файлов** (`docker compose … config`):
  - образ службы равен закреплённому;
  - переменные издателя/CDNVIDEOHUB, `SEO_INDEXING_ENABLED`, `TITLE_OVERLAYS_*`, `SITE_PROFILE`, `REDIS_URL`, `DATABASE_URL` по sha256 равны работающему контейнеру;
  - если переменная есть в контейнере, но отсутствует в конфигурации, это остановка: пересоздание бы её сняло. Исключение — переменная, заданная в самом образе;
  - цели монтирований и секретов совпадают с работающими;
  - у `web-biz` `SEO_INDEXING_ENABLED=true` — наложение D169 применено.
- Снимок до выпуска (`yummy-b016-check.py snapshot`): у пяти контейнеров есть издатель на странице и meta robots.

**Сборка — любой отказ → код 4, контейнеры не тронуты.** Отказом считается каждое из:
worktree, любой патч (`--forward --batch`), «патчи ничего не изменили», коммит, сборка, метка
ревизии образа ≠ коммиту, тегирование. Наружу выходит только тег. Он проверяется регулярным
выражением `^yummyani/web:rel-[0-9a-f]{12}$` и меткой ревизии. Вывод git, patch и docker
уходит в stderr.

**Резервная копия трёх БД** делается официальным `deploy/staging/backup.sh`: дамп и
репетиция восстановления во временную БД. Это условие выпуска (правило фабрики). Отказ →
код 5 до первого пересоздания. Средством отката копия не служит.

**Выкладка biz → org → site, по одной.** Следующая начинается только после приёмки предыдущей:
1. Копия `compose.vars`, тег отката на прежний образ.
2. Атомарная замена **одной** строки `WEB_*_IMAGE`: временный файл в том же каталоге, права и владелец прежние, fsync, rename, проверка.
3. Пересоздание только этой службы той же трёхфайловой командой, что подняла работающие контейнеры (`--no-deps --force-recreate`).
4. Ожидание healthy (240 с).
5. Приёмка витрины:
   - работает новый образ с нужной ревизией;
   - `compare` с исходным снимком: у всех пяти контейнеров прежние издатель и `data-publisher-id` на странице, индексация (meta robots), наложения, монтирования; образы меняются только у выложенных;
   - на главной 0 ссылок `--uuid`;
   - карты 200: первый проход с пределом 90 с (на случай истёкшего ключа), затем ≤ 5 с.

**Откат при неуспехе шагов 3–5.** Касается только образа этой витрины:
- прежняя строка закрепления → пересоздание → healthy;
- работает прежний образ по Id;
- снимок равен исходному.

БД не восстанавливается: `deploy/staging/rollback.sh`, который делает restore из дампа,
не вызывается. Это запрещено правилами фабрики и не нужно, потому что в патчах нет миграций.

**Приёмка постоянного исправления — отдельно от проверки прогретого кеша.** Шаги:
1. **Управляемая пауза прогрева.** Файл `var/yummy-sitemap/warm-pause.json` с крайним сроком. `yummy-sitemap-warm.sh` его соблюдает, просроченная пауза не действует. Пауза снимается в `finally`, и прогрев возобновится сам, даже если приёмка оборвётся.
2. **Текущее состояние** — по заголовку `x-sitemap-inventory`. Если на каком-то запросе `cold`, холодный старт наблюдается и проверяется (200). Иначе это записывается как «не наблюдался»: общий Redis не очищается, поведение покрыто тестом `sitemap-inventory-cache.test.ts`.
3. **Ожидание устаревания.** Пауза длится 3600 с минус возраст, плюс 30 с. Если инвентарь за это время обновил обходчик, ожидание повторяется не больше двух раз.
4. **Устаревший кеш.** Все 9 частей трёх доменов отвечают 200 за ≤ 5 с в состоянии `stale`.
5. **Фоновая перестройка** завершается без прогрева: в течение 420 с появляется `fresh` с малым возрастом.
6. **Итог:** ни одного 504 за всю приёмку; во всех `titles.xml` больше 8000 `<loc>`; на трёх главных 0 ссылок `--uuid`.

## yummyani7.site / .info (часть B) — согласование с Архитектором

Сценарий их не трогает. Образ там задан литералом в `deploy/compose.yaml` репозитория
витрины. У yummyani7-site этот файл в рабочей копии Архитектора незакоммичен: в нём
закрепление издателя, а последний коммит 40a73ec — «откат назначения publisher_id».

Решение владельца по номерам издателя для yummyani7.site и yummyani7.info уже есть и
передано Архитектору. Номера здесь не повторяются; источник — `config/site-cells.json:
publisher.publisher_id`.

Нужно от Архитектора:
1. зафиксировать `deploy/compose.yaml` обеих витрин с этим закреплением;
2. сменить образ на тег biz из `images.json` выпуска (база та же — 4c5796e).

Тогда выкладка yummyani7.* — тот же цикл: снимок, пересоздание `web`, `compare`, карты.

## Прогрев — временная мера, отдельно от причины

`yummy-sitemap-warm.timer` установлен владельцем 15.10. Первый проход в 08:20–08:21Z — 15
карт пяти доменов 200 за 0,13–0,74 с.

- **Что даёт.** Робот почти всегда попадает в горячий кеш.
- **Чего не делает.**
  - Причину не устраняет: холодная сборка остаётся, её запускает таймер.
  - На yummyani7.* сам проход может получить 504.
  - Потолок 8000 и T081 не трогает.
- **Снятие** — после `run` с кодом 0 и выкладки части B. Снимает владелец:
  `systemctl disable --now yummy-sitemap-warm.timer`, затем удалить оба юнита из
  `/etc/systemd/system` и выполнить `daemon-reload`.

## Риск, который остаётся

**Холодный старт.** Если данных нет вовсе, а это первая выкладка после потери Redis, запрос
ждёт сборку: ~35–60 с, а с поднятым потолком немного дольше. На yummyani.site/.org/.biz
предел nginx — 60 с, на yummyani7.* — 30 с. Поэтому такой запрос на yummyani7.* получит 504,
но сборку доведёт, и следующий ответ будет из кеша. Штатно этого не бывает: данные живут 7
суток и обновляются в фоне. Предел nginx — настройка сайта, её меняет только владелец.
