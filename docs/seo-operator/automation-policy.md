# Политика автоматизации и расписание

## Основной механизм: Claude Code Routines

Routines в этом аккаунте **доступны** (проверено вызовом `list_triggers`,
вернулся пустой список — API работает, активных Routine нет).

Ежедневный прогон оформляется как Routine со свежей сессией на каждое
срабатывание: суточная работа не должна зависеть от состояния предыдущего
разговора.

Рекомендуемое расписание: ежедневно в 06:00 UTC, после того как поисковая
статистика за предыдущие сутки стабилизировалась.

Routine **не создаётся автоматически этой сессией**: пока portfolio registry
пуст и ни один источник данных не подключён, ежедневный прогон каждый раз
выдавал бы один и тот же отчёт «нет данных, нет сайтов». Это шум, а не работа.
Точный вызов для запуска — в [`runbook.md`](runbook.md); он выполняется одной
командой, когда появятся доступы.

## Резервный механизм: собственный worker

Если Routines окажутся недоступны, тот же прогон выполняет
`seo_operator/scheduler.py` на обычном сервере (cron или systemd timer).
Реализовано и покрыто тестами:

| Свойство | Как обеспечено |
| --- | --- |
| Очередь | `Queue` — JSON-файл, атомарная перезапись через `rename` |
| Идемпотентность | повторная постановка задачи с тем же `job_id` игнорируется |
| Блокировка | `FileLock` на `O_EXCL`; второй worker получает `LockBusy` |
| Освобождение при падении | лок снимается в `finally`, даже если задача упала |
| Зависшие локи | перехват по возрасту и по исчезнувшему pid |
| Повторы | до 3 попыток с экспоненциальной задержкой |
| Checkpoints | завершённые шаги не выполняются повторно после перезапуска |
| Audit log | каждое применение и откат пишутся в `var/audit/` |

Ключевое свойство — восстановление: worker, убитый в середине задачи, при
перезапуске продолжает с невыполненного шага, а не начинает заново. Проверено
`test_restart_resumes_from_checkpoint`.

## Что делает ежедневный прогон

1. `probe` — проверка доступности источников.
2. Gate качества данных. При `FAIL` метрики не публикуются.
3. Сбор данных по доступным источникам.
4. Технический анализ и поиск возможностей.
5. Обработка редакционного цикла: просроченные обещания, истёкшие пины,
   переходы «анонс → релиз».
6. Наблюдение за активными экспериментами, решение keep/rollback.
7. Ежедневный отчёт владельцу.

Прогон никогда не выходит за пределы canary самостоятельно.

## Режим по умолчанию

Ежедневный прогон запускается в режиме `dry_run`, пока владелец явно не
разрешит `canary` на конкретном сайте. Это означает: в отсутствие решения
человека оператор считает и докладывает, но не пишет.
