# Единый список внешних блокеров

Всё, что нужно от вас, одним пакетом. Оператор реализован, протестирован и
проверен на синтетическом тенанте; для работы на реальных сайтах не хватает
только перечисленного ниже.

Состояние на 2026-08-22, установлено пробами из сессии, а не предположениями.

## 1. Портфель сайтов — блокирует всё остальное

Ни один из 15–20 сайтов не передан оператору. В репозитории нет ни доменов, ни
site manifests, ни упоминаний фабрики сайтов, CMS, PAGE_MATRIX или
CDNVideoHub/VK contracts — проверено поиском по всему дереву.

Нужно по каждому сайту: домен, тематика, аудитория, текущая структура рубрик,
уровень риска (low/medium/high), решение по редакционному аккаунту
(«Редакция сайта» / «AI-ассистент редакции» / нет) и разрешена ли модерация
комментариев.

Заполняется в `config/portfolio.json`.

## 2. Доступы к источникам данных

Секреты передаются переменными окружения; в репозитории хранятся только их имена.

| Источник | Переменные | Состояние |
| --- | --- | --- |
| Google Search Console | `GSC_SERVICE_ACCOUNT_JSON`, `GSC_PROPERTY_MAP` | нет ключа; сеть до API открыта |
| Яндекс Вебмастер | `YANDEX_WEBMASTER_TOKEN`, `YANDEX_WEBMASTER_USER_ID` | нет токена **и** сеть закрыта |
| Яндекс Метрика | `YANDEX_METRIKA_TOKEN`, `YANDEX_METRIKA_COUNTER_MAP` | нет токена **и** сеть закрыта |
| CMS | `CMS_BASE_URL`, `CMS_API_TOKEN` | CMS не названа, контракт записи неизвестен |
| Серверные журналы | `SERVER_LOG_PATH` | нет доступа к серверу |
| Мониторинг | `MONITORING_API_URL`, `MONITORING_API_TOKEN` | система не названа |

## 3. Сетевая политика окружения блокирует Яндекс

Домены `api.webmaster.yandex.net`, `api-metrika.yandex.net` и `oauth.yandex.ru`
недоступны из этого окружения: прокси отвечает `CONNECT tunnel failed, response 403`.

Это **отдельный блокер от токенов**: даже с выданными токенами Яндекс-источники
работать не будут. Требуется разрешить эти домены в сетевой политике окружения
либо запускать оператор там, где они доступны.

Google API из этого окружения достижим — проверено.

## 4. Права на запись в GitHub

`git push` в `sbc-create/test` возвращает `403`. Через API:
`403 Resource not accessible by integration`. Чтение работает.

Не хватает разрешения GitHub App **`Contents: Read and write`**; для pull request
дополнительно **`Pull requests: Read and write`**.

Из-за этого вся работа — включая предыдущий этап — существует только локально.

## 5. Права на публикацию контента

Нужны подтверждения, без которых оператор не опубликует ни одного факта:

- перечень разрешённых источников (правообладатели, лицензированные каталоги,
  профильные издания) → `config/editorial-sources.json`;
- подтверждение прав на использование материалов по каждому источнику;
- разрешение на модерацию комментариев и на редакционный аккаунт по каждому сайту.

Утверждение без источника из этого реестра технически не создаётся: объект
`Claim` выбрасывает `UnsourcedClaimError`.

## 6. Решения владельца

| Вопрос | Зачем |
| --- | --- |
| На каком сайте проводить первый canary | нужен один сайт с низким риском |
| Разрешён ли переход из `dry_run` в `canary` | по умолчанию оператор только считает и докладывает |
| Куда публикуется bundle в `deploy.yml` | цель публикации намеренно не настроена |
| Границы development и SEO-контура | общий deployment lock требует согласования |

## Что уже работает без всего этого

- Классификатор защищённых действий и PreToolUse-hook — 260 тестов.
- Конвейер dry-run → canary → наблюдение → откат на синтетическом тенанте.
- Планировщик с очередью, локами, повторами и checkpoints.
- Схемы, реестры, редакционный цикл, отчётность.

Порядок снятия: пункт 4 разблокирует сохранение работы, пункт 1 — всё
остальное, пункты 2 и 3 вместе — измерения.
