# ADR-004. Общее состояние управляющего слоя на файловой системе

- Статус: принято
- Дата: 2026-09-04
- Область: `ratelimit.py`, `idempotency.py`

## Контекст

Ограничение частоты жило в памяти процесса. При двух экземплярах Control API
объявленный предел «столько-то в минуту» означал вдвое больше, и заметить это
было можно только по последствиям. Идемпотентность проверяла наличие записи, а
результат сохраняла позже: между этими действиями второй процесс не находил
записи и выполнял ту же команду ещё раз — то есть повтор после таймаута создавал
второе задание.

Оба свойства невозможно проверить изнутри одного процесса: однопроцессный тест
показывает прежнюю редакцию исправной.

## Решение

Состояние вынесено в файловую систему под блокировками.

**Предел частоты** — единый файл `var/state/control-ratelimit.json`, все ведра
проверяются и списываются под одной блокировкой. Ключи иерархические: среда,
витрина, действующее лицо, операция; витрина входит и в ключ операции.

**Идемпотентность** — заявка создаётся атомарно через `O_EXCL` **до** выполнения
команды, с арендой на случай смерти исполнителя. Различаются повтор, конфликт и
выполняющийся запрос.

## Почему не Redis

Redis на этом хосте обслуживает данные витрин — по базе на витрину. Управляющий
слой намеренно не имеет доступа к хранилищам витрин (ADR-002): это граница,
которая ограничивает радиус его ошибки. Завести к нему доступ ради счётчика
значит разменять границу на удобство.

Файловая система уже служит очереди, блокировкам и журналу аудита — та же
область надёжности, новой инфраструктуры не появляется.

## Что это не решает

Общее состояние действует в пределах одного хоста. Два хоста с разными дисками
получат независимые счётчики, и предел снова умножится. Это записано в
backlog многосерверной схемы (ADR-006) как прямое следствие, а не как упущение.

## Поведение при недоступности хранилища

Ни отказать всем, ни пропустить всех: и то и другое превращает сбой счётчика в
аварию обслуживания. Действует строгий счётчик в памяти процесса, факт
деградации возвращается вызывающему и растит `site_engine_ratelimit_degraded_total`.
Тихий переход в этот режим был бы хуже самой деградации.

## Отвергнутые варианты

*Ограничение только на прокси.* Прокси не знает ни витрины, ни области права,
ни того, изменяющий это запрос или нет; его предел — грубый и общий.

*База данных под счётчики.* Отдельная зависимость ради одного файла, который
переживает перезапуск и без неё.

*Идемпотентность «повтор игнорируется».* Недостаточно: тот же ключ с другим
телом — другая команда под использованным ключом, и молча выполнить её значит
выполнить дважды по-разному.

## Проверено

`test_multiprocess_control.py` — настоящими процессами: один ключ на два
экземпляра даёт одно задание, тот же ключ с другим телом — конфликт, предел
общий и переживает перезапуск, отказ не занимает ключ навсегда. То же
подтверждено на двух живых экземплярах API по HTTP.
