# ADR-006. Многосерверная отказоустойчивость — план, не гейт

- Статус: **предложено** (в этой итерации не внедряется)
- Дата: 2026-09-04
- Область: размещение, состояние, хранилище, маршрутизация

## Зачем эта запись

Текущая постройка честно ограничена одним хостом. Ограничения перечислены здесь
целиком, чтобы на них не рассчитывали как на отсутствующие, и чтобы следующая
итерация начинала с плана, а не с открытия.

## Что сейчас на одном хосте

| Свойство | Как сделано | Что будет на втором хосте |
|---|---|---|
| Предел частоты | файл под блокировкой | счётчики независимы, предел умножается на число хостов |
| Идемпотентность | заявка `O_EXCL` на диске | одна команда выполнится по разу на каждом хосте |
| Блокировки витрин | файловые | две выкладки одной витрины одновременно |
| Очередь заданий | каталоги на диске | задание видно только своему хосту |
| Следы и аудит | файлы | путь запроса рвётся на границе хоста |
| Витрины | контейнеры одного хоста | отказ хоста уносит весь массив |

## Предпосылки перед внедрением

1. **Общее состояние.** Предел, идемпотентность и блокировки должны переехать в
   хранилище, доступное обоим хостам. Кандидаты: отдельный экземпляр Redis
   **не** из числа тех, что обслуживают витрины; либо PostgreSQL с таблицей
   аренд. Смешивать с данными витрин нельзя — это нарушит границу ADR-002.
2. **Очередь.** Файловые каталоги заменяются очередью с видимостью на оба хоста
   и семантикой «ровно один исполнитель». Аренда обязана переживать смерть узла.
3. **Хранилище объектов.** Сборки, резервные копии и следы — в общее хранилище,
   иначе откат на втором хосте не найдёт нужного релиза.
4. **Репликация БД витрин.** Асинхронная реплика на второй хост с измеренным
   лагом; без измерения обещание восстановления беспредметно.
5. **Домены отказа.** Витрины распределяются так, чтобы отказ одного хоста не
   уносил все витрины одного заказчика.

## Целевые показатели

| Показатель | Сейчас | Цель |
|---|---|---|
| Восстановление одной витрины | 3 с (измерено) | без изменений |
| Восстановление при отказе хоста | не определено (ручное) | RTO ≤ 15 мин |
| Потеря данных при отказе хоста | равна возрасту копии | RPO ≤ 5 мин |
| Доступность управляющего слоя | одиночная точка отказа | два экземпляра за балансировщиком |

## Риски и цена

**Расщепление сознания.** Два управляющих слоя без общего состояния — это
удвоенный предел и двойные задания. Пока общее хранилище не внедрено, второй
экземпляр опаснее одного.

**Переключение DNS.** Время жизни записи определяет настоящее время
восстановления. Обещание RTO без учёта TTL — это обещание не того числа.

**Стоимость.** Второй хост той же мощности плюс хранилище состояния и объектов.
Порядок — удвоение текущих расходов на инфраструктуру.

**Сложность.** Каждая новая общая зависимость — новая причина отказа. Общее
хранилище состояния становится тем, чья недоступность останавливает оба хоста;
режим деградации для него обязателен так же, как сейчас для файлового счётчика.

## Порядок внедрения

1. Вынести предел, идемпотентность и блокировки в общее хранилище; проверить
   деградацию при его недоступности на одном хосте.
2. Перевести очередь; доказать «ровно один исполнитель» двумя рабочими.
3. Поднять второй экземпляр управляющего слоя на том же хосте за прокси;
   измерить поведение под нагрузкой.
4. Второй хост: реплика БД, общее хранилище объектов, измерить лаг.
5. Балансировщик и маршрутизация по здоровью; отдельно — переключение DNS с
   учётом TTL.
6. Учение: отказ хоста целиком, с замером фактических RTO и RPO.

Шаги 1–3 полезны сами по себе и не требуют второго хоста. Начинать следует
с них.
