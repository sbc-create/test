## 2. Порядок запуска и ёмкость

Расчёт на ИЗМЕРЕННЫХ числах витрин семейства Lords управляющего узла (RSS
работающих процессов сейчас): 653 МиБ, 1150 МиБ, **1401 МиБ**; медиана 653,
максимум 1401. Крупные — это витрины с полным каталогом (`*-details.json`
около 85 МиБ).

Резервы, которые нельзя занимать ячейками:

| на что | МиБ | почему |
| --- | ---: | --- |
| система и sshd | 500 | измерено на этом узле: занято 472 без нагрузки |
| nginx с восемью блоками | 100 | статика, без кеша |
| одно обновление каталога | 700 | обновлятель читает `details.json` целиком |
| выкладка выпуска | 200 | распаковка и сверка сумм |
| запас без swap | 1000 | подушки нет: OOM убивает процесс, а не замедляет |
| **итого резерв** | **2500** | |

Остаётся ячейкам ≈ **7445 МиБ**. Отсюда три исхода, и какой из них настоящий,
решает измерение после первой витрины:

| если RSS ячейки окажется | помещается витрин |
| --- | ---: |
| 653 МиБ (медиана управляющего узла) | 11 |
| 900 МиБ | **8** — вся партия |
| 1401 МиБ (максимум) | 5 |

**Порядок запуска — по одной, с измерением после каждого шага.** Сначала по
одной витрине каждого профиля: у них разные шаблоны и разный каталог.

| шаг | витрины | зачем именно так |
| --- | --- | --- |
| 1 | `lords-10` (`lordfilm.group`, профиль lords-films) | первая цифра RSS на этом узле |
| 2 | `lords-13` (`lordserial.su`, профиль lords-serials) | второй профиль может весить иначе |
| 3 | `lords-11`, `lords-12` | добираем films |
| 4 | `lords-14`, `lords-15` | serials парами |
| 5 | `lords-16`, `lords-17` | остаток |

**Правило остановки** (проверяется после каждого шага, а не в конце):
доступной памяти остаётся не меньше **2000 МиБ** при всех работающих
витринах и прошедшем обновлении каталога. Меньше — шаг назад и остановка на
достигнутом числе. Swap'а нет, поэтому «чуть-чуть за предел» здесь означает
убитый процесс, а не просадку.

**Диск.** Восемь ячеек — около 2,8 ГиБ (код двух поколений плюс данные
каталога ≈105 МиБ на витрину) при 66 ГиБ свободного. Запас огромный, но два
ограничения ставятся СРАЗУ, не потом:

* предел журналу systemd (`SystemMaxUse=512M`) — на управляющем узле его
  отсутствие дало 4 ГиБ журнала и около 3 ГиБ в сутки роста;
* суточные копии «до публикации» (`publish-backups`) на управляющем узле
  выросли до **23,15 ГиБ в 588 файлах**. На восьми витринах это ≈840 МиБ в
  сутки, то есть 25 ГиБ в месяц. Срок хранения назначается при первом же
  выпуске, а не после того, как раздел кончится.

## 3. Один блок команд владельца для root-консоли

Файлы уже на узле: я доставил их в `/home/k2deploy/stage/` обычной доставкой
без root и сверил на месте — `sha256sum -c SHA256SUMS` вернул **0**, 50 файлов
(16 юнитов, 16 конфигураций nginx, 8 включаемых файлов режима индексации,
8 файлов upstream, объявления upstream, опись). Блок ниже только ставит их на
место; ничего не придумывает и ничего не включает.

```bash
# host: k2-zomro-01
set -euo pipefail

# --- 1. Зависимости -------------------------------------------------------
apt-get update
apt-get install -y nginx certbot python3-certbot-nginx python3-venv
install -d -m 0755 /var/www/certbot

# --- 2. Предел журналу СРАЗУ, а не после переполнения ---------------------
install -d -m 0755 /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=512M\nSystemMaxFileSize=64M\n' > /etc/systemd/journald.conf.d/50-size-cap.conf
systemctl restart systemd-journald

# --- 3. Учётные записи и каталоги восьми ячеек ----------------------------
# Данные витрины принадлежат ТОЛЬКО самой витрине: 0750 без записи для группы.
# Каталоги кода — 2775 с группой витрины, чтобы выкладку делал k2deploy и при
# этом не имел права писать в данные.
for acc in lordfilm-group lordfilm-spb-ru lordfilm-msk-ru lordserial-su lordserial-group lordserial-spb-ru lordserial-msk-ru lordserial-net-ru; do
  id -u "$acc" >/dev/null 2>&1 || useradd --system --home-dir "/srv/$acc" --shell /usr/sbin/nologin "$acc"
  install -d -m 2775 -o "$acc" -g "$acc" "/srv/$acc"
  install -d -m 0750 -o "$acc" -g "$acc" "/srv/$acc/data"
  usermod -aG "$acc" k2deploy
done

# --- 4. Юниты ячеек: ставим, НО НЕ включаем ------------------------------
install -m 0644 -o root -g root /home/k2deploy/stage/units/nova-*.service /etc/systemd/system/
systemctl daemon-reload

# --- 5. nginx: объявления upstream и режим индексации (ЗАКРЫТЫЙ) ---------
install -d -m 0755 /etc/nginx/cells /etc/nginx/lords
install -m 0644 /home/k2deploy/stage/cells/lords-1*.robots /etc/nginx/cells/
install -m 0644 /home/k2deploy/stage/cells/lords-1*.upstream /etc/nginx/cells/
install -m 0644 /home/k2deploy/stage/nginx/site-cells-upstreams.conf /etc/nginx/conf.d/
grep -q 'include /etc/nginx/lords/\*.conf;' /etc/nginx/nginx.conf || \
  sed -i 's|include /etc/nginx/conf.d/\*.conf;|include /etc/nginx/conf.d/*.conf;\n\tinclude /etc/nginx/lords/*.conf;|' /etc/nginx/nginx.conf

# --- 6. Первая витрина шага 1 — только она ------------------------------
install -m 0644 /home/k2deploy/stage/nginx/lords-10.conf /etc/nginx/lords/
nginx -t
systemctl reload nginx

# --- 7. Узкие права k2deploy: ровно две команды, из них ни одна не пишет -
printf 'k2deploy ALL=(root) NOPASSWD: /usr/sbin/nginx -t, /usr/bin/systemctl reload nginx\n' > /etc/sudoers.d/k2deploy-nginx
chmod 0440 /etc/sudoers.d/k2deploy-nginx
visudo -c -f /etc/sudoers.d/k2deploy-nginx

# --- 8. Что получилось ----------------------------------------------------
systemctl is-system-running
nginx -v
getent group lordfilm-group
ls -ld /srv/lordfilm-group /srv/lordfilm-group/data
ls /etc/systemd/system/nova-lord*.service | wc -l
journalctl --disk-usage
```

**Ожидаемый результат по шагам.** `apt-get` ставит nginx и certbot; журнал
после перезапуска занимает не больше 512 МиБ; восемь учётных записей
появляются (`getent group lordfilm-group` печатает строку с `k2deploy` в
списке); `ls … | wc -l` даёт **16** юнитов; `nginx -t` печатает
`syntax is ok` и `test is successful`; `visudo -c -f` — `parsed OK`;
`systemctl is-system-running` — `running`.

**Условия остановки.** `nginx -t` не прошёл — снять
`/etc/nginx/lords/lords-10.conf`, перезагрузку не делать и прислать вывод.
Проверено заранее: в `lords-10.conf` слушается только 80, упоминания 443 есть
лишь в комментариях, а блок 443 лежит отдельным файлом и ждёт сертификата —
то есть эта причина отказа исключена, и дело будет в чём-то другом. `visudo -c`
не сказал `parsed OK` — файл `/etc/sudoers.d/k2deploy-nginx` удалить сразу:
битый sudoers ломает sudo целиком. `useradd` отказал на существующем имени —
проверить, не занято ли имя чужой службой, прежде чем продолжать.

**Источники блока проверены НА УЗЛЕ, а не здесь.** Пакетная проверка такие
блоки пропускает по метке `# host: k2-zomro-01` (метка действует только для
хоста из inventory), а пропуск закрыт отдельным инструментом
`automation/local/check-remote-block-sources.py`: он достаёт из блока источники
`install`/`cp` и спрашивает их у самого узла. Результат сейчас — 5 шаблонов,
найдено 16 юнитов, 8 файлов режима, 8 файлов upstream, объявления и
`lords-10.conf`; **отсутствующих источников 0**.

**Чего в блоке намеренно НЕТ.** Ни одной `systemctl enable`, ни одного
запуска витрины, ни одного обращения к certbot: сертификат требует записи A в
DNS, выпуск идёт очередью исполнителя, а до выпуска хранилище витрины пусто и
служба отказала бы «нет снимка каталога». Конфигурации 443 (`*-tls.conf`) тоже
лежат в `stage` и ждут сертификата.
