# Центральный Secret Hub

Один набор credentials CDNVideoHub на направление, а не копия на каждый сайт.
Значения вводятся один раз, хранятся зашифрованными и применяются сервисом
напрямую к инфраструктуре направления.

Архитектурные решения — D68…D74 в `knowledge/DECISIONS.md`.

## Что видит агент и чего он не видит

Сессия агента **может**: спросить состояние, запросить проверку, запустить
применение, ротацию и отзыв, увидеть дату обновления, версию и отпечаток.

Сессия агента **не может**: получить API Token или Publisher ID, вывести их
куда-либо, прочитать файлы секретов или мастер-ключ, передать значение через
argv или переменные окружения.

Это не дисциплина вызывающего кода, а разделение процессов. Значения существуют
только внутри root-процесса `site-factory-secret-hub.service`. У API нет
операции, возвращающей значение, — список операций закрыт:

```
list | status | verify | apply | rotate | revoke | enroll | import
```

Проверяется тестом `test_no_operation_returns_a_secret_value`: он перебирает все
операции, вызывает каждую на настроенном направлении и ищет значение в ответе.

## Направления

| Направление | Состояние | Куда применяется |
| --- | --- | --- |
| `yami` | настраивается | `/srv/sites/yummyani-staging/runtime/cdnvideohub` → `/run/cdnvideohub` (bind, read-only) |
| `lords` | настраивается | `LoadCredential` для `lords-01…03.service` |
| `amedia` | `BLOCKED_TARGET` | инфраструктура не передана |

Новое направление добавляется **записью в `config/secret-hub.json`**, без правки
кода: в пакете `factory/secret_hub/` нет ни списка направлений, ни условий по их
именам. Это тоже закреплено тестом
(`test_portfolio_ids_are_not_hardcoded_in_the_package`).

Amedia остаётся `BLOCKED_TARGET` до тех пор, пока не передан каталог
развёртывания, список unit'ов или compose-файл направления и способ доставки
credentials. Пустое поле — не разрешение подставить значение по умолчанию.

## Хранение

```
/etc/site-factory/secrets/secret-hub-master.key   root:root 0600   — мастер-ключ
/var/lib/site-factory-secret-hub/store.sqlite3    root:root 0600   — шифртекст и метаданные
/var/lib/site-factory-secret-hub/backups/                          — бэкапы хранилища
/var/lib/site-factory-secret-hub/consumer-backups/                 — снимки файлов потребителей
```

Мастер-ключа в SQLite нет: он приходит процессу отдельно через
`LoadCredential`, поэтому украденный файл базы без ключа секретом не является.
Значения зашифрованы AES-256-GCM; ключ записи выводится HKDF-SHA256 из
мастер-ключа и соли записи, а в AAD уходят направление, поле и версия — перенос
шифртекста из записи `lords/api_token` в `yami/api_token` перестаёт
расшифровываться, а не подменяет чужой секрет молча.

Запись значения не перетирает предыдущее: создаётся новая версия, прежняя
остаётся `superseded`. Последняя рабочая версия не удаляется никогда, в том
числе при `revoke`.

## Установка — одна команда

```bash
sudo bash /srv/site-factory/repo/automation/secret-hub/install.sh
```

Скрипт создаёт мастер-ключ (существующий **не** перезаписывает: перезапись
означает потерю всех секретов), каталог хранилища 0700, группу управления,
ставит три unit'а и запускает сервис. DNS, nginx, индексацию, Basic Auth и базы
данных он не трогает.

## Ввод credentials

### Через одноразовую форму

```bash
sudo systemctl start site-factory-secret-hub-enroll@yami.service
sudo journalctl -u site-factory-secret-hub-enroll@yami.service -n 30 --no-pager
```

В журнале — адрес, одноразовый код и отпечаток TLS-сертификата. Код печатается
**только туда**: ни в HTTP-ответе, ни в выводе `factory secrets` его нет, иначе
тот, кто запустил форму из сессии агента, смог бы ею воспользоваться.

С рабочей машины:

```bash
ssh -N -L 8443:127.0.0.1:8443 claude-control-01
```

и открыть `https://127.0.0.1:8443/`, сверив отпечаток сертификата с журналом.

Форма слушает петлевой адрес и наружу не публикуется. Публичного имени у хаба
нет, а DNS трогать запрещено, поэтому проброс порта — осознанный выбор в пользу
«никогда не публиковалось наружу», а не упущение. Адрес и порт настраиваются
(`SECRET_HUB_ENROLL_HOST`, `SECRET_HUB_ENROLL_PORT`).

Свойства формы:

| Требование | Как реализовано |
| --- | --- |
| TTL ≤ 15 минут | `MAX_TTL_SECONDS`; запрос может попросить меньше, но не больше |
| одноразовый код только в root-консоли | stderr unit'а → `journalctl`, доступный root |
| API Token — password field | `type="password"`, как и поле кода |
| Publisher ID — отдельное поле | `type="text"`: по контракту это не секрет |
| POST body, без query string | `GET` с параметрами и любой путь кроме `/` → 404 |
| access_log off | `log_message` и `log_request` — no-op; журнала запросов нет вовсе |
| не более пяти попыток | `MAX_ATTEMPTS`; пятая закрывает сессию |
| CSRF | токен формы, постоянное по времени сравнение по UTF-8 байтам |
| тело ≤ 8 KiB | проверяется и по заголовку, и по факту чтения |
| исчезает после успеха/TTL/5 ошибок | сервер закрывается, до закрытия отвечает 404 |
| не Basic Auth | одноразовый код в теле POST |
| проверка до записи | живой read-only `GET`; неверные значения не пишутся |

### Импортом существующих файлов

Обнаружение безопасно и не читает содержимое — только `stat`:

```bash
python3 -m factory secrets discover
```

Сам импорт выполняется root-процессом:

```bash
sudo systemctl start site-factory-secret-hub-import@yami.service
```

Импорт проверяет значения живым запросом до записи. Старые файлы **не
удаляются**: архивная копия (0600) делается только по явному `--archive`, а
оригиналы остаются на месте до полной приёмки.

## Команды

```bash
python3 -m factory secrets status                      # состояние всех направлений
python3 -m factory secrets discover                    # какие файлы уже лежат на хосте
python3 -m factory secrets verify   --portfolio yami   # живой read-only запрос к провайдеру
python3 -m factory secrets apply    --portfolio yami   # применить к инфраструктуре
python3 -m factory secrets apply    --portfolio lords
python3 -m factory secrets rotate   --portfolio <name> # новая версия + перевыдача
python3 -m factory secrets revoke   --portfolio <name> # отзыв без удаления значения
```

`status` показывает ровно то, что разрешено: направление, `configured`,
`verified`, `updated_at`, отпечаток, потребителей и состояние выката. Значения
не показываются и не могут быть получены.

Флага, принимающего значение секрета, у CLI нет намеренно: такой флаг положил бы
значение в `ps`, в историю shell и в журнал `sudo`. Это закреплено тестом
`test_cli_has_no_flag_that_accepts_a_value`.

## Применение и откат

Порядок `apply` продиктован требованием отката:

1. бэкап зашифрованного хранилища — до единой мутации;
2. живая проверка credentials; неуспех — выход, **работающие сайты не тронуты**;
3. проверка цели: каталог, unit, наличие монтирования в compose;
4. снимок прежних файлов потребителя;
5. атомарная запись (временный файл рядом + `os.replace`, права до наполнения);
6. проверка записанного: файл на месте, права 0400, владелец root;
7. только теперь — перезапуск, и только unit'ов этого направления.

Ошибка на любом шаге возвращает предыдущее состояние. Отказ на втором
потребителе возвращает и первого: половина сайтов на новом токене и половина на
старом — состояние, которое никак не называется.

Работающий сайт не останавливается ради применения. Для Yami перезапуска нет
вовсе: контейнер читает файл при старте, и решение о рестарте принимает
оператор.

Изоляция направлений структурная: `apply_portfolio` получает один `Portfolio` и
видит только его потребителей. Общий каталог или общий unit у двух направлений
отвергаются при загрузке реестра.

## Пароли сайтов

Basic Auth частью Secret Hub не является и этим слоем не устанавливается.
Сайты остаются публичными без пароля, с сохранёнными
`SEO_INDEXING_ENABLED=false`, `X-Robots-Tag: noindex, nofollow`,
`robots.txt: Disallow: /` и sitemap без индексируемых URL. Проверяется тестами
`TestSitesStayPublicAndNoindex` по фактической конфигурации nginx на хосте.

## Проверки

```bash
python3 -m pytest tests/unit/test_secret_hub_*.py -q
```

Покрыто: шифрование и расшифрование, неверный мастер-ключ, подмена и перенос
шифртекста, атомарность записи, права 0600/0700/0400, отсутствие endpoint'а
чтения, отсутствие значений в ответах, логах, argv и окружении, пять неудачных
попыток, TTL, CSRF, отказ провайдера не приводит к записи, изоляция направлений,
откат файлов и версий, `rotate`/`revoke`, secret scan, а также фактическое
состояние nginx и systemd на хосте.

Тесты хоста, которые нельзя выполнить (сервис не установлен, каталог закрыт),
помечаются SKIPPED с причиной. Пройденными они от этого не становятся: пока
`install.sh` не запущен от root, живая проверка хоста остаётся невыполненной.
