## 2. Архитектурное решение и почему оно такое

Выбран blueprint `payload-next-multisite`: Payload CMS 3 + Next.js 16 + PostgreSQL 16.
Полное сравнение с DLE и WordPress Multisite — `adr/0006-payload-next-multisite.md`.
Коротко: три домена на DLE дают три лицензионных контура и три админки, а задание
требует одной CMS; WordPress Multisite хранит контент сайтов раздельно и не даёт
типизированной модели каталога с тремя разными SEO-политиками без набора
исключений. DLE blueprint не удалён и остаётся выбором для других заданий —
пакет выбирает blueprint явным полем.

Каждое утверждение ADR в нём же связано с тестом, который его проверяет.

## 5. CMS: что видит редактор и что он не может сломать

Админка русская, язык не переключается по браузеру. В шапке — селектор сайта;
данные соседнего сайта не подмешиваются ни в списки, ни в счётчики, ни в связи.

Роли: супер-администратор, администратор сайта, редактор, модератор, аналитик.
Роль назначает только супер-администратор — редактор не может повысить себя
(проверено тестом, а не соглашением).

Группы в панели: «Управление сайтами», «Каталог (общий)», «Контент сайта»,
«Модерация», «Операции», «Настройки сайта», «Права и источники», «Служебное».

Черновики, автосохранение и запланированная публикация включены для публикаций
тайтлов, подборок, материалов и страниц.

**Что осталось за рамками первого релиза и почему:** массовое создание диапазона
серий, кроп и фокальная точка медиа, история редиректов при смене slug, дашборд
качества данных, предпросмотр на выбранном домене. Это заявлено в §5 задания,
но не реализовано — и не выдаётся за сделанное.

## 6. Комментарии и модерация

Комментарии собственные. Создание через REST закрыто (`create: () => false`);
единственный путь — серверный endpoint `/api/comments/submit`, который проверяет:
подписанный токен формы (привязан к сайту и к объекту обсуждения), скрытое
поле-ловушку, минимальное время заполнения, длину, число ссылок, глубину ветки,
частоту отправки и ключ идемпотентности.

Премодерация включена по умолчанию: комментарий не виден на сайте и краулеру,
пока модератор его не опубликовал. IP не хранится — для лимитов используется
хэш-отпечаток; e-mail гостя и метаданные отправки закрыты от публичного чтения.

Полный путь проверен запуском: отправка → отсутствие на странице → публикация
модератором → появление на своём сайте → отсутствие на других сайтах → отказ
администратору другого сайта изменить эту запись.

**Не реализовано:** отдельный экран очереди с вкладками и массовыми действиями
(модерация ведётся в списке коллекции «Комментарии» с фильтром по состоянию),
жалобы отправляются только серверным кодом, уведомления модератору отсутствуют.

## 7. Контракт CDNVideoHub и Content API

**Плеер.** Зафиксирован как полученный документ:
`knowledge/cdnvideohub/PLAYER_CONTRACT.yaml`, версия
`CDNVIDEOHUB_KNOWLEDGE_PACK_v1.0`, происхождение — сообщение владельца от
22.08.2026. Независимая сверка с сайтом провайдера **не выполнялась**: среда
исполнения не пропускает соединение (то же ограничение, что и с референсом).
В документе это записано явным полем `verified_against_official_docs: false`.

Реализовано: прямой `<video-player>` без нашего iframe, скрипт подключается один
раз, `disable-licensed="false"` задаётся кодом и не настраивается, конфликт
`only-voice` и `priority-voice` отклоняется, вызываются только `selectSeason` и
`selectEpisode`, слушается только `noData`, кнопка «Повторить» пересоздаёт
элемент, место под плеер зарезервировано пропорцией.

**Content API.** Раздел 9 переданного pack прямо говорит, что endpoint,
параметры, пагинация и поля намеренно не приведены и берутся из
`docs/CDNVIDEOHUB-METADATA-CONTRACT.md`. Этого документа в переданном
репозитории нет. Поэтому адаптер написан целиком, но управляется описанием
контракта: `knowledge/cdnvideohub/content-api.yaml` со статусом `not_provided`,
и до его заполнения синхронизация отвечает `BLOCKED_INPUT`, а не подбирает
адреса. Живой контрактный прогон помечен SKIPPED с причиной.

Санитизированный результат живого прогона отсутствует — прогона не было.

| страницы сезонов | 143 символа собственного текста при минимуме 200 | индексируются только с заметкой редакции (D37) |
| SEO-мутации 2 из 3 | ворота проверялись только живым HTTP | правила вынесены в чистые функции и покрыты проверками (D39) |
| `<video-player>` | до загрузки скрипта провайдера занимал 0 пикселей | размер задаёт наша таблица стилей |

Прогон после исправлений выполнен с чистого состояния целиком, а не точечно.


## 10. Снимки экрана

45 файлов в `var/artifacts/screenshots/`: три сайта × пять маршрутов (главная,
каталог, карточка тайтла, серия, лента материалов) × три ширины (390, 768, 1440).
Снимки делаются в том же прогоне, что и проверки, из production-сборки.

Различие тем проверяется не глазами: отдельный тест сравнивает вычисленные
токены (ширина контейнера, фон, кегль, скругление) и требует трёх разных
значений — совпадение любых двух роняет проверку.

## 11. SEO-аудит и пересечение между сайтами

Матрица индексируемости не переписана: `knowledge/SEO_INDEXABILITY_MATRIX.yaml`
осталась единственным источником правил, а её копия в TypeScript сверяется с ней
построчно (27 проверок). Профиль сайта может только сужать матрицу; попытка
расширить роняет тест.

Ворота `cross_site_uniqueness` (`factory/seo/uniqueness.py`) сравнивают то, что
сервер реально отдал:

| Правило | Что ловит |
|---|---|
| CSU-1..3 | совпадение title / description / H1 между индексируемыми страницами разных сайтов |
| CSU-4 | почти одинаковый основной текст (containment по 4-словным сочетаниям) |
| CSU-5 | содержательная страница без собственного текста |
| CSU-6 | полностью совпадающий состав индексируемых адресов |
| CSU-7 | canonical, ведущий за пределы своего сайта |

Ворота нашли реальные дубли в собственном стенде — одинаковые юридические
страницы, почти одинаковые тексты материалов, один и тот же каталог,
индексируемый двумя сайтами. Это исправлено по существу (разные владельцы
разделов, разные H1, разные тексты), а не понижением порога.

Пустой вход и единственный сайт трактуются как непроведённая проверка, а не как
«уникально».

## 12. Адреса staging и production

**Production-выката не было.** Ни один пакет не авторизован
(`production_authorized: false`), production-домены не переданы, цель
`payload-local` объявлена `production_capable: false` и отвергает production
на уровне адаптера.

Staging — локальный одноразовый стенд: одно приложение на порту из диапазона
8110–8129, три сайта различаются заголовком Host (`site-a.localhost`,
`site-b.localhost`, `site-c.localhost`). Внешних адресов нет и заявлять их
нечестно.

## 13. Бэкап, восстановление и откат

`tests/tools/restore_proof.py` — 10/10 шагов: снимок состояния, дамп, изменение
данных, восстановление, повторный снимок, совпадение с исходным, исчезновение
внесённого изменения и проверка владения схемой. Артефакт: `var/artifacts/restore-proof.json`.

По пути исправлены два настоящих дефекта, которые обесценивали бэкап:
дамп без `--clean` не восстанавливался в непустую базу, а восстановление от
имени владельца кластера отбирало у приложения права на схему.

Откат выполнен фактически: `python3 -m factory rollback --site site-a` вернул `current` на
предыдущий релиз, health-проверка 200, два других сайта продолжили отвечать
своим содержимым. Откат не требует пересборки — каталог прежнего релиза цел.

## 15. Что осталось незакрытым

Список честный: это то, что не сделано или сделано частично, а не то, что
«запланировано на потом».

**Внешние блокировки — работа невозможна без входных данных:**

| Блокировка | Статус | Что разблокирует |
|---|---|---|
| Публичные названия трёх сайтов | не переданы — используются внутренние `site_a/b/c` | список названий и доменов от заказчика |
| Production-домены | не переданы | записи в `inventory/targets.yaml` и `production_authorized: true` |
| Endpoint'ы и схема Content API | в knowledge pack отсутствуют (`status: not_provided`) | `docs/CDNVIDEOHUB-METADATA-CONTRACT.md` |
| `publisher_id` и `title_id` mapping | не переданы | значения из личного кабинета CDNVideoHub |
| Права на контент | подтверждены только для фикстур | договор или письменное подтверждение правообладателя |
| Измерение референса amd.online | недоступно из этой среды (`ERR_TUNNEL_CONNECTION_FAILED`) | сеть или ручные измерения |

Ни одна из этих позиций не заполнена догадкой: пакет отвечает `BLOCKED_INPUT`,
а не подставляет значение по умолчанию.

**Сознательно не реализовано (backlog, а не дефект):**

- аутентификация посетителей, профили, списки «смотрю/буду смотреть», рейтинги —
  мёртвых пунктов меню не заведено;
- кланы, премиум-подписка, достижения;
- предпросмотр черновика на выбранном домене прямо из админки;
- отдельный экран очереди модерации (модерация идёт в общем списке коллекции);
- пагинация ленты материалов (`/news/`) — при росте числа записей часть
  материалов окажется вне обхода краулером;
- страница `content_unavailable` описана в матрице, но в рендере не задействована.

**Проверки, не выполненные из-за среды (помечены SKIPPED, не PASS):**

- живой контрактный прогон плеера с `player.cdnvideohub.com` — домен недоступен;
- измерение референса;
- WebKit и Firefox — в образе установлен только Chromium.

Пока эти проверки не выполнены, production-ворота остаются закрытыми: в
`factory/pipeline.py` невыполненная обязательная проверка даёт `QA_FAILED`, а не
молчаливый пропуск.
