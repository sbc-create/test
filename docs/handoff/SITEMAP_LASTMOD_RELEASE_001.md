# Передача: `lastmod` частей карты — честная дата вместо отсутствующей

Кому: линиям, которые выпускают рантаймы витрин семейств Animedia, Animego,
Lords и Zona. Моя сессия изолирована: `git` в репозиториях ячеек из неё
отклоняется защитой рабочих копий (проверено, не предположено), поэтому выпуск
не мой.

## 1. Дефект, измеренный по сети

MOD-111, измерено 20.10 по всем 17 индексируемым домéнам
(`automation/local/sitemap-index-audit.py`), перепроверено 21.10 на двух
витринах прямым чтением:

```
$ curl -s https://animedia.space/sitemap.xml
<sitemapindex …><sitemap><loc>https://animedia.space/sitemap-1.xml</loc></sitemap></sitemapindex>
$ curl -s https://zonafilm.cc/sitemap.xml
<sitemapindex …><sitemap><loc>…/sitemap-1.xml</loc></sitemap><sitemap><loc>…/sitemap-2.xml</loc></sitemap></sitemapindex>
```

`lastmod` у частей нет вовсе — у **12 домéнов** сети. Обходчик читает индекс
первым и по `lastmod` решает, перезапрашивать ли часть на 45 000–67 000
адресов; решать ему нечем.

**Чего этот дефект НЕ означает:** что карта неверна. Адреса на месте, части
отдаются, содержимое целое. Речь ровно о подсказке обходчику.

## 2. Правка: одна, в `построить_sitemap`

Дата каждой части = **максимум дат внутри этой части**. Если внутри нет ни
одной даты — `lastmod` не ставится вовсе.

**Почему не дата сборки.** Подстановка «сегодня» хуже отсутствия: обходчик
поверил бы, что часть обновилась, и перечитал бы 45 000 адресов, в которых
ничего не менялось. У частей постарше дата законно старая — у Lords и Zona
свежайшая запись во второй части от июня 2025, и так и должно быть.

## 3. Патч собирается командой, файлом отдавать НЕЛЬЗЯ

```bash
python3 automation/local/prepare-sitemap-lastmod-patch.py \
    --source /srv/<витрина>/current/src/seo_layer.py --verify
```

Патч ложится в `var/patches/sitemap-lastmod-seo-layer.patch` (38 строк, вне
git — проверка гигиены запрещает `.patch` в дереве, и она права: закоммиченный
патч против живого файла устаревает молча).

**Почему именно патч, и причина здесь ДРУГАЯ, чем обычно: файлы РАЗОШЛИСЬ, и
ветка НЕ новее.** Установленный `seo_layer.py` на animedia — 22 624 Б, в моей
ветке — 39 884 Б, но установленный содержит `крошки_со_страницы` и
`_НАВ_КРОШЕК`, которых в ветке нет ВООБЩЕ. Копия файла в любую сторону снесла бы
чужую работу. Сборщик отказывается работать, если якорь встречается не один раз
или правка уже есть.

## 5. Репетиция на установленном файле — что именно проверено

`artifacts/evidence/sitemap-lastmod-patch-20261021.txt`. Загружаются ДВА модуля
— работающий файл и он же с патчем — и строят карту на наборе из трёх частей:

| проверка | итог |
| --- | --- |
| части после патча **побайтно те же** | ок |
| до патча `lastmod` в индексе не было | ок |
| после патча `lastmod` в индексе есть | ок |
| `sitemap-1.xml` → `2025-06-10` (максимум ВНУТРИ первой части) | ок |
| `sitemap-2.xml` → `2026-10-19T08:00:00Z` (максимум внутри второй) | ок |
| `sitemap-3.xml` → **без `lastmod`** (внутри нет ни одной даты) | ок |
| первой части НЕ подставлен максимум по всему набору | ок |
| сегодняшняя дата не подставлена | ок |

**Первая версия репетиции ничего не проверяла, и я это нашёл подменой.** Набор
умещался в ОДНУ часть, а тогда «максимум внутри части» и «максимум по набору»
совпадают. Теперь предел адресов на часть в репетиции понижен до 10, части три,
и у них РАЗНЫЕ максимумы. Подмена «максимум по всему набору» даёт три провала из
восьми проверок — проверено.

## 6. Приёмка на витрине — после выпуска, не вместо

```bash
python3 automation/local/sitemap-index-audit.py <витрина>
curl -s https://<витрина>/sitemap.xml
```

Состояние ДО выпуска снято 21.10 на канарейке, чтобы приёмке было с чем
сравнивать:

```
[НЕТ] animedia.space: индекс 200, частей 1
       sitemap-1.xml  200 адресов  8235 | индекс None | внутри 2026-10-21T06:02:21+03:00
       → sitemap-1.xml: в индексе нет lastmod — обходчику нечем решать
```

То есть свежайшая дата ВНУТРИ части уже известна проверке, и после выпуска
именно она обязана появиться в индексе — ни сегодняшнее число, ни пустота.

Ожидание, названное ДО выпуска:

* у каждой части индекса есть `lastmod`, и он равен максимальной дате ВНУТРИ
  этой части (проверка 3 в `sitemap-index-audit.py`, сейчас падает);
* **число адресов в частях не меняется** — отрицательный контроль;
* **дата сборки никому не подставлена**: часть, внутри которой свежайшая запись
  от июня 2025, обязана получить в индексе июнь 2025. Если все части получат
  сегодняшнее число — правку откатывать, а не досматривать: отсутствующую дату
  обходчик игнорирует, а ложной верит;
* положительный контроль, который нельзя потерять: у четырёх витрин Yummy
  проверка индекса проходит уже сейчас. Если после правки она начнёт падать и у
  них — правка задела не то.
