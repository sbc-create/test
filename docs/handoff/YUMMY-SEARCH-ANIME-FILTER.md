# Handoff: поиск теряет треть запросов из-за порядка «найти → отфильтровать»

**Кому:** владельцу приложения витрины (`yummyani/web`).
**От кого:** слой шаблонов Site Factory (семейство `yummy`).
**Статус:** воспроизводится на боевом каталоге; витрина закрывает последствие
запасным поиском, но причина в приложении и правка принадлежит ему.

## Что видно снаружи

Запрос обычным словом отдаёт ноль результатов при непустом каталоге.

| запрос | записей в каталоге с этим словом | `/api/search` приложения |
| --- | --- | --- |
| `воин` | 115 | 0 |
| `небес` | 95 | 0 |
| `любовь` | 76 | 0 |
| `жизнь` | 73 | 0 |
| `девушка` | 62 | 0 |
| `герой` | 56 | 0 |
| `битва` | 35 | 0 |

Это не единичные слова. Замер на 60 частых словах из настоящих названий:
**18 из 60 (30 %) отдают ноль**, хотя записи с ними в каталоге есть.
Свидетельство — `artifacts/evidence/templates/yummy/parity-01/search-loss.json`,
инструмент — `tools/yummy/search_probe.py`.

Соседние формы того же слова работают: `воины` — 26 записей, находит;
`воин` — 115 записей, не находит. Многословный запрос с тем же словом тоже
работает: `мобильный воин` — 49. То есть дело не в индексе названий.

## Где причина

```
src/modules/catalog/catalog-query.ts
```

* **`searchAnimeListItems()`** (строка 276) — вся последовательность;
* **`client.searchTitles(normalized, API_WALK_LIMIT)`** (строка 285) — запрос
  к поставщику;
* **`confirmAnimeIds(client, …)`** (строка 296) — отсев не-аниме;
* **`API_WALK_LIMIT = 100`** (строка 80) — размер первой выборки.

```ts
const collected = [...(await client.searchTitles(normalized, Math.min(limit, API_WALK_LIMIT)))];
…
const eligible = await confirmAnimeIds(client, collected.map((item) => item.providerTitleId));
const mapped = collected.filter((item) => eligible.has(item.providerTitleId))…
```

Поиск спрашивает поставщика **по всему его каталогу** — фильмы, сериалы,
аниме вместе, — берёт первую сотню найденного и только потом отсеивает
не-аниме. У частого слова первая сотня поставщика состоит из не-аниме
целиком, и до посетителя не доходит ничего.

Что подтверждает именно эту причину, а не «плохой индекс»:

* `listTitles()` (строка 332) умеет `direction: ANIME_DIRECTION` и им
  пользуется везде, кроме поиска;
* `searchTitles()` в клиенте
  (`src/modules/catalog/infrastructure/cdnvideohub/client.ts`, строка 215)
  отправляет только `q` и `limit` — параметра направления там нет вовсе;
* редкое слово (`Гандам`, `океан`, `тьмы`) проходит: у него в первой сотне
  поставщика аниме есть.

## Нужная правка

Порядок «сначала сузить до аниме, потом искать» вместо «найти всё, потом
отсеять». Два способа, любой закрывает дефект:

1. **направление в запросе поиска.** Добавить `direction` в `searchTitles()`
   и передавать `ANIME_DIRECTION` из `searchAnimeListItems()`. Самый дешёвый
   вариант, если ручка поставщика это принимает.
2. **добор страницами.** Если поставщик направление в поиске не принимает —
   ходить по его выдаче постранично, пока не наберётся нужное число
   подтверждённых аниме или не кончится выдача. Ограничение по числу
   запросов уже есть рядом: `MAX_WALK_REQUESTS` (строка 81).

Первый способ предпочтительнее: второй тратит обращения к поставщику на
заведомо ненужные страницы.

## Как проверить после правки

```bash
python3 tools/yummy/search_probe.py \
  --readmodel <снимок контура> --app http://127.0.0.1:3101 \
  --out /tmp/search-loss-after.json --words 60
```

Признак исправления — `lost_by_app: 0`. Число в `in_catalog` берётся из
контура и от правки не зависит, поэтому до и после сравнимы напрямую.

## Что витрина делает до правки

Витрина не подменяет поиск приложения: пока приложение что-то находит,
отвечает оно. Ноль обрабатывается в два шага:

1. **расширение запроса** — пробуются последовательно укороченные варианты с
   сохранёнными разделителями (`Жил-был-воин` → `Жил-был`), каждый
   проверяется по настоящему индексу приложения;
2. **запасной поиск** — если и они пусты, отвечает собственный каталог
   контура: те же записи, тот же адрес, объявленный порядок (точное
   совпадение, начало названия, вхождение). Страница прямо говорит, что
   индекс приложения не вернул ничего, и сохраняет введённый запрос в поле
   поиска.

Подсказки (`/api/search`) отдаются в той же форме, что у приложения, — иначе
их клиент не покажет.

Это обход, а не исправление: он не помогает ни приложению, ни другим его
потребителям, и снимается в тот день, когда порядок в `searchAnimeListItems`
станет правильным.
