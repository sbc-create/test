## 1. Дефект, измеренный на витрине

MOD-81 (P0), измерено 18.10 и перепроверено **21.10**
(`automation/local/sitemap-generation-lag.py --domain 1lordserials1.online`):

```
записей в каталоге 68451, произведений в карте 67681, нет в карте 770, лишних 0
проба отсутствующих (12 из 770): noindex 0, index 12, без метки 0
ПРОБЕЛ КАРТЫ, примеры: bayki-iz-sklepa-ot-komiksov-do-televideniya, bezumnyy-zver, …
```

**770 индексируемых произведений поисковику не названы**, и это не оценка: из
выборки 12 отсутствующих все 12 ответили `index`. Полный опрос всех 770 дал
`index` у 770 из 770 (`sitemap-catalog-reconcile-anime.py` без предела).

## 2. Причина — прочитана в установленном дереве

Поток карты в ядре берёт поколение каталога так
(`/srv/site-1lordserials1-online/current/src/seo_layer.py:554`):

```python
данные = getattr(getattr(рантайм, "Обработчик", None), "данные", None)
поколение = (getattr(данные, "revision", ""), записей)
if поколение != прошлое:
    итог = обновить_карту(рантайм, каталог, хост)
```

а наложение, перечитав снимок, обновляет ТОЛЬКО свой набор
(`overlay/freshness.py`, `_перестроить`): `self.набор = Набор(...)`. Классовые
поля ядра остаются от старта, поколение не меняется НИКОГДА, и поток карты не
получает повода пересобрать файлы. `адреса_карты` читает те же классовые поля
и больше ничего — проверено чтением, а не предположено.

**Перезапуск витрины исправлением НЕ является:** он соберёт карту один раз и
снимет пробел, а причина останется — карта снова застынет на поколении запуска.

## 3. Правка: три присваивания

Прецедент в сети: `lords-02` делает ровно это у себя
(`/srv/lordserial33-biz/current/src/lords02_reload.py:226-228`), и карта там
сегодняшняя.

```bash
cd /home/claude/wt-nova-publish-memory-02
python3 automation/local/prepare-overlay-reload-patch.py --verify
```

Патч ложится в `var/patches/overlay-reload-core-fields.patch` (33 строки, вне
git: закоммиченный патч против живого файла устаревает молча). Сборщик
отказывается, если якорь встречается не один раз или правка уже есть.

**Чего патч НЕ делает, намеренно:** не вызывает `сброс_популярного_кэша()` и не
обнуляет `Снимок._снимок`. У наложения прямо записано, почему: читатель кэша в
ядре двухшаговый, и `clear()` из потока перечитывания даёт `KeyError` и 500 на
главной — в момент публикации каталога, то есть когда владелец смотрит.
Недельный порядок полки — объявленный контракт. Проверка «патч не добавил
вызовов сброса» входит в репетицию.

**Порядок присваивания не случаен** и взят у прецедента: сначала `данные`,
потом `подробности` и `индекс`. Окно между присваиваниями есть при любом
порядке; этот даёт безопасную сторону — новая запись пока не находится по
старому индексу («ещё не в списке»), тогда как обратный порядок дал бы индекс
со слагами, которых в данных нет. Присваивание стоит ПОСЛЕ успешной сборки
набора: на битом снимке `_перестроить` уходит в `except`, и ядро остаётся на
прежнем поколении целиком.

## 4. Репетиция: 6 проверок, провалов 0

Настоящее ядро тянет снимок 16.7 МБ и подробности 75.8 МБ, поэтому репетиция
копирует ВЕСЬ каталог наложения (`from . import newness, shelves`), а ядро
подменяет моделью: классы `Данные`, `Подробности`, `Обработчик` и
`построить_индекс_исходный`. Поколение читается ровно так же, как его читает
поток карты.

| проверка | итог |
| --- | --- |
| ДО патча поколение ядра `('r3', 3)` → `('r3', 3)` | дефект воспроизведён |
| ПОСЛЕ патча `('r3', 3)` → `('r5', 5)` | поколение дошло до ядра |
| набор наложения обновляется в обоих состояниях (5 записей) | правка не задела перечитывание |
| счётчик `перечитано` = 1 в обоих | не задет |
| битый снимок: ядро осталось на `('r5', 5)`, ошибка названа | половина поколения не отдаётся |
| вызовов сброса кэша было 0, стало 0 | кэши не тронуты |
