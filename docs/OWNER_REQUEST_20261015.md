# Один запрос владельцу: девять операций, всё остальное подготовлено

Запись от 2026-10-15, 17:50. Здесь собрано ровно то, что сессия сделать не
может: права root на узлах, DNS, секреты, обращение во внешний сервис и

подготовлено и проверено; у каждой операции названо, что она разблокирует.

трафик. Операции независимы: блокировка одной не держит остальные.

## 1. Срок хранения копий публикации — освобождает 22 ГиБ немедленно

**Почему первое.** На разделе 2,5 ГиБ из 203 (1,2 %). На нём живут все
витрины, их данные и журналы; бэкап хоста не идёт с 29 сентября, а
доказанного восстановления нет с 23-го. Это единственная операция, которая
меняет состояние сразу.

**Решение, которое нужно принять:** глубина отката публикации каталога. Три
суток — самый долгий срок, при котором бэкап возобновляется (семь суток не
проходят: нужно 30,25 ГиБ при 19,97 свободных после очистки).

```bash
find /srv/site-factory/repo/var/lords/publish-backups -type f -mtime +3 -printf '%TY-%Tm-%Td %10s %p\n' | sort | tail -20   # посмотреть
find /srv/site-factory/repo/var/lords/publish-backups -type f -mtime +3 -delete                                             # удалить
systemctl start site-factory-backup.service && systemctl status site-factory-backup.service --no-pager
ls -la /srv/backups/ | tail -4    # ожидается новый host-*.tar.gz И его *.verified.json
```

Числа, варианты и что теряется — `docs/OWNER_BACKUP_RESUME_20261015.md`.

### 2а. Тем же порядком — реестр ячеек

Та же картина у реестра. Исправленные статусы `lords-02` и `lords-03`

На выкладку это не влияет (исполнитель берёт размещение из `runtime`), но
портит любую выборку «живых»: именно из-за устаревшего статуса две живые

Писать в тот каталог эта сессия не вправе: он общий для нескольких живых
сессий. Нужен перенос ветки в рабочую копию — тем же решением, что и для
публикатора в пункте 2.

**И третий реестр, с самой резкой датой.** `config/analytics.json` существует
в трёх копиях: ветка (29 записей, 15.10), рабочий каталог службы сбора
(21 запись, 08.10) и `/srv/site-factory/repo` — **6 записей от 27 августа**,
то есть файл старше счётчиков, о которых молчит. Значения при этом не
расходятся нигде: из 21 домена, присутствующего больше чем в одной копии, ни
один не отличается ни по одному полю (проверено
`automation/local/analytics-registry-copies.py`). Расходится только охват — и
этого достаточно, чтобы чтение короткой копии дало вывод «целей нет»: так
сегодня и вышло у одной из линий. На `/srv`-путь при этом прямо ссылается
`config/site.json` каждой витрины словами «Создание и сверка счётчика —
config/analytics.json фабрики».

Решение, которое просят линии витрин и которое я считаю сильнее сведения
копий руками: инструмент должен ОТКАЗЫВАТЬСЯ работать с копией старше
объявленного источника. Свести копии можно один раз — расходиться они будут
снова, а ни у одной из них нет признака, по которому видно, что она не
главная.

### 2б. Тем же порядком — отправка целей Метрики

Та же зависимость у самого дорогого для цели роста изменения. У тринадцати
доменов счётчик считает визиты и НЕ отправляет ни одного события: в рантайме
семейства не было ни одного вызова `reachGoal` (доказано пробой живой страницы
и чтением кода — `docs/verification/analytics-event-receipt-20261015.md`).
Отправка восьми целей из девяти написана и проверена исполнением скрипта в
node плюс рендером страницы, но лежит в ветке
`claude/nova-publish-memory-02`.

До витрин она доезжает ТОЛЬКО их выпуском. Линии витрин ведут другие сессии,
и выпуск за них эта сессия не делает. Домены, которых это касается:
`lordfilm47.space`, `lordserial33.biz`, `1lordserials1.online`,
`lordserials22.info`, `animedia.icu`, `animedia.space`, `an1meg0.site`,
`an1mego.site`, `animeg0.site`, `zonafilm.space`, `zonafilm12.site`,
`zonafilm.cc` и восемь витрин партии K2 после перевода DNS.

Критерий приёмки измерим и уже готов: `python3
automation/local/metrika-hit-probe.py --domain <домен>` называет цели на
странице произведения, а через семь суток отчёт Метрики показывает ненулевые
достижения у тех же доменов. Без этого план роста измеряется только визитами,
то есть следствием, и поведенческих сигналов (запуск плеера, выбор серии,
поиск) нет ни по одному домену кроме Yummy.

## 3. Выпуск кода на узле K2 — закрывает дефект доступности серий у восьми витрин

Восемь витрин партии родились без модуля согласования доступности серий:
доступность серии у них — одно число суточного снимка, и карточка способна
обещать серию, которой у провайдера нет (та самая жалоба про «Провайдер не
отдал источник»). Модуль и проверка уже доставлены на узел бандлами и сверены
там по сумме, голове и признаку; сухой прогон выпуска прошёл на всех восьми.

```bash
sudo /home/k2deploy/stage/k2-release-code.sh lords-10
sudo /home/k2deploy/stage/k2-release-code.sh lords-11
sudo /home/k2deploy/stage/k2-release-code.sh lords-12
sudo /home/k2deploy/stage/k2-release-code.sh lords-13
sudo /home/k2deploy/stage/k2-release-code.sh lords-14

sudo /home/k2deploy/stage/k2-release-code.sh lords-16

```

Сценарий не трогает данные витрины, nginx, DNS, сертификаты и режим
индексации; плеер переносит из текущего выпуска; при неудаче healthz или
не-200 возвращает прежний выпуск сам. Повторный запуск безопасен.

Тот же выпуск привезёт второе исправление — отправку целей Метрики. На этих
восьми витринах она пока **инертна, и это правильно**: счётчика у них нет
(`counter_state: planned`, `counter_id: null`), а без счётчика рантайм не
печатает ни тега, ни скрипта целей вовсе. Решение владельца 13.10 по этой
партии прямо запрещает и Метрику, и замену её на Google Analytics — код
доставлен заранее, чтобы при будущем решении о счётчике не понадобился
отдельный выпуск. Выигрыш от целей получают тринадцать ДЕЙСТВУЮЩИХ доменов,
и им нужен выпуск их линий (пункт 2б).

То есть одна и та же линия недостижима для связи и забирает память у
работающих витрин. Ни перенос витрин, ни починка памяти в ячейках этого не
решают: нужно, чтобы к ней вернулся человек — либо она была остановлена.
Сессия её не трогает: чужая сессия с собственным оператором.

## 9. Идентификаторы и доступ для аналитики восьми витрин

Счётчики восьми витрин объявлены в реестре в состоянии `planned`
(`counter_id: null`, аналитика выключена) — это объявление домена, а не
настроенная аналитика. Создание счётчиков идёт командой
`analytics apply --confirm-writes`, ей нужен OAuth-токен из credential службы
`analytics-cabinet`, который сессия не читает. Пока DNS не переведён, собирать
всё равно нечего, поэтому пункт стоит последним.
