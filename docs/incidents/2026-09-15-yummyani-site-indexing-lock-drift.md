# 2026-09-15 · yummyani-site · расхождение слоёв запрета индексации

## 1. Что произошло

Статус: `LCK-001` (расхождение слоёв запрета индексации), витрина `yummyani-site`,
домен `yummyani.site`.

В ходе задания `SEO-PREINDEX-READINESS-LOCKED-01`, прямо запрещавшего открывать
индексацию, на `yummyani.site` был выложен мета-тег `robots: index, follow` и
наполнена карта сайта. Выкладку выполнила **не** сессия, ведущая это задание.

| | |
| --- | --- |
| Время последней проверки «замок цел» | 2026-09-15T16:58Z — 9/9 закрыты |
| Старт контейнера с изменением | **2026-09-15T17:17:32Z** (`docker inspect .State.StartedAt`) |
| Время обнаружения | 2026-09-15T17:25Z, ручной перезапуск разовой проверки |
| Обнаружено автоматикой | **нет** — суточный цикл такого вопроса не задавал |

Изменение точечное и намеренное, а не сбой конфигурации:

```
yummyani-staging-web-site-1   SEO_INDEXING_ENABLED=true    APP_ENV=production
yummyani-staging-web-org-1    SEO_INDEXING_ENABLED=false   APP_ENV=production
```

Из трёх контейнеров переключён один. Это совпадает с заявленным намерением
открытого PR `sbc-create/yummyani#14` — «yummyani.site открыт для индексации,
остальные площадки не затронуты».

## 2. Влияние

Затронут один домен. Состояние слоёв на момент отчёта:

| Слой | Состояние | Кто отдаёт |
| --- | --- | --- |
| `X-Robots-Tag: noindex, nofollow` | держит | приложение `yummy-frontend.py` (:9132) и nginx |
| `robots.txt: Disallow: /` | держит | приложение `yummy-frontend.py` |
| `meta robots` | **снят**, отдаёт `index, follow` | контейнер `yummyani-staging-web-site-1` (:3101) |
| профильный флаг `indexing_enabled` | держит (`false`) | `config/site-profiles/yummyani-site.json` |

Фактической индексации **не произошло и произойти не может**, пока держатся
первые два слоя: `robots.txt` запрещает обход целиком, а `X-Robots-Tag`
авторитетен для любого робота, который страницу всё же скачает. Оба отдаёт
приложение, а не только nginx, — проверено запросом к `127.0.0.1:9132` напрямую.

Публикации в поисковые системы не было: отправок карты сайта, IndexNow и
URL Inspection — ноль.

Утечки данных между сайтами нет.

**Существенно не текущее состояние, а потеря глубины.** Было четыре независимых
запрета, из которых для открытия надо снять все; стало три, и HTML при этом
активно зовёт робота, противореча заголовку. До полного открытия остаётся одна
выкладка.

## 3. Что фактически проверялось

| Команда | Результат |
| --- | --- |
| `curl -sSI https://yummyani.site/` | `x-robots-tag: noindex, nofollow` |
| `curl -sS https://yummyani.site/robots.txt` | `User-agent: *` / `Disallow: /` |
| `curl -sS https://yummyani.site/` → `meta robots` | **`index, follow`** |
| `curl -sSI http://127.0.0.1:9132/` | `X-Robots-Tag: noindex, nofollow` — слой независим от nginx |
| `curl -sS https://yummyani.site/sitemap.xml` | 5 шардов (было `<urlset></urlset>`) |
| `docker inspect yummyani-staging-web-site-1` | `SEO_INDEXING_ENABLED=true`, старт 17:17:32Z |
| `seo-operator dry-run` | `LCK-001 yummyani-site`, замок закрыт на 8 из 9 |

## 4. Root cause

Две сессии работали над одним production-доменом с противоположными мандатами и
друг о друге не знали. Одна выполняла задание, требующее сохранить запрет до
письменной команды владельца; вторая — задание открыть индексацию `yummyani.site`.

Техническая причина, по которой это осталось незамеченным: контур не имел
проверки **согласованности** слоёв. Существующие проверки отвечали на вопрос
«индексируется ли сайт», и на него ответ не изменился — сайт по-прежнему не
индексируется. Вопрос «говорят ли слои одно и то же» не задавался, поэтому
снятие одного из четырёх запретов не отразилось нигде: ни в находках, ни в
примечаниях, ни в счётчиках отчёта.

«Другая сессия выложила» — обстоятельство, а не причина. Причина в том, что
контур не умел это заметить.

## 5. Что предотвратит повтор

В том же изменении добавлен `seo_operator/indexing_lock.py`: суточный цикл
читает четыре слоя по каждой витрине и поднимает критическую находку `LCK-001`,
если они разошлись. Согласованно открытый сайт находкой не считается — это
решение владельца, а проверка про согласованность.

На живом портфеле проверка находит ровно этот случай:

```
LCK-001 yummyani-site — слои запрета индексации разошлись:
сняты meta_robots, держат profile_flag, robots_txt, x_robots_tag
замок индексации: закрыт полностью на 8 из 9, расходится на 1, открыт на 0
```

Покрытие: `tests/operator/test_indexing_lock.py`, 12 проверок, включая
воспроизведение этого инцидента и два разных «нет» — неизмеренный слой молчит,
измеренный без ответа поднимает тревогу.

## 6. Данные

Резервные копии не затрагивались: изменение касается заголовков и мета-тега, а
не содержимого. Целостность каталога не менялась. Откат выкладки не выполнялся —
см. ниже.

## Почему откат не выполнен

Сессия, ведущая `SEO-PREINDEX-READINESS-LOCKED-01`, откат **не выполняла**
сознательно:

1. Изменение точечное и совпадает с намерением открытого PR — это осознанная
   работа, а не авария.
2. Откат означал бы перезапуск production-контейнера против действующей
   выкладки другой сессии; при встречных действиях домен начнёт «мигать».
3. Санкционировал ли владелец открытие, из доступных данных не следует, а
   спросить в профиле `UNATTENDED_SAFE` нельзя.

Собственных production-мутаций у этой сессии ноль, отправок в поисковые системы
ноль.

## Требуемое решение владельца

Одно из двух, и оно за владельцем:

* открытие `yummyani.site` санкционировано — тогда привести к согласованности
  остальные три слоя и закрыть `LCK-001` осознанно;
* открытие не санкционировано — вернуть `SEO_INDEXING_ENABLED=false` контейнеру
  `yummyani-staging-web-site-1` и решить судьбу PR `sbc-create/yummyani#14`.

Оставлять расхождение — худший из трёх вариантов: сайт держится не замыслом, а
тем, что из четырёх запретов пока действуют три.
