# Runbook оператора — общий модуль комментариев

Контур: `claude/community-comments-platform-01`
Модуль: `COMMUNITY_COMMENTS`, версия `0.1.0-mvp`, API `v1`
Статус: `READY_FOR_LOCAL_REVIEW` — production запрещён

## Что сейчас включено

Ничего. Все ворота нули, и это не заготовка под заполнение: потолки в
`factory/comments_platform/flags.py` тоже нули и зажимают любое значение из
конфига, окружения и операторского override до нуля. Единица в
`config/comments-platform/sites.json` ничего не включит.

Включение требует изменения исходного кода (потолок), изменения конфига
(значение сайта), ревью и записи в аудит. Так сделано намеренно: одна
правка одного файла не должна включать комментарии на девяти сайтах.

Проверить фактическое состояние:

```bash
python3 -c "
from factory.comments_platform.flags import FlagResolver
from factory.comments_platform.tenancy import SiteRegistry
r = SiteRegistry.from_file('config/comments-platform/sites.json')
for b in r.all_bindings():
    print(FlagResolver().resolve(b).as_dict())
"
```

Браузерный набор поднимает статический сервер на `127.0.0.1:8787` сам и не
требует ни стенда, ни доступов. `file://` использовать нельзя: браузер
запрещает оттуда `fetch`, и один тест из-за этого проходил по неверной
причине — запрос падал, сообщение об ошибке оставалось видимым, и
утверждение не различало эти случаи.

## Аварийная остановка

Уровень 1 — остановить запись и чтение, страница сайта продолжает работать:

```python
from factory.comments_platform.flags import KillSwitch
KillSwitch.engage_global()
```

Либо снаружи процесса: `COMMENTS_KILL_SWITCH=1`. У этого переключателя
полярность обратная флагам — окружение может его **поднять**, но не опустить.
Безопасность выигрывает спорные случаи.

Состояние читается заново на каждой проверке: оператор, дёрнувший стоп, не
ждёт перезапуска процесса. Возврат — `KillSwitch.release_global()`, тоже без
перезапуска.

Per-site остановка, не задевающая остальные сайты:

```python
resolver.set_site_override(TenantScope("lords", "lords-01"), kill_switch=1)
```

## Модерация

Состояния: `pending`, `published`, `quarantined`, `hidden`, `restored`,
`removed`. Полный граф переходов —
`artifacts/evidence/community-comments-platform-01/01-contracts/STATE_MACHINE.json`.

Что важно знать оператору:

* Ни одно состояние не удаляет текст. `hidden` и `removed` мягкие, тело
  остаётся в базе. Автоматика, уничтожающая доказательства, делает решение
  непроверяемым и необратимым.
* Автоматика может скрыть, но никогда не удаляет. `removed` — только человек.
* Ручное действие без причины не проходит: запись в аудит без причины
  отклоняется, а действие без записи невозможно.
* Правка комментария возвращает его в модерацию. Иначе «написать безобидное,
  дождаться одобрения, переписать» — открытая дверь.
* `removed` — терминальное состояние. Если удаление было ошибкой, это новое
  решение с новой записью, а не отмена прежней.

Очередь: `service.moderation_queue(scope, principal)`. Она отдаёт превью, а
не тело: очередь — это список, а модератор открывает то, с чем собирается
что-то сделать.

## Отказ античита

При недоступности античита комментарий **удерживается**, а не публикуется.
Иначе «положить фильтр» становится стратегией публикации. Это видно в ответе:
`moderation.degraded = true`, состояние `pending`.

## Откат

Четыре уровня, от самого мягкого. Подробно —
`05-rollout/ROLLBACK_PLAN.json`.

1. Kill switch — секунды, обратимо, без перезапуска, отрепетировано тестом.
2. Погасить сайт (`read_enabled`, `write_enabled` в 0) — данные не меняются.
3. Вернуть прежний артефакт (перезакрепить `module_version` и сумму).
4. Откатить схему (`migrations/0007` downgrade) — **только после backup**.
   Это уничтожает данные комментариев, и снятый непосредственно перед
   откатом backup — единственный путь восстановления. Репетиция этого пути
   есть в `test_resilience.py::TestMigrationRollbackRehearsal`.

Backup снимается штатным online backup API SQLite, а не копированием файла
живой WAL-базы: копия может поймать надорванную страницу. Проверка копии —
`PRAGMA integrity_check` и `PRAGMA foreign_key_check`.

## Приватность

Сервис не хранит паролей, email и сырых IP. Сетевой идентификатор — HMAC на
ключе арендатора с посуточной ротацией и сроком хранения 7 дней.

Операции подготовлены, но на production не запускаются:

* выгрузка по субъекту — `store.export_subject(scope, subject_id)`;
* анонимизация — `store.anonymize_subject(scope, subject_id)`.

Анонимизация отвязывает человека от комментариев, но не удаляет их: удаление
строк пробило бы дыры в каждом разговоре, в котором он участвовал.

## Что считать инцидентом P0

Подтверждённая выдача данных одного сайта на другом. Это блокирует выкат
целиком. Счётчик `cross_tenant_attempts_total` делает это наблюдаемым;
ненулевое значение само по себе не означает утечку — отражённая проба тоже
его увеличивает. Недопустимо другое: ноль отказов рядом с отданным ответом.

Также блокируют выкат: pending или hidden в публичной выдаче, ручное
действие без причины, пробел в аудите привилегированной операции, падение
теста в любой обязательной категории.

## Чего не делает этот модуль

Не меняет `robots`, `meta robots`, canonical, sitemap, hreflang,
индексируемость сайта и JSON-LD рейтингов. Не отдаёт краулеру версию,
отличную от пользовательской: ветки по user-agent в модуле нет и параметра
для неё нет. Не трогает `community-ratings-gateway.service` и таблицы
рейтингов.
