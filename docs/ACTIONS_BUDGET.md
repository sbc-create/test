# Расход GitHub Actions: порядок запуска проверок

Измерено 13 октября 2026, окно 48 часов (11.10 11:00Z — 13.10 11:00Z).
Проверяется инструментами, а не памятью:

```bash
python3 automation/local/actions-spend.py --hours 48 [--budget <минут/месяц>]
python3 automation/local/workflow-policy-check.py
```

## Как считаются минуты и чего измерить нельзя

**Минуты реконструированы по заданиям**, а не взяты из биллинга. Причина
измерена: `/actions/runs/{id}/timing` отдаёт этому токену `billable` = 0 даже у
прогона, который шёл на раннере GitHub четыре с половиной минуты (прогон
`38326615302`, задание «Unit tests + APKs» 00:20:04 → 00:24:29, runner «GitHub
Actions 1000001850»). Первый замер по этому полю дал «0 минут» при 498
прогонах — то есть считал нули.

Реконструкция: сумма по заданиям `ceil(длительность / 60)`, только по тем, что
реально шли на раннере GitHub (у пропущенных по `if` поле `runner_name` пусто).
GitHub списывает именно по заданиям с округлением вверх; множитель Linux — 1.

**Размер бюджета здесь не измеряется.** API биллинга
(`/users/{u}/settings/billing/actions`) требует права `user`, которого у токена
нет: ответ `404` плюс «This API operation needs the "user" scope». Подставлять
«обычное» число тарифа нельзя — это вход владельца. Поэтому норма и прогноз
считаются от переданного `--budget`, а без него инструмент печатает предел, а
не догадку.

**Открытые репозитории квоту не тратят, и это пришлось проверить.** Первый
замер я сделал через `users/<логин>/repos` — тот отдаёт только открытые, нашёл
один репозиторий из двадцати шести, и «расход 0» оказался свойством запроса.
Правильный путь — `/user/repos`. Фабрика лежит в **открытом**
`sbc-create/test` (origin рабочей копии), её 276 минут за 48 часов в бюджет
**не входят**.

## Поправка: моя оценка отмены была завышена в 28 раз

Сначала я посчитал так: прогон **вытеснен**, если более новый прогон той же
пары (рабочий процесс, ветвь) создан раньше, чем прежний закончился, — и
записал в экономию минуты, потраченные после этого момента. Получилось 2 603
минуты за 48 часов, 62,8 % квоты. **Это неверно, и поправку принесла сессия
приложения.**

Я не посмотрел, ЧТО изменилось между коммитом прогона и коммитом, который его
вытеснил. Проверил на всех 42 вытесненных прогонах приложения (`compare` по
каждой паре):

| чем вытеснен | прогонов | минут за 48 ч | в сутки |
| --- | ---: | ---: | ---: |
| **изменением кода** — вот это напрасно | **2** | **90** | **45** |
| тем же коммитом или только `.md` — код тот же, результат в силе | 40 | 2 459 | 1 230 |

Пример, с которого началась поправка: `2b5a0815 → e0139e5c` — один коммит,
меняющий только `docs/STATUS.md` **в репозитории приложения** (в этой
ветви такого файла нет; проверено `compare` — один файл). Значит
ручной прогон на `2b5a0815` проверял **тот же код**, и отменять его было бы
не экономией, а уничтожением годного результата.

**Возвратимо отменой: 45 мин/сутки, а не 1 302.** Это 2,2 % квоты. Моя оценка
была завышена в 28 раз, и держалась она на подмене: «перекрытие по времени» я
принял за «устаревший результат».

### Что тогда расходует квоту на самом деле

Разбор перекрытий на одном коммите показал другую картину. Набор платных
заданий у прогона PR и у ручного запуска РАЗНЫЙ:

```
коммит cb73dab755d9: прогонов 2, минут 139
   22:15:37Z  pull_request       success  5 мин   задания: Unit tests + APKs
   22:52:26Z  workflow_dispatch  failure  134 мин задания: E2E phone, E2E tv,
                                                  E2E tv 4K, E2E tv soak,
                                                  E2E tv-playback, Unit tests + APKs
```

То есть это не дубли: ручной запуск добавляет эмуляторы. Повтор ОДИНАКОВОГО
набора заданий на одном коммите даёт всего **2 мин/сутки**.

Значит расход держится не на дублях и не на устаревших прогонах, а на трёх
других вещах, и все три измерены:

1. **Частота тяжёлой матрицы.** 32 запуска за 48 часов по ~130 минут —
   1 058 мин/сутки. Это 51 % всей квоты, и единственный рычаг здесь — реже.
2. **Провалы — НЕ напрасный расход, и это вторая снятая мною оценка.** Я
   записал 2 741 минуту в прогонах с исходом `failure` как признак потерь:
   `E2E phone` 20 провалов из 32 запусков, `tv-playback` 13 из 32, `soak` 5
   из 12. Сессия приложения объяснила: большая часть этих провалов —
   **намеренное воспроизведение дефектов** до исправления и правка самих
   тестов. То есть минуты были связаны с конкретным проверяемым риском, а
   задание именно этого и требует. Отдельно `soak` (прогон `38319104103`,
   37 минут) упал не по воспроизведению, а по собственной проверке честности:
   в `/data/anr` появился дамп без `am_anr` и без DropBox, такой дамп
   засчитывается как FAIL; по журналу это предварительный дамп сторожа
   `system_server`, причина не установлена. Вывод: исход `failure` сам по себе
   напрасным расходом не является, и считать его так — та же подмена, что с
   вытеснением.
3. **Повторная сборка APK.** Задание `Unit tests + APKs` исполнялось 87 раз за
   377 минут, из них 178 внутри ручных запусков: тот же коммит собирается и в
   прогоне PR, и в ручном. Переиспользование по `github.sha` сессия приложения
   отклонила с технической причиной — `versionCode = run_number` нужен для
   проверки обновления поверх выпуска. Причина принята; значит эти ~80
   мин/сутки снимаются не ключом артефакта, а отдельной задачей.

### Почему отмена всё равно нужна — и почему в ячейках она безопасна

В ячейках отмена включена вместе с `paths-ignore`, и это существенно: коммит
только с документацией в ячейке **не запускает прогон вовсе**, поэтому отменить
годный результат он не может. Отмена там срабатывает только на изменении кода —
то есть ровно тогда, когда прежний результат действительно устарел.

Измеренный возврат в ячейках — не больше 27 мин/сутки (54 минуты за 48 часов),
и по причине вытеснения я их не разделял: величина мала в любом случае.
Остальное в ячейках — предотвращение, а не возврат.

## Порядок запуска

| что изменилось | когда запускается |
| --- | --- |
| документация, отчёты, `*.md`, `adr/` | **ничего**: `paths-ignore` на `push` и `pull_request` |
| изменение кода на рабочей ветви | проверки ячейки (`checks/run.sh` + `site_id` + манифест), прежний прогон той же ветви **отменяется** |
| полная приёмка | на `main`, при открытии PR и по ручному запуску; отмена на `main` **выключена** — приёмку выпуска обрывать нельзя |
| плановая тяжёлая регрессия | не чаще раза в сутки и только при изменениях; расписание чаще суток проверка считает нарушением |
| soak, 4K, повторные эмуляторные | только ручным запуском с явным входом (`inputs.e2e`, `inputs.tv4k`, `inputs.soak`) — при изменениях соответствующей функциональности или по конкретному дефекту |

Повторить успешно проверенную неизменившуюся версию можно только с записанной
причиной: `workflow_dispatch` с `inputs` и текстом причины в заголовке
запуска. Инструмент расхода считает такие повторы отдельно
(«повторная проверка одной версии»: 13.10 — 39 групп, 42 лишних прогона,
230 минут).

## Что сохранено

Сокращение не отменяет ни одной обязательной проверки:

* `checks/run.sh` в каждой ячейке — 183 с из 190 с прогона, запускается на
  каждом изменении кода;
* проверка «репозиторий описывает именно свой сайт» и штамп манифеста;
* сборка артефакта с `digest` и его выгрузка на 30 дней;
* `scripts/verify.sh` и сверка записи доказательств в фабрике — на любом
  изменении кода, схем, инструментов и самих рабочих процессов;
* `Unit tests + APKs` приложения — на каждом PR;
* обязательные проверки безопасности и выпуска не трогались.

## Достоверность выпуска

Проверенный артефакт обязан соответствовать своему коммиту:

* артефакт ячейки несёт `release-manifest.json` с отпечатком рантайма, и шаг
  манифеста падает, если штамп разошёлся с содержимым;
* отмена вытесненного прогона не оставляет «зелёного» следа: отменённый прогон
  имеет исход `cancelled`, а не `success`;
* на `main` отмена выключена, поэтому приёмка выпуска всегда доходит до конца;
* **старый успешный прогон за проверку нового кода не выдаётся**: ключ артефакта
  приложения предлагается перевести с `github.run_number` на `github.sha`
  именно затем, чтобы повторное использование было возможно ТОЛЬКО для того же
  коммита.

Главный рычаг — первый, и он не технический: он про то, когда человек или
сессия нажимает запуск. Остальные вместе дают около 127 мин/сутки из 2 072.
Поэтому ожидаемое состояние я называю вилкой: **от 1 945 мин/сутки** (если
изменится только то, что внедрено файлами) **до ≈950** (если тяжёлая матрица
пойдёт раз в сутки на готовый набор изменений).

### Главный вывод: дело не в потерях, а в стоимости самой проверки

После двух снятых оценок (вытеснение и провалы) напрасного расхода в окне
остаётся немного — около **127 мин/сутки из 2 072, то есть 6 %**. Остальное
было связано с конкретной работой: воспроизведением дефектов, правкой тестов,
приёмкой изменений. Сокращать там нечего без потери смысла.

Значит задача не «устранить потери», а **уложить стоимость проверки в
бюджет**, и арифметика здесь решает за нас. Один полный прогон матрицы стоит
≈130 минут. Тогда месячный бюджет поддерживает:

| бюджет, мин/месяц | полных прогонов матрицы в месяц | в сутки |
| ---: | ---: | ---: |
| 2 000 | **15** | 0,5 |
| 3 000 | 23 | 0,8 |
| 10 000 | 76 | 2,5 |
| 50 000 | 384 | 12,8 |

При ночном режиме (16 прогонов в сутки) бюджет в 2 000 минут кончается меньше
чем за сутки — что и произошло в 00:20Z 12 октября. Это не следствие
небрежности: это следствие того, что эмуляторная матрица в таком темпе дороже
любого разумного месячного тарифа.

Отсюда три следствия, и ни одно из них не «поднять бюджет»:

* **матрица целиком — не инструмент повседневной проверки.** Для хода работы
  нужен один прибор дешевле: `Unit tests + APKs` стоит 4–5 минут, то есть на
  месячные 2 000 минут их приходится около четырёхсот;
* **воспроизведение дефекта — одним сценарием, а не матрицей.** Матрица из
  трёх устройств плюс 4K плюс soak стоит ≈130 минут; один сценарий `phone` —
  около 23. Разница в пять с половиной раз при том же ответе о конкретном
  дефекте;
* **полная матрица — перед выпуском и по плановому расписанию не чаще раза в
  сутки**, как и записано в порядке запуска выше.

### Что уже измерено

Правила приложения внедрены на рабочей ветви (`app/cycle-4`, решение D-022
репозитория приложения) и отличаются от моего предложения в двух местах —
обоснованно:

* `pull_request` **убран**, вместо него `push` на `main` и `app/**` с
  `paths-ignore`. Причина сильнее моей: GitHub сопоставляет фильтр путей
  `pull_request` со **всем диффом PR**, поэтому пуш одной документации в ветвь,
  где диффом тронут код, всё равно пересобирал APK. Пуш сопоставляется со
  своими коммитами;
* группа параллельности — `ci-${{ github.event_name }}-${{ github.ref }}`, то
  есть **по событию и ветви**. Пуш не отменяет ручную приёмку: иначе коммит в
  документацию обрывал бы матрицу на два часа. Моё предложение (одна группа на
  ветвь) здесь было хуже, и измерение это подтверждает — 40 вытеснений из 42
  шли без изменения кода.

Проверка порядка запуска на этом файле даёт **ноль нарушений** по всем пяти
