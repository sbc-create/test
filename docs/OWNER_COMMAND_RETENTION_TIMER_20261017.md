# Один блок: расписание удержания суточных копий публикации

Запись от 2026-10-17, 09:25 UTC. Вчера владелец разрешил ротацию копий
публикации с правилом «семь последних суток и не меньше двух исправных пар у
каждой витрины». Правило применено дважды руками; расписания у него нет, и
поэтому оно уже один раз успело нарушиться.

## Почему это нужно: измерено сегодня

| что | значение |
| --- | --- |
| наборов в каталоге утром 17.10 | **восемь** (10–17.10) при сроке хранения семь |
| причина | сегодняшний набор `daily-20261017` лёг, а самый старый никто не снял: ротация была разовым прогоном |
| свободно до повторного прогона | 13,04 ГиБ (сутками ранее было 18,90) |
| снято повторным прогоном только что | **2,26 ГиБ**, 52 файла набора `20261010` |
| свободно стало | **15,30 ГиБ** |
| прирост копий | ≈1,2 ГиБ в сутки — то есть без расписания запас снова съедается за считанные дни |

Условия владельца перед удалением проверены тем же инструментом: 13 витрин, у
каждой осталось не меньше двух полных пар `catalog` + `details`, свежая пара
каждой сверена sha256 с отчётом прогона.

**Поправка к постановке, чтобы не искали не тот инструмент.** Файл
`automation/host/backup-retention.sh` существует, но он про ДРУГОЕ: удержание
архивов узла (`host-<stamp>.tar.gz` + `.verified.json`). Копии публикации
(`publish-backups`) удерживает `automation/local/backup-retention.py` — он
написан вчера и таймера действительно не имеет. Путать их нельзя: у них разные
каталоги и разные правила.

## Поправка к первой редакции этого блока: таймер нельзя вешать на ветковое дерево

Первая редакция указывала
`ExecStart=/usr/bin/python3 /home/claude/wt-nova-publish-memory-02/automation/local/backup-retention.py`,
то есть **постоянный системный таймер с `--apply` зависел бы от моего
веткового рабочего дерева**. Это ошибка, и её нашла линия SEO; проверено:
инструмент существует ровно в одном месте — `wt-nova-publish-memory-02`
(14 181 Б, sha256
`7d11d9330da3807dfac8060476c3efaea7eabca13fc9e8d045b020afa710f87d`), в
чекауте служб `wt-portable-site-cell-01` его нет.

Почему это хуже обычного несущего пути: задание **удаляющее**. Уберут ветковое
дерево — таймер начнёт молча отказывать, и раздел заполнится снова, то есть
случится ровно та авария, против которой таймер и ставится. А переключение
ветки в том же дереве подменило бы исполняемый сценарий без чьего-либо
решения.

Поэтому инструмент сначала переносится туда, где живут службы и данные, и
только потом на него указывает расписание. Выбран
**`/srv/site-factory/repo`** — полный чекаут того же репозитория фабрики, вне
рабочих деревьев агентов, принадлежит учётной записи `claude`, и именно в его
`var/lords/publish-backups` публикатор пишет копии. Инструмент к месту запуска
не привязан: зависимостей из репозитория у него нет (только стандартная
библиотека), а каталоги копий и отчётов заданы абсолютными путями.

Альтернатива — копия в `/usr/local/sbin` — названа и отклонена: она выпадает
из-под контроля версий, и расхождение с репозиторием никто не заметит.

## Блок команд

Сервер `claude-control-01`. Шаги 1–2 — от учётной записи `claude`
(владелец чекаута), остальные — от root. Таймер ставится один, служба работает от
учётной записи `claude` (владелец файлов копий — она же).

```bash
# 1. Перенос инструмента в чекаут служб (от claude). Берётся из моей ветки,
#    поэтому версия остаётся под контролем версий, а не копией «как есть».
cd /srv/site-factory/repo
git fetch origin claude/nova-publish-memory-02
git checkout FETCH_HEAD -- automation/local/backup-retention.py

# 2. Закоммитить в ветку ЭТОГО чекаута — без этого шага файл остаётся
#    незакоммиченным изменением, принесённым из чужой ветки, и любая уборка
#    рабочего дерева (`git restore .`, `git checkout .`) снесёт его, а таймер
#    с --apply начнёт молча отказывать. Ветка чекаута — та, на которой он
#    стоит: claude/players-only-production-009 (проверено по .git/HEAD).
git add automation/local/backup-retention.py
git commit -m "удержание копий публикации: инструмент в чекауте служб"

# Проверка: чисто ли дерево по этому файлу. Ожидается пустой вывод
git status --porcelain automation/local/backup-retention.py

# Проверка: тот самый файл, а не похожий. Ожидается
# 7d11d9330da3807dfac8060476c3efaea7eabca13fc9e8d045b020afa710f87d
sha256sum /srv/site-factory/repo/automation/local/backup-retention.py

# Проверка: план на нынешнем состоянии. Ожидается «удалять нечего»
python3 /srv/site-factory/repo/automation/local/backup-retention.py --keep-days 7
```

```bash
cat > /etc/systemd/system/publish-backups-retention.service <<'UNIT'
# Удержание суточных копий публикации: семь последних суток прогонов и не
# меньше двух полных пар (каталог + подробности) у каждой витрины. Условия
# проверяются ДО удаления самим инструментом: при нарушении он выходит кодом 2
# и ничего не удаляет.
[Unit]
Description=Удержание копий публикации: семь суток
Documentation=file:///srv/site-factory/repo/docs/OWNER_DISK_P0_20261015.md

[Service]
Type=oneshot
User=claude
Group=claude
WorkingDirectory=/srv/site-factory/repo
ExecStart=/usr/bin/python3 /srv/site-factory/repo/automation/local/backup-retention.py --keep-days 7 --apply
UNIT

cat > /etc/systemd/system/publish-backups-retention.timer <<'UNIT'
# Через час после суточного прогона публикатора (03:30 UTC): к этому времени
# новый набор уже лёг, и снимается ровно самый старый.
[Unit]
Description=Удержание копий публикации: ежедневно

[Timer]
OnCalendar=*-*-* 04:40:00 UTC
Persistent=true
RandomizedDelaySec=120
AccuracySec=1min
Unit=publish-backups-retention.service

[Install]
WantedBy=timers.target
UNIT

systemctl daemon-reload
systemctl enable --now publish-backups-retention.timer

# Проверка 1: таймер назначен. Ожидается непустой NEXT на 04:40 UTC
systemctl list-timers publish-backups-retention.timer --all

# Проверка 2: прогон на сегодняшнем состоянии ничего не удаляет (наборов ровно
# семь после моего прогона). Ожидается «удалять нечего»
systemctl start publish-backups-retention.service
journalctl -u publish-backups-retention.service -n 20 --no-pager
```

Откат: `systemctl disable --now publish-backups-retention.timer` и удаление
двух файлов юнитов. Данные при откате не затрагиваются.

## Чего в блоке намеренно нет

* **принудительной очистки сверх правила.** Инструмент удаляет только наборы
  старше седьмого и только в названном каталоге; при нарушении условий по
  парам или при негодной свежей копии он отказывается удалять вообще;
* **кеша сборки и образов.** Это отдельный рычаг и отдельное решение: сейчас
  кеш сборки 8,59 ГБ (вырос с 5,55 после двух сборок), образы 30,75 ГБ. По
  образам действует разбор по ролям из `docs/OWNER_DISK_P0_20261015.md`;
* **изменения срока хранения.** Семь суток — ваше решение от 16.10; менять его
  я не предлагаю, только исполняю по расписанию.

## Поправка 09:30: без коммита перенос неполон

Первая редакция переноса ограничивалась `git checkout <моя ветка> -- <файл>`.
Этого мало, и замечание линии SEO верно: так файл попадает в рабочее дерево
чекаута, **не становясь частью ветки, которую этот чекаут отслеживает**. Два
следствия, и оба мы уже видели сегодня в других формах:

* любая уборка рабочего дерева (`git restore .`, `git checkout .`) снесёт
  файл, и таймер с `--apply` начнёт молча отказывать — тот же молчаливый отказ,
  только не от удаления дерева, а от обычной уборки внутри него;
* «версия под контролем версий» было бы выполнено наполовину: файл есть в
  какой-то ветке, но не в той, на которой стоит чекаут, и `git status`
  показывал бы расхождение неопределённо долго.

Поэтому в блок добавлен шаг 2 — коммит в ветку чекаута
(`claude/players-only-production-009`, проверено по `.git/HEAD`; последний
коммит там `4918360` от 15.09, то есть дерево месяц стабильно) и проверка
`git status --porcelain` по этому файлу с ожиданием пустого вывода.

После коммита запись в `config/load-bearing-paths.json` стоит пересмотреть:
путь перестанет быть несущим в нынешнем смысле — инструмент будет жить в
версионированном состоянии чекаута служб, а не в единственной копии внутри
веткового дерева. Снимать запись заранее, до переноса, нельзя.
