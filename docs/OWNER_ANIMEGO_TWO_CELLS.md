# Две ячейки AnimeGo: карта сайта готова, нужна одна команда владельца

`an1mego.site` (animego-02) и `animeg0.site` (animego-03). Правка карты сайта
сделана, проверки репозитория зелёные, препятствия, не связанные с правами,
устранены. Осталось одно действие под root — и оно описано здесь целиком, вместе
с тем, что команда поставит, что проверит и как вернёт прежнюю версию при отказе.

## 1. Штатный путь обновления этих ячеек — их собственный установщик

Миграции не требуется, и делать её ради карты сайта не нужно. У каждой ячейки
есть свой установщик `deploy/install.sh`, и он и есть штатный путь: именно он
раскладывал код в `app/` до сих пор (выложенное дерево совпадает с HEAD
репозитория байт в байт — сверено sha256 файла рантайма).

Обе ячейки живут по схеме «служба исполняет дерево `app/`». Схему **не меняем**:
перевод на `releases/` + `current` — отдельная операция с отдельной приёмкой, и
к карте сайта она отношения не имеет.

### Команда

```bash
sudo bash /home/claude/wt-portable-site-cell-01/var/site-repos/an1mego-site/deploy/install.sh
sudo bash /home/claude/wt-portable-site-cell-01/var/site-repos/animeg0-site/deploy/install.sh
```

Две команды, по одной на ячейку. Каждая меняет только свой сайт: ни DNS, ни
соседние сайты, ни publisher ID других домен она не трогает.

### Что именно поставит

| | an1mego.site | animeg0.site |
| --- | --- | --- |
| site_id | animego-02 | animego-03 |
| ветка и коммит | `claude/an1mego-panels-01` → `1790fb77fac7` | `claude/animeg0-launch` → `7e3253ccd82f` |
| CI на этом коммите | **зелёный** (прогон 19:44:36Z) | **зелёный** (прогон 19:44:37Z) |
| build_id ПОСЛЕ установки | `animego-02-2bad793aafb4` | `animego-03-017d8f6aea20` |
| build_id сейчас на сайте | `animego-02-dce8f5236b93` | `animego-03-f28f1e38a77a` |
| порт витрины | 9150 | 9151 |
| служба | `nova-an1mego-site.service` | `nova-animeg0-site.service` |

Содержимое правки: карта сайта (сборщик в общем `seo_layer`, разделы `/catalog/
/schedule/ /top/`, `LORDS_SITEMAP_DIR` из каталога данных, ссылка `Sitemap:` в
`robots.txt` при готовой карте, fail-closed маршрут) плюс `checks/sitemap_wired.py`
в прогоне проекта.

### Чего команда НЕ тронет

* **каталог данных** `/srv/<аккаунт>/data` — установщик пишет только в `app/`;
  снимки каталога, `site-data`, редакционные материалы и журналы остаются как
  есть;
* **настройку плеера.** `config/player.json` живёт вне git. Установщик сначала
  забирает действующий файл из `app/config/player.json`, если в репозитории его
  нет, и затем исключает его из `rsync --delete`. Publisher ID обеих ячеек —
  10252, он объявлен в их пакетах и ниоткуда не заимствуется;
* **режим индексации.** Состояние живёт в `/srv/sites/indexing/<домен>.json`,
  вне выпуска;
* **соседние сайты и DNS.**

### Что проверит сама команда

1. `checks/manifest_and_entrypoint.py`, `checks/no_secrets.py`,
   `checks/ascii_shell_identifiers.py` — до любой записи;
2. `run.py --check --data-dir /srv/<аккаунт>/data` — полнота конфигурации,
   наличие и совпадение publisher ID, наличие снимка каталога. Ошибка здесь
   останавливает установку ДО первой записи;
3. после раскладки и `systemctl restart` — что **порт отдаёт тот самый build_id**,
   который объявляет репозиторий. Это ловит случай «код разложен, а процесс
   остался прежним»: именно поэтому в установщике `restart`, а не `enable --now`;
4. `/healthz` отвечает в течение 40 секунд.

### Как вернёт прежнюю версию при отказе

Откат добавлен в установщик этой задачей; раньше его не было, и отказ проверки
оставлял сайт на новом коде.

* **до первой записи** в `app/` создаётся снимок прежнего кода в
  `/srv/<аккаунт>/app.prev` (`cp -a`, один снимок, данные не копируются);
* если **build_id не совпал** или **`/healthz` не ответил** — установщик
  вызывает `restore_previous`: возвращает код из `app.prev` (`rsync --delete`, с
  исключением `config/player.json`), возвращает владельца файлов, перезапускает
  службу и ждёт `/healthz` до 40 секунд. Исход печатается словами: «откат
  выполнен» либо «ОТКАТ НЕ ПОДТВЕРЖДЁН» с последними 30 строками журнала службы;
* если снимка нет (первая установка на пустой `app/`) — установщик говорит это
  прямо и код не трогает повторно, чтобы не ухудшить состояние наугад.

Ручной откат, если он понадобится отдельно:

```bash
sudo rsync -a --delete --exclude config/player.json \
    /srv/an1mego-site/app.prev/ /srv/an1mego-site/app/
sudo chown -R an1mego-site:an1mego-site /srv/an1mego-site/app
sudo systemctl restart nova-an1mego-site.service
```

## 2. Что было препятствием и что с ним стало

| препятствие | причина | состояние |
| --- | --- | --- |
| `checks/boundaries.py` красная | отпечаток `класс ВидАнимедиа` отставал от кода на ОДНУ строку: зашитый `<meta name="robots" content="noindex, nofollow">` заменён вычисленным `{мета_роботов()}` коммитом про режим индексации | **исправлено**: изменение проверено построчно, отпечаток переставлен, причина записана в сам замок. Остальные семь областей не трогались — они и так совпадали |
| `checks/verify_pins.py` красная | `src/indexing_mode.py` отсутствовал в замке, потому что `tools/update_pins.py` этих двух ячеек разошёлся с соседней: блок записи этого модуля был только у an1meg0-site | **исправлено**: блок перенесён, замок пересобран инструментом. Файл сверен с шаблоном фабрики — байт в байт (`29d67d135c3e` у всех трёх ячеек) |
| CI отсутствует | проверки отказывали там, где проверять нечего. Причин три, и все про входы, которых на раннере нет: пять проверок песочницы требовали каталог данных площадки; `delivery_guard` падал `FileNotFoundError` на `tempfile(dir=var)`, потому что `var/` в git не хранится; `data_chain` печатал `FAIL контракт поставщика прочитан` и всё равно возвращал 0 — отказ был громким и ни на что не влиял | **исправлено**: пропуск при отсутствии снимков перенесён из соседней ячейки в `content_update`, `data_chain`, `sections_update`, `community_storage`, `moderation`; `var/` создаётся; отсутствие контракта объявляется пропуском, а не отказом. Пропуск объявляется вслух и пройденной проверкой не считается. Заведён `.github/workflows/release.yml`. **Проверено настоящими прогонами CI: оба зелёные** (37519638878 был красным до починки, прогон после починки — success на обеих ячейках) |
| права на `app/` | каталог принадлежит `<аккаунт>:<аккаунт>`, установка требует root (useradd, systemctl, `/etc/nginx`) | **остаётся**: это и есть команда владельца выше |
| `config/player.json` нечитаем фабрикой | `root:root 0600` — так и должно быть | **остаётся**: из-за этого живой ярус `checks/sitemap_wired.py` и проверки песочницы у меня пропускаются с названной причиной; под root они работают |

## 3. Приёмка после установки

Выполняется с этой стороны, root не нужен:

```bash
python3 automation/local/sitemap-acceptance.py an1mego.site animeg0.site
python3 automation/local/public-acceptance.py an1mego.site animeg0.site
python3 automation/local/player-idle-check.py https://an1mego.site/title/<слаг>/ 60
```

Ожидается: `/sitemap.xml` 200 и индекс карт, части 200 правильным `urlset`,
адресов больше одного, дублей 0, чужих домен 0, служебных путей 0, `robots.txt`
называет карту, `canonical` выбранных адресов совпадает с `loc`, публичный
`x-site-factory-build-id` совпадает с установленным build_id, главная и карточки
200, плеер без нажатия не пересоздаётся.

Сверка «карта описывает ТЕКУЩИЙ каталог» — числом адресов в публичной карте
против записей снимка каталога ячейки плюс объявленные разделы плюс главная:

```bash
python3 automation/local/sitemap-acceptance.py an1mego.site | grep "адресов"
python3 -c "import json;print(len(json.load(open('/srv/an1mego-site/data/animego-02-catalog.json'))['items']))"
```

Ожидается: адресов в карте = записей снимка + 3 раздела (`/catalog/`,
`/schedule/`, `/top/`) + главная. Для шести уже принятых домен сверка сошлась до
единицы; здесь ожидается то же.

## 5. Чего я НЕ делал

* **не переводил ячейки на схему `releases/current`.** Зелёный CI сам по себе
  этого пути и не открывает — проверено сухим прогоном очереди уже ПОСЛЕ того,
  как прогоны стали зелёными:

      $ python3 -m factory cell trigger --site animego-02
      BLOCKED_INPUT: sbc-create/site-an1mego-site: успешного прогона на
      разрешённой ветке нет. Разрешены ['main', 'claude/extract-*', 'release/*']

  Зелёный прогон лежит на ветке `claude/an1mego-panels-01`, и исполнитель её не
  принимает. То есть для перехода на очередь понадобился бы ещё и перевод
  релизной ветки — отдельное решение, а первая активация через очередь это и есть
  смена схемы выкладки на живом домене, а не обновление карты сайта;
* не отключал ни одной проверки и не ослаблял ни одного требования: все правки
  различают «нечего проверять» и «проверка не прошла», и пропуск объявляется
  вслух;
* не переписывал контрольные суммы без разбора: отпечаток `класс ВидАнимедиа`
  переставлен после построчного сравнения, замок `pins.lock.json` пересобран
  инструментом ячейки после переноса пропущенного блока;
* не трогал DNS, publisher ID других домен, каталоги данных и настройку плеера;
* не выкладывал повторно шесть принятых домен.
