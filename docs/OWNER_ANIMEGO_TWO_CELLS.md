# Две ячейки AnimeGo: карта сайта готова в репозитории, выкладка — за владельцем

`an1mego.site` (animego-02) и `animeg0.site` (animego-03). Правка карты сайта в
их репозиториях сделана, проверена и отправлена в ветку. Выложить её штатной
операцией фабрики **нельзя**, и причина измерена, а не предположена.

## Почему штатная операция отказывает

```
$ python3 -m factory cell trigger --site animego-02
BLOCKED_INPUT: sbc-create/site-an1mego-site: успешного прогона на разрешённой
ветке нет. Разрешены ['main', 'claude/extract-*', 'release/*']
```

Причина не в ветке, а в том, что прогона **не существует вовсе**:

| | an1mego.site | animeg0.site | для сравнения: an1meg0.site |
| --- | --- | --- | --- |
| `.github/workflows/` в репозитории | **нет** | **нет** | `release.yml` |
| прогонов CI за всё время | 0 | 0 | есть |
| выкладок через очередь | 0 | 0 | 2 (4 октября) |
| каталог выпусков `/srv/<аккаунт>/releases` | **нет** | **нет** | есть |
| что исполняет служба | `/srv/<аккаунт>/app/run.py` | то же | `current/run.py` |

То есть эти две ячейки живут по прежней схеме: служба исполняет **дерево
`app/`**, а не выпуск по символической ссылке. Выложенное дерево совпадает с
HEAD репозитория байт в байт (проверено sha256 файла рантайма), значит обновляют
его копированием, а не очередью.

Первая выкладка через очередь была бы не «обновлением карты», а **переводом
ячейки на схему выпусков** (`prepare → install_release → warm_up → switch_route
→ promote`) на живом домене. Это отдельная операция с отдельной приёмкой, и
решение о ней принимает владелец, а не задача про карту сайта.

## Что сделано и готово

| | an1mego.site | animeg0.site |
| --- | --- | --- |
| ветка | `claude/an1mego-panels-01` | `claude/animeg0-launch` |
| коммит с картой | отправлен в origin | отправлен в origin |
| разделы в карте | `/` `/catalog/` `/schedule/` `/top/` | те же |
| `checks/sitemap_wired.py` | пройдена (ярусы 1 и 3) | пройдена (ярусы 1 и 3) |

## Что требуется от владельца — ровно одно из двух

**Вариант А (как обновляли до сих пор).** Скопировать дерево репозитория в
`app/` от имени пользователя ячейки и перезапустить службу. Каталог
`/srv/<аккаунт>/app` принадлежит `<аккаунт>:<аккаунт>` с правами `0775`, доступа
к нему у фабрики нет:

```bash
sudo -u an1mego-site rsync -a --delete \
    --exclude .git --exclude __pycache__ \
    /home/claude/wt-portable-site-cell-01/var/site-repos/an1mego-site/ \
    /srv/an1mego-site/app/
sudo systemctl restart nova-an1mego-site.service
```

и то же для `animeg0-site` со службой `nova-animeg0-site.service` и портом 9151.

**Вариант Б (перевести ячейки на выпуски).** Завести `release.yml` в обоих
репозиториях и провести первую активацию через очередь. Это отдельная работа:
появляются `releases/`, `current`, прогрев кандидата и откат. Её объём и порядок
стоит решать отдельно от карты сайта.

## Проверка после выкладки

```bash
python3 automation/local/sitemap-acceptance.py an1mego.site animeg0.site
```

Ожидается: `/sitemap.xml` 200, индекс карт, адресов больше одного, дублей 0,
чужих домен 0, `robots.txt` называет карту, `canonical` выбранных адресов
совпадает с `loc`.

## Отдельная находка, НЕ связанная с картой

`checks/boundaries.py` в обоих репозиториях красная, и причина чужая:

```
— класс ВидАнимедиа: ИЗМЕНЕНА. Это чужой код: правка либо ошиблась адресом,
  либо должна приехать отдельным коммитом ядра
```

Проверено отпечатками самой проверки: класс `ВидАнимедиа` разошёлся с замком
**до** правки карты (на HEAD отпечаток `486ce7549129`, в замке `63ec2e1cb8e0`), а
правка карты его не касается — отпечатки до и после совпадают. Класс `ВидОснова`
с замком сходится.

Замок этих двух репозиториев я переставил ТОЛЬКО по строке `модуль
seo_layer.py` — это общий модуль семейства, который обновила эта задача.
Отпечаток `класс ВидАнимедиа` не трогал: `--принять` переписал бы его заодно и
объявил бы чужое изменение просмотренным мной. Разбираться с ним должен тот, кто
его внёс, — отдельным коммитом ядра.
