# Права и способ доступа: AniList, Kitsu, Simkl

Запись о том, как именно мы получаем оценки каждого источника и на каком
основании. Составлена по результатам read-only проверки 2026-09-21
(Этап A), evidence —
`artifacts/evidence/unified-ratings-01/01-discovery/STAGE_A_DISCOVERY.json`.

Приоритет доступа, заданный владельцем: официальный API → уже
разрешённый коннектор проекта → публичный документированный источник →
разбор публичной страницы. Понижать приоритет самостоятельно нельзя.

## AniList — READY

* **Способ**: официальный публичный GraphQL, `POST https://graphql.anilist.co`.
* **Ключ**: не требуется.
* **Лимит источника**: сервер объявляет его сам заголовком
  `X-RateLimit-Limit: 30` (наблюдено 2026-09-21). Наш cap — 20 запросов в
  минуту и 0.4 rps, то есть строго ниже объявленного.
* **Что берём**: `Media.averageScore` (шкала 0–100), число оценивших —
  сумма `Media.stats.scoreDistribution[].amount`, `Media.idMal` для
  сопоставления, `siteUrl` для provenance.
* **Что не берём как оценку**: `popularity`, `favourites`, `rankings`,
  `trending`. Это счётчики пользователей и мест в списке; у популярного
  тайтла они в разы больше числа оценок.
* **Ограничения**: запросы только на чтение; авторизация не используется;
  обход лимита не выполняется — 429 гасит источник до разрешённого времени.

## Kitsu — READY (резервный источник)

* **Способ**: официальный публичный JSON:API, `https://kitsu.io/api/edge`.
* **Ключ**: не требуется.
* **Лимит источника**: в ответах не объявлен. Поэтому cap выбран заведомо
  низким — 20 запросов в минуту: неизвестный лимит это повод идти
  медленнее, а не быстрее.
* **Что берём**: `attributes.averageRating` (шкала 0–100, приходит
  строкой), число оценивших — сумма `attributes.ratingFrequencies`,
  `attributes.userCount` отдельным полем, сопоставление — через
  `GET /mappings?filter[externalSite]=myanimelist/anime`.
* **Важное различие**: `userCount` — число пользователей, у которых тайтл
  в библиотеке. Оно заметно больше числа оценивших (для `anime/1` —
  162 344 против 25 близких к сумме частот) и числом голосов не является.
  Источник различает эти величины, и мы храним обе раздельно.
* **Ключи `ratingFrequencies`**: 2..20. Это оценка 1–10 с шагом 0.5,
  умноженная на два.

## Simkl — BLOCKED_SECRET

* **Способ**: официальный API, требует `client_id` зарегистрированного
  приложения.
* **Состояние**: ключа нет ни в secret storage, ни в `inventory/`.
  Read-only проверка без ключа вернула
  `HTTP 412 {"error":"client_id_failed"}`.
* **Что сделано**: адаптер написан целиком и отказывает **до** сетевого
  запроса. Без ключа обращение к источнику — это либо мусорный трафик,
  либо попытка выглядеть зарегистрированным клиентом, и со стороны Simkl
  одно неотличимо от другого.
* **Чего не сделано и не будет**: подстановка чужого или выдуманного
  `client_id`, разбор публичных страниц Simkl вместо API, использование
  платного тарифа без отдельного бюджета.
* **Контракт шкалы**: помечен `verified=False`. Ожидается 0–10, но пока
  живой ответ не получен, это память, а не проверенный факт, и
  нормализация возвращает `CONTRACT_UNVERIFIED` вместо числа.
* **Разблокировка**: одно внешнее действие — выдать `secret_ref`
  `simkl_client_id`. После этого нужен повторный Этап A, чтобы подтвердить
  контракт шкалы живым ответом, и только затем пилот.

## Shikimori — READY через существующий коннектор

Разрешение владельца от 2026-09-19, `docs/rights/shikimori-ratings.md`,
`config/rating-sources.yaml → shikimori.authorization.status: granted`.

Новый адаптер не создавался: разрешение выдано на существующий
проверенный коннектор `factory/ratings/adapters/shikimori.py`, прошедший
Stage 1–5 на живых данных. Второй клиент к тому же API означал бы второй,
непроверенный способ доступа и удвоенную нагрузку на тот же лимит.

## IMDb и Кинопоиск — FEED_ONLY

Решение владельца от 2026-09-06, `docs/rights/provider-feed-ratings.md`:
скрапинг IMDb и Кинопоиска запрещён. Значения берутся только оттуда, где
они уже есть — из договорного фида поставщика (`imdb_rating`,
`kinopoisk_rating` в каталожном снимке).

Адаптер `provider_feed` не имеет сетевого клиента вовсе, его
`max_requests_per_minute` равен нулю, и в отчёте он показывает
`network_calls_made: 0`.

В provenance такого значения записано «договорный фид поставщика», а не
«IMDb». Разница существенна: мы показываем не оценку, которую сами
измерили у площадки, а число, переданное нам по договору. Если поставщик
задержит обновление, устареет именно наше значение, и это видно по
`source_updated_at`.
