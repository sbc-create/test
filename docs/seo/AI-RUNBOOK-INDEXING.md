# Runbook: состояние индексации и карта сайта

Для автономного исполнителя (Qwen). Каждый шаг — команда и то, как читать её
ответ. Раздел «Что делать запрещено» — не формальность: перечисленное там уже
приводило к закрытию живой витрины.

## 1. Где что лежит

| Вопрос | Ответ |
| --- | --- |
| перечень обслуживаемых сайтов | `config/FLEET-REGISTRY.json` — единственный реестр с доменами |
| желаемое состояние индексации | `config/site-profiles/<site_id>.json`, поле `seo_profile.indexing_enabled` |
| основание решения | там же, `seo_profile.indexing_reason` |
| кто может открыть или закрыть | **только владелец**, отдельной командой; см. §4 |
| что читает состояние | `factory/indexing/state.py` |
| что вычисляет слои | `factory/indexing/layers.py` |
| правила карты сайта | `factory/seo/sitemap_truth.py` |

`config/portfolio.json` содержит поле `indexing_expected`. Это **производное**
значение для отчётов оператора. Источником оно не является и расходиться с
профилем не имеет права.

## 2. Посмотреть желаемое состояние

```bash
python3 -c "
from pathlib import Path
from factory.indexing.state import GitProfileProvider, resolve
и = resolve(GitProfileProvider(profiles_dir=Path('config/site-profiles'), revision=1))
print(и.report())
print(и.snapshot.matrix())"
```

Ожидаемый ответ сегодня: `open_count=1`, `closed_count=8`, открыт
`yummyani.site`.

Если напечатано «Релиз заблокирован» — состояние прочитать не удалось. Это не
повод что-либо править: см. §6.

## 3. Посмотреть фактически отдаваемое состояние

Одним `GET`, не `HEAD`: посредник добавляет `X-Robots-Tag` только на `GET`, и
однажды именно `HEAD` привёл к неверному выводу о том, какой слой закрывает
витрину.

```bash
curl -fsS -D - https://yummyani.site/ -o /tmp/page.html
grep -i '^x-robots-tag' /tmp/page.html   # у открытой витрины заголовка нет
grep -o '<meta name="robots"[^>]*>' /tmp/page.html
curl -fsS https://yummyani.site/robots.txt | head -3
```

Три слоя обязаны говорить одно и то же. Расхождение — критический отказ, а не
предупреждение.

## 4. Кто может открыть или закрыть сайт

Только владелец. Изменение проходит как правка `seo_profile.indexing_enabled`
в профиле сайта вместе с `indexing_reason`, принятая через обзор изменений.

Ни выкладка, ни перезапуск, ни откат, ни CI, ни обновление шаблона, ни
генерация карты сайта желаемое состояние не меняют. Если состояние изменилось
после любой из этих операций — это авария, а не результат.

## 5. Как выкладка, перезапуск и откат сохраняют состояние

Решение живёт в версионируемом источнике, а посредник читает собранный из него
артефакт. Поэтому:

* выкладка нового артефакта пересобирает то же решение;
* перезапуск службы читает тот же источник заново;
* откат приложения возвращает код, но не решение;
* возврат файлов прежней выкладки не возвращает прежнее состояние: снимок с
  меньшей revision не переписывает подтверждённый.

Проверяется harness'ом:

```bash
python3 -m pytest tests/unit/test_indexing_persistence_harness.py -q
```

21 проверка, сценарии: новый сайт, открытый сайт, закрытый сайт, отказы.

## 6. Как диагностировать дрейф

```bash
python3 -m pytest tests/unit/test_indexing_persistence_harness.py -q   # контур
```

Живая сверка — чтением, по всем девяти доменам сразу: сравнить желаемое из §2 с
фактическим из §3. Три исхода, и все три обязаны быть названы: совпадает,
разошлось, **не измерено**. Неизмеренное состояние не проходит как «в порядке».

Если реестр недоступен — берётся подтверждённый снимок, релиз блокируется,
живое состояние не трогается. Пустая матрица никогда не публикуется: «закрыть
всё» — это тоже изменение.

## 7. Как работает дата изменения в карте сайта

`lastmod` берётся только из реального создания или значимого изменения
содержания конкретной страницы. Запрещены: время сборки, время выкладки,
текущее время и общая константа на весь шард.

Неизвестную дату **пропускают**, а не подставляют. Одинаковые даты допустимы —
но только когда за ними стоит одно и то же подтверждённое событие.

Текущее состояние и найденные дефекты — `docs/seo/SITEMAP-TRUTH-AUDIT.md`.

## 8. Как строится `images.xml`

Знаменатель покрытия — все опубликованные индексируемые карточки, а не только
те, у которых изображение нашлось. Иначе доля равна 100 % при любом числе
потерь.

Карточка без исходного изображения остаётся в `titles.xml` без элемента
изображения, и причина исключения **записывается**. Дописывать запись ради
ровной цифры запрещено: выдуманное изображение хуже отсутствующего.

## 9. Что делать запрещено

* менять `seo_profile.indexing_enabled` без owner-команды;
* открывать любой из восьми закрытых доменов;
* отправлять карту сайта или адреса в поисковые системы;
* править файлы под `/srv` — это production, а не источник;
* считать `/srv/sites/yummyani-staging/repo` источником истины;
* заводить второй реестр, второй Action Ledger или ещё одно место с желаемым
  состоянием;
* заполнять пропущенный замер нулём или правдоподобной строкой — отсутствие
  замера обозначается `NOT_MEASURED`;
* выкладывать частично: если хоть один слой не вычислен, не публикуется ни один.

## 10. Когда нужен Core

Если требуется durable-состояние с revision, Action Ledger и командами
OPEN/CLOSE — это Core. См. `docs/seo/CORE-HANDOFF-PERSISTENT-INDEXING.md`.
Создавать это в SEO запрещено.

## 11. Когда нужна команда владельца

Любое изменение матрицы индексации, любое открытие домена, любая отправка в
поисковые системы, любая выкладка в production.

## 12. Как доказать, что production не изменён

```bash
git status --porcelain            # дерево чисто
git log --oneline -1              # коммит назван
```

Плюс сверка матрицы до и после работы по §3: она обязана совпасть. Формулировка
«проверено» без запуска команды — ошибка отчёта, а не стилистика.
