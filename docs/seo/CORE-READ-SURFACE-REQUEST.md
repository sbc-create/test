# Поверхность чтения состояния индексации: запрос и его закрытие

> **Закрыто.** Маршруты `GET /api/v1/indexing/state` и
> `GET /api/v1/indexing/state/{site_id}` добавлены в Core (PR #77, коммит
> `31348653`). SEO читает их клиентом `factory/indexing/core_client.py`.
> Ниже — исходный запрос: он объясняет, почему поверхность понадобилась и
> каким требованиям обязана отвечать.

SEO не может подключиться к durable-состоянию Fleet Core, потому что читать его
сейчас можно только двумя способами, и оба запрещены потребителю.

## Что есть

`FLEET-CORE-003` реализовал состояние индексации (`indexing_state`,
`indexing_revision`, `indexing_outbox`) и контракт чтения
`fleet-indexing-read/1.0.0` в модуле
`factory/site_engine/audit/indexing_contract.py`.

Контракт объявлен верно: он отдаёт `site_id`, `domain`, `desired_state`,
`revision`, `last_known_good_revision`, `updated_at`, `source_event_id`,
`approval_ref`, `reason`, `snapshot_digest`, `schema_version`, `registered`,
различает «не зарегистрирован» и «провайдер недоступен» и не имеет методов
изменения.

## Чего нет

Точки входа. `прочитать(соед)` принимает **`sqlite3.Connection`**. Чтобы им
воспользоваться, потребитель обязан либо открыть базу Core напрямую, либо
импортировать внутренние модули Core в свой процесс.

HTTP-поверхность журнала — `/api/v1/audit/**` — состояния индексации не отдаёт:

| Маршрут | Что отдаёт |
| --- | --- |
| `/api/v1/audit/health` | живость службы |
| `/api/v1/audit/integrity` | проверку цепи хэшей |
| `/api/v1/audit/checkpoints/latest` | последнюю контрольную точку |
| `/api/v1/audit/projection` | метаданные проекции **утверждений аудита** |
| `/api/v1/audit/events` | ленту событий |
| `/api/v1/audit/sites/{site_id}` | сырые события сайта |

Ни один не возвращает `desired_state`, `indexing_revision` и `state_digest`
одним атомарным ответом. Собрать состояние из ленты событий значит повторить
логику Core на стороне SEO — то есть завести второго вычислителя того же
состояния. Это ровно тот дефект, ради устранения которого всё затевалось.

## Что требуется

Один маршрут чтения поверх уже существующего контракта. Новой логики он не
требует — только выставляет наружу то, что уже посчитано:

```
GET /api/v1/indexing/state            → снимок всего флота
GET /api/v1/indexing/state/{site_id}  → состояние одного сайта
```

Требования к ответу:

1. **Атомарность.** Состояние и ревизия приходят вместе. Два запроса — два
   разных момента, и склеенный из них ответ не соответствует ни одному.
2. **Поля контракта** ровно те, что объявлены в `fleet-indexing-read/1.0.0`.
   Ни одного поля «по догадке».
3. **Отказ называется отказом.** Недоступность возвращает ошибку, а не пустой
   снимок: пустая матрица означала бы «все закрыты» и закрыла бы живую витрину.
4. **Только чтение.** `POST`, `PUT`, `PATCH`, `DELETE` на этих маршрутах
   отвечают `405`. Команды `OPEN_INDEXING` и `CLOSE_INDEXING` остаются там, где
   они есть, и требуют разрешения владельца.
5. **Права.** Службе `seo` достаточно `OBSERVE`. Выдавать ей `EXECUTE` нельзя.
6. **Неизвестный `site_id`** — ошибка, а не `CLOSED`. «Не знаем такого» и
   «решили не индексировать» — разные ответы.

## Почему SEO не сделает это сам

Три запрета, и каждый обоснован:

* **второй API** — два ответа на один вопрос начнут расходиться в первый день;
* **прямой SQLite** — потребитель, знающий схему хранения, привязан к ней
  навсегда, и Core перестаёт быть волен её менять;
* **копия состояния в SEO** — второй источник истины, то есть исходный дефект
  в новом месте.

## Что сделано до упора в это

Блокер обнаружен на входном gate, до единой строки адаптера. Второй API не
создавался, хранилище Core не копировалось, прямого доступа к SQLite в SEO нет.

Работа, не зависящая от состояния индексации, выполнена отдельно: правка
генератора карты сайта в репозитории приложения (`lastmod` и адрес с
`noindex`). Привязка генератора к envelope Core остаётся за этим запросом.
