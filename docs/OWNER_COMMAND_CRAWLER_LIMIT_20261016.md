# Один блок команд владельца: ограничить внешний обходчик по диапазонам адресов

Запись от 2026-10-16, 17:35 UTC. Решение по пункту 5
`docs/OWNER_DECISIONS_20261016.md` ещё не принято; здесь — готовое правило,
проверенное мною на деле, чтобы «да» стоило один блок, а не переписку.

## Почему это стало условием, а не пожеланием

Сегодняшний выпуск снял ошибки записи кеша отрисовки (706 и 980 за 5 минут →
0 и 0), и линия SEO это воспроизвела независимо. Скорости это НЕ дало:
`biz` 0,70–4,54 с, `org` 0,71–2,81 с при контроле `.site` 0,22–1,68 с, а
процессор `web-org` в тот же момент — 99,64 % при нуле ошибок кеша.

Причина измерена и объяснима: обходчик идёт по РАЗЛИЧНЫМ адресам (около 13
запросов в секунду по 8 329 страницам), а кеш страницы помогает только при
повторных обращениях к одному адресу. Обход различных страниц от кеша не
получает ничего — каждый запрос остаётся полной отрисовкой. Поэтому
ограничение обходчика — условие, при котором исправление кеша вообще
проявится в скорости, а не отдельный необязательный пункт.

Что ограничение даст в скорости — отдельное измерение ПОСЛЕ, и обещать его
числом я не буду.

## Ключ — адрес, и только адрес

В журнале nginx строк `HeadlessChrome` ноль: обходчик представляется обычным
`Chrome/145.0.0.0 Safari/537.36`. Фильтр по названию браузера промахнётся
полностью, и вводить его вы прямо запретили. Диапазоны (измерение линии
приложения за 10,6 часа 16.10): `47.82.*` — 297 адресов, 200 853 запроса;
`43.119.*` — 322 адреса, 224 265 запросов; вместе 425 118 из 498 486 (85,3 %).
С публичного адреса нашего узла — 801 запрос (0,16 %).

**Предел ставится на диапазон целиком, а не на адрес.** Это важно: при 297 и
322 адресах предел «на адрес» умножился бы в сотни раз и смысла не имел.

## Что проверено мною, а что проверите вы

Проверено на деле, в контейнере с nginx 1.27.5 (`yummyani-staging-proxy-1`,
отдельный процесс на 127.0.0.1:18080, живой конфигурации узла не касался):

| проверка | результат |
| --- | --- |
| синтаксис правила (`nginx -t`) | `syntax is ok`, `test is successful` |
| источник ИЗ диапазона `47.82.0.0/16` | 1-й запрос 200, далее **429, 429** |
| источник ВНЕ диапазонов (`8.8.8.8`) | 4 из 4 — **200**, предел не применяется |

Предел в проверке нарочно взят строгим (`rate=1r/m` без запаса), иначе отказ
при медленном обстреле не наступил бы. Подстановка источника сделана через
`geo $http_x_test_ip` — в предлагаемом правиле на его месте настоящий адрес
клиента.

**Чего я проверить не могу:** узел работает на nginx 1.18.0-6ubuntu14.21, а
проверка исполнена на 1.27.5. Все четыре директивы в 1.18 есть
(`limit_req_status` — с 1.3.15), но подтверждающий запуск `nginx -t` на узле —
ваш, и он стоит первым шагом блока.

**Ловушка, на которую я сама попалась** — на случай, если будете проверять
правило отдельным сервером: `return 204` в `location` исполняется в фазе
rewrite, ДО фазы, в которой работает `limit_req`. На таком сервере исправное
правило выглядит как неработающее (у меня — 80 запросов из диапазона, ни
одного 429). Проверять надо на обработчике содержимого (`empty_gif`, файл,
`proxy_pass`).

## Блок команд

Сервер: **`claude-control-01`**. От root. Правка публичного поведения
индексируемых доменов — ваша зона: линия выпуска конфигурацию nginx только
читает.

```bash
# 1. правило. Файл новый, существующие не затрагиваются
cat > /etc/nginx/conf.d/10-yummy-crawler-limit.conf <<'CONF'
# Ограничение частоты для двух диапазонов внешнего обходчика.
# Измерено 2026-10-16: 425 118 из 498 486 запросов (85,3 %) за 10,6 часа.
# Ключ — диапазон целиком: у обходчика 297 и 322 адреса, предел «на адрес»
# умножился бы в сотни раз. Пустой ключ = предел не применяется, поэтому все
# остальные посетители и поисковые роботы правилом не затронуты.
geo $yummy_bulk_range {
    default        0;
    47.82.0.0/16   1;
    43.119.0.0/16  2;
}

map $yummy_bulk_range $yummy_bulk_key {
    0  "";
    1  "range-47-82";
    2  "range-43-119";
}

limit_req_zone $yummy_bulk_key zone=yummy_bulk:10m rate=2r/s;
limit_req_status 429;
limit_req zone=yummy_bulk burst=20 nodelay;
CONF

# 2. проверка синтаксиса. ожидается: "syntax is ok" и "test is successful"
nginx -t

# 3. применение без обрыва соединений
systemctl reload nginx

# 4. ответ живых страниц не изменился? ожидается: 200 на всех трёх
curl -s -o /dev/null -w '%{http_code} ' https://yummyani.biz/ \
  https://yummyani.org/ https://yummyani.site/; echo

# 5. отказы пошли и попали ИМЕННО в обходчика? ожидается: строки
#    "limiting requests, excess:" с адресами 47.82.* и 43.119.*
tail -50 /var/log/nginx/error.log | grep "limiting requests" | tail -5
```

Откат — один шаг: `rm /etc/nginx/conf.d/10-yummy-crawler-limit.conf && nginx
-t && systemctl reload nginx`.

## Чего правило стоит в числах

Предел `2r/s` на диапазон с запасом 20 даёт около **4 запросов в секунду на
оба диапазона вместо измеренных 11** — примерно 345 тысяч запросов в сутки,
чего обходчику с избытком хватает на полный обход 8 339 страниц. Полного
отказа я не предлагаю: он чаще даёт повторные попытки, а не тишину. Если
решите жёстче — замените `rate=2r/s` на `rate=1r/s`, остальное не меняя; если
совсем закрыть — скажите, и правило будет другим (`return 429` для тех же
диапазонов), но проверять его придётся заново.

## Что измерить после применения, и чего не утверждать

1. доля `47.82.*` и `43.119.*` в журнале за сутки — должна упасть;
2. доля безголовых визитов в Метрике за ТЕ ЖЕ полные сутки с тем же фильтром;
3. время до первого байта на странице произведения, несколько проходов, и
   ошибки записи кеша (сейчас 0 на `biz` и `org`);
4. **чего не утверждать:** что страницы станут быстрее — это надо измерить, а
   не предположить. Ограничение снимает причину загрузки процессора; станет ли
   время приемлемым, покажет пункт 3.
