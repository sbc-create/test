## Согласие владельца из чата: готово к установке

Механизм собран и отрепетирован целиком, кроме двух действий root.

Как это работает: инструмент моста `register_owner_consent` согласие **не
создаёт**. Он передаёт привилегированной стороне привязку
`sha256(код|домен|действие)`; та сверяет **одноразовый код владельца**, гасит
его и вызывает ту же команду `authorize-indexing.sh`. Без кода согласие не
регистрируется — иначе инструмент был бы правом модели выдать разрешение себе.

Честная граница названа: код, вписанный владельцем в чат, модель видит — он
пришёл ей аргументом. Поэтому код одноразовый и срочный, а захваченное
значение мертво сразу после операции. На диск, доступный `claude`, код не
попадает ни разу: в заявке лежит привязка, а она не годится ни для другого
домена, ни для отзыва вместо выдачи.

### Одна команда администратора

```bash
sudo bash /home/claude/wt-portable-site-cell-01/automation/host/install-cell-executor.sh \
  && sudo bash /home/claude/wt-portable-site-cell-01/automation/host/install-owner-consent-codes.sh --count 10 --days 30
```

Первая половина доставляет исполнителю операцию `owner-consent` (установленная
копия её ещё не знает), вторая выдаёт коды и печатает их **один раз**.

После этого приёмка выполняется из чата на изолированной ячейке:

```json
register_owner_consent {"site": "site-a.localhost", "action": "grant",  "code": "oc-…"}
domain_indexing_readiness {"site": "site-a.localhost"}
register_owner_consent {"site": "site-a.localhost", "action": "revoke", "code": "oc-…"}
```

Что уже доказано без root (`pytest tests/unit/test_owner_consent_from_chat.py`,
13 проверок): выдача создаёт якорь, диагностика фабрики его видит
(`owner_consent.проверить` → true), повтор тем же кодом отвергается словом
«одноразовые», отзыв убирает якорь и `проверить` снова false, сухой прогон код
не расходует, а без команды владельца операция отказывает названной причиной.
