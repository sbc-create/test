# Договор публичного отпечатка

Что именно обязана доказывать проверка `served_fingerprint` при выкате и откате
витрины парка nova, и почему прежняя формулировка доказывала не то.

## Устройство, из которого всё следует

Исполняемый файл в парке **один**: `/srv/lords/.frontend/lords-frontend.py`.
Его запускают юниты всех витрин — Lords, Zona и остальных. Версию оформления
выбирает **манифест витрины**, свой у каждой:
`template-manifest.json` у `lords-01`, `template-manifest-zona-01.json` у
`zona-01`. Рантайм читает манифест при старте и от значения `design_version`
зависит ветка отрисовки.

Отсюда два разных утверждения, которые легко перепутать и нельзя сравнивать
друг с другом:

| величина | что это | где берётся |
| --- | --- | --- |
| отпечаток файла | sha256 физического файла на диске | `point.json.artifact_sha256`, `executable_sha256` |
| объявленный релиз | что витрина говорит о себе | заголовки `X-Site-Factory-*`, они же поля манифеста |

Совпадают они только пока все витрины парка на одной сборке. Как только одна
уехала вперёд, общий файл принадлежит её сборке, а соседняя витрина законно
объявляет свой прежний релиз. **Это исправное состояние, а не расхождение.**

## Что было сломано

`served_fingerprint_match` сравнивал заголовок `X-Site-Factory-Artifact-Sha256`
с `point.json.artifact_sha256`, то есть объявленный релиз с отпечатком файла.
При учебном откате `zona-01` 2026-09-14 это дало `ROLLBACK_FAILED` на полностью
удавшемся откате: домен отдавал `1.0.2`, все ответы `200`, а снимки
`zonafilm.space` до установки и после отката совпали побайтно по телу,
встроенным CSS и JS на всех трёх адресах.

Та же ошибка стояла третьим условием в `prove_serving_chain.py` и роняла сухой
прогон Zona в `MISMATCH`.

## Что обязан доказывать публичный отпечаток

1. Публичный домен обслуживается **правильным релизом**: объявленная личность
   совпадает с манифестом, который читает найденный юнит, — по всем полям
   (`template_family`, `design_version`, `build_id`, `source_commit`,
   `artifact_sha256`), а не по одному.
2. Запрос попал в **правильный upstream**: домен → nginx → порт → юнит → файл →
   манифест → ответ, круг замкнут и юнит активен.
3. После отката публично отдаётся `1.0.2`; после возврата вперёд — `1.1.0`.
4. **Измеренные** отпечатки тела, встроенного CSS и встроенного JS совпадают со
   снимком, снятым с домена до установки. Это не самоотчёт рантайма: манифестом
   такое совпадение не подделать.

Первые три утверждения строятся на том, что витрина о себе **объявляет**.
Четвёртое — на том, что она **отдала**. Оба обязательны: заголовок без
измерения доказывает лишь, какой манифест подхватила служба; измерение без
заголовка не различает две сборки, отрисовавшие одинаковую страницу.

## Нормализация: единственное исключение

| поле | откуда берётся | почему не характеризует релиз | чем закрыто |
| --- | --- | --- | --- |
| переводы строк (`\r\n` → `\n`) | переписывание в канале между рантаймом и клиентом | релиз не задаёт способ кодирования переноса; содержимое при этом то же | `test_перевод_строки_crlf` — совпадение засчитывается; `test_нормализация_переносов_не_прячет_подмену` — подмена одного байта разметки под той же нормализацией остаётся провалом |

Других исключений нет, и они не нужны: динамических полей в разметке рантайма
нет (проверено поиском по источнику), а снимки `zonafilm.space`, снятые с
разницей в 19 секунд, совпали побайтно.

Сжатие, chunked-передача, порядок и регистр заголовков на отпечаток не влияют:
он считается по декодированному телу.

## Ожидание схождения

Переждать разрешено ровно одно — доигрывающий перезапуск службы. Предел
жёсткий: `СХОЖДЕНИЕ_ПОПЫТОК = 6`, `СХОЖДЕНИЕ_ИНТЕРВАЛ = 3 с`,
`СХОЖДЕНИЕ_ТАЙМАУТ = 30 с`, каждая попытка записывается в отчёт вместе с тем,
что домен объявил. Отданный **третий** релиз — не запаздывание, а неправильная
витрина: ожидание прекращается немедленно, не расходуя попытки.

## Обход кэша

Запрос с `?nova-cache-bust=…` выполняется и записывается **только как
диагностика**: он отвечает на вопрос «кэш это или витрина». Зачётом служит
обычный публичный адрес, потому что по нему ходит зритель. В вердикт результат
диагностического запроса не входит.

## Проверка выполняется на настоящем домене

`https://<домен><путь>` с настоящими Host и SNI. Проверка через `127.0.0.1`
или `localhost` публичной проверкой не считается и в инструментах отсутствует.

## Почему проверка стала строже, а не мягче

| было | стало |
| --- | --- |
| одно поле объявленного релиза (`artifact_sha256`) | все пять полей |
| сравнение с отпечатком файла — структурно неверное | сравнение с манифестом точки отката |
| измерения отданного не было вовсе | отпечатки тела, CSS и JS против снимка до установки |
| `prove_serving_chain`: три условия | шесть, включая версию, путь исполняемого файла и активность юнита |
| пустое значение совпадало с пустым | пустое не доказательство: ожидаемый релиз обязан быть заполнен |
| финальная проверка — один запрос | три последовательных, засчитываются только все |
| провал финальной проверки оставлял витрину на кандидате | витрина возвращается на прежний здоровый релиз |

Точка отката прежнего образца структуру доказать не может. Откат по ней
выполняется, но вердикт честно объявляется недоказанным с причиной
`POINT_WITHOUT_SERVED_SNAPSHOT`.

## Где это проверено

* `tests/lords/test_rollback_served_fingerprint.py` — воспроизведение боевого
  случая, отрицательные случаи, допустимые транспортные различия, пределы
  ожидания;
* `tests/lords/test_serving_chain_proof.py` — правило замыкания цепочки;
* `tests/lords/test_canary_run_orchestrator.py` — многократная финальная
  проверка и возврат при её провале.
