### Gate 0 — цепочка отказа найдена и доказана

2. `site-factory-backup.sh` собрал архив `host-20260903T032419Z.tar.gz` (1.13 GB)

3. Поскольку запись `*.verified.json` создаётся только после успешной проверки,
   она не появилась. Файл-архив остался, подтверждения нет.
4. `check_backups` в health-скрипте датирует последний хороший бэкап именно по

   возраст 34 ч при пороге 30 ч → второй алерт health.

То есть оба алерта health (`disk_root: 90% >= 80%`, `backup: age_hours 34 >= 30`)
и падение backup — одно и то же событие, а не три независимые проблемы.

**Дефект удержания (найден при чтении скрипта, не при падении).** Retention в
`site-factory-backup.sh` перебирает `host-*.verified.json` и удаляет пару
`.tar.gz` + `.verified.json`. Архив неудачного прогона не имеет `.verified.json`,
поэтому не попадает ни в один список удаления **никогда**: каждый провал
оставляет на диске осиротевший гигабайтный файл, который сам приближает
следующий провал. Это положительная обратная связь, а не разовый сбой.

**Selfcheck** падает по другой причине: `FAIL: SITE-MATRIX.json: реестр не
сопоставлен ни одной схеме` — в реестре появился файл, для которого нет
соответствия схеме; остальные девять реестров проходят.

### ДЕФЕКТ A — `playbackFingerprint` не может отличить никакие два состояния

`scripts/episode-watcher.mjs:246`

```js
export function fingerprintPlayback(detail) {
  return [...(detail?.source_types ?? [])].sort().join("|");
}
```

`source_types` — массив **объектов**, что подтверждено ответом источника:
`[{"code": "webrip", "label": "WEB-Rip"}]`. `join("|")` приводит объект к строке
`"[object Object]"`. В снимке лежит соответственно
`playbackFingerprint: "[object Object]|[object Object]"` (пастух),
`"[object Object]"` (Клеватесс 2).

Отпечаток различает только **количество** источников воспроизведения, но не их
состав: замена `webrip` на `bdrip` для конвейера неотличима от отсутствия
изменений. Сортировка объектов бессмысленна.

Честная оценка серьёзности: поле **сохраняется, но в диффе не сравнивается** —
`PLAYBACK_AVAILABLE` возникает по переходу булева `videoAvailable`
(`episode-watcher.mjs:382`). Поэтому сегодня события из-за этого не теряются.
Это мёртвое испорченное поле и ловушка: любой следующий потребитель, который
поверит имени поля, получит молчаливо неработающую детекцию. Ровно так уже
случалось с озвучками — их отпечаток пришлось версионировать
(`voicesFingerprintVersion`). Исправление обязано включать версию отпечатка,
иначе первый прогон после починки выдаст ложные события на все 7287 карточек.

### ДЕФЕКТ C — сторож не отличает тишину источника от зависшего конвейера

## ВАЖНАЯ ПОПРАВКА К PHASE 1: причина потери контента найдена, и она не в этом прогоне

Раздел выше говорил, что «потеря в конвейере на контрольных случаях не
воспроизводится». Это верно как измерение **сегодняшнего** состояния и неверно
как вывод о причине. Причина существовала, она найдена, и её починил соседний
поток — поэтому контрольные случаи и проходят.

В репозитории `yummyani` (отдельный от site-factory, `sbc-create/yummyani.git`),
ветка `claude/night-yummy-schedule-12`, в рабочем дереве лежит незакоммиченная
правка `scripts/episode-watcher.mjs`. Её содержание:

```
-const DIRECTIONS = ["anime"];
+const ВЫБОРКИ = [
+  { direction: "anime" },
+  { genres: "dungua" },
+  { genres: "china_anime" },
+];
```

Наблюдатель обходил каталог **одним** фильтром `direction=anime`. Поставщик
размечает содержимое жанрами, и под этот фильтр не попадала китайская анимация:

| тайтл | genre_codes | попадал в обход |
|---|---|---|
| Сказание о пастухе богов | `dungua` | **нет** |
| Моя судьба злодея | `china_anime` | **нет** |
| Клеватесс 2 | `anime` | да |

Тайтл вне выборки не даёт события никогда — сколько бы серий у него ни выходило.
Замер авторов правки на 2026-09-02: `direction=anime` — 6774 записи,
`genres=dungua` — 481, `genres=china_anime` — 233, объединение 7287. То есть
**513 произведений наблюдатель не видел вообще**.

Это и есть корневая причина симптома «пропуски тайтлов и серий», и она в
точности объясняет распределение контрольных случаев из задания: два невидимых
тайтла оказались как раз дунхуа и китайской анимацией, а Клеватесс 2 —
единственный из трёх с жанром `anime` — работал.

Независимое подтверждение из этого прогона: в живом снимке ровно **7287**
произведений (совпадает с объединением), оба ранее невидимых тайтла присутствуют
и публично отдают 200. То есть правка не только написана, но и работает в бою.

Что из этого следует для оценки:

* `CONTENT_ROOT_CAUSE` = обход каталога одним фильтром `direction=anime` вместо
  объединения выборок; 513 тайтлов вне обхода. Найдено и исправлено потоком
  `claude/night-yummy-schedule-12`, не этим прогоном.
* Правка **не закоммичена**. Пока она живёт только в рабочем дереве, её потеряет
  любой `git checkout` или пересоздание стенда, и парк вернётся к потере 513
  тайтлов. Это самостоятельный риск, и он важнее большинства пунктов ниже.
* Утверждение «Моя судьба злодея, серия 17» остаётся не выполнимым из источника:
  поставщик отдаёт `episodes_count: 9`. Здесь тишина источника, а не потеря.

## Gate 0 — итог после исправлений

### Восстановление: что доказано и чем именно

Требование Gate 0 «в изоляции проверь restore одной свежей копии либо поставь
точный blocker» закрывается двумя независимыми механизмами, и важно не
перепутать, что доказывает каждый.

**1. Восстановление архива control-host.** Доказывается внутри каждого удачного
прогона бэкапа: архив распаковывается во временный каталог и каждый файл
сверяется по SHA-256 с манифестом, снятым с источника **до** упаковки
(`site-factory-backup.sh`, шаг 3). Запись `.verified.json` появляется только
после этой сверки. Последнее такое доказательство — `host-20260902T032255Z`.
Прогон 2026-09-03 до сверки не дошёл, поэтому доказательства за сегодня нет.

**2. Восстановление базы стенда.** `tests/tools/restore_proof.py`, еженедельно
через `site-factory-restore-proof.timer`. Это настоящий круговой прогон, а не
проверка наличия дампа: снимок состояния → бэкап → **изменение данных** →
восстановление → повторный снимок и сравнение. Проверка засчитывается, только
если прежнее содержимое вернулось, **а внесённое изменение исчезло** — то есть
доказывается, что восстановление действительно перезаписало данные.
Последний прогон 2026-08-30T05:01:45Z, `status=0/SUCCESS`, 50 s CPU.
Следующий — 2026-09-06.

Итог: механизм доказательства восстановления существует, работает и не
подменяет доказательство наличием файла. Отдельный blocker по restore не нужен.

## ДЕФЕКТ B — доказанная причина и поправка к оценке серьёзности

Ранее в этом журнале дубли карточек описывались как дефект проектора витрины с
подразумеваемой SEO-опасностью. Измерение это опровергает частично: причина
найдена верно, серьёзность была завышена.

### Причина, доказанная по коду

`src/modules/catalog/watcher-shelves.ts:104-116` (репозиторий `yummyani`):

```ts
export function hrefOf(title: WatchedTitle): string {
  const human = humanTitleSlug(source);
  return titleHref({ ...source, publicSlug: `${human}${PUBLIC_TITLE_SEPARATOR}${title.id}` });
}
```

Полки, построенные из снимка наблюдателя, отдают **составной** адрес
`{человекочитаемая-часть}--{uuid}`. Полки, построенные из каталога, отдают
канонический адрес без uuid. Один и тот же тайтл, попавший на полку каждого
вида, получает два разных href — и на главной рисуется дважды.

Это объясняет и то, почему набор дублей менялся между замерами (6 пар в 14:15,
3 пары в 15:11): он зависит от того, какие тайтлы в данный момент оказались
одновременно на полке наблюдателя и на полке каталога.

### Почему составная форма стоит там намеренно

Комментарий в том же файле объясняет выбор, и он обоснован: канонический
`publicSlug` живёт на стороне приложения и **в снимок наблюдателя не попадает**.
Одной транслитерации недостаточно — она даёт правдоподобный, но несуществующий
адрес, и раньше «пять из шести ссылок полки „Сейчас выходят“ отдавали 404 на
живом сайте». Составная форма разбирается маршрутизатором обратно в
идентификатор и приводит к настоящему каноническому адресу.

То есть это не небрежность, а сознательный размен: живые ссылки вместо
битых, ценой uuid в адресе.

### Что показал внешний замер

```
/anime/bezuprechnyy-mir--01915137-...   308 -> /anime/bezuprechnyy-mir
/anime/bezuprechnyy-mir                 200
/anime/boevoy-programmer-sirase--...    308 -> /anime/boevoy-programmer-sirase
/anime/bog-bogatstva-chzhanlun-dou--... 308 -> /anime/bog-bogatstva-chzhanlun-dou
```

Составной адрес отдаёт **308 Permanent Redirect** на канонический. Значит:

* **канонизация не сломана** — поисковые системы схлопнут оба адреса в один,
  дублирующегося контента нет. Моя прежняя формулировка это преувеличивала;
* **зато дублирование в интерфейсе реально**: пользователь видит один и тот же
  тайтл на главной дважды. Это и есть настоящий дефект;
* каждая такая ссылка стоит лишнего перехода 308 → 200 при клике;
* заявленный в `public-title-route.ts` инвариант «provider UUID must never
  appear in those paths» в отдаваемых ссылках всё-таки нарушен, хотя редирект
  и защищает канонизацию.

### Что чинить (владельцу ленты, не этому прогону)

Два независимых шага, и первый дешевле и важнее:

1. **Схлопывать карточки главной по `titleId`, а не по href.** Дедупликация
   сейчас, судя по результату, идёт по адресу — а адреса у одного тайтла два.
   Это убирает видимое дублирование сразу и не требует менять снимок.
2. Донести канонический `publicSlug` до снимка наблюдателя (или разрешать его
   при отрисовке из каталога) — тогда полки начнут отдавать канонический адрес,
   исчезнет лишний переход 308 и восстановится инвариант. Делать это **вместо**
   пункта 1 нельзя: пока snapshot не несёт publicSlug, возврат к транслитерации
   вернёт те самые 404.

## PERF-CACHE-01 — причина некэшируемости доказана

Заголовок `cache-control: private, no-cache, no-store, max-age=0, must-revalidate`
на публичной главной не задаётся ни в коде приложения, ни в nginx. В исходниках
`no-store` стоит ровно в трёх местах и все три законны: `sitemap.xml`,
`robots.txt`, `sitemap/[id]`.

Заголовок ставит сам Next.js, потому что страницы объявлены динамическими:

```
страниц page.tsx в src/app:            41
из них с export const dynamic="force-dynamic":  37
```

**37 из 41.** Динамическими объявлены не только страницы с личными данными, но и
то, что меняется раз в сутки или реже: правовые страницы, FAQ, «Источники»,
«Возрастная политика», карточки тайтлов, страницы сезонов и серий.

Отсюда и измеренная разница с Lords, которые отдают заранее собранные файлы:

| | Lords (статика) | Yummy (force-dynamic) |
|---|---|---|
| TTFB | 84–94 мс | 265–493 мс |
| HTML | 24–37 KB | 239–241 KB |
| полная загрузка | 0.085–0.105 с | 1.65–1.97 с |

### Почему это не только про скорость

Архитектурное правило задания №6: «Public request path не зависит синхронно от
CMS, ingestion, control plane или source API. Сайт обслуживает последний
проверенный immutable release / last-known-good snapshot; при сбое обновления
свежесть ухудшается, но уже опубликованный сайт продолжает работать».

`force-dynamic` на 37 страницах из 41 означает ровно обратное: каждый публичный
запрос синхронно ходит в базу и рендерит заново. Падение или замедление БД
немедленно становится падением витрины — деградации до «последнего хорошего
снимка» не существует. Это нарушение непереговариваемого правила, а не вопрос
оптимизации.

Отдельно отмечу: коммит `a4476fd` («главная перестала пересобирать одно и то же
на каждый запрос») действительно есть в истории, но внешний заголовок на
2026-09-03 по-прежнему `no-store`. Значит та правка сняла повторную работу
внутри рендера, а не саму динамичность маршрута. Это не противоречие, это разные
уровни: без снятия `force-dynamic` HTTP-кэш не включится ни при какой внутренней
мемоизации.

### Что делать (владельцу ленты)

Порядок важен — от безопасного к требующему проверки:

1. Разделить страницы на действительно динамические (модерация, комментарии,
   личные状態) и остальные. Из 37 к первым относится единицы.
2. Для статичных по смыслу страниц (правовые, FAQ, источники) — обычный
   статический рендер. Для каталожных — ISR с адресной ревалидацией по событию
   публикации, а не по таймеру: событийная инвалидация уже есть в конвейере.
3. Только после этого задавать cache matrix и `stale-while-revalidate` /
   `stale-if-error`. Пока маршрут `force-dynamic`, заголовки бессмысленны.
4. Tenant в ключе кэша обязателен: три домена обслуживаются одним образом
   `yummyani/web`, и общий ключ дал бы утечку между сайтами.

`src/modules/catalog/catalog-index.ts:236`

```ts

```

Один запрос, `page.items` берётся напрямую. Обхода курсора нет — ни `has_more`,

него индекс физически не может содержать больше сотни серий на сезон.

про 688 серий, а индекс витрины про 100. Расхождение между этими двумя числами

Рядом отмечу второе: `catch` вокруг этого блока проглатывает ошибку, пишет

обогащения выглядит как успешная сборка с неполными данными.

1. Обходить курсор до `has_more == false`, как это уже делает наблюдатель.
2. Ограничить обход разумным потолком и логировать его достижение явно — молчаливое
   усечение и есть текущий дефект, повторять его на новом уровне нельзя.
3. Регрессионный тест на тайтле с более чем 100 сериями: индекс обязан содержать
   больше сотни, а `/season/1/episode/150` — отвечать 200.
4. После починки — адресная переиндексация 105 затронутых тайтлов, а не всего каталога.

## RATINGS P1 — покрытие измерено

По всему каталогу на 2026-09-03:

```
тайтлов:               7288
с оценкой Кинопоиска:   182  (2.5 %)
с оценкой IMDb:         262  (3.6 %)
хотя бы одна оценка:    279  (3.8 %)
подставных нулей:         0
```

Симптом «оценки почти нигде не заполнены» подтверждён числом: **96.2 % карточек
без единой оценки**.

Хорошая новость и её причина: подставных нулей ноль. `stateFromDetail` пишет
`kinopoisk_rating ?? previous ?? null`, то есть отсутствие сохраняется как
`null`, а не как 0. Требование «не подставлять 0 и не выдумывать оценку»
выполняется уже сейчас, и при доработке его нельзя потерять.

Чего в снимке нет структурно. Требование задания — хранить
`source + fetched_at + vote_count + confidence`. Фактически в записи есть только
`kinopoiskScore`, `imdbScore` и общий `detailFetchedAt` (время загрузки всей
карточки, а не оценки). То есть:

* неизвестно, откуда пришла оценка, если источников станет больше одного;
* неизвестно, когда именно она снята — `detailFetchedAt` обновляется при любом
  обходе, даже когда оценка не менялась;
* нет числа голосов, поэтому 7.5 по трём голосам неотличимо от 7.5 по тридцати
  тысячам;
* нет доверия, поэтому нормализация шкал разных источников будет неразличимой.

Это не ошибка, а незаполненная часть контракта: расширять запись придётся до
того, как появится второй источник оценок, иначе смешаются несравнимые шкалы.

Замечание о приоритете: 3.8 % покрытия — это P1, и он **дешевле** дефекта D по
последствиям. Отсутствующая оценка честно показывается как отсутствующая;
недостижимые 13 568 серий — это контент, за которым пользователь пришёл.

## Gate 2 — недостающая проверка совместимости написана

### Уточнение к прошлой поправке

В прошлый раз я написал, что контракт «частично сделан». Это тоже требует
уточнения: `template-manifest.schema.json` и `schemas/site-engine/` лежат на
ветках `claude/sprint06-stream` и `deploy/day05-lords`, **но не на `origin/main`**.
В моём worktree от main их нет. То есть артефакты контракта существуют, но в
базу интеграции не влиты, и заморозка контракта потребует сначала их вливания.

### Что сделано

`factory/contracts/schema_compat.py` — сравнение двух версий JSON Schema с
классификацией по влиянию на потребителя. Файл новый, каталог новый,
пересечения с чужими ветками нет по построению.

Категории намеренно три, а не две:

* `BREAKING` — потребитель против старой схемы может перестать работать;
* `ADDITIVE` — старый потребитель продолжает работать;
* `REVIEW` — решает человек.

Третья категория существует ради случаев, формально совместимых для одной
стороны и ломающих для другой. Главный из них — **новое значение enum**: тому,
кто данные пишет, оно ничем не грозит, а тот, кто разбирает их исчерпывающим
сопоставлением, на нём падает. Отнести это к безопасным значило бы соврать,
отнести к ломающим — завалить ленту ложными срабатываниями.

Что распознаётся как ломающее: удаление поля; добавление **обязательного** поля;
существующее поле стало обязательным; сужение типа; потеря `null` в типе;
удаление значения из enum; появление enum там, где его не было; сужение
`additionalProperties` до `false`. Обход рекурсивный, включая `items` массивов —
вложенность как раз то место, где ломающее изменение прячется от глаз в диффе.

Косметика (`description`, `title`) не показывается вовсе: настоящие находки не
должны тонуть в шуме.

Код возврата CLI равен числу ломающих изменений, поэтому CI падает видимо.
Флаг `--allow-breaking` оставлен для осознанного перехода на новую major.

### Доказательство

13 тестов, по одному на правило классификации, на настоящих парах схем.

Отдельно проверено на **реальной** схеме манифеста шаблона (11 полей верхнего
уровня, 9 обязательных) с внесёнными настоящими ломающими изменениями:

```
BREAKING: family: поле удалено
BREAKING: title_page: существующее поле стало обязательным
ломающих изменений: 2 — требуется новая major-версия      exit=2
```

То есть проверка работает не только на игрушечных фикстурах.

### Чего это не закрывает

Gate 2 требует ещё сгенерированного типизированного SDK/DataProvider,
детерминированных канонических fixtures с mock-сервером и conformance-пакета.
Их здесь нет. Проверка совместимости — одна из четырёх недостающих частей, и
называть Gate 2 пройденным по ней нельзя.

Ключ индекса каталога (`catalog:year-index:*`) не содержит арендатора, и я

Разделение сделано номером базы Redis, а не префиксом ключа. Разное число ключей

выглядят раздельными. **Cross-site leakage по кэшу отсутствует.**

`REDIS_URL` и невидима в самом ключе. Ошибка в конфигурации одного контейнера
схлопнет её молча, тогда как арендатор внутри ключа сделал бы ошибку заметной.

## PLAYER P0 — измерен, и заявленный симптом не воспроизводится

Плеер оставался единственной областью P0, о которой этот прогон не знал ничего.
Пробел закрыт настоящим браузером (Chromium через Playwright 1.62.1), а не

### Метод

14 публичных страниц тайтлов (те же, что прошли сверку каталога). На каждой
ожидается терминальное состояние плеера по атрибуту `data-player-status`:
`ready`, `playing`, `error`, `unavailable`, `timeout`. Бюджет — 15 секунд из

### Результат

```

статус ready:                  14
не достигли за 15 с:            0

Симптом «плеер долго запускается и иногда не запускается» на этой выборке **не

на выборке **выполняется** с большим запасом.

### Чего этот замер НЕ доказывает — и это важнее результата

* **Это не click-to-first-frame.** Измерено время до состояния `ready`
  оболочки плеера, а не до первого кадра видео. Метрика DoD (p75 ≤ 2 с,

  величин обнадёживает, но подменять одно другим нельзя.
* **Выборка мала для заявленного SLO.** 14 страниц не доказывают «startup
  success ≥ 99 %»: такая цифра требует сотен запусков на согласованной матрице
  браузеров и провайдеров. Здесь один браузер, один сайт, один прогон.
* **Замер сделан с control-host**, то есть по сети короче пользовательской.
  Реальные времена у посетителя будут хуже; насколько — не измерено.
* **`unavailable` в парке встречается.** Отдельная проверка страницы
  «Моя судьба злодея» дала терминальное `unavailable` за 1639 мс. Это честное
  терминальное состояние, а не зависание, но доля таких тайтлов не измерена.

Итог: областей P0 без единого измерения больше нет, а объявлять
`PLAYER_SLO` выполненным по этой выборке нельзя. Правильный следующий шаг —
прогон по матрице браузеров с настоящим click-to-first-frame и снаружи сети
парка.

## Gate 2 — канонические фикстуры и mock-сервер

Исходное задание просило выпустить harness даже без новых референсов. Я
неправильно превратил это в вопрос к владельцу в прошлом отчёте — просить
разрешения на то, что уже поручено, не нужно. Сделано.

### `factory/contracts/fixtures.py`

96 наборов: 12 ViewModel × (5 состояний + 3 крайних случая).

ViewModel: `site_header`, `title_card`, `listing`, `new_episodes`, `updates`,
`news`, `announcements`, `rating`, `search`, `pagination`, `player`, `not_found`.
Состояния: `normal`, `loading`, `empty`, `degraded`, `error`.
Край: `long_text`, `missing_media`, `unknown_optional`.

Три свойства, ради которых это модуль, а не JSON-файлы рядом с каждым шаблоном:

* **детерминированность** — ни `now()`, ни случайности. Время задано двумя
  зафиксированными мгновениями, а свежесть выражается их разностью. Иначе снимок
  вёрстки менялся бы сам по себе, и визуальные проверки отключили бы как мигающие.
* **полнота состояний** — шаблон, умеющий только `normal`, ломается в бою ровно
  тогда, когда данные не пришли, то есть в худший момент.
* **край, а не середина** — вёрстка расходится на длинном заголовке внутри
  списка и на отсутствующей картинке, а не на аккуратной строке из трёх слов.

Смысловое различие, которое здесь закреплено тестом: **`degraded` — это не
`error`**. Degraded означает, что данные есть, но устарели, и страница обязана их
показать с честной пометкой. Error означает, что показывать нечего. Смешение
этих состояний и даёт пустую витрину там, где можно было отдать вчерашний снимок.
Отдельно закреплено, что `unknown_optional` даёт `None`, а не `0`: ноль вместо
отсутствующей оценки — это ложь пользователю.

### `factory/contracts/mock_server.py`

Источник данных, поднимаемый одной командой и не зависящий ни от чего. Без него
«независимая сборка шаблона» остаётся словами: лента упирается в чужой стенд, а
падение витрины неотличимо от падения источника.

Зависимостей нет намеренно — достаточно стандартной библиотеки. Лишний пакет в
шаблонной ленте это ещё одна причина, по которой сборка не воспроизведётся.

Разбор адреса вынесен в чистую функцию `resolve`: проверять маршрутизацию на
настоящем сокете значит получить тест, падающий от занятого порта, то есть
мигающий вместо проверяющего.

Проверено живьём, а не только функцией:

```
GET /health                          {"status": "ok", "fixtures": 96}
GET /viewmodel/title_card/degraded    200, карточка с пометкой устаревания
GET /viewmodel/nosuch                 404
```

Неизвестное имя отвечает 404, а не пустым телом: молчаливая пустота выглядит как
«данных нет» и уводит расследование в сторону.

### Состояние Gate 2

Из четырёх недостающих частей закрыты три: проверка совместимости схем,
канонические фикстуры, mock-сервер. Остаётся **сгенерированный типизированный
SDK/DataProvider** — и он же единственный, который нельзя сделать осмысленно
прямо сейчас: генерировать SDK надо из замороженной схемы, а
`template-manifest.schema.json` до сих пор лежит на ветках и не влит в `main`.

Поэтому Gate 2 пройденным не объявляется. Но harness, который задание просило
подготовить заранее, готов и проверен: 35 тестов на три модуля.

## Граница шаблона — правило 5 теперь проверяется, а не декларируется

Непереговариваемое правило: шаблону запрещены прямые обращения к БД, источнику,
очередям и инфраструктуре, а также raw HTTP к CMS. До сих пор его не проверял
никто — оно жило только в тексте задания.

`factory/contracts/template_boundary.py` ловит пять классов нарушений: прямой
драйвер БД, клиент кэша или очереди, инфраструктурный модуль, серверный секрет
в шаблоне, raw HTTP к CMS или источнику.

Три решения, каждое со своей причиной:

* **Проверка текстовая, а не исполняющая.** Чтобы узнать, что импортирует чужой
  шаблон, его пришлось бы исполнить — то есть запустить в своей проверке ровно
  тот код, безопасность которого проверяешь.
* **Комментарии пропускаются.** Упоминание запрета в пояснении не является его
  нарушением, и наказывать за документацию нельзя.
* **Каждое сообщение называет замену, а не только запрет.** Запрет без замены
  разработчик обходит, а не выполняет. Поэтому вместо «нельзя pg» —
  «данные берутся из SDK/DataProvider».

Отдельно закреплено тестом, что обычный `fetch` к своему же API **не**
помечается: правило про поход в CMS, а не про любой сетевой вызов. Иначе его
обошли бы в первый же день.

### Проверено на настоящих шаблонах

```
themes/basis-video   граница шаблона не нарушена   exit=0
blueprints/lords     граница шаблона не нарушена   exit=0
```

Чистый результат сам по себе ничего не значит — он одинаково выглядит у
дисциплинированного шаблона и у слепой проверки. Поэтому в копию темы
внедрены настоящие нарушения:

```
assets/enhance.js:59: прямой драйвер БД — данные берутся из SDK/DataProvider…
assets/enhance.js:60: секрет в шаблоне — серверные секреты шаблону не выдаются…
нарушений границы шаблона: 2
```

Оба найдены с точным файлом, строкой и заменой; копия удалена, оригинал не
тронут. Оговорка: в теме всего два файла-исходника, поэтому её чистота —
слабый сигнал о дисциплине парка, а не доказательство.

## Почему прогон остановлен на PARTIAL

Все три оставшихся блокера требуют действия, которое по своей природе не моё:
запуск от root с записью в production, выкладка в прод, покупка хоста. Задание
прямо предписывает в таком случае не обходить запрет, подготовить точную команду
с оценкой воздействия и откатом и продолжать независимые ленты — что и сделано,
одиннадцать раз подряд, пока независимая работа не закончилась.

## CWV измерены — и CLS главной не проходит бюджет

В финальном отчёте поле CWV стояло как «не измерено». Пробел закрыт: LCP и CLS
сняты штатными `PerformanceObserver` в Chromium на двух профилях —
desktop 1440×900 и mobile Pixel 7.

```
профиль   страница                        LCP     CLS       TTFB
desktop   yummyani.site/                  512-760  0.2989    360
desktop   yummyani.site/anime/…zlodeya    948      0         516
desktop   lordfilm47.space/               156      0.0037     33
desktop   lordserial33.biz/               356      0.0047     32
mobile    yummyani.site/                  964-972  0.4398      —
mobile    yummyani.site/anime/…zlodeya    812      0         202
mobile    lordfilm47.space/               220      0          69
mobile    lordserial33.biz/               148      0          26
```

### Вердикт по бюджетам DoD

* **LCP ≤ 2.5 с — проходит везде** с большим запасом: худшее значение 972 мс.
* **CLS ≤ 0.1 — главная Yummy НЕ проходит**: 0.2989 на desktop и 0.4398 на
  mobile, то есть втрое и вчетверо выше бюджета. На мобильном хуже.
* CLS у Lords (0.004) и у карточки тайтла (0) — в пределах бюджета.
* **INP не измерен**: он требует настоящего взаимодействия, и подменять его TBT
  значило бы выдать одну величину за другую.

### Почему это надёжная находка, а не шум

Значения **побитово повторились** в трёх независимых прогонах: 0.2989 на desktop
и 0.4398 на mobile каждый раз. Совпадение до четвёртого знака означает
детерминированный сдвиг — конкретный элемент меняет размер после отрисовки, — а
не случайную сетевую дрожь. Такое ищется и чинится адресно.

Отдельно: в первом прогоне мобильная главная упала по таймауту 45 с. В двух
повторах она загрузилась за ~970 мс. Считать это отказом нельзя — один случай
не воспроизвёлся, и я записываю его как незакрытое наблюдение, а не как дефект.

### Связь с рекламными слотами

Задание требует закладывать рекламные места с зарезервированной геометрией и
CLS-safe заглушками. Главная уже сдвигается втрое-вчетверо выше бюджета **до**
всякой рекламы. Добавлять слоты поверх такого фундамента нельзя: сначала
детерминированный сдвиг, потом слоты, иначе виноватыми окажутся слоты.

### CLS главной — виновник найден поимённо

Число без адреса нечинимо, поэтому сняты `sources` записей `layout-shift` — узлы,
которые фактически сдвинулись.

```
desktop 1440×900   одно смещение   value 0.2989   at 1098 мс   footer.portal-footer
mobile  Pixel 7    одно смещение   value 0.4398   at  992 мс   div.portal-container
```

На каждом профиле весь бюджет расходуется **одним-единственным** событием, а не
россыпью мелких. Это и объясняет побитовую повторяемость: сдвиг детерминированный.

Общая подпись у обоих: крупный блочный элемент смещается около секунды после
загрузки. На desktop уезжает подвал, на mobile — сам контейнер содержимого,
то есть на узком экране сдвигается больше страницы, отсюда и 0.4398 против 0.2989.

`ГИПОТЕЗА` (не проверена, требует шага владельца): время ~1 с совпадает с
гидратацией клиентских блоков главной; элемент над подвалом получает высоту
позже первой отрисовки и толкает всё вниз. Проверяется прямо: зарезервировать
геометрию подозреваемого блока и пересмотреть CLS — если упадёт до нуля, гипотеза
подтверждена. Кандидаты на первый взгляд — карусель и полки, у которых высота
до данных не задана.

Чинить это надо **до** рекламных слотов, а не после: задание требует CLS-safe
заглушки с зарезервированной геометрией, а фундамент уже сдвигается втрое-вчетверо
выше бюджета. Слоты, положенные поверх, окажутся виноватыми без вины.

### Проверка гипотезы о гидратации: опыт поставлен неверно

Я собрал опыт «CLS с включённым и выключенным JS»: если без JS сдвиг исчезает,
причина в гидратации. Опыт невозможен по построению, и это моя ошибка: CLS
снимается через `PerformanceObserver` **внутри страницы**, а при выключенном JS
`page.evaluate` не выполняется вовсе. Прогон повис и был остановлен; никакого
результата он дать не мог.

Полезное следствие: пришлось вернуться к уже снятым числам, и они гипотезу о
гидратации скорее **не поддерживают**.

```
desktop, главная:  TTFB 360 мс → LCP 760 мс → сдвиг 1098 мс → DCL 2046 мс
```

Сдвиг происходит **до** `domContentLoaded`, то есть во время загрузки документа,
а не после того, как клиентские компоненты ожили. Гидратация в Next.js
происходит позже этой отметки, поэтому объяснять сдвиг ею — против имеющегося
времени.

`ГИПОТЕЗА` (уточнённая, по-прежнему не доказанная): виновата потоковая отдача
SSR. 37 страниц из 41 объявлены `force-dynamic`, разметка приходит по частям, и
блок полок, дописанный около секунды, толкает вниз то, что под ним: на широком
экране — подвал, на узком — весь контейнер содержимого. Это согласуется и с
адресами сдвига, и с тем, что событие ровно одно.

Как проверить дёшево и без правок в чужой ленте: снять `content-length` и время
последнего байта документа; если поток документа закрывается около 1.1 с,
совпадение с моментом сдвига перестаёт быть догадкой. Этот шаг оставлен
следующему исполнителю — здесь он не выполнен.

Что остаётся твёрдым независимо от объяснения: сдвиг детерминирован (0.2989 и
0.4398 побитово в трёх прогонах), состоит из одного события и адресован
конкретным узлам. Этого достаточно, чтобы чинить резервированием геометрии, не
дожидаясь окончательного диагноза.

### Дешёвая проверка выполнена: документ действительно течёт сквозь момент сдвига

Шаг, который я назвал и оставил невыполненным, сделан. Он read-only и занял
минуту.

```
yummyani.site/   content-length отсутствует  → документ отдаётся потоком
  прогон 1   первый байт 0.335 с   последний 1.882 с   242 615 B
  прогон 2   первый байт 0.282 с   последний 0.784 с   242 615 B
  прогон 3   первый байт 0.274 с   последний 0.808 с   242 615 B

lordfilm47.space/ (контроль, статика)
             первый байт 0.095 с   последний 0.104 с
```

Окно потоковой отдачи главной — от 0.5 до 1.6 секунды. **Сдвиг в 1098 мс лежит
внутри этого окна**, то есть разметка в момент сдвига ещё дописывалась.

Контроль усиливает вывод: у статических Lords окно составляет 9 мс, потока нет —
и CLS там 0.004 против 0.2989. Разница ровно по той оси, которая предполагалась.

**Статус гипотезы: подтверждена корреляцией и контрольным сравнением, но не
доказана причинно.** Совпадение момента сдвига с окном потока и контраст со
статикой — сильное свидетельство, однако прямого опыта «зарезервировали
геометрию → CLS упал» здесь не ставилось, а без него говорить «доказано» нельзя.
Такой опыт требует правки в чужой активной ленте и оставлен владельцу.

Практический вывод от этого не зависит и не меняется: чинить резервированием
геометрии блока полок. Дополнительно сокращение числа `force-dynamic` страниц
(37 из 41) укорачивает само окно потока, то есть бьёт по причине, а не по
симптому — и это та же правка, что требуется для включения HTTP-кэша.

## CMS/API (направление Qwen) — единственная нетронутая область, оценена

В финальном отчёте это направление стояло как «не проверялось». Оценка read-only
сделана; выводы смешанные, и хорошее здесь держится не на замысле.

### Что хорошо

```
seo-engine-api-1   127.0.0.1:8099->8000/tcp     только loopback, наружу не слушает
GET /api/v1/health                    200        health без токена — нормально
GET /api/v1/sites   (без токена)      401        аутентификация ДЕЙСТВИТЕЛЬНО требуется
```

Служба привязана к петле, снаружи парка недостижима, и защищённый эндпоинт
отвечает 401 без учётных данных. Требование DoD «Qwen не может выполнить
destructive/global/security operations» на сегодня **выполняется**.

### Чем оно выполняется — и почему это слабое основание

Не моделью разрешений, а **отсутствием возможности**: в контракте `v1` объявлены
11 эндпоинтов и все до одного `GET`. Ни `POST`, ни `PUT`, ни `PATCH`, ни
`DELETE`. То есть контур `validate → dry-run → apply → verify/rollback`,
идемпотентность, `expected revision`/ETag, operation ID и audit actor —
**не существуют**, а не «существуют и защищены».

Гарантия такого рода исчезает в тот день, когда добавят первый write-эндпоинт,
и исчезнет молча. Записывать её в «пройдено» нельзя.

### Два расхождения контракта с реальностью

* **Схема умалчивает об аутентификации.** `components.securitySchemes` в
  `openapi-v1.json` **отсутствует**, а работающая служба отвечает 401. Клиент,
  сгенерированный из этой схемы, не станет посылать учётные данные и
  сломается на первом же вызове. Для Gate 2 это существенно: SDK предполагалось
  генерировать именно отсюда.
* **Объявленный эндпоинт не реализован.** `GET /api/v1/ingestion/status` есть в
  схеме и отвечает **404** в работающей службе.

Оба — ровно тот класс расхождений, который ловится provider-тестом «схема против
живой службы». Такого теста в наборе нет, и это отдельный пробел Gate 2:
у меня есть проверка совместимости схемы **с самой собой между версиями**, но не
схемы **с реализацией**.

### Оговорка о полноте

Перечень живых эндпоинтов снять не удалось: `/openapi.json` по этому адресу
вернул пустой набор. Поэтому утверждение «в работающей службе нет write-методов»
я делаю **только про контракт**, а не про реализацию: не проверено, есть ли за
пределами схемы недокументированные методы. Это следующий шаг, и он не сделан.

## Provider-сверка: схема против живой службы

Пробел, который я назвал «реальнее, чем отсутствие SDK», закрыт.
`factory/contracts/provider_conformance.py`.

Проверка совместимости схем сравнивает схему **саму с собой между версиями** и
ничего не знает о том, делает ли служба обещанное. Именно это расхождение
дороже всего: клиент генерируется из схемы и ломается о реализацию.

### Проверено на настоящей схеме и живой службе

```
$ provider_conformance schemas/site-engine/openapi-v1.json http://127.0.0.1:8099

MISSING: /api/v1/ingestion/status: объявлен в схеме, но служба отвечает 404
UNDECLARED_AUTH: (схема): служба требует аутентификации, но securitySchemes
                 в схеме нет — сгенерированный клиент не пошлёт учётные данные

расхождений схемы с реализацией: 2
```

Оба расхождения я нашёл до этого руками. Проверка нашла их **сама**, из схемы и
службы, без подсказок — это и есть доказательство, что она не игрушечная.

### Решения, каждое со своей причиной

* **Дёргаются только `GET`.** Вызвать `POST` у живой службы ради проверки
  значило бы изменить её состояние: проверка обязана быть безопасной.
* **Шаблонные пути пропускаются.** `404` на подставленном идентификаторе
  означает «нет такой записи», а не «нет маршрута», и принять одно за другое —
  готовое ложное срабатывание.
* **`401` и `403` считаются подтверждением существования маршрута.** «Нельзя» —
  это не «нет».
* **Недоступная служба даёт `SKIPPED`, а не провал.** Падение по недоступности
  приучило бы игнорировать красный результат, и тогда настоящее расхождение
  прошло бы незамеченным.
* **Обратное расхождение тоже ловится.** Схема, обещающая защиту, которой служба
  не требует, опаснее молчания: на неё полагаются.

9 тестов. Итого harness контракта: **пять модулей, 56 тестов** — совместимость
схем, канонические фикстуры, mock-сервер, граница шаблона, provider-сверка.

### Что это меняет для Gate 2

До этой проверки я считал, что SDK блокирует только незамороженная схема.
Теперь видно, что схему сначала надо **починить**: генерировать SDK из схемы,
которая не объявляет обязательную аутентификацию, — значит выпустить заведомо
нерабочий клиент. Порядок стал определённым: починить `securitySchemes` и
`ingestion/status` → заморозить → генерировать SDK.

### Поправка к оценке контура CMS/Qwen: один из «дефектов» им не был

Прочитав обоснование коммита `842dd53`, я обязан отозвать часть собственных
выводов.

**1. `/api/v1/ingestion/status` → 404 — не дефект, а замысел.**
`site-engine` выключен по умолчанию: «без флага маршрутов нет, а в production он
не включается даже с флагом. Отвечает при этом 404, а не 403 — наличие маршрута
тоже сведения, и сообщать их незачем». То есть 404 выбран сознательно вместо
403 ради сокрытия существования маршрута. Я записал это как «объявлен, но не
реализован» — неверно.

**2. «Гарантия держится не моделью разрешений, а отсутствием возможности» —
формулировка несправедливая.** Read-only поверхность API описана в коммите как
осознанное решение, а не как недоделка. Там же перечислены и другие решения того
же рода: слишком большой `limit` — ошибка, а не молчаливое усечение;
`episode_list_available: false` вместо пустого списка, потому что «серий нет» и
«поимённого списка у источника нет» — разные утверждения; `complete: null`,
когда источник промолчал, вместо `false`; конфигурация без `credentials_ref`,
потому что ссылка на секрет — тоже сведения. Это последовательная линия, а не
пробел.

**3. Правка схемы руками была бы ошибкой.** В том же коммите: «OpenAPI
порождается из кода, а не пишется рядом». Я собирался предложить дописать
`securitySchemes` в `openapi-v1.json` — такая правка была бы затёрта при
следующей генерации. Пункт плана исправлен: чинить **генератор**, а не файл.

**Что остаётся в силе.** `UNDECLARED_AUTH` — настоящий пробел: служба отвечает
`401`, схема аутентификацию не объявляет, и сгенерированный из неё клиент
учётные данные не пошлёт. Это по-прежнему блокирует осмысленную генерацию SDK.
Но чинится в генераторе OpenAPI, и это не «расхождение контракта с реальностью
по недосмотру», а незакрытая часть генерации.

**Что поправлено в самом инструменте.** Категория `MISSING` переименована в
`MISMATCH`, и её текст теперь называет оба возможных объяснения: маршрут не
реализован либо намеренно выключен, причём различить их по коду ответа
невозможно. Инструмент, который называет намеренное решение дефектом, приучает
игнорировать свои же находки — а это ровно то, чего он должен избегать.

Общий урок тот же, что и в случае с ownership: я принял отсутствие за упущение,
не прочитав обоснование, которое лежало в истории файла в одной команде отсюда.

## ОТЗЫВ ВЫВОДОВ: я сверял схему одной службы со службой другой

Это самая серьёзная ошибка прогона, и она отменяет целый раздел выше.

### Что произошло

Я взял `schemas/site-engine/openapi-v1.json` (заголовок: **Site Engine API**) и
сверил его со службой на `127.0.0.1:8099`. На этом порту слушает
**`seo-engine-api-1`**, образ `seo-engine-api` — совершенно другое приложение.
Сам `site-engine` в парке **не запущен вовсе**: контейнеров нет, systemd-юнитов
нет.

Проверено:

```
docker ps --filter publish=8099   →  seo-engine-api-1 | образ seo-engine-api
docker ps | grep site-engine      →  контейнеров site-engine НЕТ
заголовок сверявшейся схемы       →  Site Engine API
```

### Что из-за этого недействительно

* **`MISMATCH /api/v1/ingestion/status → 404`** — недействительно. `seo-engine`
  и не обязан реализовывать маршруты `site-engine`.
* **`UNDECLARED_AUTH`** — недействительно. `401` пришёл от аутентификации
  `seo-engine`, к схеме `site-engine` отношения не имеющей.
* **«Проверка нашла оба расхождения сама, без подсказок»** — недействительно
  вдвойне: и найденное руками, и найденное инструментом происходило из одного и
  того же неверного сопоставления.
* **Пункт плана «починить `securitySchemes` в генераторе»** — снят. Он опирался
  на замер, которого не было: настоящий `site-engine` я не проверял ни разу.

### Что остаётся в силе

* Сам модуль и его девять модульных тестов: они работают на подставных ответах и
  неверным сопоставлением не затронуты. Класс расхождений, который он ловит,
  реален.
* `seo-engine` привязан к петле и требует аутентификации на `/api/v1/sites` —
  это наблюдение про `seo-engine`, и как таковое оно верно.
* `site-engine` только на чтение и выключен по умолчанию — это из обоснования
  коммита `842dd53`, то есть из документации, а не из моего замера.

### Поправка в самом модуле

Docstring цитировал два «настоящих случая» как повод для написания. Повод был
ложным, и оставлять его нельзя: файл, объясняющий себя выдуманным примером,
подрывает доверие ко всему, что в нём написано. Теперь там прямо сказано, что
проверка на настоящей паре «схема ↔ её служба» **не выполнялась**.

### Урок

Восьмой случай одного и того же: предположение, объявленное фактом. Здесь —
«служба на порту рядом и есть та, про которую схема». Стоило посмотреть на имя
образа, что заняло одну команду. Особенно скверно, что ошибка была не в выводе,
а в постановке: инструмент отработал верно на тех данных, что я ему дал.

## Поправка: «снять force-dynamic» — вредный совет, и он едва не попал в план

В списке действий для владельца у меня стояло «снять `force-dynamic` (37 из 41) —
чинит CLS и HTTP-кэш одной правкой». Совет неверный, и выполнение его вернуло бы
в production уже случавшийся дефект.

### Почему `force-dynamic` там стоит

Комментарий над самой директивой (`src/app/pages/faq/page.tsx:9-12`):

> `og:url` запеклись бы с `APP_URL` из Dockerfile — `http://build.invalid`.
> Именно это и попало в production на всех информационных и юридических
> страницах. Рендер по запросу берёт `SITE_URL` того контейнера, который
> отвечает клиенту.

Измеренная причина: **один образ обслуживает три сайта**.

```
yummyani-staging-web-site-1   yummyani/web:day05-site-f   SITE_PROFILE=site  SITE_URL=https://yummyani.site
yummyani-staging-web-org-1    yummyani/web:day05-site-f   SITE_PROFILE=org   SITE_URL=https://yummyani.org
yummyani-staging-web-biz-1    yummyani/web:day05-site-f   SITE_PROFILE=biz   …
```

При сборке образа арендатор неизвестен, поэтому статическая генерация запекла бы
адрес сборки. `force-dynamic` — не небрежность, а исправление реального инцидента.

### Что тогда действительно чинить

Классификация 37 страниц по признакам настоящей динамики (`cookies()`,
`headers()`, `searchParams`, `noStore`):

```
33 страницы   0 признаков      /(portal), /anime/[slug], /legal/*, /pages/*, /posts/*, …
 4 страницы   есть признаки    /catalog (6), /catalog/announcement (6), /search (4), /admin/moderation (2)
```

Но «ноль признаков» **не означает** «можно делать статикой»: ограничение здесь не
в запросе, а в арендаторе, и оно не выражается ни одним из этих признаков.

Правильное направление — **ISR вместо `force-dynamic`** на тех 33 страницах:
рендер по-прежнему происходит в рантайме, то есть `SITE_URL` берётся из
переменных того контейнера, который отвечает, — а результат кэшируется. Оба
ограничения соблюдены одновременно: арендатор верный, кэш появляется, окно
потоковой отдачи схлопывается, и вместе с ним уходит причина CLS.

Альтернатива — сборка отдельного образа на арендатора — дороже и ломает
«одна поддерживаемая codebase, versioned immutable artifact».

### Заодно

В парке крутится осиротевший контейнер `yummyani-staging-web-org-run-3f9fc60b248c`
на образе `yummyani/web:staging` — разовый запуск, который не убрали. На витрину
он не влияет (ingress на него не смотрит), но занимает память и образ.

### Урок

Девятая поправка того же рода. На этот раз я поймал её **до** того, как совет был
исполнен, и только потому, что перед тем как рекомендовать удаление, прочитал
комментарий над удаляемой строкой. Ровно этого не хватило в восьми предыдущих
случаях.

### Проверка рекомендации об ISR: кэш не потечёт между арендаторами

Рекомендовать ISR имело смысл только если кэш ISR не общий на три сайта. Иначе
страница, отрисованная контейнером `site`, досталась бы `org` — то есть я выдал
бы вторую регрессию подряд. Проверено до того, как совет исполнен:

* **кастомный `cacheHandler` в `next.config.ts` не задан** — значит используется
  файловый кэш Next по умолчанию, живущий внутри контейнера;
* **`.next/cache` наружу не смонтирован.** У контейнеров всего два монтирования,
  и оба — исходные данные, общие по назначению:
  `runtime/episode-state → /var/lib/yummy/episode-state` и
  `runtime/cdnvideohub → /run/cdnvideohub`. Каталога кэша рендера среди них нет.

Следовательно кэш ISR у каждого контейнера свой, рендер происходит с его
собственным `SITE_URL`, и межарендаторной утечки не возникает. Рекомендация в
силе.

Оговорка на будущее: если когда-нибудь появится общий `cacheHandler` (например,
на Redis ради общего кэша между репликами), это условие сломается **молча**, и
арендатор в ключе кэша станет обязательным. Ровно та же ловушка, что и с
разделением баз Redis по номеру: изоляция, которой не видно в ключе, исчезает
при первой же смене конфигурации.

## Поправка к главному результату: исправления было недостаточно

Заявление «`fb3b4c5` возвращает 13 568 серий» было **неполным**, и я обнаружил
это, проверяя, действительно ли пересборка индекса задействует исправленный код.

### Что выяснилось

У `listEpisodes` **два** вызывающих, и у каждого была своя одинаково неполная
реализация:

```
src/modules/catalog/catalog-index.ts:236   фоновый индекс   ← исправлен в fb3b4c5
src/modules/catalog/catalog-query.ts:537   страница тайтла  ← НЕ был исправлен
```

Решающая деталь из журнала самой пересборки: `"sourceCount": 223`. Фоновый
индекс считает 223 тайтла текущего года, а не 7288. «Боевой мастер» с его 688
сериями в этот набор не входит — его страницу обслуживает `catalog-query`.

То есть **исправленный путь и сломанный путь были разными**, а замер на
публичном домене показывал сломанный. Выкатка одного `fb3b4c5` не вернула бы
серии, и я бы это узнал только после выкладки.

### Что сделано

Обход вынесен в `src/modules/catalog/episode-walk.ts` и используется обоими
вызывающими (`67725b8`). Общий модуль здесь не аккуратность ради аккуратности:
пока копий было две, починка одной оставляла вторую сломанной — ровно это и
произошло.

Заодно сделано видимым второе усечение, найденное рядом: `seasons.slice(0, 12)`
молча отбрасывал сезоны сверх двенадцатого. Ограничение **сохранено** — менять
его без замера стоимости обхода нельзя, — но теперь оно пишет в журнал. Таких
тайтлов в парке три: «Югио! Поспеши!» (61 сезон), «Покемон» и «Покемон:
Современное поколение» (по 25).

Прогон: 85 файлов, 694 теста, все проходят; typecheck по затронутым файлам чист.

### Что это меняет в инструкции для владельца

Вливать нужно **обе** ветки-правки, а не одну:
`fb3b4c5` (фоновый индекс) и `67725b8` (страница тайтла и общий модуль).
Обе лежат в `claude/catalog-episode-pagination-deployed` от боевой ревизии
`d39e843`. После вливания — гашение ключей каталога и адресная переиндексация,
затем внешняя проверка `/anime/boevoy-master/season/1/episode/150 == 200`.

### Урок

Десятая поправка, и самая дорогая по последствиям, если бы не нашлась: я
проверял, что фикс верен, но не проверял, что он в **том** коде, который
обслуживает измеренный симптом. Нашлось это не из подозрения, а из вопроса
«а задействует ли пересборка индекса исправленный путь» — то есть из проверки
собственной рекомендации, а не собственного кода.

### Проверка списка ключей для гашения: список полон, но нужен не везде

Последняя непроверенная из моих рекомендаций — какие ключи гасить после выкатки.
Проверена; вывод уточняет инструкцию.

**Страница тайтла кэша в Redis не имеет.** `catalog-query` кэширует детали через
`keyedTtlCache` из `@/lib/cache/ttl-cache` — кэш **в памяти процесса**. Он
умирает вместе с контейнером, значит подмена образа очищает его сама:
для пути страницы тайтла гасить нечего, исправление вступает в силу сразу.

**Гасить нужно только индекс витрин.** В Redis лежит ровно четыре ключа на
арендатора, и мой список совпал с фактическим содержимым:

```
db0: catalog:anime-ids:v1  catalog:year-index:published:v7  catalog:year-index:version:v7  catalog:year-index:stale:v6
db1: catalog:anime-ids:v1  catalog:year-index:published:v7  catalog:year-index:version:v7
db2: catalog:anime-ids:v1  catalog:year-index:published:v7  catalog:year-index:version:v7
```

Эти переживают подмену образа, поэтому без гашения витрины продолжат отдавать
прежний индекс до истечения TTL.

Мелочь на заметку: `catalog:year-index:stale:v6` остался только в `db0` при
текущей версии ключей `v7` — след прошлой версии. Вреда не приносит, места
занимает мало, удаляется вместе с остальными.

**Итоговый порядок выкатки уточнён:** подмена образа лечит страницу тайтла сама;
гашение четырёх ключей в базе арендатора нужно ради полок и главной; затем
пересборка индекса и внешняя проверка.

## НАХОДКА: контентный конвейер исполняется из изменяемого git-checkout

Найдено при проверке дефекта C и важнее самого дефекта C.

```
yummy-episode-watcher  ExecStart=/usr/bin/node /srv/sites/yummyani-staging/repo/scripts/episode-watcher.mjs
yummy-watchdog         ExecStart=/usr/bin/node /srv/sites/yummyani-staging/repo/scripts/watchdog-run.mjs
yummy-enrich           ExecStart=/usr/bin/node /srv/sites/yummyani-staging/repo/scripts/enrich-episode-details.mjs
```

Все три контентных юнита исполняются **напрямую из рабочего дерева git**, а не
из неизменяемого артефакта. Ветка этого дерева — `claude/night-yummy-schedule-12`,
то есть та, которую кто-то последней оставил в checkout.

Следствие измерено прямо сейчас:

```
contentState в развёрнутом сторожe (night-yummy-schedule-12):  0
contentState в ветке, из которой собран боевой образ:          5
```

То есть **веб-контейнеры работают с одного кода, а контентный конвейер — с
другого**, и второй старше. Никакого сигнала об этом расхождении нет.

Это тот же класс риска, что и незакоммиченная правка `episode-watcher.mjs`,
о которой я тревожился раньше, но шире: дело не в одной правке, а в том, что
`git checkout` в этом каталоге **молча меняет поведение боевого контента**.
Ни выкатки, ни отката, ни записи о том, какая версия работает.

Архитектурное правило требует, чтобы сайт обслуживался последним проверенным
неизменяемым релизом. Веб-контейнеры это правило соблюдают — у них образ с
меткой ревизии и сверкой метки при выкатке. Контентный конвейер не соблюдает
его вовсе.

**Что чинить (владельцу инфраструктуры).** Юниты должны запускать те же
скрипты из образа, которым собран сайт, — так же, как это уже делает
`yummy-catalog-index-sync`, который поднимает `docker compose run` на боевом
образе и потому заведомо совпадает с витриной. Образец для подражания лежит
в том же парке.

## Поправка к ДЕФЕКТУ C

Мой прежний вывод — «сторож объявляет неизменность состояния нормой, source
silence и stuck pipeline неотличимы» — **неверен как утверждение о коде**.

В `scripts/watcher-watchdog.mjs` есть ровно то различение, которого я требовал:
`contentState` со значениями `source-quiet`, `behind-source`, `unknown`, порог
`sourceAheadSeconds`, и комментарий, описывающий тот самый инцидент
(2026-09-02, блок «Новые серии» семь часов показывал запись от 06:58, сторож
отвечал `ok`). Там же прямо сказано: «источник молчит, и это норма, о которой
надо сказать словом, а не тишиной».

Сторож также уже проверяет: возраст последнего успешного цикла (warning 10 мин,
critical 15), активность таймера, зависший замок (25 мин), незавершённый полный
обход (45 мин), неподвижность страховочного обхода, долю отказов detail и
возраст снимка. И отдельно оговаривает, что неизмеренная величина нормой не
считается.

Я судил по строке журнала `[watchdog] ok — состояние не менялось`, приняв её за
«контент не менялся — значит норма». На деле она означает, что не менялось
**состояние алерта**, и сторож намеренно не повторяет одно и то же сообщение,
чтобы его не перестали читать.

Верным остаётся **следствие**, но по другой причине: в бою различения нет —
не потому что его не написали, а потому что работает старая ветка. Дефект
не в стороже, а в способе его доставки, и он описан выше.

### ДЕФЕКТ B, окончательное уточнение: дело не в дублях карточек

Третий и последний замер по этому дефекту опровергает и мою предыдущую
формулировку. Я говорил «пользователь видит один тайтл дважды». Проверка того,
**на каких полках** стоят повторы, показывает иное.

Повторяющихся тайтлов на главной 23, но все они стоят на **разных** полках:

```
Новые серии                12 тайтлов
Новое на сайте             40
Анонсы                     13
Аниме летнего сезона        6
Новые серии и обновления    5
Актуальное                  4
Сейчас выходят              4
Появилось видео             2
```

Тайтл на нескольких полках — нормальное поведение портала, а не дефект.
Показывать новинку и в «Новые серии», и в «Анонсы» законно.

**Настоящий дефект измерен отдельно и он другой:**

```
«Новые серии»              12 тайтлов
«Новые серии и обновления»  5 тайтлов
общих                       5
доля общих от меньшей полки  100 %
уникальных у второй полки    0
```

Полка «Новые серии и обновления» **не показывает ничего**, чего нет в «Новые
серии», и носит при этом почти то же имя. Для пользователя это две одинаково
названные полки, вторая из которых не добавляет ни одной записи. Это ровно тот
класс, который задание требует устранить: непонятные и дублирующие друг друга
названия блоков.

Решение — продуктовое, и я его не принимаю за владельца. Варианты: убрать
вторую полку; дать ей отличный источник (например, изменения без новых серий);
переименовать обе так, чтобы различие читалось.

Побочно подтверждено: 31 ссылка из 92 на главной несёт uuid-суффикс (прежний
замер давал 25 из 68 — доля та же). Это отдельная, уже описанная причина:
полки из снимка наблюдателя отдают составной адрес, полки из каталога —
канонический. Каждая такая ссылка стоит лишнего перехода 308.

## Точный счёт возвращаемых серий: 12 104, а не 13 568

Число 13 568 я получил вычитанием: `сумма серий у 105 тайтлов − 100 × 105`, то
есть предположив, что каждый затронутый тайтл показывает ровно сотню. Для
односезонных это верно, для многосезонных — нет. Замер по всем 105 тайтлам
обращениями к поставщику даёт другое.

```
доступно сейчас (предел 100 на сезон, 12 сезонов)      11 964
станет после обхода курсора                            23 462
  возвращает обход курсора                             11 498
  остаётся за пределом двенадцати сезонов                 606

после обоих исправлений (курсор + предел сезонов 64)   24 068
  совпадает со снимком наблюдателя точно
ИТОГО возвращается                                     12 104
```

### Почему двух исправлений, а не одного

«Боевой мастер», один сезон на 688 серий: было 100, стало 688 — семь страниц.
Обход курсора решает всё.

«Покемон: Современное поколение», 1229 серий в 25 сезонах: обход курсора
возвращает **ноль**, потому что ни один его сезон не длиннее ста. Там связывал
предел `seasons.slice(0, 12)` — тринадцать сезонов не читались вовсе.

Два разных ограничения давали один и тот же симптом, и по одному тайтлу
отличить их было нельзя. Замер по всем ста пяти показал, что первое стоит
11 498 серий, второе — 606.

### Что осталось честно сказать

Предел сезонов поднят до 64, а не убран: испорченный ответ поставщика с
бесконечным списком сезонов иначе увёл бы обход в никуда. Достижение предела
логируется, чтобы молчаливого усечения не вернулось.

Числа получены обращениями к настоящему поставщику по всем 105 тайтлам, а не
оценкой. Это делает их проверяемыми: тот же скрипт
(`evidence/exact-recovery.mjs`) можно прогнать после выкатки и сверить.

## CONTENT_SLO измерен и нарушен: серия не попадает в список 35+ минут

Проверка автономного обновления дала не только подтверждение автономности, но и
дефект. Он найден замером, а не из отчёта.

### Цепочка, сверенная по четырём источникам

Тайтл «Монстрик Карамелька», серия 10 (событие наблюдателя в 18:12:57):

```
поставщик, счётчики сезона   episodes_count=10  available=10
поставщик, список серий      10 элементов, номера 1..10, has_more=false
снимок наблюдателя           availableEpisodes=10, detailFetchedAt 18:37:43
публичная страница тайтла    список серий 1..9, максимум 9      ← в 18:48
описание страницы            «В каталоге 9 серий»
страница самой серии 10      HTTP 200
```

То же у «Пыли Мёбиуса»: событие 18:07:17 (8→9), поставщик 9, страница 8.

**Прошло 35 и 41 минута при требовании DoD «≤15 минут».**

### Что это не

Проверено и исключено:

* **не индекс** — тайтла нет в опубликованном `catalog:year-index:published:v7`
  (найдено записей: 0), страница идёт живым путём;
* **не HTTP-кэш** — параметры обхода кэша и заголовок `no-cache` дают тот же
  результат, и второй арендатор (`yummyani.org`) показывает то же самое;
* **не фильтрация** — `catalogEpisodesFromApi` только отображает элементы,
  ни одного условия отбора в ней нет;
* **не отсутствие данных** — серия 10 существует у поставщика и её собственная
  страница отдаёт 200. Недостижим именно **список**, то есть найти серию
  просмотром нельзя, а по прямой ссылке можно.

Единственное отличие серии 10 от соседних — озвучка: у неё субтитры, у 8 и 9
дубляж. Совпадение это или причина, замером не установлено.

### Что в цепочке кэшей объявлено

```
next: { revalidate: 300 }                     5 минут
METADATA_RESPONSE_CACHE_TTL_MS   = 5*60*1000  5 минут  (окно свежести)
METADATA_RESPONSE_CACHE_STALE_MS = 6*60*60*1000  6 часов (горизонт «источник недоступен»)
maxEntries = 200                              LRU
```

Все окна свежести — пять минут. Наблюдаемые 35 минут превышают **каждое**
объявленное окно, то есть что-то отдаётся за пределами своего срока.
Главный подозреваемый — шестичасовой горизонт `staleUntil`: по комментарию он
предназначен для случая «источник недоступен», а источник доступен. Но
доказательства этому у меня нет, и причину я не называю.

### Почему это важнее, чем кажется

Это ровно тот разрыв `source → canonical → public`, который задание требует
обнаруживать сверкой. Канонический слой **корректен и свеж** — снимок знает про
десятую серию через минуту после её появления. Теряется она на последнем шаге,
и никакой сигнал об этом не поднимается: сторож смотрит на здоровье
наблюдателя, а не на витрину.

### Следующий шаг для владельца

Инструментировать один запрос страницы тайтла: залогировать, отдан ли ответ
поставщика из `memoryMetadataResponseCache` и с каким `expiresAt`/`staleUntil`.
Одна запись в журнале отличит «отдали протухшее вместо свежего» от «сходили к
поставщику и получили девять». Гадать между этими двумя нельзя — они чинятся
по-разному.

### Порядок важен: ISR нельзя вводить до починки свежести

Я рекомендовал ISR вместо `force-dynamic` — это чинит CLS и включает HTTP-кэш.
Замер свежести показывает, что делать это **сейчас нельзя**, и порядок надо
назвать явно.

`force-dynamic` означает рендер по запросу. Даже при этом новая серия не
попадает в список 35 минут. ISR добавляет поверх ещё один слой кэширования —
страница будет отдаваться из кэша до истечения `revalidate`. То есть ISR
**сложится** с уже существующим отставанием, а не заменит его.

При требовании DoD «≤15 минут» это означало бы ухудшение измеренного P0 ради
улучшения другого измеренного P0.

**Правильный порядок:**

1. Найти и устранить причину 35-минутного отставания списка серий
   (`CONTENT-FRESHNESS-01`). Пока она не названа, любое добавление кэша —
   это ставка вслепую.
2. Убедиться замером, что новая серия появляется в списке за минуты.
3. Только после этого вводить ISR, выбрав `revalidate` так, чтобы сумма
   отставания и окна ревалидации укладывалась в пятнадцать минут.
4. Событийная инвалидация по публикации предпочтительнее таймера: она
   позволяет держать `revalidate` большим без потери свежести.

Это же объясняет, почему я не стал реализовывать ISR сам, хотя дефект CLS
воспроизводим: правка, верная по одному измерению, ухудшила бы другое, и
проверить это можно только после выкатки.

### Уточнение CONTENT-FRESHNESS-01: разрыв самоустраняется, и моё утверждение об окнах было неверным

**Разрыв закрылся сам.** «Монстрик Карамелька», серия 10:

```
18:12:57  событие наблюдателя 9 -> 10
18:48     публичный список: серии 1..9          (35 минут)
18:55     публичный список: серии 1..10         (42 минуты)
```

То есть путь не сломан — он медленный. Это меняет характер дефекта: чинить надо
не потерю, а срок.

**Поправка к моему разбору.** Я писал: «все объявленные окна свежести в цепочке
равны пяти минутам, наблюдаемые тридцать пять превышают каждое». Это неверно.
В том же пути есть тридцатиминутные окна, которые я пропустил:

```
METADATA_RESPONSE_CACHE_TTL_MS   5 мин    ответы поставщика
next: { revalidate: 300 }        5 мин    Data Cache
CACHE_TTL_SEC                   30 мин    catalog:anime-ids:v1 (Redis + память процесса)
WANTED_TTL_SEC                  30 мин    отметка «индекс требуется пересчитать»
LOCK_TTL_SEC                    15 мин    замок пересчёта
METADATA_RESPONSE_CACHE_STALE_MS 6 часов  горизонт «источник недоступен»
```

Тридцать минут плюс цикл пересборки почти точно совпадают с наблюдаемыми
35–42 минутами. Совпадение подозрительное, но **не доказательство**: 30-минутный
TTL покрывает набор допустимых идентификаторов, то есть решает, какие тайтлы
показывать вообще, а не сколько у них серий. «Монстрик» на витрине уже был.
Поэтому причину задержки списка серий я по-прежнему не называю.

**Отдельная находка, которую назвать можно без инструментирования.**
`CACHE_TTL_SEC = 30 мин` управляет набором `catalog:anime-ids:v1`, а он решает
допуск тайтла на витрину (`eligible.has(providerTitleId)`). Значит **новый
тайтл** не может появиться публично быстрее чем за тридцать минут — само по
себе это превышает бюджет DoD в пятнадцать минут вдвое, независимо от всего
остального. Это проверяемо чтением кода и не требует замера.

**Что исключено окончательно.** Внутренний кэш ответов не отдаёт протухшее на
обычном пути: `get()` возвращает `null` по истечении `expiresAt`, а `getStale()`
вызывается только при отказе сети. Шестичасовой горизонт, которого я подозревал,
здесь ни при чём.

Это ровно то расхождение, которое я описал в `CONTENT-INFRA-01`, — теперь оно

### Инструмент поймал собственную ложно-безопасную оценку

Первая версия смотрела только на первый аргумент `ExecStart`. У контентных

ответ хуже отсутствия проверки: он закрывает вопрос неверно.

Исправлено: проверяются все похожие на путь аргументы. Случай закреплён

что он неочевиден и повторим.

Он не чинит и ничего не меняет — только отвечает «откуда исполняется» и
называет ветку. Перевод юнитов на исполнение из образа остаётся за владельцем
инфраструктуры; образец, как это делать, уже есть в парке
(`yummy-catalog-index-sync` поднимает `docker compose run` на боевом образе).

Отдельно отмечу: сам этот образец **не версионирован нигде** — он существует
только как файл на хосте. Юниты YummyAnime тоже: в `site-factory` их нет, в
`yummyani` нет ни одного файла с юнитами. То есть автоматизация, управляющая
боевым контентом, не подлежит ни ревью, ни откату, ни воспроизведению на новом
хосте.

## ДЕФЕКТ B, окончательно: новые озвучки обнаруживаются и не показываются никому

Разбираясь с полкой-подмножеством, я дважды приписал причину не тому месту.
Обе ошибки называю, потому что вывод менялся вместе с ними.

**Первая ошибка.** Увидев `latestPerTitle(withinWindow(events, now), EPISODE_ADDED)`
в `watcher-shelves.ts:156`, я решил, что лента «обновлений» фильтрует события по
одному виду. Строка оказалась внутри `newEpisodeCards` — то есть это полка
«Новые серии», и фильтр там **верен**.

**Вторая ошибка.** Затем я посчитал, что полка «и обновления» отбрасывает 43 %
событий. Она вообще не питается журналом событий: `home.updates` собирается
каталожной выборкой `sort=updated` у поставщика. Источники у двух полок
**разные**, и совпадение их содержимого (5 из 5) — свойство данных, а не кода.

**Что осталось после проверки — и это настоящая находка.**

Виды событий и их полки:

```
EPISODE_ADDED       100  57.1%   newEpisodeCards      → «Новые серии»
VOICEOVER_ADDED      49  28.0%   ПОЛКИ НЕТ            → не видно нигде
METADATA_UPDATED     22  12.6%   (служебное)
PLAYBACK_AVAILABLE    2   1.1%   playbackCards        → «Появилось видео»
SOURCE_ANOMALY        1   0.6%   (диагностика)
TITLE_CREATED         1   0.6%   newTitleCards        → «Новое на сайте»
```

`VOICEOVER_ADDED` объявлен константой в `watcher-events.ts:20` и **больше не
используется нигде** во всём приложении: ни сборщика полки, ни показа на
странице тайтла. Проверено поиском по `src` и `scripts` — единственное вхождение
это само объявление.

То есть второй по частоте вид событий — 49 из 175, 28 % — обнаруживается
наблюдателем, пишется в журнал и не доходит до пользователя ни на одной
поверхности. Для аниме-портала появление новой озвучки у уже вышедшей серии —
ровно то обновление, за которым следят.

Это же объясняет, почему полка «Новые серии и обновления» выглядит дублем:
обновление, которое отличало бы её от «Новых серий», не показывается.

**Оценка серьёзности, честная.** Это не потеря данных: события сохранены, и
после появления поверхности их можно показать задним числом. Но пока поверхности
нет, конвейер делает работу, результат которой никто не видит.

**Решение за владельцем продукта**, потому что это вопрос раскладки главной, а
не исправление ошибки: где показывать, отдельной полкой или подписью на
карточке. Данные для решения теперь есть — 49 событий за наблюдаемое окно.

## Обход класса «однопроходный запрос к поставщику»

Найдя отсутствие обхода курсора у серий, я проверил весь класс, а не только тот
случай, что бросился в глаза.

```
listTitles  catalog-query.ts:545, 701, 865   курсор обходится  ✓
listTitles  catalog-query.ts:448, 941        одна страница — намеренно, выборка ограничена по смыслу
listTitles  catalog-index.ts:233, 278, 844   одна страница — то же
listSeasons catalog-query.ts:610             ОДНА СТРАНИЦА, limit 100
listSeasons catalog-index.ts:310             ОДНА СТРАНИЦА, limit 100
listEpisodes episode-walk.ts:34              курсор обходится ✓ (исправлено этим прогоном)

**`listSeasons` — единственный оставшийся однопроходный вызов того же вида.**
Проверено, есть ли усечение на деле: максимум сезонов в каталоге — **61**

Правило «не менять работающее без воспроизводимого дефекта» здесь применимо
буквально, поэтому я его не трогал. Записано как известный латентный риск: если
у поставщика появится тайтл длиннее ста сезонов, список сезонов усечётся молча —
ровно так же, как усекались серии, и так же незаметно.

## Проверка собственного исправления на границе

Обход курсора обязан вести себя верно ровно на сотне — там, где заканчивается
страница. В каталоге таких тайтлов пять.

«Агрессивная Рэцуко», ровно 100 серий в одном сезоне, ответ поставщика:

```
элементов: 100   has_more: False   next_cursor: None
```

Обход делает **один** запрос и возвращает 100: ни лишнего обращения к
поставщику, ни усечения. Граница пройдена верно, и это проверено на живых
данных, а не рассуждением о том, как поставщик «должен» себя вести.

## Lords проверен: половина парка ведёт себя правильно

До сих пор я смотрел на Lords только снаружи (заголовки, TTFB). Проверил
конвейер — и он оказался в порядке. Отрицательный результат стоит записать
так же, как находку: иначе следующий исполнитель потратит время там, где
уже смотрели.

### Что измерено

```
таймер          lords-content-refresh, каждые ~10 минут, активен
последний цикл  19:12:35 — «обновляю живой каталог (приращением, если можно)»
гейт рендера    lords-01 6df60c58ca4b, lords-02 c639dda8b78d, lords-03 3c3ea26629dc
                «вход не изменился — сборка пропущена»
сборок с 12:00  пропущено 90, выполнено 3 (14:19, 14:45, 15:20)
последний релиз lords-01 158f67886c34 (15:09), lords-02 (15:14), lords-03 (15:19)
```

### Почему это не затор

Ключевой вопрос тот же, что у Yummy: источник молчит или мы перестали замечать?
Ответ дают времена изменения staging-каталогов: `/srv/lords/lords-0{1,2,3}/.staging`
изменены в **19:12**, то есть на последнем прогоне. Выборка источника
происходит каждый цикл; неизменной оказывается контрольная сумма входа, а не
работа загрузчика.

Четыре часа без релиза — настоящая тишина источника. Для каталога фильмов и
сериалов это правдоподобно, и, в отличие от Yummy, здесь ошибиться нельзя:
сборки в 14:19, 14:45 и 15:20 доказывают, что изменение входа приводит к релизу.

### Что здесь сделано правильно

Гейт рендера сравнивает контрольную сумму входа и пропускает сборку, когда вход
не изменился. Это ровно то, чего требует правило «не делать полный рендер
десятков тысяч страниц ради единичного изменения», и оно исполняется, а не
декларируется. У гейта есть собственный тест (`tests/unit/test_lords_render_gate.py`).

### Единственное замечание

Отчётные строки (`[поток]`, `[витрина]`, `[enrich]`), которые печатает
инструмент обновления каталога, в журнал юнита не попадают: видно только
«обновляю живой каталог». То есть **что именно** выбрано и сколько записей
получено, по журналу не установить — приходится смотреть на времена изменения
файлов, как это только что и пришлось делать мне.

Это не дефект работы, а пробел наблюдаемости, и он того же рода, что у Yummy:
конвейер исправен, но доказать это извне нечем. Замечание записано без правки —
менять работающий блок без воспроизводимого дефекта я не стал.

## RPO баз витрин — трое суток, и не по замыслу

Пункт DoD, который я сам отметил неизмеренным, измерен. Результат хуже, чем
я ожидал.

```
последняя копия баз YummyAnime   2026-08-31 16:35
сейчас                           2026-09-03 19:24
RPO                              3 суток 3 часа и растёт
таймера для неё                  НЕТ
```

### Почему так вышло

`deploy/staging/backup.sh` вызывается ровно из одного места — `deploy.sh:57`,
перед заменой образа. То есть копия снимается **только при выкатке**. Последняя
выкатка была 31 августа; с тех пор ни одной копии.

Другого механизма нет, и это проверено, а не предположено:

* базы лежат в томах docker
  (`/var/lib/docker/volumes/yummyani-staging_pg_site_data/_data`), то есть
  **вне `/srv/sites`**, который собирает host-бэкап;
* единственный ежедневный таймер резервного копирования —
  `site-factory-backup` — собирает состояние хоста и баз витрин не касается;
* он же, вдобавок, падает с 2026-09-03 03:28.

Итого: потеряй сейчас том с базой — пропадёт всё, что накопилось с 31 августа.
Для витрин это комментарии, редакционные материалы и всё, что живёт в postgres.

### Что сам скрипт делает хорошо

Он не просто дампит: считает контрольную сумму, **загружает дамп в отдельную
базу и проверяет, что он читается**, и записывает digest образа, чтобы откат
сцеплял данные с тем образом, которому они принадлежали. Отказ на любом шаге
фатален. Это ровно то, чего требует правило «бэкап считается рабочим только
после restore drill».

Проблема не в качестве копии, а в том, что её никто не снимает.

### Что подготовлено

`automation/host/systemd/yummy-site-backup.service` и `.timer` — ежедневно в
02:37 (не в круглую минуту: в ноль стартует слишком многое, а host-бэкап идёт
в 03:20). 4 теста.

### Предупреждение, вписанное в сам юнит

**У скрипта нет удержания.** Каждый прогон создаёт новый каталог, старые не
удаляются никогда — за всё время накопилось шесть наборов только потому, что
копии снимались редко. Ежедневный таймер сделает рост постоянным, а этот диск
уже ломался ровно на неограниченном росте бэкапов: 2026-09-03 host-бэкап упал
с `No space left on device`.

Поэтому в юните написано прямо: включать таймер следует **вместе** с
удержанием, а не раньше него. Отдельным тестом закреплено, что предупреждение
из юнита не исчезнет.

Удержание я не дописывал: это чужой скрипт в другом репозитории, и добавление
удаления файлов туда без владельца — не та правка, которую делают мимоходом.

## Rollback-gate: механизм исправен, но откат Yummy стоил бы трёх суток данных

Проверено без выкатки — по артефактам, скриптам и датам.

### Lords — готов

```
lords-01  текущий 158f67886c34  релизов 2  предыдущий ef32742ba42e
lords-02  текущий 1ffe5a2364c8  релизов 2  предыдущий d4705039263e
lords-03  текущий 6a12572bb1b7  релизов 2  предыдущий 0fef6d70e54b
```

Откат — переключение симлинка `current`, атомарное и мгновенное. Глубина отката
единица, и это соответствует `keep_releases: 2` в `SITE-MATRIX.json`, то есть
настроено, а не случилось.

### Yummy — механизм хорош

`deploy/staging/rollback.sh` принимает арендатора, метку копии и, при желании,
образ. Он **ограничен одним арендатором намеренно**: «весь смысл трёх
контейнеров и трёх баз в том, что плохой релиз на одной витрине не требует
трогать две другие. Ничто здесь не удаляет базу, не принадлежащую цели».
Это ровно та изоляция, которой требует задание.

Образы для отката на месте: `rollback-day05`, `rollback-6ae98f75`,
`day05-site-e`, `day05-site-d`. Плюс сам `deploy.sh` откатывается сам при
неудаче health или verify.

### И тем не менее откат сегодня был бы разрушительным

`rollback.sh <арендатор> latest` восстанавливает **парную копию базы**. А
`latest` указывает на `20260831T163547Z` — 31 августа 16:35. Сейчас 3 сентября.

То есть **штатная процедура восстановления после плохого релиза сама уничтожила
бы трое суток данных**: комментарии, редакционные материалы, всё, что накопилось
в postgres с 31 августа.

Это соединяет две находки, которые по отдельности выглядели умеренно:

* копии баз снимаются только при выкатке, таймера нет (RPO трое суток);
* откат восстанавливает парную копию.

Порознь первое — «рискуем потерять данные, если умрёт том». Вместе — «наш
собственный документированный способ починки ломает больше, чем чинит».

Поэтому расписание копий (`yummy-site-backup.timer`, подготовлено) — не
гигиена, а условие работоспособности отката. Пока копия трёхдневная, откат
Yummy остаётся крайним средством, а не рутинной операцией, и это надо знать
до того, как он понадобится.

## Инвентарь утечек: что течёт, сколько и чьё

Замечено в самом начале прогона, доведено до чисел только сейчас.

### Про циклы ожидания

Восемь процессов вида

```
bash -c until [ -f /tmp/lords-cycle-finished ]; do sleep 30; done; echo ЗАВЕРШЁН
```

ждут файла-сигнала, которого **не существует** и не появлялось трое суток. Они
будут ждать вечно: сторожевого срока у цикла нет, и завершиться сам он не может.

Это не про потребление — восемь bash и семнадцать sleep стоят копейки. Это про
образец: фоновое ожидание без срока переживает задачу, ради которой заведено, и
накапливается. Тот же образец я уже видел в этом прогоне у себя, когда
ожидание завершения набора тестов ушло в фон и перестало быть нужным.

### Разрыв свежести: два случая, границы, воспроизводимость

Замеры доведены до конца по обоим случаям. Разрыв не разовый и не постоянный —
он устойчивый и самоустраняющийся.

```
случай 1  «Монстрик Карамелька» 9→10
          событие 18:12:57
          18:48 — страница 9   (35 мин, отстаёт)
          18:55 — страница 10  (42 мин, догнала)
          → задержка в промежутке (35 … 42] минут

случай 2  «Ура мечте!» 47→48
          событие 18:43:44
          19:16 — страница 47  (33 мин, отстаёт)
          19:51 — страница 48  (68 мин, догнала)
          → задержка в промежутке (33 … 68] минут
```

Общее для обоих: **отстаёт дольше 33 минут и в конце концов догоняет**. Первый
случай зажат плотнее и даёт верхнюю оценку около 42 минут.

Бюджет DoD — пятнадцать минут. Наблюдаемое превышает его примерно в два с
половиной раза, и превышает **в каждом** замеренном случае, а не в среднем.

Что это меняет в характере дефекта: чинить надо срок, а не потерю. Данные
доходят, поэтому реконструкция не нужна — нужна причина задержки. Она сузится
до одной строки журнала, как только выкатится инструментирование (`21bebf9`):
оно скажет, отдан ли список серий из кэша или из сети, и этого достаточно,
чтобы различить два оставшихся объяснения.

Отдельно стоит записать, что источник за этот час молчал: последнее
`EPISODE_ADDED` — в 18:43:44, дальше только `PLAYBACK_AVAILABLE` и прочее.
Значит третий замер придётся делать на следующем выходе серии, и ждать его
искусственно незачем — двух воспроизведений с границами достаточно, чтобы
причину искали по журналу, а не по симптому.

### Поправка: отставание не постоянное, а переменное — и это подсказка

Двумя коммитами выше я написал, что список догоняет источник «примерно за сорок
минут». Четвёртый случай это опровергает.

```
№1  «Монстрик Карамелька»        отстаёт 35 мин   актуален 42 мин
№2  «Ура мечте!»                 отстаёт 33 мин   актуален 68 мин
№3  «Необыкновенный неудачник»   отстаёт 21 мин   актуален 41 мин
№4  «Чувственные слова»          отстаёт  5 мин   актуален 25 мин  ← быстрее всех
```

Случай №4 стал актуальным на 25-й минуте, тогда как случай №1 на 35-й ещё
отставал. Значит фиксированного окна нет: задержка **переменная**, от ≤25 до
~41 минуты.

**Почему это важнее, чем точное число.** Переменная задержка — подпись
периодического обновления, а не постоянного лага. Если перечень пересобирается
раз в T минут, то событие, случившееся перед самой пересборкой, появится почти
сразу, а случившееся сразу после — только через T. Наблюдаемый разброс от ≤25
до ~41 минуты укладывается ровно в эту картину.

Постоянный лаг и периодическое обновление чинятся по-разному: первый — сроками
кэша, второе — частотой или событийной инвалидацией. Разброс говорит, что искать
надо период, а не таймаут.

**Что я сделал неправильно.** Три согласованных верхних границы (41, 42, 68) я
принял за сходимость к одному числу и назвал его практическим выводом. Четвёртый
замер показал, что сходимости не было — были три точки, случайно попавшие в
верхнюю часть диапазона. Утверждать число по трём точкам без замера в нижней
части было преждевременно, и «примерно сорок минут» из предыдущей записи
отзывается.

Что остаётся твёрдым: бюджет DoD в пятнадцать минут превышен во всех четырёх
случаях, и перечень устаревает целиком, а не поштучно.

### Кэш обновляется лениво, и частота моего опроса могла входить в измеряемое

Поправка выше советовала искать период. Периода, объясняющего 25–41 минуту, в

                                     уже существовал (37→44)
```

Тридцать минут численно похожи на наблюдаемое, но пути к симптому у них нет:
`catalog:anime-ids:v1` хранит идентификаторы, а не перечни серий. Совпадение
чисел я за механизм не считаю — в этой сессии я уже дважды ошибался с

**Что действительно нашлось — возраст записей кэша:**

```

моложе 10 минут         11
моложе 30 минут         28
моложе часа            117
```

Записи живут 300 секунд, но переписываются только когда страницу запрашивают.
Кэш ленивый. У Next просроченная запись отдаётся как есть, а обновление идёт
фоном — то есть **первый запрос после истечения возвращает старое**, а новое
видит лишь следующий.

Отсюда неприятная возможность: я опрашивал примерно раз в двадцать минут, и
тогда каждый мой замер показывал то, что подтянулось на предыдущем замере. Часть
наблюдённых 25–41 минуты может быть не задержкой сайта, а следом моей
собственной сетки опроса. Живой посетитель, обновивший страницу дважды, увидел
бы иное.

**Как проверяется.** Сменой частоты, а не рассуждением. Запущен `freshness-probe.sh`:
ждёт следующего EPISODE_ADDED и опрашивает страницу раз в минуту. Если задержка
схлопнется примерно до пяти минут, прежние числа были во многом артефактом
измерения; если останется около сорока — отставание настоящее, и искать надо
дальше. Обращение идёт по `titleId`, сайт отдаёт 308 на канонический slug.

До результата опросчика прежние 25–41 минуты считаю **измеренными, но не
истолкованными**. Твёрдым остаётся только то, что не зависит от частоты опроса:
перечень устаревает целиком, а не поштучно, и каждая серия при этом достижима
по прямой ссылке.

### Распространённость расхождения: в покое его нет

Ждать события не обязательно. У наблюдателя есть снимок с числом серий по
каждому тайтлу, и его можно сверить с живыми страницами прямо сейчас.

```
снимок взят      2026-09-04T01:00:52Z   (минутами ранее)
пригодных        4194 тайтла
выборка          30
совпало          30
отстаёт           0
впереди           0
```

Выборка ограничена односезонными сериалами не длиннее сотни серий **намеренно**:
развёрнутый образ `d39e843f` читает одну страницу сезона, и у длинных сериалов
расхождение дал бы этот дефект, а не свежесть. Так меряется именно свежесть.

**Что это меняет.** Отставание — не постоянное состояние каталога, а
**переходное окно после изменения**. В покое перечни сходятся с источником
полностью. Прежняя формулировка «перечень устаревает целиком» верна только
внутри окна распространения, а не вообще.

**Чего это не отменяет.** Ровно ничего из четырёх событийных случаев: там новая
серия не появлялась десятками минут, и это измерено. Здесь же последнее событие
было в 22:36, за два часа до замера, — всё давно догнало.

**И чего это тем более не значит.** Выборка построена так, чтобы исключить ту
самую совокупность, где расхождение постоянно: тайтлы длиннее сотни серий, где
недостижимы 12 104 серии. «Тридцать из тридцати» — это про свежесть коротких
сериалов, а не про исправность каталога.

**Честно о точности.** Ноль отставаний на тридцати наблюдениях даёт по правилу
трёх верхнюю границу примерно в 10% при 95% уверенности. То есть измерено не
«отставания нет», а «в покое оно ниже одной десятой».

### Период кэша измерен: 299 секунд. И он не объясняет наблюдаемое

Ожидание события заменено измерением. Страница запрашивалась каждые двадцать
секунд девять минут подряд, и считались записи кэша, переписанные за последнюю
минуту. Вспышка держится в счётчике около минуты после самой записи.

```
01:22:26   7 записей   первое обращение, кэш холодный
01:26:00   4 записи    другое подмножество, своя фаза
01:27:25   7 записей   те же семь
между вспышками нули — запросы идут из кэша
```

Между двумя семёрками **299 секунд** — ровно настроенные `revalidate: 300`.
Значит кэш работает как объявлено, а не «залипает»: под непрерывным запросом он
обновляется каждые пять минут. Разные подмножества записей имеют разную фазу,
оттого частичные вспышки по четыре.

**Что это исключает.** Складываем известные звенья:

```
кэш данных сайта        ≤ 5 мин   (измерено, 299 с)
таймер наблюдателя      ≤ 5 мин   (OnUnitActiveSec=5min)
итого                   ≤ 10 мин
наблюдалось в событиях    25–41 мин
```

Собственный кэш сайта дать наблюдаемую задержку **не может**. Он снят с
подозрения — измерением, а не рассуждением.

**Куда сместилось подозрение.** Наблюдатель узнаёт о новой серии через
`detail:active` и `detail:sweep`, то есть обращаясь к карточке тайтла напрямую.
Страница же собирается запросами каталога. Если у поставщика эти пути имеют
разную свежесть, витрина будет отставать от наблюдателя ровно так, как
измерено, — при полностью исправном кэше на нашей стороне.

Проверяется это сравнением двух ответов поставщика в момент события: карточка
против выборки каталога. Инструмент для этого уже лежит в ветке —
`logEpisodeFetch` из `21bebf9` помечает каждый ответ как `cache` или `network`,
но он не выкачен, а образ `d39e843f` его не содержит.

**Оговорка о границах.** Мерилось на одной странице тайтла и на одном стенде.
Путь стандартный, но это одно наблюдение периода, а не распределение.

### Зависание неограниченно, и это значит SIGKILL на боевых сайтах Lords

В записи о правке SIGTERM я написал, что юнит «доживал до таймаута соединения в
тридцать секунд». Это описание механизма неверно, и я его отзываю.

Тридцать секунд были порогом **теста**, а не наблюдённым временем выхода.
Процесс за это время ни разу не вышел сам — я просто не ждал дольше. Померил:

```
serve.py возвращён к бесконечному ожиданию (то же, что в шести релизах)
попытка 12: НЕ ВЫШЕЛ за 150 с — зависание неограниченно
```

Механизм на это и указывал, а я не довёл рассуждение: таймаут обработчика в
тридцать секунд закрывает поток молчащего соединения, но главный поток стоит в
`stop.wait()`, и разбудить его нечем — сигнал уже доставлен и снят. Ждать
нечего и некого, ожидание вечное.

**Что отсюда следует для боевых сайтов.**

```
lords-01 -> 158f67886c34   бесконечное ожидание
lords-02 -> 1ffe5a2364c8   бесконечное ожидание
lords-03 -> 6a12572bb1b7   бесконечное ожидание
TimeoutStopUSec у всех трёх юнитов = 1 мин 30 с
```

Значит остановка сайта, заставшая открытое молчащее соединение, идёт так:
systemd шлёт SIGTERM, процесс не реагирует, полторы минуты юнит висит в
состоянии остановки, затем прилетает SIGKILL. Не косметика: девяносто секунд
простоя и грязное завершение при каждой такой остановке. Частота под нагрузкой
измерена отдельно — примерно один запуск из семи.

Тяжесть, названная теперь по факту, а не по догадке: правка в ветке чинит не
будущие сборки, а то, что работает на всех трёх сайтах сейчас.

```

Утверждение достоверно: положительный ответ `--is-ancestor` означает, что путь
в истории существует локально.

**yummyani — определить отсюда нельзя, и мои промежуточные выводы отзываются.**

По дороге я объявил, что ветки разошлись на «108 коммитов сверху и 119 снизу»,
а затем — что у них вовсе нет общей базы. Оба вывода неверны:

```
git rev-parse --is-shallow-repository  →  true
.git/shallow есть
```

Клон **поверхностный**. В таком клоне предки обрезаны, поэтому `merge-base`
пуст, оба «корня» — искусственные границы обрезки, а счётчики 119 и 108 равны
попросту глубине клона. Отрицательный ответ `--is-ancestor` здесь тоже ничего
не значит: связующей истории просто нет на диске.

Осторожность в асимметрии: положительный ответ в поверхностном клоне доверия
заслуживает, отрицательный — нет. Именно на этом я и споткнулся.

**Почему не углубляю клон сам.** `git fetch --unshallow` пришлось бы делать в
`/srv/sites/yummyani-staging/repo/.git` — это git-каталог **боевого чекаута**,
с которым моё рабочее дерево делит объектную базу. Операция не разрушительна,
но она меняет состояние боевого репозитория и тянет всю историю; повода
достаточного нет, а решение не моё.

**Что это значит для владельца.** Семь коммитов yummyani трогают одиннадцать
файлов, из них три — ядро каталога (`catalog-index.ts`, `catalog-query.ts`,
`cdnvideohub/client.ts`). Сливаются ли они чисто с настоящим main, здесь не
установлено, и утверждать это я не буду. Для **выкатки** это неважно: ветка
основана на развёрнутой ревизии `d39e843`, и `deploy.sh` работает с ней
напрямую.
