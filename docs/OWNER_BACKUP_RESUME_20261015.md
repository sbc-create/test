# Бэкап не идёт 16 суток: при каких условиях он возобновится

Запись от 2026-10-15. Вопрос задания: «установи безопасные условия
возобновления резервного копирования и проверки восстановления». Ниже —
измеренное состояние, причина отказа в числах самой политики и три варианта
решения с ценой каждого. Ни один файл не удалён: удаление копий — решение
владельца.

## Состояние, измерено

| что | факт |
| --- | --- |
| последний архив хоста | `host-20260929T032303Z.tar.gz`, **29 сентября 03:53**, 3,33 ГБ |
| **доказательство восстановления у него** | **отсутствует**: файла `host-20260929T032303Z.verified.json` нет (у архивов 20, 21 и 23 сентября он есть) |
| последний архив с доказательством | `host-20260923T032424Z`, 23 сентября |
| последний git bundle репозитория | `repo-latest.bundle`, **8 октября** 03:45 |
| таймер | `site-factory-backup.timer`, ежедневно 03:20 UTC, `Persistent=true` — то есть он не отключён, а каждую ночь ОТКАЗЫВАЕТСЯ |
| свободно на разделе | **2,5 ГиБ из 203 (1,2 %)** |

Два разных факта, и путать их нельзя: **копия от 29 сентября есть, а
доказанного восстановления нет с 23 сентября.** «Файл бэкапа существует»
доказательством восстановления не считается — это правило
`.claude/rules/infrastructure.md`, и здесь оно сработало буквально.

## Почему отказывает: числа самой политики

Прогон `automation/host/backup-preflight-space.sh` на текущих размерах
(источники 29,8 ГиБ: `var/` фабрики 27,8 + `/srv/sites` 2,1; bundle 2,5 ГиБ):

| оценка сжатия | пик этапов | нужно | свободно | исход |
| --- | ---: | ---: | ---: | --- |
| осторожная, вдвое (умолчание) | 47,22 ГиБ | **61,66 ГиБ** | 2,52 ГиБ | отказ |
| измеренная, 8,7× | 36,03 ГиБ | **48,24 ГиБ** | 2,52 ГиБ | отказ |

Пик складывается из источников, архива и bundle, плюс запас 20 % и **резерв
5 ГиБ работающим сайтам** — бэкап не вправе занимать последние гигабайты,
иначе падает не бэкап, а сайты. Отказ происходит ДО сбора, предыдущие копии
целы: это правильное поведение, а не поломка.

## Единственный крупный рычаг: копии перед публикацией

`var/lords/publish-backups` — **25,50 ГиБ, 640 файлов, 30 суток** (10.09 →
14.10). Это 86 % всех источников бэкапа. Считано по РЕАЛЬНО занятым блокам
(`st_blocks`), инод учтён один раз: номинальный размер сложил бы жёсткие
ссылки дважды.

Суточный прирост — около 1,17 ГиБ (26 файлов в день). Исключение четырёх
доменов, которые владелец заменяет, уже убрало из этого прироста 390 МиБ в
сутки.

| срок хранения | останется копий | освободится | бэкап после этого |
| --- | ---: | ---: | --- |
| как сейчас | 25,50 ГиБ | — | **отказ** (нужно 61,66, свободно 2,52) |
| **7 суток** (с 08.10) | 8,05 ГиБ | 17,45 ГиБ | **всё ещё отказ**: нужно 30,25, свободно 19,97 |
| **3 суток** (с 12.10) | 3,50 ГиБ | 22,00 ГиБ | **проходит**: нужно 22,06, свободно 24,52 |
| **1 сутки** (с 14.10) | 1,18 ГиБ | 24,32 ГиБ | **проходит**: нужно 17,88, свободно 26,84 |

Отсюда прямой ответ на вопрос «при каких условиях»: **три суток — самый
长 срок хранения, при котором бэкап возобновляется**. Семь суток не проходят
даже при измеренном сжатии.

## Что теряется и что остаётся при сроке 3 суток

Остаётся: откат публикации каталога на любой из трёх последних суток по
каждой витрине (26 файлов в сутки — по одному на витрину плюс служебные).
Этого достаточно для того, ради чего копии и делаются: вернуть витрину к
состоянию до вчерашней или позавчерашней публикации, если доставка привезла
испорченный снимок.

Теряется: возможность вернуться к состоянию недельной и месячной давности.
Такого возврата за 30 суток не делалось ни разу (в журнале публикаций
обращений к копиям старше суток нет), но решение всё равно за владельцем:
это уменьшение глубины отката, а не очистка мусора.

**Защищённое не трогается ни в одном варианте**: `host-*.tar.gz`,
`*.verified.json`, `repo-latest.bundle`, `repo-previous.bundle`, рабочие
каталоги других сессий и данные витрин.

## Второй рычаг, меньший: docker

Измерено 17:05: образы 23,08 ГБ, из них **7,62 ГБ не используются ни одним
контейнером**; кеш сборки 10,21 ГБ, из него 1,67 ГБ освободимо. Из образов
29 — это образы откатов (`yummyani/web:rollback-*`), и часть из них —
действующий откат живых витрин: их удалять нельзя. Разбирать их по одному
можно только с таблицей «какой образ чьим откатом является», и это отдельная
работа; в условиях возобновления бэкапа она не нужна — хватает срока хранения
копий.

Попытка освободить кеш сборки старше 6 часов дала 0 Б: весь освобождаемый кеш
младше, то есть принадлежит сегодняшним сборкам.

## Команды владельцу

Удаление копий старше трёх суток (сначала покажет, что удалит):

```bash
find /srv/site-factory/repo/var/lords/publish-backups -type f -mtime +3 -printf '%TY-%Tm-%Td %10s %p\n' | sort | tail -20
find /srv/site-factory/repo/var/lords/publish-backups -type f -mtime +3 -delete
```

Проверка, что бэкап после этого согласен начать сбор (ничего не меняет):

```bash
python3 -c "import shutil;print(shutil.disk_usage('/srv').free//1024)"
bash /srv/site-factory/repo/automation/host/backup-preflight-space.sh 7000000 0 2600000 <свободно_кб> 0
```

Запуск бэкапа и проверка результата:

```bash
systemctl start site-factory-backup.service
systemctl status site-factory-backup.service --no-pager
ls -la /srv/backups/ | tail -4        # ожидается новый host-*.tar.gz И его *.verified.json
```

## Чего эта запись не решает

Срок хранения — лечение симптома. Причина суточного прироста в 1,17 ГиБ —
полная копия снимка каталога перед каждой публикацией (26 файлов по ~45 МиБ).
Жёсткие ссылки её НЕ убирают: проверено опытом, после `os.replace` занятое
место то же (`docs/verification/hardlink-space-20261015.md`). Настоящее
решение — хранить разницу, а не копию целиком, либо не копировать неизменные
снимки; второе измерено и ничего не даёт (из 156 суточных копий повторов
ноль). Это отдельная задача, и до её решения срок хранения придётся держать
коротким.
