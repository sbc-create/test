# Переносимая ячейка сайта (PORTABLE-SITE-CELL-01)

Один домен — один сайт — один арендатор — один закреплённый шаблон — один
Git-проект — один экземпляр CMS. Общий код при этом остаётся в одном месте: в
ячейку уходит выбранный шаблон, набор модулей и закреплённые версии, а не копия
фабрики.

Документ описывает то, что **реализовано и проверено**. Непройденное названо
непройденным в конце.

## Зачем это устроено именно так

| Решение | Почему не иначе |
| --- | --- |
| Отдельный Git-проект, а не ветка монорепозитория | У ветки нет собственной истории сайта, собственных прав на выкладку и собственного артефакта, который ставится без доступа к фабрике. Ветка — удобство для того, кто уже внутри; проект — граница. |
| Артефакт с digest, а не сборка на сервере | Собранное на целевом сервере — другая сборка, и проверяли не её. |
| Данные вне каталога релиза | Смена релиза не должна касаться комментариев, а откат кода — возвращать вчерашние. |
| Владение полями, а не «последний записавший победил» | Обновление каталога стирало SEO-описание, следующая SEO-правка обнуляла число серий, и круг замыкался. |
| Атомарное резервирование шаблона | Два заказа, поданных в одну минуту, получали один профиль и расходились уже на живых доменах. |
| Снимок через SQLite Online Backup API | Копия файла работающей базы — это снимок в середине транзакции. |

## Состав

| Модуль | Отвечает за |
| --- | --- |
| `factory/cell/ledger.py` | атомарная запись журналов и взаимное исключение |
| `factory/cell/templates.py` | пул шаблонов: `free → reserved → assigned` |
| `factory/cell/registry.py` | паспорт ячейки: домен → проект → версии → цель |
| `factory/cell/siterepo.py` | генерация Git-проекта сайта с `AGENTS.md` и проверками |
| `factory/cell/release.py` | воспроизводимый артефакт, `release-manifest`, отказ устаревшему выкату |
| `factory/cell/tenant.py` | локальные данные: комментарии, голоса, личности, изоляция |
| `factory/cell/sync.py` | доставка обновлений: курсор, дубли, удаления, свежесть |
| `factory/cell/ownership.py` | владение полями и ревизии содержимого |
| `factory/cell/transfer.py` | export / install / verify / cutover / rollback |
| `factory/cell/onboarding.py` | этапы заведения сайта с продолжением с места сбоя |
| `factory/cell/pilot.py` | витрина пилота и инвентарь опубликованных адресов |

Реестры: `config/template-pool.json`, `config/site-cells.json`.
Оба меняются **только** через модули: правка руками обходит блокировку, а с ней
и защиту от выдачи одного шаблона двум заказам.

## Команды

```bash
python3 -m factory cell registry                      # все ячейки и расхождения
python3 -m factory cell registry --site <домен|site_id>   # куда нести задачу
python3 -m factory cell templates                     # пул шаблонов
python3 -m factory cell reserve  --site <id> --order <id> --domain <домен> [--dry-run]
python3 -m factory cell repo     --site <id> [--destination <путь>] [--dry-run]
python3 -m factory cell release  --site <id> [--dry-run]
python3 -m factory cell install  --site <id> --artifact <файл> [--dry-run]
python3 -m factory cell verify   --site <id> --route /catalog/ --route /search/
python3 -m factory cell export   --site <id> [--dry-run]
python3 -m factory cell cutover  --site <id> --target <корень> --reason <текст> [--dry-run]
python3 -m factory cell rollback --site <id> --reason <текст> [--dry-run]
python3 -m factory cell freshness --site <id>
python3 -m factory cell onboarding --order <id>
```

Ни одна из них не переключает домен и не трогает живые сайты. Переключение
маршрутизации — отдельный шаг с подтверждением владельца.

## Конвейер нового сайта

```
domain_validated → template_reserved → repo_ready → release_ready
  → server_staged → data_verified → sync_verified → seo_verified → live
```

Этапы записываются на диск после каждого. Прогон, оборванный на пятом шаге,
продолжается с пятого: повтор с первого израсходовал бы второй шаблон и завёл
второй проект. Частичный провал не отмечается как «готово» — сводка считается
по фактическим статусам этапов.

Семейство, профиль содержимого и сервер берутся **из заказа**. Из имени домена
они не выводятся: `animedia.space` не означает ни семейства, ни профиля.

## Границы, которые проверяются кодом

- **Один домен — одна ячейка.** Повторная регистрация домена отвергается.
- **Похожее имя не подставляется.** `lords` → отказ со списком похожих, а не
  выбор первого подходящего.
- **Отозванные `publisher_id` 10331/10332/10333** не проходят регистрацию.
  Пустой `publisher_id` — `BLOCKED_INPUT`, а не умолчание.
- **Чужой артефакт не ставится**: `site_id` манифеста сверяется с целью.
- **Подменённый манифест не открывает чужие данные**: `site_id` записан внутри
  базы, и верим базе, а не вызывающему.
- **Устаревшая сессия не перезаписывает свежий релиз**: сравнивается родство
  коммитов, а не время.
- **Выкат кода не откатывает содержимое**: `content_revision` защищена
  отдельно от версии кода.

## Что даёт проект сайта

В `AGENTS.md` каждого проекта записано и проверяется:

1. правки только этого сайта, переход в соседний проект запрещён;
2. массовая замена по всей фабрике запрещена;
3. общее ядро меняется отдельной задачей, версия продвигается отдельным выпуском;
4. плавающих версий (`latest`, `main`, `HEAD`) не бывает — `checks/run.sh` падает;
5. данные и секреты не коммитятся — `checks/run.sh` падает;
6. живой код по SSH не правится.

Пункты 4 и 5 — исполняемые проверки, а не обещания.

Вместе с проектом генерируется шаблон CI (`.github/workflows/release.yml`):
группа параллелизма на сайт (два выката одного сайта одновременно невозможны,
прерывание на середине запрещено), отказ чужому `site_id` и отказ выкату,
основанному на предке уже развёрнутого коммита. Переключения домена в нём нет
намеренно: это отдельное решение, а не побочный эффект зелёной сборки.

## Пилот

```bash
PYTHONPATH=. python3 tests/tools/cell_pilot.py \
  --evidence artifacts/evidence/portable-site-cell/pilot.json
python3 -m pytest tests/integration/test_cell_pilot.py -q
```

Пилот целиком живёт во временном каталоге: свой пул шаблонов, свой реестр, свои
данные, свои релизы. Живые сайты, настоящий пул и рабочие каталоги не
участвуют. Пул шаблонов пилота — **копия**: настоящий пул исчерпан, все четыре
шаблона закреплены за `lords-01…04`.

## Где исполнитель ищет репозитории сайтов

Корневая копия пакета живёт в `/usr/local/lib/site-factory-cell`, рабочие копии
репозиториев сайтов — в рабочем каталоге фабрики. Это разные сущности с разными
владельцами, и вывести вторую из первой нельзя. Установщик записывает основание
явно:

    /usr/local/lib/site-factory-cell/cell-install.json   {"site_repos_root": "…"}

Относительный `repo.path` из реестра разрешается только относительно него, и
только внутри него — `registry.repo_path` единственное место, где это делается.
Пока каждый вызывающий выводил путь сам, двое выводили его неверно, и первая
настоящая заявка на выпуск была отвергнута: исполнитель искал
`tools/build_release.py` рядом с собой. Снаружи установка при этом выглядела
работающей — юнит стоит, таймер идёт, очередь разбирается.

Доверие от этого не расширяется. Репозиторий доступен на запись обычной учётной
записи, но основание записал root, размещение (учётная запись, юнит, порт,
каталоги под `/srv`) по-прежнему берётся только из корневой копии реестра, а код
репозитория root не исполняет ни разу: сборка идёт под учётной записью сайта, а
root получает готовый файл и сверяет у него коммит и digest. Дерево с
несохранёнными изменениями не выкладывается вовсе.

## Происхождение выпуска

Перед каждой выкладкой исполнитель доказывает у GitHub связку целиком:

    разрешённый репозиторий (из реестра, ключом -R)
      -> разрешённая ветка (registry.ВЕТКИ_ВЫПУСКА)
        -> точно этот коммит (headSha == commit заявки)
          -> завершённый успешный прогон (status/conclusion)

Выпадение любого звена — отказ. Невозможность спросить — тоже отказ: раньше
здесь возвращалось `checked: false`, и выпуск шёл дальше, то есть результат
выглядел одинаково и когда происхождение доказано, и когда его не спросили.
Отказ наступает ДО взятия замка и до единой операции над витриной.

У root нет входа в `gh`, поэтому токен приходит юниту от systemd:

    sudo bash automation/host/install-gh-credential.sh            # ввод без эха
    sudo bash automation/host/install-gh-credential.sh --from-file <путь>
    sudo bash automation/host/install-gh-credential.sh --check    # только проверить

Нужен fine-grained personal access token владельца `sbc-create`, Only select
repositories — только `site-*` из реестра, права Repository permissions:
Actions **Read-only** и Metadata **Read-only**. Больше ничего: токен на запись
дал бы службе менять то, что она проверяет.

Проверка доступа идёт **из контекста службы** (`systemd-run` с тем же
`LoadCredential` и тем же кодом), а не из оболочки владельца: успешный `gh` у
подающей стороны ничего не говорит о службе — у неё другой пользователь, другой
HOME и другой источник учётных данных. Установка различает два исхода явно:
«ГОТОВ К ВЫПУСКУ» (код 0) и «УСТАНОВЛЕН, ВЫПУСК ЗАБЛОКИРОВАН» (код 3).

Подтверждённая ручная активация (`factory cell activate --confirm-activation`)
закрыта: она исполняла сценарий репозитория от root и не спрашивала GitHub ни о
чём. Выпуск идёт через очередь.

## Теневые конфигурации nginx

    bash automation/host/nginx-shadow-configs.sh          # показать
    sudo bash automation/host/nginx-shadow-configs.sh --fix  # убрать из загрузки

В `nginx.conf` стоит `include /etc/nginx/sites-enabled/*` — без фильтра по
расширению. Резервная копия, оставленная рядом с рабочей конфигурацией,
загружается как вторая конфигурация: те же `server_name` на тех же портах,
`conflicting server name` в журнале и маршрут из копии на расстоянии одной
буквы в имени файла. Сценарий переносит такие файлы в `/var/backups`, сохраняя
содержимое, и возвращает их, если `nginx -t` не прошёл.

Менять `*` на `*.conf` нельзя: в `sites-enabled` лежит `000-default-deny` без
расширения, и такая «починка» выключила бы запрет по умолчанию.

Копии, которые снимает `wire-nginx-upstream.sh`, лежат вне `/etc/nginx`, и это
проверяется в самом сценарии.

на подтверждение, и задача, о которой не подтверждена доставка, переданной не

## Открытые ограничения

| Ограничение | Что именно не проверено | Что нужно, чтобы снять |
| --- | --- | --- |
| `REMOTE/CI=NOT_RUN` | Настоящий remote проекта сайта не создавался, CI не запускался. Шаблон `.github/workflows/release.yml` сгенерирован и разбирается. | Пространство Git-проектов для сайтов и права на создание репозиториев в нём. Чужие учётные данные не извлекаются. |
| `CROSS_HOST_TEST=NOT_RUN` | Перенос проверен между двумя каталогами одной машины. Межсерверный перенос не проверялся. | Адрес и параметры целевого сервера, штатный SSH-доступ. |
| `DNS_SWITCHED=NO` | Переключение домена не выполнялось и в пилот не входит. | Выбранный домен, согласованное окно, путь отката. |
| `LIVE_SEO=NOT_RUN` | Проверен контракт владения полями и доставка. Живая публикация через боевой SEO-процесс — нет. | Доступ к действующему SEO-процессу из изолированной среды. |
| `TOPVISOR=NOT_RUN` | Проект не создавался. | Учётные данные и разрешение на платные операции. |
| Пул шаблонов исчерпан | Свободных шаблонов нет: все четыре закреплены. Новый заказ получит `PoolExhausted`. | Пополнение пула — вход от владельца. |
| RAM пилота не измерялась | Витрина статическая, постоянного процесса сайта в пилоте нет. | Профиль сайта с работающим процессом. |
| `OS_LEVEL_ISOLATION=NOT_RUN` | Доказаны отдельные каталоги, отдельные базы и отказ при подмене `site_id`. Отдельный uid/gid, `LoadCredential` на сайт и ACL — не делались. | Решение владельца о модели прав на целевом сервере. Менять права действующих процессов в этом цикле запрещено. |

## Что нужно перед фактическим переключением

Выбранный домен; адрес и параметры нового хоста; штатный SSH-доступ;
подтверждённое окно краткой паузы записи; способ маршрутизации; путь отката с
сохранением новых записей. Пароли и приватные ключи в переписку не передаются —
только `secret_ref`.
