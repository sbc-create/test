# Вход исполнителя домена

Первое действие сессии, которая будет что-то менять по конкретному сайту.
Без инструктажа работа не начинается: правила семейства и запреты по домену
нельзя угадать, а ошибка на чужих условиях (контроль опыта, закреплённый
шаблон, запрет продвижения) дороже любой сэкономленной минуты.

```bash
python3 automation/local/brief.py --list                    # кто активен и на каком этапе
python3 automation/local/brief.py --domain <домен>          # три уровня + следующий шаг
python3 automation/local/brief.py --domain <домен> --short   # только сводка
```

Коды возврата: `0` — три уровня выданы; `1` — домен не активен или ожидает
замены; `2` — уровень знаний отсутствует, работать нельзя.

## Что обязательно сделать после инструктажа

1. **Взять задачу из очереди домена** (`config/domain-queues/<домен>.json`), а
   не придумать свою. Порядок выбора работы — `docs/knowledge/NETWORK.md`, §6.
2. **Не брать занятую задачу**: состояние `подготовлено` или `проверено`
   означает, что её кто-то ведёт.
3. **Записать результат в очередь и в паспорт**: состояние
   (`исследовано → подготовлено → проверено → опубликовано → эффект измерен`),
   доказательство, дату. Коммит и зелёный тест — это «подготовлено».
4. **Заблокированную задачу назвать блокером** (`blocked_by`) и взять
   независимую задачу другого домена, а не ждать.

## Перед тем как завести задачу из исследования

```bash
python3 automation/local/running-experiments.py
```

Задача, повторяющая гипотезу ДЕЙСТВУЮЩЕГО опыта, до вердикта не исполняется:
она ставится как «заблокировано» с названным вердиктом. Реестр опытов живёт в
копии-владельце, в своей копии его может не быть — 22.10 из-за этого были
заведены две задачи, нарушавшие правило канарейки, и ещё десять пришлось
пометить пересечением.

## Чего делать нельзя

* менять `config/active-domains.json` без задания владельца: это список из его
  задания, а не рабочая заметка;
* работать по домену из раздела `awaiting_replacement`;
* ослаблять защиту, схему или проверку ради удобства;
* выдавать коммит, текст или зелёный тест за опубликованный результат.

## Проверка самого инструктажа

```bash
python3 -m pytest tests/unit/test_brief_loads_knowledge.py -q
```

Проверки закрепляют обещанное заданием: у каждого активного домена есть все
три уровня, инструктаж их действительно выдаёт, а отсутствие уровня даёт
отказ, а не молчаливый пропуск.

## Готовый skill для установки владельцем

Каталог `.claude/skills/` закрыт для записи из сессии (deny-правило), поэтому
skill я не создаю, а передаю текстом. Это ОДНА операция владельца, после
которой исполнитель получает инструктаж командой `/site-brief`.

**Файл:** `.claude/skills/site-brief/SKILL.md`

```markdown
---
name: site-brief
description: Инструктаж исполнителя перед работой над доменом сети — общие правила сети, правила семейства, паспорт домена и следующий шаг очереди. Вызывать ПЕРВЫМ действием в сессии, которая будет что-то менять по конкретному сайту.
---

# site-brief

Первое действие исполнителя домена.

    python3 automation/local/brief.py --list
    python3 automation/local/brief.py --domain <домен>

Коды: 0 — три уровня выданы; 1 — домен не активен; 2 — уровень отсутствует.

Дальше — по `docs/SITE_BRIEF.md`: взять задачу из очереди домена, не брать
занятую, записать результат с доказательством, заблокированную назвать
блокером и перейти к независимой задаче другого домена.
```

**Проверка после установки:** в новой сессии `/site-brief yummyani.site`
обязан напечатать строку `=== ИНСТРУКТАЖ: yummyani.site ===` и этап домена.
Пока skill не установлен, тот же результат даёт прямой вызов
`brief.py` — механизм работает, короткой команды нет.
