## 1. Что уже работало до введения (прочитано 2026-10-08 ~11:00Z)

Источник — файлы юнитов в `/etc/systemd/system`, ссылки включения в
`timers.target.wants`, отметки срабатывания `/var/lib/systemd/timers/stamp-*`
и журнал моста MCP. `systemctl` профилем недоступен, поэтому всё — чтением файлов.

**Почасового SEO-анализа на этой машине нет.** Таймеров с часовым периодом
SEO-назначения нет, `/etc/cron.hourly` пуст. Почасовая активность видна только
в журнале моста: за сутки до 2026-10-08 11:10Z — 138 обращений, из них 10 на
часовой сетке (±2 мин), владельцы аренд `seo-analysis-2026-10-06/07/08`,
`seo-audit-*`. Это сессии исполнителя Qwen: его планировщик живёт на
`srv-qwen`, которого нет в `inventory/` (подробно —
[`EDITOR_SCHEDULER_20261006.md`](EDITOR_SCHEDULER_20261006.md)). Прочитать его
расписание отсюда нельзя; повторные проверки исключаются разделением
ответственности (§3) и пунктом MOD-16.

## 2. Расписание (UTC; МСК = UTC + 3)

| время | что | бюджет | запросов к сайтам |
| --- | --- | --- | --- |
| 05:00 ежедневно | `analytics-cabinet` — снимок Метрики | — | API Метрики |
| 05:25, 11:25, 17:25, 23:25 | `seo-regular-check` — короткая проверка | 420 с | ≤ 120 (2 на домен + новые публикации) |
| пн 05:32 | `seo-regular-weekly` — приоритеты и оценка изменений | 300 с | ≤ 20 |
| 05:40 ежедневно | `seo-regular-daily` — анализ и **один** отчёт владельцу к 09:00 МСК | 840 с | ≤ 400 (sitemap, цели заданий) |

Проверка каждые 6 часов не обходит сеть: главная и `robots.txt` каждого домена
плюс публикации, текст которых изменился с прошлой проверки. Sitemap и цели
заданий проверяются раз в сутки.

**Задержка аналитики.** Снимок появляется раз в сутки и покрывает «7 дней до
вчера». Поэтому:

* повторное чтение того же снимка не считается наблюдением — у каждого домена
  хранится отпечаток значений, отдельно для проверки и для суточного прогона;
* неделя сравнивается со снимком D-7, окна которого не перекрываются;
  соседние суточные снимки перекрываются на шесть дней из семи и как
  «изменение» не используются;
* снимок старше 30 часов называется `STALE`.

## 3. Ответственность: SEO-исполнитель и редактор

| действие | SEO-исполнитель | редактор |
| --- | --- | --- |
| проверка сайтов, индексации, sitemap, аналитики | **да** (seo-regular) | нет |
| регистрация редакционного задания (`editorial_queue_register`) | **да**, один адрес — одно задание | нет |
| поиск и состояние (`editorial_queue_find/status`) | да | да |
| взять задание (`editorial_queue_next`) и закрыть (`editorial_queue_result`) | **нет** | **да** |
| подготовка и публикация текста | нет | да |
| проверка фактического результата публикации на сайте | **да** (каждые 6 ч, после правки текста) | нет |
| оценка изменения по исходным показателям | **да** (еженедельно) | нет |

Конкурирующих заданий на один адрес SEO-исполнитель не создаёт: перед
регистрацией — `editorial_queue_find` по абсолютному адресу. Сейчас правило
нарушается (MOD-10: 46 выдач SEO-владельцам за сутки); техническое закрепление
в контракте моста передано Архитектору —
[`handoff/SEO_TO_ARCHITECT-001.md`](handoff/SEO_TO_ARCHITECT-001.md).

## 4. Один отчёт, без двойных уведомлений

* Владельцу — **один** отчёт: `var/seo-regular/reports/daily/<дата МСК>.md`
  (и `.json`). Итог недели входит в ближайший суточный отчёт один раз.
* Проверка каждые 6 часов отчёта не пишет. Она уведомляет только о **новой
  критической** проблеме: юнит завершается кодом 3 (failed) — тот же канал, что у
  `site-factory-health`. Та же проблема на следующей проверке юнит не роняет.
* Отчёт `seo-content-operator-report` (yummyani.site, редакционные счётчики)
  остаётся источником для редакционного цикла; владельцу он не доставляется
  (`BLOCKED_NO_AUTHORING_CONFIG`). Канала доставки отчёта владельцу в проекте нет —
  это решение владельца (MOD-13).

Модуль ничего не публикует, не берёт задания, не меняет индексацию, nginx,
реестры и данные сайтов. Пишет только `var/seo-regular`. Секретов не получает.

## 6. Установка и подтверждение

Таймеры ставятся в `/etc/systemd/system`; у сессии агента нет root, поэтому
установка — одна команда владельца:

```bash
sudo bash /home/claude/wt-portable-site-cell-01/automation/host/install-seo-regular.sh --dry-run   # показать
sudo bash /home/claude/wt-portable-site-cell-01/automation/host/install-seo-regular.sh             # поставить
```

Подтверждение — без root, чтением:

```bash
python3 -m seo_operator.cli regular status
```

`confirmed: true` только когда таймеры установлены и включены **и** есть хотя бы
один завершённый запуск с `trigger = systemd-timer`. Ручные запуски выводятся
отдельно (`last_manual_run`) и расписание не подтверждают.

**Состояние на 2026-10-08:** таймеры подготовлены, не установлены — root у
сессии нет; `install-seo-regular.sh --dry-run` выполнен (exit 0). Запуска по
расписанию ещё не было, и утверждать обратное нельзя. Ручные запуски:

## 7. Откат

```bash
sudo systemctl disable --now seo-regular-check.timer seo-regular-daily.timer seo-regular-weekly.timer
sudo install -m 0644 /etc/systemd/system/analytics-cabinet.timer.before-seo-regular-<метка> /etc/systemd/system/analytics-cabinet.timer
sudo systemctl daemon-reload
```

Состояние `var/seo-regular` удалять не нужно: это журнал и история наблюдений.
