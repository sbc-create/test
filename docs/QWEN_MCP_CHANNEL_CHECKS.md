# Ограничения канала srv-qwen: исправление и разделение проверок

## Что было неверно

В первой редакции отчёта и скрипта стояло
`restrict,permitopen="127.0.0.1:9000",command="/bin/false"`. Строка выглядела
разрешающей, а канал по ней не поднялся бы: `restrict` выключает проброс
портов, а `permitopen` его НЕ включает. Дословно по `sshd(8)` этого же хоста
(раздел AUTHORIZED_KEYS FILE FORMAT):

| опция | что говорит документация |
| --- | --- |
| `restrict` | «disable port, agent and X11 forwarding, as well as disabling PTY allocation and execution of ~/.ssh/rc» |
| `port-forwarding` | «Enable port forwarding previously disabled by the restrict option» |
| `permitopen="host:port"` | «Limit local port forwarding with the ssh -L option such that it may only connect to the specified host and port» |

То есть `permitopen` — ограничитель цели, а не выключатель запрета.

## Фактическая строка после исправления

    restrict,port-forwarding,permitopen="127.0.0.1:9000",command="/bin/false" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBdXYS9HsyXBfoYfC1fSpJGYkhQq2ap8y2Zcx+gXZ9AR site-factory-bridge@srv-qwen

Её собирает `automation/host/install-mcp-bridge-grant.sh`. После записи он
сверяет СМЫСЛ строки (ищет `restrict,port-forwarding,permitopen="…"`) и
останавливается, если `port-forwarding` потерялся: строка без него запрещает
тот проброс, который ей полагается разрешить.

Серверные ограничения не менялись — блок `Match User sfbridge` остался тем же.

## Отказ первого запуска у владельца и его причина

Запуск 2026-10-03 остановился на строке 44:

    install-mcp-bridge-grant.sh: line 44: КОРЕНЬ=/home/claude/wt-portable-site-cell-01:
    No such file or directory

Причина не в путях, а в ИМЕНИ переменной. Идентификатор bash —
`[A-Za-z_][A-Za-z_0-9]*`; кириллическое имя присваиванием не является, поэтому
строка разбирается как ЗАПУСК КОМАНДЫ `КОРЕНЬ=/home/...` и даёт `rc=127`.
`bash -n` такое пропускает: конструкция синтаксически законна — измерено
(`bash -n` даёт `rc=0` и на исходном, и на нарочно возвращённом дефекте).

Измерено на bash 5.1.16 этого хоста, что именно ломается:

| конструкция | с кириллическим именем |
| --- | --- |
| `ИМЯ=значение` | запуск команды, `No such file or directory`, `rc=127` |
| `for ИМЯ in …` | `not a valid identifier` |
| `${ИМЯ}` | `bad substitution` |
| `export ИМЯ=…` | `not a valid identifier` |
| `$ИМЯ` без скобок | МОЛЧА раскрывается в литерал `$ИМЯ` — худший случай |
| имя функции, ограничитель heredoc | bash принимает (dash — нет) |

Русский текст в комментариях, сообщениях, значениях, подстановках по умолчанию
(`${var:-нет}`) и в телах heredoc идентификатором не является: тела heredoc в
установщиках фабрики содержат Python, где unicode-имена законны. Проверка
отличает одно от другого и потому не требует переписывать документацию и
сообщения латиницей.

### Что могло выполниться до отказа — ничего

Выше строки 44 в скрипте только комментарии и `set -Eeuo pipefail`: ни одной
команды, меняющей состояние. Фактическое состояние хоста после отказа
(проверено 2026-10-03):

| цель установщика | состояние |
| --- | --- |
| `/etc/systemd/system/site-factory-mcp.service` | отсутствует |
| `/etc/ssh/sshd_config.d/20-site-factory-bridge.conf` | отсутствует (в каталоге только `01-hardening.conf`, `50-cloud-init.conf`, `60-cloudimg-settings.conf`) |
| `/var/lib/site-factory-bridge` | отсутствует |
| учётная запись `sfbridge` | отсутствует в `passwd` |
| `127.0.0.1:9000` | не слушает (`ConnectionRefusedError`) |

Копий `.bak.*`, созданных этим запуском, нет. Повторный запуск безопасен и
начинается с чистого состояния; идемпотентность и резервные копии сохранены
без изменений.

### Настоящая причина повтора: проверка была, её не запустили

`tests/unit/test_host_scripts_ascii.py` существовал до этой задачи и покрывал
`automation/host/*.sh` — то есть и сам установщик. Проверено возвратом дефекта:
на кириллическом имени он падает с `строка 56: 'КОРЕНЬ'`. Перед передачей
команды владельцу прогонялся только тест моста (`test_qwen_mcp_bridge.py`), и
дефект ушёл наружу при работающем механизме. В журнале того же теста это уже
четвёртый такой случай (№9, №10, №11, №14) — там же записано, что проверка,
запускаемая «когда вспомню», защитой не является.

Отсюда правило, которое дороже самого исправления: **команда владельцу не
отдаётся без прогона проверок тех скриптов, которые она запускает**:

    python3 -m pytest tests/unit/test_host_scripts_ascii.py \
                      tests/unit/test_install_mcp_bridge_grant.py -q

### Чем закрыто

| мера | где |
| --- | --- |
| все имена переменных и `for` — ASCII; логика, сообщения и комментарии не менялись | `automation/host/install-mcp-bridge-grant.sh` |
| исполнение установщика ЦЕЛИКОМ в песочнице: первый проход, повтор, отказ `sshd -t` | `tests/unit/test_install_mcp_bridge_grant.py` (5 проверок) |
| запрет не-ASCII идентификаторов — охват расширен с `automation/host` на ВСЕ скрипты репозитория (238 файлов), добавлены формы `${ИМЯ}`, `$ИМЯ`, `export ИМЯ=` | `tests/unit/test_host_scripts_ascii.py` |
| тот же дефект в `acceptance.sh` каталога прогона | исправлен (`ДОМЕН`→`DOMAIN`, `КАТАЛОГ`→`WORKDIR`, `ИНСТРУКЦИЯ`→`HANDOVER`, `код`→`RC`) |

Проверка исполнением сделана в песочнице: пути перенаправлены во временный
каталог, `systemctl`, `useradd`, `passwd`, `sshd`, `curl`, `id` подставные, а
суть установщика — `grep`, `install`, `cp`, `ssh-keygen`, запись файлов,
heredoc, резервные копии — работает по-настоящему. Подтверждено:

1. скрипт доходит до конца (`rc=0`), в выводе нет ни `No such file or
   directory`, ни `bad substitution`, ни `not a valid identifier`;
2. в список ключей попадает РОВНО ожидаемая строка с `port-forwarding`;
3. блок Match содержит все девять директив, а `sshd -t` вызывается ДО
   перезагрузки службы (порядок проверен по журналу вызовов);
4. повтор не создаёт дубликат, переписывает устаревшую редакцию строки и
   сохраняет чужой ключ; рядом остаётся `.bak.<метка>`;
5. при отказе `sshd -t` конфигурация возвращается из копии байт в байт и
   `systemctl reload` НЕ вызывается.

Проверка самой проверки: возврат одного имени в кириллицу оставляет `bash -n`
чистым и валит все пять тестов. Зелёный результат поэтому означает исполнение,
а не только разбор.

## Проверки, ВЫПОЛНЕННЫЕ в сессии фабрики

| проверка | как | результат |
| --- | --- | --- |
| семантика опций | `sshd(8)` этого хоста | `permitopen` не включает проброс; нужен `port-forwarding` |
| отпечаток присланного ключа | `ssh-keygen -lf` | `SHA256:AbTvnN9WdSN8elbkKJJG0WXoV/+rVgAL14af8JNCc3g` — совпал |
| синтаксис блока Match | `sshd -t -f` плюс A/B с нарочно испорченной директивой | мой блок принят (разбор доходит до загрузки root-ключа); испорченный даёт `Bad configuration option` на той же строке |
| **эффективная конфигурация для `sfbridge`** | `sshd -T -C user=sfbridge,host=srv-qwen,addr=83.237.185.70` с тестовой конфигурацией и СВОИМ ключом хоста | `allowtcpforwarding local`, `permitopen 127.0.0.1:9000`, `permitlisten none`, `permittty no`, `x11forwarding no`, `allowagentforwarding no`, `permittunnel no`, `allowstreamlocalforwarding no` |
| та же конфигурация для `claude` | то же | `allowtcpforwarding no` — разрешение канала другим учётным записям НЕ достаётся |
| HTTP моста | настоящий сокет на петле | `initialize`, `tools/list` (6 инструментов, пишущего нет), `system_readiness` (23 сайта, источник `config/site-cells.json`), `list_registered_sites` (`version 1`, отпечаток `4511cf3add1b3e88`) |
| синтаксис скриптов | `bash -n` | без замечаний |

Блок Match для расчёта эффективной конфигурации брался НЕ из копии, а из самого
скрипта установки: иначе проверялся бы текст, который на хост не поедет.

## Что осталось LIVE-приёмкой и почему

`ssh`-клиент запрещён профилем сессии фабрики (цели нет в
`inventory/ssh-hosts.yaml`), а закрытый ключ канала остаётся на `srv-qwen` и
переносу не подлежит. Поэтому проверки, требующие настоящего соединения,
выполняются ТАМ, где лежит ключ — готовым скриптом
`verify-channel-from-srv-qwen.sh` (каталог прогона):

1. настоящий HTTP через настоящий туннель: `initialize`, `/healthz`,
   `system_readiness`, сверка 23 сайтов и отпечатка `4511cf3add1b3e88`;
2. отказ для ДРУГОГО порта (`-L 127.0.0.1:22`);
3. отказ для ОБРАТНОГО туннеля (`-R`);
4. отказ оболочки, выполнения команды и PTY.

Запуск на srv-qwen после установки владельцем:

    sudo bash verify-channel-from-srv-qwen.sh

**НЕ ПРОВЕРЕНО** до этого запуска: фактический проброс по ключу и фактические
отказы по пунктам 2–4. Они зависят от конфигурации, которой на фабрике ещё
нет: юнит не установлен, `127.0.0.1:9000` не слушает, учётной записи `sfbridge`
не существует.
