## Почему это не лечится повтором

Установленная копия сценария несёт прежнюю редакцию, и у неё два измеренных
порока:

1. **вывод ansible уходил в `/dev/null`** — причина отказа уничтожалась самим
   сценарием, поэтому четверо суток отказов (19–22.10) не оставили ни строки
   диагностики;
2. **выход кодом 1 на первой же неудаче** — 22.10 отказ пришёл на `lords-10`, и
   остальные СЕМЬ витрин не обрабатывались вовсе, хотя комплекты для них были
   собраны и лежали рядом.

То есть повтор прежней редакции снова отдаст один отказ без причины и снова
лишит каталога семь исправных витрин.

### 4. Доставка

Команда доставки — та, которой пользуется суточный прогон; её вызов остаётся за
владельцем, потому что это единственный шаг, меняющий витрины.

Проверка результата **через содержимое и ревизию, а не через код возврата**:

```bash
python3 /home/claude/wt-nova-publish-memory-02/automation/local/k2-freshness.py
# ожидается: СВЕЖО у всех восьми, код 0
```

Если хотя бы одна витрина осталась «УСТАРЕЛО» — причина теперь НЕ уничтожена:

```bash
tail -40 /srv/site-factory/k2-delivery/var/k2-data/last-copy-failure.log
```

      /srv/site-factory/k2-delivery/automation/local/k2-deliver-catalog.sh

Откат возвращает ровно прежнее поведение и ничего не теряет: сценарий не
хранит состояния, комплекты лежат отдельно в `var/k2-data`.

## Чего этот блок НЕ делает и не обещает

* **не открывает индексацию** восьми витрин: у них `open_authorized: false` и
  `X-Robots-Tag: noindex, nofollow` — проверено, и это ожидаемое состояние по
  решению владельца (D209), а не находка;
* **не включает таймер доставки** — отдельное решение;
* **не трогает реестр ячеек**: сведение копий остаётся открытым вопросом
  (MOD-137), и слияние реестров открыло бы K2 для автоматических выпусков, что
  запрещено;
* **не обещает, что доставка пройдёт**. Исправленная редакция гарантирует
  другое: причина отказа сохранится, а отказ одной витрины не лишит каталога
  остальных. Это условие для разбора, а не сам разбор.
