# Обязательные проверки: что падает, чьё это и что с этим делать

Обязательная проверка одна — `Verify (schemas, lint, tests)`, она же
`scripts/verify.sh`, восемь стадий. Этот документ называет каждое падение, его
владельца и способ воспроизвести вывод, а не пересказывает его.

**Ничего не отключено и не ослаблено.** Ни одна стадия не пропущена, ни одна
проверка поведения не смягчена, ни один тест не удалён и не помечен `skip`.
Выпуск не объявляется успешным на том основании, что базовая ветка падает так
же: ниже прямо сказано, что мешает зелёному прогону и кто это снимает.

---

## 1. Важное про то, ЧТО проверяет CI

Рабочий процесс запускается по событию `pull_request`. GitHub проверяет не
вершину ветки, а **слияние вершины ветки с базой PR** — здесь это
`claude/portable-site-cell-01`. База движется: за время работы она ушла вперёд
на 34 коммита двумя порциями.

Практическое следствие: прогон CI может покраснеть или позеленеть без единого
коммита в моей ветке. Так и произошло — между двумя соседними прогонами
пропали пять падений аналитики и появилось одно падение линтера, хотя мой
коммит между ними трогал один файл песочницы.

Поэтому «какой прогон чей» определяется не номером прогона, а сверкой с базой.

### 2.1 `Lint (ruff)` — `factory/analytics/cli.py:134` SIM102

```
factory/analytics/cli.py:134:9: SIM102 Use a single `if` statement instead of
nested `if` statements
```

Пришло с базой в коммите `d53d370` («analytics: сплошной прогон не заводит
счётчики незапущенным доменам»). Воспроизведение:

```bash
git checkout --detach origin/claude/portable-site-cell-01
.venv/bin/python -m ruff check factory/analytics/cli.py
#   Found 1 error.
```

Мой файл — ни один; в моей ветке `ruff check` по всему дереву проходит.

**Владелец:** автор ветки `claude/portable-site-cell-01` (слой аналитики).
**Что нужно:** свести два вложенных `if` в один — правка механическая,
поведение не меняет:

```python
if (entry.get("counter_state") == "planned" and not entry.get("counter_id")
        and not поимённо):
```

Сам я в этот файл не вношу: он правится в чужой ветке прямо сейчас, и моя
правка стала бы конфликтом в чужой работе, а не помощью.

### 2.2 `test_cell_queue_executor.py::test_грязное_дерево_не_выкладывается`

```
factory.cell.privileged.PrivilegedRefused: zona-01: в источнике нет файлов
снимка ['zona-01-catalog.json', 'zona-01-details.json'];
половина снимка хуже прежнего целого
```

Тест проверяет отказ по грязному дереву, а падает раньше — на засеве
хранилища. `executor.активировать` вызывает `_засеять_хранилище` ДО проверки
`source_dirty` (строка 427 против 436), а тот идёт в `stage_snapshot`, если в
каталоге площадки не хватает файлов снимка.

**Тест зависит от состояния ХОСТА.** На этой машине он проходит, потому что
`/srv/zonafilm-space/data` наполнен настоящими снимками зоны и `нехватка`
получается пустой. На чистом бегунке нет ни площадки, ни общего каталога
производителя — и отказ наступает до того, что тест собирался проверить.

Воспроизведено на чистой вершине базы `03c0f21`
(`artifacts/evidence/lords-template-1.1.0/ci_repro.py`): подменяются ровно два
отличия бегунка — пустая площадка сайта и пустой общий каталог
производителя, — после чего база даёт тот же `PrivilegedRefused` дословно.

**Владелец:** тот же. **Что нужно:** тесту — свой каталог площадки и свой
общий каталог (`tmp_path`), чтобы он проверял то, ради чего написан, а не
наличие боевых данных на машине.

Моей ветки это не касается: `factory/cell/executor.py` она не меняет, а её
правки в `factory/cell/privileged.py` — только приведение к ruff
(`contextlib.suppress` вместо `try/except: pass`, слияние двух ветвей `if` с
одинаковым телом, порядок импортов, `X | None` вместо строкового аннотирования).
Ни одна не меняет поведения.

### 2.3 `test_site_engine_gate.py::TestSixLiveProfiles::test_every_live_profile_passes`

Профили `animedia-01`, `animedia-02` и другие не проходят
`site-package.schema.json`: в них поля `backup_policy_ref`,
`content_profile_ref`, `deployment`, `environment`, `family`,
`lifecycle_state`, `monitoring_profile_ref`, `registry_note`, которых схема не
допускает. Ни одного профиля Lords в списке нет.

Падает на чистой базе: полный прогон вершины `3c52b91` —
`6 failed, 4283 passed`, и это падение в шестёрке.

**Владелец:** владелец схемы пакета сайта и профилей Animedia.
**Что нужно:** согласовать схему с профилями — расширить схему или убрать поля.
Шаблон Lords здесь ни при чём, и ослаблять схему ради зелёного прогона нельзя
(правило 4 репозитория).

## 3. Что дал мой вклад: сверка с базой

Одинаковой командой (`.venv/bin/python -m pytest tests/ -q`), на одной машине:

| Дерево | Итог |
| --- | --- |
| база `3c52b91` | 6 упало, 4283 прошло, 16 пропущено |
| моя ветка после слияния с ней | 7 упало, 4393 прошло, 16 пропущено |

Плюс 110 прошедших проверок — это мои. Шесть падений базы — её же.
Седьмое в моём прогоне — `tests/operator/test_factory_bridge.py::
TestPortfolioView::test_view_reads_the_real_factory_packages`; в прогоне CI
его нет, а в другом местном прогоне вместо него оказался

одного рода с 2.2: читают состояние машины (пакеты фабрики, исходный текст

одного только моего кода: `tests/unit/test_lords_*.py`,
`test_cell_delivery_guards.py` и `test_lords_template_single_source.py`

**Своих падений у ветки нет.** Единственное, что нашлось за мной,

активации на его собственной фикстуре-заглушке `'{}'`. Исправлена фикстура —
проверка осталась строгой.

## 4. Почему «21» и «59» — это не одно и то же число

В отчёте первого захода стояло 21 падение в CI и 59 на машине. Расхождение
объясняется не нестабильностью, а тем, что сравнивались разные прогоны.

| | CI | тот местный прогон |
| --- | --- | --- |
| команда | `.venv/bin/python -m pytest tests/ -q` | `python3 -m pytest tests/unit -q` |
| что собирается | всё дерево `tests/` | только `tests/unit` |
| интерпретатор | `.venv` с `requirements.txt` | системный, без части зависимостей |
| `webauthn` | установлен | **нет модуля** |
| `/srv` боевого хоста | отсутствует | присутствует и наполнен |
| Python | 3.11 | 3.10 |

Главный вклад — интерпретатор: в системном нет `webauthn`, и каждый тест,
который его импортирует, падает на импорте. Второй — состав: `tests/unit` это
не всё дерево. Третий — хост: раздел 2.2 показывает падение, которое на этой
машине НЕ воспроизводится, и обратные случаи тоже есть.

Вывод, который из этого следует: сравнивать можно только одинаковые команды на
одинаковых деревьях. Все числа в разделе 3 получены именно так.
