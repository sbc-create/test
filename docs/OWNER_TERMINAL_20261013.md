# Пакет владельца на 13 октября: один терминальный блок

Всё, что требует root, собрано здесь. Команды идут **по порядку**, каждая
печатает ожидаемый результат, и у каждой назван откат. Блок составлен так, чтобы
его можно было вставить в терминал сервера целиком; если удобнее по шагам —
шаги независимы в тех местах, где это сказано прямо.

**Каталог для всех команд:**

```bash
cd /home/claude/wt-portable-site-cell-01
```

Это дерево службы. Шаги 0 и 2 работают именно с ним: цифра состава посчитана по
его содержимому. Запускать из другого каталога не нужно — пути внутри
инструментов абсолютные, но `cd` убирает двусмысленность.

**Остановка на первой ошибке.** Если вставляете блок целиком, включите её:

```bash
set -euo pipefail
```

Без этого неудачный шаг не остановит следующие, а это именно то, чего здесь
нельзя: шаг 2 ставит код, который шаг 1 должен был подготовить.

## Шаг 0. Подтвердить состав устанавливаемой версии

```bash
python3 automation/host/executor-update-plan.py --expect 06f74262107c
```

**Ожидаемо:** код 0 и последняя строка

```
состав совпадает с закреплённым (06f74262107c): подтверждён, установку можно начинать.
```

Выше неё — что именно изменится: **13 файлов к обновлению, 3 к добавлению**.
Отдельной строкой план сообщает про **9 файлов, не прочитанных этой учётной
записью** (`config/site-cells.json` и его копии под root 0600) и называет это
пределом измерения, а не совпадением. Под `sudo` список прочитается целиком:

```bash
sudo python3 automation/host/executor-update-plan.py --expect 06f74262107c
```

Если под `sudo` план покажет больше изменений — **это правильный исход**, а не
сбой: значит в составе есть файлы, которые моя учётная запись не видит. Пришлите
вывод, состав подтвердится заново.

**Если цифра не совпала:** план откажет с кодом 1 и напечатает новую цифру. Это
тоже правильный исход. Ничего не устанавливайте, пришлите вывод — между
проверкой и установкой состав изменился, и установка шла бы вслепую.

**Откат:** шаг 0 ничего не меняет. Отката не требует.

## Шаг 2. Обновить установленную копию исполнителя

Сначала показ, потом установка. Между ними ничего не меняйте в дереве: цифра
состава из шага 0 относится к тому, что показал `--dry-run`.

```bash
sudo bash automation/host/install-cell-executor.sh --dry-run
sudo bash automation/host/install-cell-executor.sh
python3 automation/host/executor-update-plan.py --expect 06f74262107c
```

**Ожидаемо:** после установки план печатает **0 файлов к обновлению**. Это и есть
приёмка шага: не «сценарий отработал без ошибки», а «расхождения между деревом и
установленной копией больше нет».

**Откат:** сценарий переносит прежнюю копию в `/usr/local/lib/site-factory-cell.prev`
— **и удаляет прежний `.prev` перед этим** (`rm -rf "$DEST.prev"`, затем
`mv "$DEST" "$DEST.prev"`).

Состояние на 06:20 МСК: установленная копия от **12.10 20:25**, а `.prev` хранит
копию от **10.10 19:56**. То есть шаг 2 заменит `.prev` копией от 12.10 — это и
есть правильная цель откатa, но **копия от 10.10 будет потеряна**. Если она
нужна, отложите её до шага 2:

```bash
sudo cp -a /usr/local/lib/site-factory-cell.prev /usr/local/lib/site-factory-cell.20261010
```

Возврат к копии, которая была до шага 2:

```bash
sudo systemctl stop site-cell-executor.timer
sudo rm -rf /usr/local/lib/site-factory-cell
sudo mv /usr/local/lib/site-factory-cell.prev /usr/local/lib/site-factory-cell
sudo systemctl start site-cell-executor.timer
```

## Шаг 3. Убрать из загрузки nginx копии конфигураций

```bash
bash automation/host/nginx-shadow-configs.sh
sudo bash automation/host/nginx-shadow-configs.sh --fix
```

Первая команда только показывает. Вторая переносит копии в `/var/backups` с
сохранением исходного пути, выполняет `nginx -t` **до** reload и, если проверка
не прошла, возвращает файлы на место сама.

**Ожидаемо:** показ (первая команда, проверено 06:20 МСК, код 0) называет
**четыре копии**, все из семейства Yummy:

```
/etc/nginx/sites-enabled/yummyani.biz.conf.bak.20260910T093711Z
/etc/nginx/sites-enabled/yummyani.org.conf.bak.20260910T0940Z
/etc/nginx/sites-enabled/yummyani.site.conf.bak.20260910T0940Z
/etc/nginx/sites-enabled/yummyani.site.conf.bak.cr06.20260920T203413Z
```

После `--fix` — `nginx -t` без строк `conflicting server name`.

Отдельной строкой показ сообщает про `/etc/nginx/conf.d/lords.conf`: «не
читается, ветка не проверена». Это предел измерения моей учётной записи, а не

**Откат:** файлы лежат в `/var/backups` с исходным путём в имени; возврат —
копирование обратно и `nginx -t` перед reload. Содержимое копий не менялось.

## Шаг 5. Развести www-зеркала и основные хосты (четыре домена)

**Шаг независим от остальных.** Касается `an1meg0.site`, `lordserials22.info`,
`zonafilm12.site`, `zonafilm.cc`: сейчас www отдаёт сам сайт с кодом 200,
`canonical` на www-хост и открытой индексацией — то есть второй сайт с тем же
содержимым.

```bash
python3 automation/host/www-redirect/check-server-names.py
python3 automation/host/www-redirect/apply-www-split.py
sudo python3 automation/host/www-redirect/apply-www-split.py --apply --reload
python3 automation/host/www-redirect/check-server-names.py
```

Первая команда показывает исходное состояние: проверено 06:18 МСК — **код 1 и
все четыре файла названы**, с текстом «блок 443 всё ещё слушает www.… вместе с
основным именем». То есть проверка действительно умеет падать на неисправленном
состоянии, а не только подтверждать исправленное. Вторая показывает, что будет
сделано. Третья правит и перезагружает. Четвёртая — приёмка.

**Ожидаемо:** после правки `check-server-names.py` даёт **0 замечаний**.

**Почему это сценарий, а не `sed`.** У `zona-02.conf` **два** блока с одинаковой
строкой `server_name zonafilm.cc www.zonafilm.cc;` — порт 80 и порт 443. Из блока
80 имя `www.` убирать нельзя: именно он перенаправляет `http://www` на https.
Глобальная замена сломала бы это молча, замена по номеру строки — при следующей
правке файла. Сценарий выбирает блок по его `listen`; проверено на настоящем
содержимом (`zona-02.conf`: блок 80 сохраняет `www.`, блок 443 теряет) и
восемью проверками в `tests/unit/test_apply_www_split.py`.

**Откат:** сценарий делает копию каждого файла (`*.bak-www-<отметка>`), а при
неудачном `nginx -t` возвращает все файлы сам и не перезагружает nginx. Ручной
возврат:

```bash
sudo cp /etc/nginx/lords/zona-02.conf.bak-www-<отметка> /etc/nginx/lords/zona-02.conf
sudo nginx -t && sudo systemctl reload nginx
```

## Шаг 6. Перенаправить http на https (девять домéнов, B020)

**Шаг независим от остальных.** Девять домéнов отдают сайт по http с кодом 200 —
то есть два адреса одной страницы. Измерено мной 13.10 ~05:20 МСК независимо от
замера SEO-сессии, результаты совпали:

```
отдают по http (200, перехода нет): 9
   animedia.icu  animedia.space  an1meg0.site  lordserials22.info
   yummyani7.site  yummyani7.info  zonafilm.space  zonafilm.cc  zonafilm12.site
переходят на https: 8   (301 или 308)
не измерено: 4   домены не разрешаются в DNS (в паспорте они planned)
```

`canonical` на https на этих страницах есть, поэтому дубль смягчён, но http-версия
обходится и отдаётся.

**Инструмент уже написан и ждёт применения** — работы тут нет, есть решение:

```bash
python3 automation/host/http-redirect-install.py --dry-run
sudo python3 automation/host/http-redirect-install.py --apply
python3 automation/host/http-redirect-install.py --dry-run
```

**Ожидаемо:** показ печатает «изменилось бы файлов: 9, отказов: 0» (проверено
05:20 МСК), после применения тот же показ даёт 0 файлов к изменению.

Правка повторяет образец тех восьми, где перенаправление уже стоит (`lords-01`):
в блоке `:80` тело `location /` заменяется на
`return 308 https://$host$request_uri;`. Путь ACME
(`location ^~ /.well-known/acme-challenge/`) **не трогается и проверяется до
правки** — «перенаправлять всё подряд» сломало бы продление сертификата; если
пути ACME в блоке нет, инструмент отказывает, а не правит. Блоки `:443`, TLS,
upstream и заголовки не затрагиваются.

**Откат:**

```bash
sudo python3 automation/host/http-redirect-install.py --rollback
```

Возвращает файлы из копий, снятых этой же правкой.

**Проверка результата** (своя, не доверяя инструменту правки):

```bash
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' http://zonafilm.space/
```

Ожидаемо: `308 https://zonafilm.space/`.

**Отдельно и НЕ в этом шаге: HSTS.** Его отдаёт только `yummyani.site`
(`max-age=31536000`), у остальных 16 его нет. HSTS необратим на срок `max-age` —
браузер запомнит требование https и не станет слушать обратное. Это отдельное
решение владельца, и в один шаг с перенаправлением его складывать нельзя:
перенаправление откатывается одной командой, HSTS — нет.

## Шаг 8. Решение владельца: сеть до API Яндекс.Вебмастера

**Это единственная причина, по которой у нас нет опережающего признака по
индексации.** 85 показателей из 140 неизмеренных — это пять метрик Вебмастера
(`pages_in_search`, `excluded_pages`, `external_links`, `technical_issues`,
`popular_queries`) по семнадцати витринам.

Причина измерена, а не предположена (13.10, 06:10 МСК / 03:10Z):

```
api-metrika.yandex.net     имя разрешается (87.250.251.47, 2a02:6b8::2a3)
                           TCP 443 — соединение есть, ответ 404 на пустой GET
api.webmaster.yandex.net   имя разрешается (213.180.193.61, 2a02:6b8::2:61)
                           TCP 443 — СОЕДИНЕНИЕ НЕ УСТАНАВЛИВАЕТСЯ, таймаут 10,2 с
переменных прокси в окружении нет (HTTPS_PROXY, HTTP_PROXY, NO_PROXY не заданы)
```

То есть **имя разрешается, а порт 443 не отвечает** — это не отсутствие доступа
и не ошибка в токене: сборщик честно пишет «webmaster: сеть недоступна
(URLError). Повторы исчерпаны». Метрика по той же сети работает, и её 301
показатель измерены.

**Действие владельца:** открыть исходящее соединение до
`api.webmaster.yandex.net:443` (или назвать маршрут, через который его следует
делать). Сам я этого не касаюсь: изменения firewall и DNS вне manifest запрещены
правилами фабрики, и правильно запрещены.

**Проверка после:**

```bash
curl -sS -o /dev/null -m 20 -w '%{http_code}\n' https://api.webmaster.yandex.net/
```

Любой код ответа вместо `000` означает, что путь открыт; дальше сбор проверяется
штатно:

```bash
python3 automation/local/analytics-freshness.py
```

Ожидаемо: `ИСТОЧНИК_НЕДОСТУПЕН` падает с 85 до нуля, а `pages_in_search`
появляется у семнадцати витрин. **Это и есть признак, которым измеряется
результат работы по картам сайта и внутренним ссылкам** — без него он виден
только по визитам и с задержкой обхода.

Отдельно: у четырёх домéнов Вебмастер **выключен в реестре аналитики осознанно**
— это не та же причина, и трогать их не нужно.

## Что проверить одной командой после шагов 1–6

```bash
python3 automation/local/delivery-state.py
```

Единый вид состояния доставки: **подготовлено → установлено → загружено
процессом → проверено в работе**. Ни одна стадия не выводится из предыдущей, и у
каждой свой источник: файл, установленная копия, `/proc/<pid>/stat` и артефакт
приёмки не старше кода. На момент сборки этого файла два компонента стояли
«установлено да, загружено **нет**» — это и есть шаг 1.
