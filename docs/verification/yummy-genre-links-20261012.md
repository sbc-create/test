# Yummy: жанры в карточке — что уже есть, что нужно и кто выпускает

Запись ночного цикла 12 октября. Пакет 2 требует установить реальную цепочку
сборки и доставки Yummy, владельца, привязку живого к исходникам и довести
подготовленный патч до разрешённого выпуска либо честно оставить статус
«не выложено».

## 1. Патч нужен ТРЁМ витринам из пяти, а не пяти

Измерено 12.10 около 03:10 МСК на живых карточках (`/anime/<слаг>`, переходы
пройдены):

| домен | карточку отдаёт | жанры в карточке | патч |
| --- | --- | --- | --- |
| yummyani.org | приложение Next.js | **ссылки есть**: `/catalog/genre/comedy`, `/drama`, `/fantasy` | не нужен |
| yummyani7.info | приложение Next.js | **ссылки есть**, те же три | не нужен |
| yummyani.site | приложение Next.js | текстом | нужен |
| yummyani.biz | приложение Next.js | текстом («Сёнен, Боевик, Фэнтези, Аниме») | нужен |
| yummyani7.site | приложение Next.js | текстом | нужен |

Это меняет характер работы: правка уже существует в каком-то образе, и речь о
**выравнивании трёх отстающих витрин на образ с готовым исправлением**, а не о
выпуске новой разработки. Слаги в существующих ссылках совпадают с тем, что
даёт патч (`canonicalGenreSlug` → `comedy`, `drama`, `fantasy`), то есть
контракт один.

## 2. Цель ссылок существует и работает

| адрес | ответ |
| --- | --- |
| `/catalog/genre/action` | 200, 24 тайтла, H1 «Аниме в жанре «Боевик»», self-canonical |
| `/catalog/genre/comedy`, `/drama` | то же |
| `/catalog/genre/boevik` (транслитерация) | 200, 0 тайтлов |
| `/catalog/genre/net-takogo-zhanra-12345` | 200, 0 тайтлов |

**Пустой слаг нормы §3 п.4 НЕ нарушает**, и это стоит сказать прямо, потому
что у Lords, Zona, Animedia и AnimeGo этот же класс пришлось закрывать кодом
404: у Yummy все разделы жанров отдают `noindex`, а норма запрещает
ИНДЕКСИРУЕМУЮ 200. Нарушений 0 из 15 проб на пяти витринах.

Из того же факта следует ограничение патча: разделы жанров закрыты от индекса
целиком, включая рабочий `action` с 24 тайтлами. Значит ссылки дают
навигацию и внутреннюю перелинковку, но не индексируемые landing-страницы.
Открытие разделов — отдельное решение: по §3 п.1 для индексируемости нужны
подтверждённое назначение, уникальное содержимое, self-canonical и внутренние
ссылки, и менять режим индексации можно только с действующим разрешением
владельца для точного домена и штатным writer.

## 3. Живое состояние: у Yummy ДВЕ версии, а не одна

| домен | версия ячейки (заголовок) | карточку отдаёт |
| --- | --- | --- |
| yummyani.site | `2dbabffb9287-yummy-site` | приложение |
| yummyani.org | `936a4eb4f909-yummy-org` | приложение |
| yummyani.biz | `de6a07b702d9-yummy-biz` | приложение |
| yummyani7.site | `69fb5cd571cf-yummy-07` | приложение |
| yummyani7.info | `cfc852f445b3-yummy-08` | приложение |

Заголовок `x-site-factory-build-id` — версия ЯЧЕЙКИ, то есть Python-слоя
(`var/site-repos/yummyani-*/src/yummy-frontend.py`), который проксирует в
`LORDS_LEGACY_UPSTREAM`. Карточка приходит из ОБРАЗА приложения, и журнал
исполнителя о его версии не знает ничего. Поэтому «живой build» у Yummy
двусмыслен без уточнения слоя, и приёмка ячейки не доказывает версию
карточки. Главная страница отдаётся ячейкой, карточка — приложением.

## 4. Цепочка сборки и доставки, владелец

По сведениям сессии Yummy (`wt-portable-site-cell-01-f7`, состояние на 01.10;
позже она не проверяла):

* образ собирается **вручную на хосте**, не в CI: `deploy/staging/deploy.sh`
  из `sbc-create/yummyani`, `compose build web-build` с `GIT_REVISION=HEAD` и
  сверкой метки `org.opencontainers.image.revision` с HEAD. Запуск из чистого
  worktree: `REPO=<worktree> DEPLOY_SERVICES=web-site bash
  deploy/staging/deploy.sh <sha>`. Перед пересозданием контейнеров —
  indexability-preflight, проверка учётных данных, бэкап трёх БД, теги
  откката; после — health и `verify.sh`;
* тег `:staging` остаётся подвижным, но витрины на него не смотрят: каждая
  закреплена на неизменяемом `yummyani/web:rel-<12 знаков sha>` через
  `WEB_SITE_IMAGE` / `WEB_ORG_IMAGE` / `WEB_BIZ_IMAGE` в
  `runtime/compose.vars`. На 01.10: site → `rel-054c6170519d`, org →
  `rel-8be8d8b5bdf2`, biz → `rel-4c5796eae24c`;
* `yummyani7.site` и `yummyani7.info` — **другой стек** (`/srv/sites/yummyani7-*`),
  и его сессия Yummy не смотрела;
* база для `web-site` — текущая живая ревизия, не ниже `054c617`, иначе
  пропадёт исправление «Актуального». Один образ на три витрины подтянет
  чужие изменения: у каждой своя линия коммитов.

## 5. Статус выпуска: не выложено, и почему

Сессия Yummy выкладывать отказалась: её пользователь этого не поручал, а
выкладка на живой домен — решение владельца, а не просьба соседней сессии.
Отказ правильный, и обходить его я не пытался.

Своим механизмом выложить не могу: операции GitHub вне профиля моей сессии,
docker и стек Yummy — чужая область, а правка HTML на лету в прокси ячейки
отвергнута по существу: разметка разошлась бы с RSC-нагрузкой и гидратацией, и
моя же мера показывала бы «исправлено» там, где не исправлено.

Отдельно: в реестре ячеек пять витрин Yummy — отдельные ячейки со своими
репозиториями, и защита фабрики (`registry.require_not_extracted`) отказывает
публикации через общий путь монорепо. Так что выкладка возможна только
механизмом Yummy, и это отказ кода, а не осторожность.

**Статус: патч готов, путь выпуска определён, исполнитель ждёт решения
владельца. Нужен трём витринам из пяти.**

## 6. Что проверю после выкладки

По каждому выложенному домену: ссылка в HTML карточки, переход, состав
раздела, его canonical и метаданные, и отдельно — что ячейка и приложение
назвали свои версии. Команды и пробы — в черновике сессии; инструмент замера
разделов работает по слагам из разметки самой витрины, а не по придуманным.
