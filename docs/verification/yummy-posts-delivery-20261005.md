Разработка — ветка `claude/yummy-posts-delivery-01` и отдельный worktree
`/home/claude/wt-yummy-posts-delivery-01`; чужие рабочие ветки не
переключались. Доставка исправления — влитием в `claude/indexing-operation-02`

## 2. Причина — доказана, а не предположена

**Монтирование ОДНОГО ФАЙЛА привязано к inode на момент создания контейнера, а
издатель заменяет файл атомарно (`os.replace`), получая НОВЫЙ inode. Контейнер
навсегда остаётся на прежнем.**

Три независимых подтверждения:

1. **inode расходятся** — 3356117 на хосте против 3356113 в контейнере
   (таблица выше). Это прямой признак оторвавшегося монтирования, а не
   «другого содержимого».
2. **тот же каталог, смонтированный КАТАЛОГОМ, показывает актуальный файл.**
   Внутри контейнера:

       /app/content/editorial-posts.json           22 025 Б   Oct 5 09:24
       /app/content/overlays/editorial-posts.json  23 715 Б   Oct 5 16:04

   Один и тот же файл хоста: по файловому монтированию — старый, по
   каталоговому — новый. Значит дело в форме монтирования, а не в содержимом,
   правах или пути.
3. **воспроизведено в изоляции** на своём контейнере `alpine` (ни одного
   обращения к производственным контейнерам):

       хост до запуска        inode=265757 size=32
       контейнер видит        inode=265757  {"posts":["first"]}
       после os.replace       хост inode=266098 size=41
       контейнер видит        inode=265757  {"posts":["first"]}   <- отстал
       после docker restart   inode=266098  {"posts":["second","third"]}
       после записи НА МЕСТЕ  inode=266098  {"posts":["fourth"]}  <- без перезапуска

Остальные подозреваемые проверять не потребовалось: содержимое НЕ совпадает, и
расхождение объяснено целиком. Схема записи, фильтрация `published`, разбор
слага, маршрут и nginx работают — это видно по тому, что существующие 12
записей отдаются (`/posts/raspisanie-i-obnovleniya` → 200), а
`/posts/100kano-radio-57` отсутствует ровно потому, что приложение этой записи
не видит.

## 3. Постоянное исправление

### Запись НА МЕСТЕ вместо замены файла

`factory/qwen/posts.py::_записать_сохранив_inode` — один `pwrite` полного
содержимого по смещению 0, без `os.replace` и без усечения. Короткое
содержимое дополняется ХВОСТОВЫМИ ПРОБЕЛАМИ (JSON их допускает), поэтому
размер файла монотонно не убывает.

Почему именно один `pwrite`, а не `ftruncate` + `write`: читатель приложения
кэширует по `mtime` и на негодном JSON **возбуждает исключение**
(`editorialFileSchema.parse` без запасного значения, прочитано в
`src/modules/editorial/editorial-post.ts` работающего образа). Между
`ftruncate` и `write` читатель увидел бы пустой файл и потерял бы раздел
целиком. Один `pwrite` на ext4 идёт под `i_rwsem` и для читателя неделим.

Это НЕ перезапуск, временно показывающий текущую запись: inode больше не
меняется, поэтому каждая следующая публикация Qwen доходит до контейнера сама.

### Диагностика доставки

`доставка_в_контейнер(s)` читает файл ВНУТРИ контейнера и сверяет размер,
отпечаток и inode. Фактический ответ на производстве (новым кодом):

    in_sync: false
    host:           {bytes: 23715, inode: 3356117, sha256: 1586951a04719122, posts: 13}
    container:      yummyani-staging-web-org-1
    mount_declared: true
    container_file: {bytes: 22025, inode: 3356113, sha256: 92e0948530b6feed, posts: 12}
    reason:  "монтирование оторвалось от файла: контейнер держит inode 3356113,
              на хосте 3356117..."
    remedy:  "однократная перепривязка: docker restart yummyani-staging-web-org-1.
              Дальше запись идёт НА МЕСТЕ и перезапуск больше не нужен"

Это поле добавлено и в `posts_status` (`delivery`), так что состояние больше не
может выглядеть исправным при оторвавшейся доставке.

## 4. Подтверждение результата исправлено

`publish_post` больше не называет записанное опубликованным:

* `подтвердить_публично` требует ДВА признака — код 200 на `/posts/<slug>` И
  ссылку на запись в разделе `/posts`. Страница может ответить 200 и не попасть
  в перечень; это разные утверждения;
* проверка ОГРАНИЧЕННАЯ: 4 попытки по 2 с. Бесконечное ожидание превратило бы
  отказ в зависание, одна попытка — редкую задержку в ложный отказ;
* исход операции несёт `written`, `public_confirmed`, `public` (код, попытки,
  причина) и `delivery` (сверка с контейнером);
* инструмент моста: `ok` = записано И подтверждено, плюс `next_action` с
  прямым «НЕ объявлять публикацию состоявшейся» и названной причиной;
* CLI: код 3 — «записано, но на странице НЕ подтверждено» (ровно тот случай,
  под который код 3 и объявлен), 2 — отказ, 0 — подтверждено;
* ветвь `nothing-to-do` тоже проверяет публично: «в файле уже есть» само по
  себе ничего не обещает.

## 5. Что осталось: одно действие владельца

Код влит, диагностика работает, тесты зелёные. Остаётся то, что фабрика
сделать не может: **перепривязать монтирование один раз и перезапустить службу
моста, чтобы новый код начал исполняться.**

    sudo docker restart yummyani-staging-web-org-1 && sudo systemctl restart site-factory-mcp.service

Почему обе половины нужны, и почему именно по одному разу:

* `docker restart yummyani-staging-web-org-1` — монтирование одного файла
  устанавливается при создании пространства имён контейнера, поэтому
  перезапуск связывает его с ТЕКУЩИМ inode (3356117, 13 записей). Этим же
  действием уже созданная Qwen запись становится публичной. Затрагивается
  ровно один контейнер — тот, что обслуживает yummyani.org; остальные четыре
  витрины Yummy работают в своих контейнерах. Недоступность — секунды на старт
  Next.js;
* `systemctl restart site-factory-mcp.service` — служба моста загрузила модуль
  новостей при старте, то есть СЛЕДУЮЩАЯ публикация Qwen без перезапуска пошла
  бы прежним кодом и снова заменила бы файл, оторвав монтирование. Без этой
  половины исправление не вступает в силу.

`systemctl` профилю сессии запрещён, поэтому команда целиком — владельца;
единственный исполнитель этого производственного изменения — он, чтобы два
писателя не пришли в одну площадку одновременно.

После этого публикации Qwen доходят сами: запись идёт на месте, inode не
меняется, перезапусков больше не требуется.
