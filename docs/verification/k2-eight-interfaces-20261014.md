## Код в бандлах соответствует проверенному

Доставка кода на узел идёт бандлами, а бандл — файл: он продолжает выглядеть
свежим после новых коммитов. Поэтому сверка не по записи, а по самим файлам:

```
$ python3 automation/local/k2-bundle-freshness.py        # код выхода 0
lords-10  c7dd85eeb24e бандл несёт текущий код
… (все восемь)
запись: var/k2-data/bundle-heads.json
```

Головы совпадают с коммитами из таблицы выше — то есть доставке подлежит ровно
тот код, который осмотрен браузером. Прежняя запись `bundle-heads.json`
называла головы, собранные ДО сегодняшних правок интерфейса, и читалась как
доказательство, не будучи им; теперь её пишет только измерение.

## Путь репозитория в реестре приведён к относительному

В общем `config/site-cells.json` у восьми ячеек стоял АБСОЛЮТНЫЙ путь одного
рабочего дерева (`/home/claude/wt-nova-publish-memory-02/var/new-sites/<site>`).
Реестр коммитится и читается на другой машине, где такого каталога нет вовсе, а
абсолютный путь вдобавок обходит проверку выхода за корень репозиториев
(`registry.корень_репозиториев()`). Переведено в относительный
`var/new-sites/<site>` — как у всех остальных ячеек; запрет закреплён проверкой
`tests/unit/test_cell_registry.py::test_путь_репозитория_не_абсолютный`.

Следствие, которое стоит знать заранее, чтобы не принять его за поломку: в этом
рабочем дереве `var/site-repos` — симлинк на соседнее дерево, поэтому локально
под ОДНИМ корнем два набора ячеек не сходятся. `registry.consistency_report()`
это честно показывает: без `CELL_SITE_REPOS_ROOT` неизвестными оказываются
ячейки общего клона (12 замечаний), с `CELL_SITE_REPOS_ROOT=/home/claude/
wt-portable-site-cell-01` — восемь новых. На хосте выпуска корень один, и
вопрос не возникает.

Та же сверка стала знать третий источник идентичности — пакет самой ячейки
(`<repo>/config/site.json`), — и замечаний стало 23 → 15. Заодно вышло наружу
настоящее расхождение, которое прежний текст проглатывал: профили
`config/site-profiles/yummyani-{site,org,biz}.json` называют те же домены под
другими `site_id`, чем реестр (`yummyani-biz` против `yummy-biz`) — одна витрина
под двумя именами. Это вход владельца: какое имя верное, решает не сессия.

## CI партии: было две причины падения, осталась одна — входная

До 14.10 18:46 у партии не было ни одного зелёного прогона CI, и причин было
две. Первая — дефект, и он исправлен; вторая — вход владельца.

| когда | что упало | почему |
| --- | --- | --- |
| каждый выпуск с 12:10 | `pins-match-sources` | замок закреплял `src/lords-frontend.py` суммой `2e5c3c0d2dc2`, а в ячейке лежит `905e2d1938a2`: исправления интерфейса сделаны В ЯЧЕЙКЕ (D212а оставляет семейный рантайм на отдельный выпуск — тот же файл исполняют 17 действующих витрин) |

Замок приведён к факту инструментом
`automation/local/relock-cell-source.py` (он требует причину аргументом и
сохраняет прежнюю сумму в `base_sha256`: решённая правка не должна стать
неотличимой от случайной). Проверено локально — `checks/verify_pins.py` → код 0
— и на стороне CI: прогоны 18:46 всех восьми витрин падают теперь РОВНО на
одной проверке.

```

site-lordfilm-spb-ru       упали: activate-scenarios
…                          (все восемь)
```

То есть зелёный прогон партии теперь в одном входе владельца, а не в двух
состояниях. Коммиты: `fa0bc69494cb`, `4d5c61e04bc2`, `e153ea56b55d`,
`9bab9a565f57`, `4e3eb1580c0e`, `230df3d09b1f`, `a917a709e6ff`, `9245ca16c8bc`.

**Моя ошибка по дороге, названная целиком.** Первая редакция скрипта коммитов
использовала имена переменных кириллицей — bash их не принимает (правило в

## Что осталось: три входа владельца (и один шаг следом за номерами)

Ни один из трёх не обходится силами сессии, и причина у каждого названа не
общими словами, а правилом или измерением.

### 1. `publisher_id` для восьми доменов — `BLOCKED_INPUT`

Без номера служба витрины не запускается вовсе: это fail-closed по замыслу, и
именно поэтому в таблице выше у плеера стоит `noaccess`. Подставить чужой или
выдуманный номер запрещено (CLOSED_WORLD, D138/D177): `10238` уже у lords-03,
lords-06 и lords-07, `10252` — у animego-04, и перенос смешал бы показы в
чужом отчёте.

Как только владелец назовёт восемь номеров, применение — одна команда на
витрину, она меняет все три места D177 сразу и сама сверяет их согласие:

```bash
python3 automation/local/assign-publisher-id.py --site lords-10 --publisher-id <N>            # сухой прогон
python3 automation/local/assign-publisher-id.py --site lords-10 --publisher-id <N> --apply
```

Для витрин этой партии команда делает ДВА нужных места из трёх: объявление
в пакете витрины и учёт в реестре. Третье — файл производителя — нужен на
ЦЕЛЕВОМ узле, а не здесь: установщик читает его там, где работает сам.
Команда создаст и местную копию `/srv/lords/.frontend/player-lords-10.json`,
но выпуску на K2 она не источник, и путать их нельзя.


**И сразу за номерами — файл плеера у производителя НА УЗЛЕ.** Это пропущенный
шаг, найденный 14.10 измерением, а не рассуждением: привилегированный
установщик для витрины, которая объявляет `publisher_id`, требует
`config/player.json` и берёт его ровно из трёх источников — действующий выпуск,
каталог приложения, `/srv/lords/.frontend/player-<site>.json`. На K2 нет ни
одного:

```
$ ansible -i var/ansible/hosts.yml k2-zomro-01 -m stat -a "path=/srv/lords/.frontend"
    "stat": { "exists": false }
$ ansible … -m shell -a "ls -d /srv/lords; find /home/k2deploy/stage -name 'player*'"
ls: cannot access '/srv/lords': No such file or directory
(файлов player* в заготовках нет)
```

Поэтому первая же активация завершилась бы отказом «витрина объявляет
publisher_id, но `config/player.json` не найден ни в действующем выпуске, ни у
производителя» — уже после того, как владелец назвал номера. Операция (root на
узле, по одному файлу на витрину, значение `source_mode` взято из собственного
образца ячейки `config/player.json.example`):

```bash
# host: k2-zomro-01
install -d -m 0755 /srv/lords/.frontend
umask 077
printf '{"publisher_id": "<N-10>", "source_mode": "provider-id"}\n' > /srv/lords/.frontend/player-lords-10.json
# … и так для lords-11 … lords-17 со своими номерами
chmod 0600 /srv/lords/.frontend/player-lords-1*.json
```

Установщик сам скопирует файл в выпуск, сменит владельца на учётную запись
витрины и поставит `0600`; подменой это не является — витрина сверяет номер из
файла с `publisher_id_expected` из артефакта, чей digest проверен по прогону CI,
и расхождение валит проверку готовности кандидата.

### 2. Блок root-консоли на узле K2

Файлы уже на узле и сверены на месте (`sha256sum -c SHA256SUMS` → 0, 50
файлов), блок только ставит их на место и ничего не включает: зависимости
(nginx, certbot, python3-venv), предел журналу, восемь системных учётных
записей с каталогами данных `0750`, юниты без `enable`, объявления upstream и
включаемые файлы режима индексации в состоянии **CLOSED**. Текст блока —
`docs/K2_NIGHT_PLAN_20261013.md` §3; у `k2deploy` sudo нет (`sudo: a password
is required`), `/srv` принадлежит root и на запись недоступен — измерено.

### 3. Записи A восьми доменов

**Что видно снаружи сейчас.** Все восемь доменов отвечают на 443, но сертификат там не на эти имена: `CERTIFICATE_VERIFY_FAILED` у всех восьми (один и тот же сертификат длиной 1291 байт). То есть посетитель видит ошибку TLS, а не чужой сайт — чужого содержимого под этими именами не публикуется, и в индексе ему взяться неоткуда. Та же причина у `HTTP 421` в цепочке запуска.

Измерено 2026-10-14 на `@8.8.8.8`: все восемь указывают на `45.131.182.225` —
прежний узел, где эти витрины не запущены. Целевой узел — `145.63.129.86`
(`k2-zomro-01`). Перевод записей делается ПОСЛЕ пунктов 1 и 2 и после проверки
origin, конфигурации, сертификата и плана отката: DNS-cutover — отдельный
журналируемый шаг, а не часть выкладки.

Прежние копии витрин на управляющем узле до подтверждённой работы новых не
удаляются.
