# K2: причина 504 установлена и исправлена — 2026-10-17

Владелец: «Доведи расследование 504 на lordfilm.spb.ru и lordserial.net.ru до
установленной причины. Совпадение с доставкой каталога пока считай гипотезой…
Исправь причину; успешный перезапуск сам по себе проблему не закрывает.»

## Что было известно

* Две витрины зависали, восстанавливались перезапуском службы, причина не
  устранялась.
* В записях владельца об инциденте (`var/k2-data/incidents/k2-{spb,net}-incident.log`)
  — ДЕСЯТКИ одновременных запросов страницы произведения с разных локальных
  портов, у каждого `BrokenPipeError` на `self.wfile.write(тело)` в
  `маршрут_тайтла`. То есть ответ готовился, но клиент (nginx) уже ушёл.
* `/var/log/nginx/*.log` и `journalctl -u nova-*` учётной записи доставки
  недоступны (`k2deploy` не в `adm` и не в `systemd-journal`) — это записано
  как «не измерено», а не додумано.

## Что опровергнуто

| Гипотеза | Чем опровергнута |
| --- | --- |
| рантайм однопоточный | развёрнутый рантайм поднимается как `ThreadingHTTPServer` |
| «холодный старт» после перезапуска | восемь выпусков 17.10: `healthz` отвечает через 6 с, `/` и `/catalog/` сразу 200 |
| узел исчерпал память | 9945 МиБ всего, 6326 МиБ доступно, swap 0, load 0.13 на 4 ядрах |
| «совпадение с доставкой каталога» (рабочая гипотеза) | осталась только совпадением одного наблюдения; настоящая причина ниже объясняет и его: доставка добавляет нагрузку к и без того последовательной отдаче |

## Измерение, которое дало ответ

`automation/host/k2-concurrency-knee.py` — одна и та же страница произведения
запрашивается с разной одновременностью НА УЗЛЕ, в обход nginx:

```
lords-11, /title/operaciya-trest/, предел nginx 30 с
  одновременно   1: медиана   0.99 с, максимум   0.99 с
  одновременно   4: медиана   4.08 с, максимум   4.20 с
  одновременно   8: медиана   7.82 с, максимум   8.32 с
  одновременно  16: медиана  15.12 с, максимум  16.58 с
```

Время растёт СТРОГО линейно: четыре одновременных запроса обслуживаются вчетверо
дольше одного. Параллелизма нет, хотя ядер четыре и сервер потоковый — сборка
страницы это чистый python, и GIL делает её последовательной. Отсюда прямо
следует наблюдаемое: при ~31 одновременном запросе ответ перестаёт
укладываться в `proxy_read_timeout 30s`, nginx закрывает соединения, и ВСЕ
ждущие получают 504, а рантайм — пачку `BrokenPipeError` на записи ответа.
Перезапуск «помогал» потому, что к этому моменту всплеск заканчивался.

## Причина внутри страницы

Профиль на настоящем каталоге витрины (64 508 записей, боковой файл 84 МиБ):

```
страница произведения: 1.739 с
   4.645 с из 4.658 с под профилем — похожие_с_мета (строка 4411)
   61 875 вызовов setcomp по каталогу
   269 832 вызова транслит ЗА ОДИН ЗАПРОС
```

Подбор похожего обходил ВЕСЬ каталог и для каждой записи заново считал коды
жанров и стран. Снимок между запросами не меняется — эта работа повторялась на
каждом запросе.

## Исправление

Коды жанров и стран считаются ОДИН раз на снимок подробностей
(`коды_соседей`), ключ кеша — путь и время файла (доставка кладёт новый снимок
на то же место). Строки кодов разделяются между записями.

**Выдача не изменилась ни на байт:** пять страниц произведений, собранных до и
после правки, дают одинаковые sha256 (`a72e1c45513f9dff`, `6c466aba4a873388`,
`350a203e42a96d8a`, `8f8012ff31e6d08b`, `a676cee45e7b0f28`).

## Проверка после выпуска

Тот же замер на том же адресе, после выпуска на всех восьми витринах:

```
  одновременно   1: медиана   0.53 с, максимум   0.53 с   (было 0.99)
  одновременно   4: медиана   0.78 с, максимум   0.82 с   (было 4.20)
  одновременно   8: медиана   1.29 с, максимум   1.47 с   (было 8.32)
  одновременно  16: медиана   2.12 с, максимум   2.81 с   (было 16.58)
  одновременно  32: медиана   3.92 с, максимум   9.99 с   (не измерялось)
```

Тридцать два одновременных запроса — 9.99 с против предела 30 с. Порог, при
котором предел перестаёт выполняться, отодвинулся примерно втрое, а базовое
время страницы упало вдвое.

Публичная проверка всех восьми витрин после выпуска: десять поверхностей
отвечают 200, самый медленный ответ — `healthz` 1.82–2.89 с.

## Что осталось

* Предел одновременности в nginx (`limit_conn`) как защита от всплеска —
  необязателен, нужен выбор числа владельцем: `docs/OWNER_BLOCKS_K2_20261017.md`,
  блок 3.
* Доступ к журналам узла для будущих разборов — блок 2 там же.
* Дальнейшее ускорение: оставшиеся 0.4 с страницы — это полный проход по
  каталогу с пересечением множеств. Он уже дешёвый, но его можно свести к
  обратному индексу «жанр → записи». Отдельная задача, на 504 больше не влияет.
