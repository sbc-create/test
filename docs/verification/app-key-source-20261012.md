# Источник ключа App Read API: найден, пригодность подтверждена, путь был прочитан неверно

Запись от 12 октября. Секрет `OTT_READ_API_KEY` в `sbc-create/ott-app-sandbox`
не появился, а диагностика владельца сообщила
`/etc/app-read-api/client.key → KEY_FILE_MISSING`. Ниже — что на самом деле.

## 1. Действующий источник ключа (значение не приводится)

Различать runtime и исходники здесь обязательно, поэтому источник взят у
РАБОТАЮЩЕГО процесса, а не из документа:

```
/proc/1147134/cmdline  (юнит app-read-api-animedia-01.service)
   argv[10]: --key-file
   argv[11]: /etc/app-read-api/client-key
```

| свойство | значение |
| --- | --- |
| путь | `/etc/app-read-api/client-key` — **дефис**, не точка |
| существует | да |
| размер | 43 байта (непустой) |
| владелец и режим | `root:claude`, `-rw-r-----` (0640) |
| каталог | `/etc/app-read-api`, `root:claude`, `drwx--x---` (0710) |
| хвостовой перевод строки | отсутствует |
| `/etc/app-read-api/client.key` | **НЕ существует** |

Каталог имеет режим `0710`: проход есть, перечисление закрыто. Поэтому `ls` по
нему отвечает «Permission denied» даже тому, кто файл прочитать может, —
и это не признак отсутствия файла. Проверять существование надо по ИМЕНИ
(`test -s <путь>`), а не перечислением каталога.

## 2. Пригодность подтверждена запросом, значение не раскрыто

Проба читает файл в память, отправляет значение в заголовке `X-App-Key` и
печатает только коды и несекретные поля ответа. Значение не печатается, не
попадает в `argv` (иначе его увидел бы любой `ps` на хосте) и никуда не
записывается. Длина ключа тоже не печатается: она сужает перебор.

| адрес | без ключа | с ключом |
| --- | --- | --- |
| `http://127.0.0.1:9180/api/app/v1/titles?sort=added&limit=1` | **401** | **200** (`rule` есть, `items` 1, `total` 8552) |
| `https://animedia.icu/api/app/v1/titles?sort=added&limit=1` | **401** | **200** (то же) |

**Пригодность: подтверждена** — без ключа отказ, с ключом выдача, и местно, и
публично. Заодно это ещё раз подтверждает, что публичный адрес открыт и закрыт
ключом.

## 3. Почему диагностика сказала «отсутствует»

Причина — **неверное имя файла в самой диагностике**, а не состояние системы:
проверялся `client.key` (с точкой), которого нет; действующий файл называется
`client-key` (с дефисом).

Проверено отдельно, чтобы не свалить вину на документацию: строки `client.key`
и `KEY_FILE_MISSING` **не встречаются ни в одном нашем документе, сценарии или
передаче**. Поиск по `docs/`, `automation/`, `factory/`, по хранилищу
координации и по каталогу передач приложения даёт только `client-key`. То есть
документация была права, а замер — нет.

Единственное место, где исторически жил ДРУГОЙ путь, — прежний файл
`/etc/site-factory/secrets/app_client_key`, и он тоже не `client.key`. Ключ,
созданный там 2026-10-11, считается раскрытым (его напечатал установщик, и он
попал в переписку); служба его больше не читает. Существует ли этот файл сейчас,
я не проверял: обращение к секретному пути останавливает защита фабрики, и
обходить её я не стал. Удаление — отдельное решение владельца, о чём и
напоминает сам установщик.

В `docs/APP_READ_API.md` добавлена строка об имени файла с прямым указанием, что
`client.key` не существует, и две проверки — существования и пригодности, — ни
одна из которых не печатает значение.

## 4. Одна команда владельцу

Выполнять в SERVER TERMINAL. Рабочий каталог не важен: пути абсолютные.
Требуется `sudo` (файл 0640 `root:claude`) и авторизованный `gh` с правом
менять секреты репозитория.

Что делает: читает существующий проверенный ключ и записывает его в
Actions secret `OTT_READ_API_KEY` репозитория `sbc-create/ott-app-sandbox`.
Нового ключа не создаёт, авторизацию не меняет, значение не печатает.

```bash
bash -o pipefail -c '
KEY=/etc/app-read-api/client-key
REPO=sbc-create/ott-app-sandbox
sudo test -s "$KEY" || { echo "ОТКАЗ: $KEY отсутствует или пуст — секрет не изменён"; exit 1; }
sudo cat "$KEY" | tr -d "\r\n" | gh secret set OTT_READ_API_KEY -R "$REPO" \
  || { echo "ОТКАЗ: gh secret set не выполнен — секрет не изменён"; exit 1; }
gh secret list -R "$REPO" | grep -q "^OTT_READ_API_KEY" \
  && echo "ГОТОВО: OTT_READ_API_KEY записан и виден в списке $REPO" \
  || { echo "ОТКАЗ: секрет в списке не появился — проверьте права gh на репозиторий"; exit 1; }
'
```

Почему именно так, по пунктам задания:

* **прекращается при отсутствии или пустом значении** — `sudo test -s` ложен и
  для отсутствующего файла, и для пустого, и дальше команда не идёт;
* **не печатает секрет** — значение идёт по конвейеру, в `argv` не попадает
  (`gh secret set` без `--body` читает stdin), в переменных оболочки не
  задерживается, на диск не пишется;
* **явно сообщает результат** — три исхода названы словами: отсутствие ключа,
  отказ записи, отсутствие секрета в списке. Молчаливого успеха нет;
* **`-o pipefail` обязателен** — без него упавший `sudo cat` отдал бы `gh`
  пустой ввод, и секрет мог быть создан ПУСТЫМ. Пустой секрет хуже
  отсутствующего: приёмка пошла бы дальше и упала бы позже и непонятнее;
* **проверка после записи не печатает значение** — `gh secret list` показывает
  имя и время обновления, а значения не показывает вовсе.

Чего команда НЕ делает и почему: не создаёт новый ключ (замена авторизации ради
прохождения теста запрещена и обесценила бы уже выданные APK) и не трогает
прежний раскрытый файл (это отдельное решение владельца).

### Сторожа проверены поведением, а не обещанием

Команда прогнана на стенде, где `sudo test -s` заменён на `test -s` (та же
семантика), а `gh` — заглушкой, считающей полученные байты. Три состояния мира:

| состояние ключа | исход | вызывался ли `gh` |
| --- | --- | --- |
| файла нет | `ОТКАЗ … отсутствует или пуст`, код 1 | **нет** |
| файл есть, пуст | `ОТКАЗ … отсутствует или пуст`, код 1 | **нет** |
| файл есть, непуст, с хвостовым `\n` | `ГОТОВО`, код 0 | да, получено 30 байт из 31 |

Третья строка подтверждает и снятие хвостового перевода строки: значение из 31
символа дошло 30 байтами. Синтаксис самой команды проверен отдельно
(`bash -n`).

Своя ошибка на этом стенде, повторная: первая редакция проверки использовала
кириллические имена переменных, а bash переменной с таким именем не создаёт —
строка выполняется как команда, значение теряется МОЛЧА, и все три прогона
«отказали» по несуществующему пути. Переписано латиницей; в самом сценарии
теперь стоит пояснение, чтобы не наступить третий раз.

## 5. Что останется после выполнения

Единственный остаток у исполнителя приложения — прогон приёмки реального
каталога, который до сих пор был `SKIPPED` из-за отсутствия секрета. Ключ при
этом остаётся **ограниченным клиентским**, а не серверным секретом: он попадает
в APK, и передача через GitHub Secrets не делает его тайной после сборки. Это
свойство записано в `docs/APP_READ_API.md` и на него не опирается ни одна
проверка прав.

Отдельно стоит помнить разницу областей поражения: ключ один, второго служба не
поддерживает (`Обработчик.ключ` — одно значение, сравнение
`hmac.compare_digest` с ним). Поэтому его копия в секретах CI расширяет круг
тех, кто может его получить, и отзывается только сменой единственного ключа —
то есть сразу у всех. Поддержка нескольких ключей (по одному в строке файла) —
правка небольшая и локальная, но это изменение установленной службы, и решение
о ней за владельцем.
