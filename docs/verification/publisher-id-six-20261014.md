# Шесть назначений publisher_id, 14 октября: что применено и чем доказано

Задание владельца от 2026-10-14 назначает шести доменам новые номера издателя и
прямо называет себя разрешением на замену. Ниже — что сделано, чем проверено и
что осталось вопросом.

Проверка — `automation/local/publisher-id-check.py <домен>`: она читает
`data-publisher-id` из DOM (это ВХОД), перехватывает запросы к
`player.cdnvideohub.com` и достаёт из них значение `publisher` (что ушло
провайдеру), и отдельно подтверждает, что дорожка действительно играет. Ответ
200 сам по себе здесь ничего не значил бы: страница отвечает 200 и с пустым
плеером.

## Как применялось

Штатным инструментом `automation/local/assign-publisher-id.py --apply`, который
меняет ТРИ места сразу (D177) и после записи сам сверяет их согласие:

1. **значение** — файл производителя `/srv/lords/.frontend/player-<site>.json`;
2. **объявление** — `config/site.json: publisher_id_expected` в пакете витрины;
3. **учёт** — `config/site-cells.json: publisher.publisher_id`.

Отказов 0 из 6, у каждой витрины `совпадает_после = {значение: true,
объявление: true, учёт: true}`. Это про ТО применение: у двух витрин Yummy
назначение затем откачено и сделано другим механизмом — закреплением в
контуре (раздел ниже), потому что в ячейке оно ломало запуск. Прежнее
состояние снято ДО правки и годится для отката:
`var/k2-data/publisher-before.json`; для двух Yummy там же записан порядок
возврата, поскольку трёх мест D177 у них нет вовсе.

Почему важны все три: привилегированный исполнитель переносит в новый выпуск
действующий `config/player.json`, и правка одного места вернулась бы следующей
выкладкой. Он же и страхует — источник, расходящийся с объявлением выпуска,
пропускается, и значение берётся у производителя.

## Два препятствия, встреченные по дороге (оба сняты)

### Отозванные номера (D213)

`10331` и `10333` числились в проекте отозванными поставщиком: регистрация их
отвергала, а `run.py` ячеек zonafilm.space и animedia.space несёт СВОЮ копию
списка — витрина не поднялась бы вовсе. Разрешено порядком из D137 (тот же
случай 2026-10-01): указание владельца о конкретном домене выше кода и
автотестов. Набор сокращён во всех местах сразу, решение записано как D213,
заморозка знаний пересчитана.

**Проверка дала ответ, которого не было у D137.** Там сказано: снаружи
отличить действующий номер от отозванного нечем — плейлист отвечает одинаково
и на выдуманный. Сегодня способ нашёлся: выпустить и посмотреть, играет ли.
`zonafilm.space` с номером 10331 и `animedia.space` с номером 10333 играют.
Значит «отозван» для этих двух значений не подтверждается ничем и опровергается
прямым измерением.

### Yummy: номер закрепляется в контуре витрины (B010 снят)

Сначала назначение этим двум было **откачено**: как только ячейка Yummy
объявляет `publisher_id`, её собственная пусковая проверка отказывает —

```
запуск yummyani7.site остановлен до первого запроса:
  — сайт объявляет publisher_id 10376, но LORDS_PLAYER_CONFIG не задан:
    плеер не настроен
```

— и CI падал на `activate-scenarios`. Причина не в номере: у семейства Yummy
своего плеера нет, просмотром занимается верхний поток Next.js
(`LORDS_LEGACY_UPSTREAM: 127.0.0.1:3104`), и `LORDS_PLAYER_CONFIG` в окружении
ячейки отсутствует НАМЕРЕННО. Ограничение было записано 12 октября
(`NIGHT_RUN_20261012` §30, пункт B010) теми же словами.

**Где номер живёт на самом деле.** Приложение читает
`CDNVIDEOHUB_PUBLISHER_ID` (`src/modules/playback/cdn-video-hub/
publisher-id.ts`), а кладёт его туда точка входа образа
(`scripts/docker-entrypoint.staging.sh`) — и предпочитает закреплённое
значение общему файлу направления:

```sh
if [ -n "${CDNVIDEOHUB_PUBLISHER_ID_PINNED:-}" ]; then
  export CDNVIDEOHUB_PUBLISHER_ID="$CDNVIDEOHUB_PUBLISHER_ID_PINNED"
else
  read_secret_file CDNVIDEOHUB_PUBLISHER_ID publisher-id
fi
```

Общий файл `/run/cdnvideohub/publisher-id` один на все витрины семейства —
именно поэтому оба домена отдавали один и тот же номер, и правка там вышла бы
за границу шести. Закрепление же касается ровно одной витрины, и тем же
способом владелец закрепил соседей 2026-10-01: yummyani.org — 10377,
yummyani.biz — 10375. То есть второго механизма не вводится, берётся уже
существующий; это и есть ответ на B010, записанный решением **D214**.

Применено `automation/local/yummy-publisher-id.py --site yummy-07|yummy-08
--apply`. Инструмент не принимает номер аргументом: он берёт его из учёта
реестра (`publisher.publisher_id`), сверяет с закреплением в контуре, при
расхождении ОТКАЗЫВАЕТ (какое из двух значений верно — решает владелец),
пересоздаёт только службу `web` и затем читает живую страницу. Общий файл
направления инструмент не читает и не меняет ни разу.

**Соседи общего приложения не изменились** — проверено тем же действием после
применения: yummyani.site — 10252, yummyani.org — 10377, yummyani.biz — 10375,
у всех трёх воспроизведение ИДЁТ. Закрепление по построению касается только
своего контура, но «по построению» здесь недостаточно: это и измерено.

### Чего в этой части не хватает

Правка контуров двух ячеек (`deploy/compose.yaml`) **не закоммичена**: git в
каталогах ячеек из этого сеанса запрещён изоляцией рабочего дерева (ячейки —
общий клон соседнего дерева). Живое состояние верно и проверено, но до коммита
очередной `git checkout`/`pull` в том клоне снял бы закрепление. Точная
операция названа в конце документа.

## Область изменений

Проверена перечислением, а не на глаз: в реестре ячеек изменились ровно шесть
записей и в них ровно поле `publisher`; ни одно непустое поле ни у одной из
33 ячеек не потеряно и не изменено. У двух Yummy запись сначала была
возвращена к пустой (назначение в ячейке ломало запуск), а затем заполнена
снова — уже с механизмом закрепления в контуре: `publisher_id` 10376 и 10371,
`publisher_id_ref` указывает на `deploy/compose.yaml`, а примечание называет
решение и инструмент. Номер `10238`
остаётся у lords-03, lords-06 и lords-07, номер `10252` — у animego-04. Общий
секрет направления (`api_token`) не затрагивался.

**Путь возврата прежних номеров закрыт (D214).** У zona-01 и animedia-02
профиль `yami` в `automation/host/nova-player-configure.py` брал номер из
ОБЩЕГО файла направления, и запасной путь оказался шире формулировки D138:
прежняя `объявление_витрины` возвращала пустое значение на КАЖДОЙ неудаче
чтения — нечитаемый реестр, отсутствующая запись, пустой `repo.path`, битый
`site.json`, — после чего операция брала номер направления.

Измерено на прежней редакции, вынутой из git: при недоступном пакете витрины и
при нечитаемом реестре операция вернула zona-01 значение направления (в стенде
подменено на 19999) вместо назначенного 10331. То есть повторный штатный запуск
молча отменял бы назначение владельца.

Теперь источник один — учёт реестра; объявление пакета обязано с ним совпадать;
любая неудача чтения и любое расхождение — отказ с названной причиной. Таблица
файлов направления удалена из инструмента целиком, чтобы путь нельзя было
вернуть правкой одной строки. Поведение закреплено
`tests/unit/test_player_publisher_source_order.py` (15 проверок).

**Та же правка в сверке источников.** `automation/host/nova-source-verify.py`
спрашивала провайдера под номером НАПРАВЛЕНИЯ, причём для zona-01 таблица
указывала вовсе на секрет соседней витрины lords-01. После назначения разных
номеров её отчёт измерял бы покрытие чужого издателя и выдавал это за проверку
витрины. Теперь номер берётся из бокового файла `player-<site>.json` — того,
которым витрина рендерит страницы, — а кэш ответов провайдера разделён по
витринам: под общим ключом профиля он складывал в один файл ответы витрин с
разными издателями.

Выпуск же был безопасен и до правки: привилегированный исполнитель
(`factory/cell/privileged.py::_перенести_локальную_настройку`) пропускает
источник, расходящийся с объявлением выпуска, и отказывается, если подходящего
нет, — подставить прежнее значение он не может.

## Побочная правка, без которой выпуск не прошёл бы

Песочница проверки `animedia-space/checks/activate_scenarios.py` держала номер
издателя ЧИСЛОМ (`10252`) и падала на смене: «publisher_id 10252, а сайт
объявляет 10333» — то есть проверка падала на собственной устаревшей константе,
а выглядело это как дефект витрины. Теперь номер берётся оттуда же, откуда его
берёт настоящий выпуск, — из объявления витрины. Соседняя ячейка
(yummyani7.site) так и делала с самого начала.

## Учёт трёх соседей остался незаполненным — это граница задания

`publisher-id-reconcile` по всем 33 ячейкам: расхождений 0, к заполнению учёта
0, без объявления 3 — `yummy-biz`, `yummy-org`, `yummy-site`. У этих трёх пусты
и учёт, и объявление, а витрины идентификатор отдают (измерено: 10375, 10377,
10252). Инструмент такое не заполняет сам и правильно отказывается: одного
источника мало.

Заполнить их учёт я не стала намеренно: задание ограничило область шестью
домена́ми, а это другие три. Механизм для них теперь назван решением D214 (тот
же `CDNVIDEOHUB_PUBLISHER_ID_PINNED`), поэтому остаток — чистое счётоводство,
по одной команде на домен, после явного разрешения владельца:

```bash
python3 automation/local/assign-publisher-id.py --site yummy-org --publisher-id 10377 --apply
python3 automation/local/assign-publisher-id.py --site yummy-biz --publisher-id 10375 --apply
```

Отдельный вопрос по `yummyani.site`: её номер 10252 приходит из ОБЩЕГО файла
направления и ничем за домен не закреплён. Это не дефект, пока владелец не
назначил ей свой номер; назначить его самостоятельно нельзя
(`BLOCKED_INPUT`), а закрепление делается тем же способом, что у yummyani7.

## Точная операция владельца (один коммит)

Закрепление уже стоит в файлах и проверено живыми страницами; требуется только
зафиксировать его в git. Выполняется в клоне ячеек, из сеанса без изоляции
рабочего дерева:

```bash
cd /home/claude/wt-portable-site-cell-01/var/site-repos/yummyani7-site
git add deploy/compose.yaml
git commit -m "publisher_id 10376 закреплён за доменом в контуре витрины"
git push origin HEAD

cd /home/claude/wt-portable-site-cell-01/var/site-repos/yummyani7-info
git add deploy/compose.yaml
git commit -m "publisher_id 10371 закреплён за доменом в контуре витрины"
git push origin HEAD
```

Проверка после коммита — тем же действием, без аргумента `--apply` он ничего не
меняет:

```bash
python3 automation/local/yummy-publisher-id.py --site yummy-07
python3 automation/local/yummy-publisher-id.py --site yummy-08
python3 automation/local/publisher-id-check.py yummyani7.site
python3 automation/local/publisher-id-check.py yummyani7.info
```
