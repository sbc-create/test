# Публикация новостей yummyani.org: что проверено 2026-10-05

Задание: подготовить штатную публикацию новостей через инструменты Qwen и
передать ему готовую операцию; саму статью не публиковать.

## 1. Фактический источник раздела `/posts` и новостного блока

| что измерено | как | результат |
| --- | --- | --- |
| кто отдаёт раздел | ответ ячейки 9131 против ответа контейнера 3102 | совпадают байт в байт (57 477 байт) — отдаёт приложение, витрина проксирует |
| откуда приложение берёт записи | `src/modules/editorial/editorial-post.ts` | `FILE_PATH = join(process.cwd(), "content/editorial-posts.json")`, `readFileSync` + `statSync` ПРИ ЗАПРОСЕ |
| чем проверяется | та же функция | схема Zod: `version: literal(1)`, массив записей со строгими полями |
| что скрыто от публики | та же схема | `status: "draft"` не показывается НИКОГДА — непубличный черновик предусмотрен самим приложением |
| где файл лежал | `docker cp` из контейнера + файл репозитория приложения | 12 записей, содержимое совпадает; файл ЗАПЕЧЁН В ОБРАЗ |
| есть ли переменная пути | исходник | НЕТ (у накладок описаний есть `TITLE_OVERLAYS_PATH`) |

Новостной блок главной использует те же записи: ссылки `/posts/<slug>` на
главной — подмножество списка раздела.

## 2. Существующие операции до этой работы

| операция | что было | годна ли для новостей |
| --- | --- | --- |
| `prepare_material` / `publish_material` / `unpublish_material` фабрики | работают с НАКЛАДКАМИ ОПИСАНИЙ тайтлов (`content_type: TITLE_DESCRIPTION`), пишут `title-overlays.json` через хранилище оператора | нет: другой вид материала, другие поля, другой файл |
| процедура приложения (`content/README.md`) | дописать объект в `posts`, выставить `status`, при желании `pnpm db:seed`, перезапустить/переразвернуть | это и есть механизм, но он требует правки файла В ОБРАЗЕ |
| снятие публикации | в приложении не описано | не было |

## 3. Что сделано на стороне сервера

1. **Доставка.** Наложение compose в репозитории фабрики
   (`automation/host/yummy-posts-delivery.override.yaml`) монтирует файл
   доставки на `/app/content/editorial-posts.json` только для чтения. Чужой
   compose не правится, образ не пересобирается, код приложения не меняется.
   Слияние списка томов проверено `docker compose config` ДО применения: все
   три прежних монтирования сохранены, новое добавлено четвёртым.
2. **Посев.** Файл доставки засеян содержимым РАБОТАЮЩЕГО контейнера (12
   записей), проверен схемой и записан атомарно. Монтирование отсутствующего
   файла создало бы на его месте каталог, а пустой посев снял бы с публикации
   всё существующее — оба случая отклоняются операцией.
3. **Операции.** `factory/qwen/posts.py`: `подготовить` (черновик, публичного
   не меняет), `опубликовать` (доставка, идемпотентна), `снять` (перевод
   записи в `draft`, запись и история сохраняются), `состояние` (только
   чтение).
4. **Инструменты Qwen.** В мост добавлены `prepare_post`, `publish_post`,
   `unpublish_post` (пишущие) и `posts_status` (чтение).

## 4. Чем доказано, что механизм работает

**Изолированный прогон** (временный корень доставки, production не задет):

    1. подготовка:  state verified, public false
    2. публикация:  created, posts 13, seeded_from_container true
    3. повтор:      nothing-to-do (защита от дубликата)
    4. состояние:   запись среди published
    5. снятие:      unpublished, posts 13 (запись НЕ удалена)
    6. повтор:      nothing-to-do
    7. прежние 12 записей на месте
    8. схема файла: беды нет

**Отказы на production без записи:** пустой текст, негодный слаг, публикация
без черновика, снятие несуществующей записи — все четыре отклонены с
названной причиной.

**Схема повторяет схему приложения, а не идею о ней:** тест читает исходник
`editorial-post.ts` и сверяет перечни типов, состояний и источников, а затем
прогоняет НАСТОЯЩИЙ файл приложения через нашу проверку — все 12 записей
проходят.

**Production после монтирования:** `/posts` → 200, набор слагов тот же (12
штук, перечень совпал), индексация открыта (`index, follow`, заголовка запрета
нет), карточка 200, воспроизведение видео в браузере идёт
(`currentTime` 0.10 → 27.89). Контейнер читает ИМЕННО файл доставки
(`docker inspect` показывает монтирование на тот путь, который читает код).

## 5. Два найденных дефекта в собственном коде, исправленные здесь же

1. **Связь витрины с контейнером искалась по имени** — и возвращала
   `yummyani-staging-web-org-1` для всех пяти витрин семейства. Посев взял бы
   новости чужого сайта: это cross-site утечка. Теперь связь по ПОРТУ
   апстрима, объявленному выпуском (D175). Проверено на всех пяти доменах:
   каждый получил свой контейнер.
2. **Негодный слаг попадал в черновики.** Слаг — публичный адрес записи, а не
   качество текста; черновик под таким ключом невозможно опубликовать (D176).

## 6. Чего ещё нет

* **Мост не перезапущен**: живой процесс работает на прежнем коде
  (`instruction_version: 2026-10-04.6`, 23 инструмента). Новые инструменты
  появятся в чате Qwen после `sudo systemctl restart site-factory-mcp.service`.
  Загруженный юнит работает в режиме ЗАПИСИ (drop-in `10-write-mode.conf`
  перекрывает `--read-only` основного файла) — перезапуск этого не меняет;
* **контрольная новость о «100カノRADIO» не публиковалась** и на production не
  заводилась: её публикует Qwen;
* **остальные витрины семейства** (`yummyani.site`, `yummyani.biz`,
  `yummyani7.*`) монтирования файла новостей НЕ получили: задание про
  `yummyani.org`. Операции для них откажут словами «контейнер видит файл
  образа», пока наложение не применено и к ним.
