## 2. Дефект операции: частичный отказ оставлял домен наполовину открытым

Найден тестом, написанным до исправления, и подтверждён исполнением на
изолированной площадке (`tests/unit/test_indexing_operation_behaviour.py`):

    AssertionError: слой nginx остался открытым после неудачной попытки
    открытия: домен наполовину открыт
    assert 'OPEN' == 'CLOSED'

Сценарий: слой nginx переключён исполнителем в открытый, публичный ответ
открытие НЕ подтвердил. Возвращался только файл состояния, слой оставался
открытым — домен терял запрет уровня nginx и держался на запрете приложения.

Исправлено двумя частями, обе нужны:

1. `indexing.вернуть_слой` + `_восстановить(..., слой_до=…)`: слой возвращается
   ШТАТНОЙ заявкой, итог проверяется ЧТЕНИЕМ слоя, в ответе — `nginx_restored`;
2. `queue.собрать(..., suffix=…)`: без суффикса идентификатор возврата
   (`<site>-idx-<mode>`) совпал бы с прежней УСПЕШНОЙ заявкой того же режима,
   очередь ответила бы `already-finished`, и возврат был бы словесным.

    python3 -m pytest tests/unit/test_indexing_operation_behaviour.py -q
    -> exit 0, 7 passed

Семь случаев на изолированной площадке (свой реестр, свой выпуск, свой корень
состояния, своя конфигурация nginx, подставная очередь, никакой сети):

| случай | результат |
| --- | --- |
| отказ без разрешения владельца | `Отказано`, файла состояния и заявки нет |
| отказ при несовпадении ожидаемого выпуска | остановка до единой записи |
| открытие и закрытие разрешённого сайта | обе смены подтверждены, заявки `indexing-nginx` с нужным режимом |
| частичный сбой (исполнитель отказал) | состояние возвращено, запись `restore` в журнале |
| исполнитель ответил «применено», слой закрыт | возврат, причина названа |
| **слой открыт, ответ не подтвердил** | возврат ОБОИХ слоёв, `nginx_restored.mode = CLOSED`, заявка возврата `mode=CLOSED` |
| повтор в том же режиме | ни записи, ни сдвига времени файла, ни второй заявки |

## 4. Непрозрачная ошибка «Error executing tool» — причина на нашей стороне устранена

`tools/call` ловил только свою `ОшибкаИнструмента`; любое другое исключение
уходило наружу, и клиент показывал одну строку без причины. Теперь непредвиденное
исключение возвращается ОТВЕТОМ:

    isError: true, error "KeyError: 'site_id'", unexpected: true,
    where "new_tools.py:44 в падать", arguments ["domain"]

Текст проходит через `factory.redaction`; в ответе нет пути к учётным данным и
значений секретов (закреплено тестом).

Инструмента `analytics_readiness` в коде фабрики не было вовсе (поиск по
репозиторию) — падавший инструмент принадлежит службе `seo-analytics-mcp` на
srv-qwen, её журналов на фабрике не существует. Гипотеза об источнике реестра
SEO после переименования прежнего сервиса НЕ ПРОВЕРЕНА: проверяется одним
прогоном `automation/srv-qwen/diagnose-seo-analytics.sh` на srv-qwen.

### Почему отклонил, и это оказался дефект ворот

Хранилище материалов `/srv/sites/lords/runtime/overlays/lordserials22.info`
**пусто** и создано **самим прогоном** `trigger` в 00:37:51 (поле
`created_now: true`). До него каталога не существовало, и тот же выпуск ворота
прошёл бы. Защита от ПОТЕРИ данных сработала там, где данных нет.

Исправлено точно, без ослабления (`factory/cell/protected.py::_непусто`): пустой
каталог данными не считается, нечитаемый по-прежнему считается присутствующим,
любой файл внутри снова требует читателя. Три проверки в
`tests/unit/test_runtime_data_ownership.py`, первая падала до исправления:

    python3 -m pytest tests/unit/test_runtime_data_ownership.py \
        tests/unit/test_cell_extracted_guard.py tests/unit/test_cell_privileged.py -q
    -> exit 0, 106 passed

**Исполнитель работает из корневой копии** `/usr/local/lib/site-factory-cell`
(`WorkingDirectory` юнита), где исправления нет: `grep -c _непусто` в её
`factory/cell/protected.py` даёт `0`. До обновления пакета владельцем заявка
будет отклоняться по той же причине.
