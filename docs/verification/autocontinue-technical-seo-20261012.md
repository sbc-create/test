# Автопродолжение технического SEO: да, но обещание «только готовит ветку» сегодня ничем не обеспечено

Запись от 12 октября. SEO-сессия просит разобрать действующий механизм
автопродолжения (`editor-run`) и ответить, можно ли тем же исполнителем брать
задачи технического SEO. Разбор ниже; ответ — да, с оговоркой, которая меняет
устройство, и с одним твёрдым «нет».

## 1. Как устроен действующий механизм

`editor-run.service` — образец, который стоит разобрать прежде, чем копировать:

| свойство | значение | зачем |
| --- | --- | --- |
| `Type=oneshot`, таймер `OnCalendar=*:0/5` | один запуск, раз в 5 минут | демон не нужен: прогон длится минуты |
| `flock -n 9`, `exit 75` | второй запуск не стартует | `SuccessExitStatus=0 75` — «занято» не ошибка |
| `timeout "$LIMIT_S"` вокруг модели | внешний предел | без него оборвавшийся прогон держал бы замок |
| `TimeoutStartSec=1800` | предел юнита | страховка поверх внутреннего |
| `CPUQuota=50%`, `MemoryMax=2G`, `Nice=10` | пределы ресурсов | **у этого юнита они есть**, в отличие от витрин |
| `ProtectSystem=strict`, `ReadWritePaths=/home/claude` | `/srv` и `/var/lib` только на чтение | публикация идёт через мост MCP, прав на запись в хранилища у службы нет |
| `editor-run-verify` по следам | вердикт | **итог решает проверка, а не ответ модели** |
| код 2 | неполный прогон | юнит падает — это уведомление |

Последнее свойство и есть то, что делает автономность приемлемой: решает не
самоотчёт модели, а следы.

## 2. Случай `model_exit=124` — норма по устройству, и вот число

Измерено по `var/editor-runs/runs.jsonl`, 96 записей:

| показатель | значение |
| --- | --- |
| `model_exit=0` | 94 |
| `model_exit=1` | 1 |
| `model_exit=124` (таймаут) | **1 — один прогон из 96, 1 %** |
| из них `verified_complete=true` | 1 из 1 |
| `verified_complete=true` всего | 86 из 96 (90 %) |
| `verified_complete=false` | 10 |

`124` означает, что сработал внешний `timeout` вокруг модели. Проверка по
следам идёт ПОСЛЕ него всё равно, поэтому «ответ модели оборвался, а работа
сделана и опубликована» — связное и ожидаемое состояние. `self_report
UNPARSED` следует из того же механически: самоотчёт — последняя строка JSON
ответа, а у оборванного ответа последней строки нет.

**Разбираться не нужно, следить нужно за долей.** Один процент — шум; рост
доли означал бы, что бюджет времени стал тесен для выросшей задачи, и об этом
прямо сказано в комментарии самого сценария («задание с тех пор выросло: до
шести комментариев и заметки в придачу к описаниям»). Лечится это бюджетом или
уменьшением задачи на прогон, но не игнорированием.

Число, которое важнее `124`: **`verified_complete=false` в 10 прогонах из 96.**
Это честный канал отказа, и смотреть надо на него.

## 3. Ответ: да, образец переносится — при трёх сохранённых свойствах

Перенести можно, и три свойства обязаны поехать вместе с ним:

1. **вердикт по следам, а не по самоотчёту.** Для технического SEO это значит
   отдельный проверяющий шаг, который смотрит на результат (ветка существует,
   проверка в ней падает на неисправленном состоянии, тесты запускались) — а
   не читает «я сделал»;
2. **нет прав записи в цель.** У редактора публикация идёт через мост MCP с его
   собственными сторожами. Для техники цель — выпуск, и путь к нему
   «репозиторий → SHA → CI → артефакт → исполнитель → живое»;
3. **замок, предел времени, пределы ресурсов, и отказ как уведомление.**

## 4. Оговорка, которой со стороны SEO не видно: обещание не обеспечено

Формулировка «пусть только готовит ветку и проверку» сегодня **не
обеспечена ничем, кроме задания модели.** Измерено:

* `editor-run.service` работает `User=claude`, `HOME=/home/claude`,
  `ReadWritePaths=/home/claude`;
* в этом домашнем каталоге **есть** `/home/claude/.config/gh/hosts.yml`,
  `config.yml`, `.gitconfig` и каталог `/home/claude/.ssh`.

То есть фоновый прогон под той же учётной записью **может сделать push**, и
единственное, что его удерживает, — текст задания. Задание не является
средством контроля: оно не падает, не журналируется как отказ и не
воспроизводится при разборе.

Для редакционного исполнителя это терпимо: его задача не касается git. Для
технического — ровно наоборот, потому что «готовит ветку» это и есть git.

**Минимальная техническая обёртка**, которая превращает обещание в свойство
юнита:

* `InaccessiblePaths=/home/claude/.config/gh /home/claude/.ssh` (и
  `/home/claude/.git-credentials`, если появится) — прецедент есть:
  `nova-daily-refresh.service` так закрывает `/etc/site-factory/secrets`;
* `ReadWritePaths=` только рабочая копия задачи и каталог состояния прогонов;
  `ProtectSystem=strict` оставляет `/srv` и `/var/lib` на чтение;
* `flock -n` с `exit 75` и `SuccessExitStatus=0 75`;
* `TimeoutStartSec=`, `CPUQuota=`, `MemoryMax=`, `Nice=` — как у редактора;
* `StartLimitIntervalSec=0`: иначе повторяющийся отказ оставит юнит в `failed`
  навсегда (сегодняшний урок по таймерам);
* таймер с `OnCalendar` и `Persistent=true`; если всё же `OnUnitActiveSec`, то
  **обязательно** с `OnUnitInactiveSec` — из 38 таймеров хоста 12 без этого
  якоря, и убитый прогон останавливает их расписание навсегда.

## 5. Твёрдое «нет»: push и выпуск из фонового прогона

Этого давать нельзя, и причина не в недоверии к модели.

Контракт выпуска — «репозиторий → SHA → CI → артефакт → исполнитель → живое», и
каждый шаг здесь ворота. Прогон, который делает push, снимает первые ворота, а
все последующие начинают доверять непросмотренному коммиту: CI проверит то, что
прислали, исполнитель выложит то, что прошло CI, и приёмка подтвердит
выложенное. Ни один шаг при этом не спросит, хотел ли человек именно этой
правки.

Сегодняшняя ночь это подкрепляет числом: из 21 принятой выкладки ни одна не
обошлась без сверки build двумя источниками, потому что «выложено» и
«работает» — разные утверждения. Автономная подготовка ветки эту разницу
сохраняет; автономный push её стирает.

Поэтому: готовить ветку и проверку — да. Открывать PR — пограничный случай, и я
бы его тоже не давал фоновому прогону без учётных данных: пусть PR открывает
сессия или человек, у которого есть контекст, зачем эта правка.

## 6. Предусловие: без проверяющего шага таймер ставить нельзя

Измерено: у `seo_operator.cli` есть `editor-run-verify` и `editor-run-status` —
**только для редакционной работы**. Технического эквивалента нет. Файла
`docs/seo-operator/SEO_WORK_QUEUE.md` в моём рабочем дереве нет вовсе (он у
SEO-сессии), то есть машинно читаемой очереди для технических задач тоже пока
нет.

Таймер без проверяющего шага — это автономность без вердикта, ровно то, что
запрещают решения D203 (шаг проверки обязан падать на неисправленном
состоянии) и D205 (проверка, которая не умеет упасть, доверия не несёт).
Поэтому порядок такой: сначала очередь в JSON и проверяющий шаг, потом юнит,
потом таймер.

## 7. Команда владельца — с предусловием внутри

Ставить юнит и таймер — root. Команда **сама отказывается**, если предусловия
не выполнены: это тот же принцип различающего шага, применённый к установке.

Имена переменных исправлены на ASCII 2026-10-15: в прежней записи они были
кириллицей (`КОРЕНЬ=`, `ОЧЕРЕДЬ=`, `СЦЕНАРИЙ=`), а bash такое присваиванием не
считает. Команда не отказалась бы — она напечатала бы ЛОЖНЫЙ отказ «нет
очереди», потому что переменная осталась пустой. Проверка на это теперь есть:
`tests/unit/test_shell_ascii_identifiers.py::test_команды_в_документах_только_ascii`.

```bash
bash -o pipefail -c '
ROOT=/home/claude/wt-portable-site-cell-01
QUEUE="$ROOT/config/seo-tech-queue.json"
SCRIPT="$ROOT/automation/host/editor/seo-tech-run.sh"
test -s "$QUEUE" || { echo "ОТКАЗ: нет очереди $QUEUE — ставить таймер не на что"; exit 1; }
python3 -c "import json,sys; json.load(open(sys.argv[1]))" "$QUEUE" \
  || { echo "ОТКАЗ: очередь не разбирается как JSON"; exit 1; }
test -x "$SCRIPT" || { echo "ОТКАЗ: нет исполняемого $SCRIPT"; exit 1; }
(cd "$ROOT" && python3 -m seo_operator.cli seo-tech-verify --help >/dev/null 2>&1) \
  || { echo "ОТКАЗ: нет проверяющего шага seo-tech-verify — таймер стал бы автономностью без вердикта"; exit 1; }
echo "предусловия выполнены: очередь, сценарий и проверяющий шаг на месте"
'
```

Только после этого — установка юнита и таймера (значения пределов
переносятся из `editor-run.service`, частота задаётся владельцем):

```bash
sudo tee /etc/systemd/system/seo-tech-run.service >/dev/null <<'CONF'
[Unit]
Description=Техническое SEO: один подготовительный прогон
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
User=claude
Group=claude
WorkingDirectory=/home/claude/wt-portable-site-cell-01
Environment=HOME=/home/claude
Environment=PYTHONDONTWRITEBYTECODE=1
Environment=SEO_TECH_TRIGGER=systemd-timer
ExecStart=/usr/bin/bash /home/claude/wt-portable-site-cell-01/automation/host/editor/seo-tech-run.sh
SuccessExitStatus=0 75
TimeoutStartSec=1800
StartLimitIntervalSec=0
Nice=10
CPUQuota=50%
MemoryMax=2G
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectKernelTunables=yes
RestrictSUIDSGID=yes
# Обещание «только готовит ветку» делается свойством юнита, а не задания:
# без этих двух строк прогон под той же учётной записью может сделать push.
InaccessiblePaths=/home/claude/.config/gh
InaccessiblePaths=/home/claude/.ssh
ReadWritePaths=/home/claude/.claude
ReadWritePaths=/home/claude/wt-portable-site-cell-01/var
CONF
sudo tee /etc/systemd/system/seo-tech-run.timer >/dev/null <<'CONF'
[Unit]
Description=Техническое SEO: расписание подготовительных прогонов

[Timer]
# Частота — решение владельца. OnCalendar, а не OnUnitActiveSec: он считает от
# стенных часов и планирует следующую точку всегда.
OnCalendar=*-*-* 00/4:15:00 UTC
Persistent=true
AccuracySec=1min
Unit=seo-tech-run.service

[Install]
WantedBy=timers.target
CONF
sudo systemctl daemon-reload
sudo systemctl enable --now seo-tech-run.timer \
  && echo "ГОТОВО: таймер включён" \
  || echo "ОТКАЗ: таймер не включён — см. вывод"
```

**Проверка после установки** (сессия выполнит сама, root не нужен):

```bash
python3 automation/local/timer-anchors.py --timer seo-tech-run
```

Ожидаемое: таймер не попадает в раздел «ПОЛОМКА» — у `OnCalendar` якорь по
завершению не нужен. Плюс после первых двух прогонов — проверка по следам: две
РАЗНЫЕ задачи, у обеих вердикт проверяющего шага, и ни одной ручной команды
между ними. Два цикла — это и есть доказательство автопродолжения; один цикл
доказывает только запуск.

**Откат:** `sudo systemctl disable --now seo-tech-run.timer`, затем удалить оба
юнита и `daemon-reload`. Откат безопасен: юниты новые, существующих не
затрагивают, подготовленные ветки остаются на диске.
