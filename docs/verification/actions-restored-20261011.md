# Восстановление GitHub Actions и возобновление выпусков, 2026-10-11

Владелец пополнил баланс GitHub и разрешил пробовать сборки и выкладки. Здесь —
что проверено фактом, что оказалось закрыто правами, и чем это доказано.

## 1. Доступность Actions — подтверждена исполнением на runner

**Моя сессия проверить это не могла.** Операции GitHub закрыты заставой профиля,
дословно:

```
PreToolUse:Bash hook error: no allow rule matched for segment 'gh';
unknown actions are denied by default; профиль: операция GitHub вне профиля
```

Это технический запрет сессии, а не настройка оплаты, и снимать его себе я не
вправе. Обходить его через инструмент, который вызывает `gh` внутри
(`automation/local/ci-status.py`), я не стал: это тот же запрет, выполненный
через посредника.

**Что проверено доступным мне способом.** `git push` профилем разрешён, сеть до
GitHub живая: ветка фабрики `claude/nova-publish-memory-02` выложена,
`git ls-remote` показывает `39a740e3d53d0d388b7922d37da325f0d218015e`, что равно
локальному HEAD. Это доказывает работу учётной записи на запись, но НЕ работу
Actions.

**Доказательство снятия ограничения** получено от SEO-сессии, которая выполняет
свои выпуски сама (её собственная работа, не моя просьба обойти запрет):

| что | значение |
| --- | --- |
| репозиторий | `sbc-create/site-lordserial33-biz` |
| прогон | **38150720579** |
| `headSha` | `d7d94e8a7509a1049cce243915db193a01f909ac` (вершина `claude/extract-lordserial33-biz-seo-01`) |
| job | `release` |
| runner | **GitHub Actions 1000001340** |
| время | 15:18:26Z → 15:21:38Z |
| шаги | checkout, setup-python, «Проверки проекта», «Репозиторий описывает именно свой сайт», «Сборка артефакта с digest», upload-artifact — все `success` |

Это именно исполнение на runner, а не запись о создании прогона: ограничение по
оплате снято.

**Почему я не запустил прогон сам.** В репозитории фабрики `ci.yml` срабатывает
только на `pull_request` и `push` в `main`; `deploy.yml` — на `push` в `main` и
`workflow_dispatch`. Push в ветку `claude/*` прогон не запускает, а PR и
`workflow_dispatch` требуют `gh`. То есть на моей стороне прогон не стартует по
причине ПРАВ, а не оплаты, и повторные попытки тут ничего не изменят.

## 2. Выпуски сайтов

Выпуск идёт штатным путём: заявка в очередь ячеек → исполнитель. Его контракт
(`factory/cell/admin_exec.py`): принимаются только `site_id` и коммит
собственного репозитория сайта; путь к артефакту, скрипт и release-manifest со
стороны не принимаются вовсе; рабочее дерево обязано быть чистым и содержать
коммит; артефакт собирается здесь же и его digest сверяется с записанным CI.

**Блокер, который возник у SEO-сессии, снят и измерен:** проверка доступа
исполнителя для `lords-02` устарела (56 ч). Заявка
`lords-02-access-2026-10-11-01` подана 16:49:28Z, результат `ok` в 16:50:01Z —
**33 секунды**. Таймер исполнителя опрашивает очередь раз в минуту
(`OnCalendar=*:0/1`), так что это нормальная задержка. Выпуск можно подавать.

Готово к выпуску у SEO-сессии (их ветви, зелёный CI у вершины): Lords 01/02/03/05,
Zona space/12, Animedia icu/space, AnimeGo ×3 — self-canonical пагинации, п.8
(404 на `?page=0/-1/abc/9999`) и п.2 (308 с `?page=1`, параметры сохраняются).
Договорённость: один выпуск на витрину (зелёный CI у вершины ветви), а живая
сверка каждого направления — отдельно. После каждой выкладки я прогоняю приёмку
по домену и добавляю домен в строгие списки `ПАГИНАЦИЯ_СТРОГО` (п.3) и
`ПАГИНАЦИЯ_РЕДИРЕКТ_СТРОГО` (п.2), чтобы регресс падал, а не растворялся.

Режимы индексации и freeze плеера не трогались: приёмка их проверяет, и ни одна
моя правка их не касалась.

## 3. Приложение Android/TV

Разрешение возобновить выпуск передано (передача 127): отправить `app/cycle-4`,
ключ клиента только через секрет CI из файла `/etc/app-read-api/client-key`
(значение в Git, переписку и отчёты не попадает), сборка и обязательная
приёмка, проверка на mobile и TV раздельно — обновление поверх sandbox-40,
реальный каталог, реклама по умолчанию выключена, история, фокус пультом, плеер
в деморежиме. Реальное видео доступным не объявлять: `sources` отдаёт пустой
массив с `NO_SOURCE_CONTRACT_RELEASED`.

**Сессия приложения выпуск НЕ начала, и это правильно.** Её пользователь
запретил ей GitHub, и она ответила: снятие запрета должно прийти от него самого,
а не через другую сессию. Я её поддержал и переубеждать не стал. У неё
`app/cycle-4` на коммите `2193d67`, ветка опережает origin на 10 коммитов.

## 4. Что остаётся и чего это требует

| блокер | природа | что снимет |
| --- | --- | --- |
| моя сессия не может запускать и читать прогоны | права профиля (`gh` вне профиля) | разрешение владельца на операции GitHub в этой сессии — либо выпуск делают сессии, которым это разрешено (так и идёт сейчас) |
| сессия приложения не начинает выпуск | запрет её собственного пользователя | подтверждение от него; её запрос отправлен |
| дерево оператора `wt-editorial-queue-repair-01` без сопровождающего | назначение | решение владельца: назвать сопровождающего или перенести модуль очереди в сопровождаемое дерево |
| перенаправление `http→https` на 9 доменах | нужен root | одна команда: `sudo python3 automation/host/http-redirect-install.py --apply` |
| покрытие жанров (2 277 записей вне кэша) | нагрузка на источник | разовый добор, команда в `docs/verification/orphan-processes-20261011.md` §8 и в отчёте 11.10 |
