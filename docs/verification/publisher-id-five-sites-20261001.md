# Замена publisher ID плеера на пяти витринах — 2026-10-01

Задание владельца: `yummyani.biz 10375 | yummyani.org 10377 | lordserial33.biz 10378 |
lordfilm47.space 10373 | animedia.icu 10332`. Значения заменяют все прежние указания
для этих домен

## Что именно считалось доказательством

Не код 200 и не число в разметке. Успех — совпадение трёх независимых измерений
на живой витрине: номер в разметке, параметр `pub` в ФАКТИЧЕСКИХ запросах к
`plapi.cdnvideohub.com` (и ни одного запроса с прежним номером за сеанс) и
настоящее воспроизведение — `readyState>=2` плюс прирост времени ≥ 10 с.
Отдельной фазой — переключение серии: плеер пересобирается, и прежний номер мог
бы вернуться именно там.

Инструмент: `automation/host/publisher-id-live-check.js`.
Сырые отчёты (вне git): `var/reports/publisher-id-20261001/<витрина>.json`.

## Сохранность изменения

* **Перезагрузка конфигурации у витрин Yummy** — выполнена: `compose restart web-biz
  web-org`, entrypoint сообщил «CDNVIDEOHUB_PUBLISHER_ID: закреплён за профилем
  biz/org», публичные страницы после перезапуска отдают 10375 и 10377.
* **Путь перенастройки плеера у ячеек** — выполнена: `объявление_витрины` на живом
  реестре возвращает 10373 / 10378 / 10332 для изменённых витрин и 10238 / 10252 /
  10252 для соседних, то есть повторный PLAYER_CONFIGURE больше не вернёт прежний
  номер и не затронет соседей.
* **Переустановка выпуска** — пройдена самим выпуском: `_перенести_локальную_настройку`
  отвергает файл плеера, расходящийся с `publisher_id_expected` выпуска, и берёт
  боковой файл производителя.
* **Доставка ДЕЙСТВИТЕЛЬНО НОВОЙ ревизии каталога — НЕ ВЫПОЛНЕНА.** Проверять
  нечем: ячейки уже стоят на самой свежей ревизии производителя
  `86f121dcdac240e7e3806cde797b030f` (собрана 2026-10-01T03:19:08Z), следующая
  приходит по суточному расписанию. Отмечено отдельно, как непроверенное.
  Доставка работает с `data/` и наложением снимка и файла `config/player.json`
  не касается — но это рассуждение, а не измерение.
