# LORDS-RELEASE-INVOCATION-REUSE-32

**Состояние:** закрыт исправлением, ожидает подтверждения канарейкой lords-02
**Слой:** release-runner (оболочка выкладки), не продуктовый код витрины
**Заведён:** 2026-09-08

## Что произошло

Юнит `lords-02-release-20260908-123612.service` завершился с `ROLLED_BACK` и
причиной «юнит сборки не запускался заново: InvocationID не изменился».
Публичный сайт не переключался, `lords-content-refresh.timer` вернулся в
`active`.

Сборка при этом **прошла успешно**. Журнал `lords-canary-render@lords-02`:

```
12:36:25  происхождение подтверждено: commit 119605bbaca2, отпечаток a0cfaf7135255d62
12:36:26  снимок каталога: cef7ea9105bd591b, записей 53282
12:38:00  снимок заморожен: …/var/canary-staging/lords-02.snapshot/lords-02.json
15:31:33  сборка завершена за 173 мин, страниц: 61733
15:31:33  готово к переключению: …/var/canary-staging/lords-02
```

Три часа работы были выброшены оболочкой, а не потеряны сборкой.

## Причина

Runner читал `InvocationID` до запуска, запускал юнит и сравнивал значение
после. Проверка опиралась на два неверных предположения:

1. **`InvocationID` неактивного юнита пуст.** Значение существует только у
   загруженного юнита с зарегистрированным прогоном. До первого запуска оно
   пусто.
2. **`CollectMode=inactive` выгружает юнит сразу после завершения.** Вместе с
   юнитом исчезает и `InvocationID`. Поэтому после успешной трёхчасовой сборки
   значение снова оказывалось пустым, «до» равнялось «после», и runner делал
   вывод, что сборки не было.

Тем же дефектом заражены соседние проверки: у ни разу не запускавшегося юнита
`Result=success` и `ExecMainStatus=0` — это значения по умолчанию, а не следы
прогона (`ExecMainStartTimestamp=n/a`). Условие
`RC=0 && Result=success && ExecMainStatus=0` проходило вхолостую.

Состояние на момент разбора подтверждает всё сказанное:

```
ActiveState=inactive  SubState=dead  RemainAfterExit=no  CollectMode=inactive
Result=success  ExecMainStatus=0  ExecMainStartTimestamp=n/a  InvocationID=
FragmentPath=/etc/systemd/system/lords-canary-render@.service
```

## Исправление

`automation/host/lords-unit-launch.sh` — запуск юнита с доказательством:

* уже работающий или зависший юнит останавливается, и ожидание идёт до
  фактического `inactive`/`failed`, а не до возврата `systemctl stop`;
* выполняется `reset-failed`;
* запуск идёт через `restart --no-block`: `restart` гарантирует новый прогон
  даже для активного юнита, а `--no-block` возвращает управление сразу —
  `systemctl start` для `Type=oneshot` блокируется до конца работы, и наблюдать
  за собственным запуском было бы нечем;
* новая непустая `InvocationID` доказывается **пока юнит работает**, за 60 с;
* `Result` и `ExecMainStatus` снимаются в том же окне, а не после выгрузки;
* окончательное свидетельство даёт артефакт — расписка о сборке, ссылка
  `current`, манифест релиза, — а состояние systemd остаётся вспомогательным;
* если новый процесс не появился, попытка завершается за минуту с диагностикой;
* в журнал идёт содержательный прогресс не реже раза в четыре минуты, есть
  сторож по общему времени.

## Проверка

`tests/unit/test_release_runner_invocation.py` — восемь проверок на настоящей
пользовательской шине systemd, а не на подделке:

* дефект воспроизводится: сравнение «до и после» не отличает состоявшийся
  прогон от несостоявшегося, а `Result=success` у незапускавшегося юнита
  предъявлен явно;
* исправленный запуск получает непустую `InvocationID` во время работы;
* повторный запуск даёт **другую** `InvocationID`;
* запуск поверх уже работающего юнита проходит;
* упавший процесс ловится ожиданием, а не запуском;
* несостоявшийся запуск обнаруживается быстрее минуты и с диагностикой;
* упавший юнит сбрасывается `reset-failed` перед новым запуском.

Первая редакция проверки на отказ ожидала, что `unit_start_confirmed` отвергнет
юнит с несуществующим `ExecStart`. Настоящий systemd повёл себя иначе: такой
юнит получает `InvocationID` и падает уже потом. Проверка переписана по факту —
запуск отвечает за начало процесса, ожидание за его исход.
