## Что произошло

Юнит `lords-release-lords-02-20260908-195624.service` завершился `ROLLED_BACK`.
Отказ наступил **после** подмены ссылки, в фазе `switch`:

```
19:59:10 [switch] ворота содержимого до подмены ссылки
19:59:48 [switch] релиз f0b9fa3eff55
20:00:48 [switch] ссылка переключена: 2c9433994fc8 → f0b9fa3eff55
20:00:51 [switch] пишу манифест релиза f0b9fa3eff55 (домен lordserial33.biz, тема lords_dark)
20:00:51 [switch] манифест не записан — откатываю: витрина без манифеста перестаёт обновляться
20:00:51 [switch] ОТКАЗ: манифест релиза не записан; витрина возвращена на 2c9433994fc8
```

Всё, что было до этого, отработало правильно. Ворота содержимого прошли:
`catalog_titles 52573`, `expected_titles 53282`, `players_new 51842` против
`players_previous 51838` — плеер не только цел, но и полнее прежнего.
Сборка не запускалась: артефакт от 15:31 был принят повторно, как и задумано.
Откат отработал штатно, production остался на `2c9433994fc8`, таймер
обновления вернулся в `active`.

## Причина

`lords-refresh-guard.py adopt` вызывает `factory/lords/template_artifact.py::собрать`,
а тот выполняет

```
git -C /home/claude/wt-release-03 archive --format=tar.gz <ревизия>
```

Фаза `switch` идёт от **root**, а дерево принадлежит `claude:claude`. Git в
такой связке отказывается работать с чужим каталогом, `собрать` поднимает
`ArtifactError`, `adopt` возвращает 3, и сценарий честно откатывает витрину.
Архива `119605bbaca2.tar.gz` в `/srv/lords/.artifacts/templates/` нет — при
времени изменения каталога `20:00`, то есть попытка была и не удалась.

Этот урок в репозитории уже усвоен — но не везде. `lords-canary-provenance.py`
начинается словами: «Происхождение и целостность оснастки canary — **без git в
привилегированном пути**… git в той операции нужен был только ради двух вещей…
Обе достижимы без git и без доверия к чужому каталогу». Проверка происхождения
была переписана, а сборка артефакта — нет. Дефект пережил собственное
исправление, потому что исправление применили к одному вызову вместо класса.

Косвенное подтверждение: обновление каталога собирает артефакты успешно,
потому что работает с закреплённым деревом
`/srv/site-factory/lords-tooling/releases/41031da…`, принадлежащим `root`.

## Исправление

`factory/lords/template_artifact.py`: когда процесс идёт от root, а дерево
принадлежит другому пользователю, `git archive` выполняется **с понижением
прав до владельца дерева** — через `setgid`/`setuid` в потомке, без `sudo` и
без выдачи root доверия к чужому каталогу. Это движение прав вниз, а не вверх:
привилегированный процесс не начинает доверять чужому дереву, он перестаёт
быть привилегированным на время чтения.

## Что сделано для выкладки этой ночью

Кандидат заморожен на `f8f20dde…`, и правка продуктового файла сдвинула бы
HEAD, а вместе с ним — условие повторного использования сборки: пришлось бы
заново отрисовывать 61 733 страницы ради файла, который к отрисовке отношения
не имеет. Поэтому выкладка идёт с исправлением на уровне runner: архив
ревизии собирается **до** переключения, от владельца дерева, и укладывается в
хранилище артефактов правами root обычным копированием. `adopt` находит готовый
архив и ветку с `git archive` не исполняет вовсе.

Отпечаток шаблона от этого не меняется: `template_artifact.py` и
`lords-refresh-guard.py` не входят в набор из шестнадцати файлов, по которому
считается `a0cfaf71…4859`. Проверено, а не предположено.

Собранный архив: `119605bbaca2.tar.gz`, 25 419 211 байт,
SHA-256 `b5f409320a64513cfa802bc5def4d08aee57a15a472c443d550b165da81b5628`.
