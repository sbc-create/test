# Уровень 1. Общие правила сети

Это то, что обязан знать ЛЮБОЙ исполнитель любого домена. Здесь нет истории
сети и нет доказательств — только правила и ссылки. Подробности читаются
тогда, когда правило мешает, а не заранее.

Уровни знаний: **сеть** (этот файл) → **семейство**
(`docs/knowledge/family/<семья>.md`) → **паспорт домена**
(`docs/passports/<домен>.md`). Получить все три за один раз:

```bash
python3 automation/local/brief.py --domain <домен>
```

## 1. Что считается результатом

Состояния различаются и не подменяют друг друга:

`исследовано → подготовлено → проверено → опубликовано → эффект измерен`

* **коммит, написанный текст и зелёный тест — это «подготовлено»**, не
  «опубликовано» и тем более не рост трафика;
* «опубликовано» требует ЖИВОГО адреса и установленной версии;
* «эффект измерен» требует исходной точки, даты публикации и сопоставимого
  периода.

Цель владельца — **устойчивые 5000+ реальных визитов в сутки на КАЖДОМ
развиваемом сайте**. Общий трафик сети и разовый пик результат домена не
заменяют.

## 2. Измерения

* **Отсутствие данных — не ноль.** Недостижимый источник даёт «не измерено» с
  причиной;
* сравниваются только ПОЛНЫЕ сопоставимые периоды в Europe/Moscow с
  одинаковыми фильтрами; неполный день с полным не сравнивается;
* окно суточной выгрузки Метрики — «7 дней до вчера», поэтому соседние
  выгрузки перекрываются на шесть дней из семи: их разность — сдвиг окна, а
  не изменение;
* **сутки могут «дозреть»**: 11–13.10 пришли недосчитанными (первое чтение
  4–91 % от итогового). Перед сравнением недель устойчивость суток
  проверяется — `automation/local/metrika-day-settled.py`;
* поисковый трафик считается ВНУТРИ очищенного сегмента, а не из общего
  разреза по источнику: общий включает роботов;
* оценка стороннего сервиса — оценка, а не измерение, и помечается так.

## 2а. Как различить потерю показов от падения спроса (без Вебмастера)

Проверено на практике 22.10 (учебный блок L-003), метод из двух шагов:

1. **разделить множества**: поисковые визиты берутся из разреза
   `traffic_sources: organic`, а не из общего числа визитов. На
   `yummyani.site` это 12 885 из 57 111 — остальное не поиск. Поисковые
   системы тоже раздельно: у семи домéнов Яндекс даёт **ноль** при ненулевом
   Google, и сложение это скрывает;
2. **сравнить НАБОР страниц с поисковыми входами** по окнам ровно в семь
   суток врозь (`automation/local/search-page-set-shift.py`; ближе — окна
   перекрываются на шесть дней из семи):
   * набор сузился И входы упали → согласуется с потерей показов;
   * набор держится, входы упали → согласуется с падением спроса или позиций;
   * набор шире, входы не меньше → рост.

Когда трафика нет вовсе — **парное сравнение технических сигналов с соседом
по семейству, у которого трафик есть**. Совпали `robots.txt`, карта,
`meta robots`, `canonical` и режим в реестре → технические причины
исключены (проверено на четырёх парах: совпадают во всех).

**Чего метод не даёт:** он не доказывает индексацию (Метрика об индексе не
знает), не вычитает сезонность и выход новых серий, и считает по пределу
`top_n = 200` — на крупнейшем домене это 96.7 % поискового итога.

## 3. Доказательство и различающий контроль

* каждое число несёт источник, каждая находка — доказательство;
* **прежде чем записать находку, проверь признак там, где дефекта нет.**
  Признак, который кричит везде, не измеряет ничего. Это правило сняло больше
  половины ложных находок сети;
* проверять нужно УСТАНОВЛЕННЫЙ код, а не код ветки:
  `docker exec <контейнер> …`, `/srv/<ячейка>/current/`. Заголовки
  `x-site-factory-*` версией приложения НЕ являются;
* «проверено» без запуска — ошибка отчёта, а не стилистика.

## 4. Чего нельзя никогда

* ослаблять защиту ради автономности: хуки, схемы и проверки сильнее удобства;
* ослаблять схему, чтобы данные прошли; удалять или пропускать падающий тест;
* выдумывать факты: даты, состав, названия, позиции, объёмы;
* писать в постоянные данные сайта из выпуска, сборки, установщика и откат;
  они только ЧИТАЮТ (`docs/RUNTIME_DATA_OWNERSHIP.md`);
* расширять продвижение за канарейку без заслуженного вердикта — и это
  касается ЗАДАЧ ИЗ ИССЛЕДОВАНИЯ тоже: прежде чем завести задачу, проверь
  `python3 automation/local/running-experiments.py`. Реестр действующих опытов
  живёт в копии-владельце, в своей копии его может не быть (22.10 я из-за
  этого завела две задачи, повторявшие гипотезы идущих опытов).
  **Срок вердикта не равен вердикту:** политика требует минимум 14 суток И
  1 000 показов, а показы не измеряются (B023). Названные даты — следующая
  ОЦЕНКА, и «ждём вердикта к такому-то числу» писать нельзя;
* коммитить прямо в `main`.

## 5. Повторяющиеся ошибки сети и чем они закрыты

Полный перечень с причинами повторения —
[`docs/RECURRING_FAILURES.md`](../RECURRING_FAILURES.md). Коротко:

| ошибка | чем закрыта |
| --- | --- |
| исчезновение серий и сокращение карты | сверка МНОЖЕСТВ адресов, не чисел: `sitemap-part-monotonic.py`, `yummy-d1-acceptance.py` |
| ложная свежесть | дата части = изменение файла части; `metrika-day-settled.py` для суток |
| расхождение установленного и проверенного | приёмка привязана к версии на сайте (`network-state.py`, build-id) |
| домен выпал из работы | `cycle-coverage.py` + единственный список `config/active-domains.json` |
| привязка дефекта к домену по тексту | только поле `domains` реестра недостатков |

## 6. Как выбирается работа

Порядок, и он не обсуждается каждый раз:

1. срочные ПОДТВЕРЖДЁННЫЕ ошибки;
2. приоритетные задачи домена из его очереди (`config/domain-queues/`);
3. проверка опубликованного;
4. конкурентное исследование и обучение по конкретным пробелам
   (`config/learning-queue.json`).

Этап домена (1 — убрать препятствия, 2 — использовать спрос, 3 — расширять
охват) **считается по измерениям**, а не назначается по порядку: исправному
сайту задержка перед ростом не создаётся.

Заблокированная задача не останавливает работу: берётся независимая задача
другого домена. Ожидание срока измерения — не простой, но и не повод не
делать ничего.

**Срок отчёта — контрольная точка, а не конец работы.** Это исправление
измеренной ошибки 22.10: на сроке ночного отчёта была остановлена вся
очередь, хотя доступные задачи были. На сроке делается три вещи — текущая
операция доводится до безопасного состояния, недовыполнение записывается в
отчёт, следующая готовая задача берётся СРАЗУ и без запроса разрешения.
Останавливает работу доказанное внешнее ограничение конкретной задачи, а не
часы. Отчёты 10:00 / 18:00 / 22:00 МСК — контрольные точки того же типа.

## 7. Границы доступа (их не обходят)

* внешний мир закрыт, кроме хостов из `inventory/network-allowlist.yaml`;
  неограниченный поиск по интернету запрещён хуком;
* из источников конкурентов сохраняются только СТРУКТУРНЫЕ факты и
  измерения; тексты, изображения, каталог и идентификаторы — нет;
* `ssh`/`scp`/`rsync`/`ansible` в цели запрещены: только штатный выпуск;
* секреты только через `secret_ref`; значение не попадает в git, лог, отчёт и
  prompt;
* `systemctl`, `journalctl` и произвольный `sudo` сессии недоступны — то, что
  требует их, готовится блоком команд для владельца с проверкой и откатом.
