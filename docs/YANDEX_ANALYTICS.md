# Яндекс.Метрика и Яндекс.Вебмастер

Эксплуатационное описание слоя аналитики. Контракт API — замороженная выжимка
официальной документации в `knowledge/YANDEX_ANALYTICS_CONTRACT.yaml`;
архитектурные решения — D50…D67 в `knowledge/DECISIONS.md`.

## Секрет

Токен лежит вне репозитория:

```
/etc/site-factory/secrets/yandex_oauth_token   root:root 0600
```

Путь настраивается переменной `YANDEX_OAUTH_TOKEN_FILE`. В переменной — **путь**,
никогда значение. Значение токена в `YANDEX_OAUTH_TOKEN`, `YANDEX_METRIKA_TOKEN`
или `YANDEX_WEBMASTER_TOKEN` считается ошибкой и останавливает работу: обходной
путь появляется ровно тогда, когда его не проверяют.

Сессия агента прочитать токен не может и не должна: каталог секретов закрыт
(`drwx------ root:root`). Сервисы получают секрет через systemd:

```ini
LoadCredential=yandex_oauth:/etc/site-factory/secrets/yandex_oauth_token
Environment=YANDEX_OAUTH_TOKEN_FILE=%d/yandex_oauth
```

systemd читает root-owned файл от имени PID 1 и кладёт копию в tmpfs, доступную
только этому процессу. Значение не появляется ни в окружении, ни в
`systemctl show`, ни в журнале.

Проверить состояние секрета, не читая его:

```bash
python3 -m factory analytics probe
```

Команда печатает права файла, HTTP-статусы обоих API и подтверждённые
возможности. Токена, его части и отпечатка в выводе нет.

## Команды

```bash
python3 -m factory analytics probe          # доступ: статус файла и HTTP-коды
python3 -m factory analytics plan           # что будет сделано; ни одной записи
python3 -m factory analytics status [--live]# состояние из реестра, опционально сверка с API
python3 -m factory analytics apply          # то же, что plan: без флага записи нет
python3 -m factory analytics apply --confirm-writes   # единственная команда, создающая счётчики
python3 -m factory analytics webmaster      # план регистрации; без --deployment-ready ничего не делает
python3 -m factory analytics report         # read-only отчёт Метрики
python3 -m factory analytics rotate-check   # пригоден ли токен, не пора ли менять
python3 -m factory analytics disable --domain <d> --confirm-writes
python3 -m factory analytics codegen        # перегенерировать клиент событий
python3 -m factory analytics events         # контракт событий в JSON
python3 -m factory analytics marker         # разметка подтверждения прав
./bin/seo-operator analytics-collect        # ежедневный read-only сбор
```

Запись включается единственным флагом `--confirm-writes`. Разрешение даётся
команде, а не режиму работы.

## Создание трёх счётчиков

Запускает человек, от учётной записи с доступом к секрету:

```bash
sudo systemctl start site-factory-analytics-apply.service
sudo journalctl -u site-factory-analytics-apply.service --no-pager -n 50
```

Unit разовый, таймера у него нет. Повторный запуск дубля не создаёт: провайдер
сперва ищет счётчик по точному нормализованному домену и, найдя, переиспользует
его. Найдя два счётчика на один домен, он ничего не выбирает — возвращает
состояние `ambiguous` и оставляет решение владельцу.

После запуска реестр `config/analytics.json` получает публичные counter ID.
Это единственное, что сохраняется в git: токен и client secret — никогда.

Если Метрика откажет из-за неподписанного соглашения об обработке данных, отказ
придёт дословно вместе с HTTP-статусом. Фабрика не отправляет
`gdpr_agreement_accepted`: принимать соглашение за владельца аккаунта она не
вправе (D55).

## Вебмастер

Порядок готов целиком, но выполняется только после того, как домен ответит по
HTTPS:

1. `ensure_webmaster_host` — добавление точного HTTPS-хоста;
2. `get_verification_marker` — получение `verification_uin`;
3. маркер печатается в каждую сборку мета-тегом
   `<meta name="yandex-verification" content="…" />` (или файлом
   `yandex_<код>.html`);
4. проверка доступности маркера по HTTP — снаружи, оператором;
5. `verify_webmaster_host` — запуск подтверждения;
6. контроль статуса через `analytics status --live`.

До этого состояние домена — `BLOCKED_DEPLOYMENT`. Это не ошибка и не `DONE`: это
отложенный шаг. Запускать подтверждение при недоступном маркере фабрика
отказывается — такой запуск даёт `VERIFICATION_FAILED` и портит историю проверок.

Маркер сохраняется в реестре и печатается при каждой сборке: Яндекс перепроверяет
права, и релиз, потерявший мета-тег, теряет подтверждение вместе с ним.

## Индексация

`SEO_INDEXING_ENABLED=false` в `config/analytics.json` и `seo_indexing_enabled:
false` в каждом пакете. Индексация включается только при одновременном
выполнении всех условий:

* домен направлен на утверждённый production-сервер;
* HTTPS работает и сайт отвечает 200;
* robots и sitemap прошли проверку;
* `production_authorized: true` в manifest;
* права в Вебмастере — `VERIFIED`;
* `seo_indexing_enabled: true` и в пакете, и в реестре;
* отдельное подтверждение владельца.

Одно невыполненное условие — отказ с его названием
(`factory.analytics.gate.indexing_allowed`). Sitemap в поисковые системы не
отправляется: ресурсы `user-added-sitemaps` и `recrawl/queue` фабрика не
вызывает.

## События и цели

Девять событий, одинаковых для трёх счётчиков:
`search`, `filter_apply`, `title_view`, `season_select`, `episode_select`,
`player_start`, `player_ready`, `player_error`, `comment_submit`.

Каждому соответствует цель Метрики типа `action` с условием
`{"type": "exact", "url": "<идентификатор события>"}`.

Клиент генерируется из `factory/analytics/events.py` в два файла:

* `themes/basis-video/assets/analytics.js` — обычный JavaScript для темы;
* `blueprints/payload-next-multisite/app/src/lib/analytics.ts` — типизированный
  клиент для Next-блюпринта.

Оба файла сгенерированы; правка руками ловится тестом. Сайты используют клиент,
не копируя код:

```js
window.siteAnalytics.track('player_error', { title_id: 'naruto', error_code: 'no_data' });
```

```ts
import { track } from '@/lib/analytics';
track('episode_select', { title_id: 'naruto', season_number: 1, episode_number: 3 });
```

Передавать можно только технические идентификаторы и категориальные значения из
перечислений. Текст комментария, имя, e-mail, поисковый запрос, токен и
Publisher ID отправить нечем: типа «свободный текст» в описании параметров не
существует, а запрещённые имена отбрасываются до сверки со списком разрешённых.

Клиент молчит и **не загружает тег Метрики вообще**, если:

* окружение не production;
* hostname не совпал точно с разрешённым;
* counter ID отсутствует;
* сбор выключен (`data-analytics-enabled="false"`).

Вебвизор выключен явно в вызове `init` и не настраивается фабрикой.

## Ежедневный сбор

```bash
./bin/seo-operator analytics-collect --json
```

Собирает четырнадцать показателей по каждому домену: посетители, визиты,
источники трафика, поисковые системы, входные страницы, глубина просмотра, время
на сайте, отказы, достижение целей, популярные страницы, страницы в поиске,
исключённые страницы с причинами, внешние ссылки, технические проблемы
Вебмастера.

Показатель, который не удалось измерить, попадает в отчёт как `не измерено` с
причиной. Ноль означает «Яндекс вернул ноль», и ничего больше.

Таймер `site-factory-analytics-collect.timer` **установлен, но не включён**:
пока ни один сайт не развёрнут, ежедневный отчёт состоял бы из одних «не
измерено». Включать после появления первого работающего production-сайта:

```bash
sudo systemctl enable --now site-factory-analytics-collect.timer
```

## Отказы

| Статус | Когда | Что делать |
| --- | --- | --- |
| `BLOCKED_SECRET` | файла секрета нет, права слишком открытые, состояние не измерено | `chown root:root`, `chmod 0600`; запускать из unit'а с `LoadCredential` |
| `BLOCKED_ANALYTICS_ACCESS` | API недоступен, 401/403, повторы 429/5xx исчерпаны | проверить токен `analytics rotate-check`; статус нерепитабельный, конвейер не продолжит с выдуманными данными |
| `BLOCKED_INPUT` (analytics.*) | нет counter ID, hostname не совпал, включён Вебвизор | заполнить пакет; счётчик создать `analytics apply --confirm-writes` |
| `BLOCKED_SEO` (seo_indexing_enabled) | индексация включена раньше выполнения условий | выключить до подтверждения прав и авторизации production |
| `ambiguous` | два счётчика на один домен | выбрать нужный вручную в Метрике; фабрика не выбирает |

## Что фабрика не делает

* не удаляет счётчики, цели и сайты — удаление необратимо;
* не создаёт зеркала: три домена остаются тремя независимыми счётчиками;
* не включает Вебвизор;
* не отправляет sitemap и не заказывает переобход;
* не меняет DNS;
* не включает индексацию без отдельного подтверждения владельца.
