# Владение модулями

Каждый модуль Site Engine отвечает за одну вещь и имеет ровно одного владельца
данных. Правило существует не ради красоты: почти все инциденты фабрики были
инцидентами размытого владения — SEO трогал каталог, витрина сама ходила к
поставщику, загрузчик решал, что показывать на главной.

| Модуль | Владеет | Не владеет | Читает |
| --- | --- | --- | --- |
| `content-ingestion` | сырыми ответами поставщика, кэшем каталога, состоянием обхода | версткой, порядком полок, метаданными SEO | адаптером поставщика |
| `content-catalog` | нормализованными тайтлами, каноническими идентификаторами | сырыми ответами | результатом ingestion |
| `episodes-seasons` | сезонами, эпизодами, дельтой серий | доступностью плеера | каталогом |
| `playback-availability` | признаком «смотрибельно» | эпизодами | каталогом, сезонами |
| `homepage-shelves` | составом и порядком полок | содержимым тайтлов | каталогом, эпизодами, рейтингами |
| `ratings` | оценками из подтверждённых источников | тайтлами | внешними идентификаторами каталога |
| `news-announcements` | новостями и анонсами | каталогом | каталогом, расписанием |
| `seo` | метатегами, канониклами, картой сайта, разметкой | каталогом, поставщиком, версткой | нормализованным контентом |
| `site-configuration` | профилем сайта, флагами | данными | схемой профиля |
| `cache-invalidation` | тегами и их сбросом | данными | контрактом событий |
| `monitoring-audit` | метриками покрытия, алертами | данными | всеми модулями |
| `provider-adapters` | переводом чужого API в наш контракт | нормализацией смысла | внешним API |
| `renderer-adapters` | переводом нормализованного контента в страницы | данными | каталогом, полками |

## Три правила, которые проверяет гейт

1. **SEO не владеет каталогом и не ходит к поставщику.** Ему нужен
   нормализованный контент — но не обязательно собственный загрузчик. Источником
   может быть локальный `content-ingestion`, общий Site Engine API либо другой
   зарегистрированный адаптер; см. `normalized_content_source` в схеме профиля.
2. **Витрина не обращается к поставщику напрямую.** Только через
   `provider-adapters` и только внутри `content-ingestion`.
3. **Ядро не знает названий сайтов.** Ни `lords`, ни `yummy` не должны
   встречаться в общем коде — различия живут в профилях.

## Почему требование сформулировано как способность

Первая редакция правила требовала у сайта с SEO модуль `content-ingestion`.
Это запрещало правильную схему: витрину, которая берёт готовый нормализованный
контент из общего API и ничего не загружает сама. Такой сайт не нарушает
разделение — наоборот, соблюдает его строже. Требование переписано как
способность (`normalized-content`), а не как конкретный модуль.
