## Что проверить независимо

1. **Повторить замер.** `node tests/tools/measure_reference.js https://amd.online/
   <out> 390,768,1440` и сверить с `VISUAL_TOKENS.yaml` в пределах указанных
   допусков. Референс — живой сайт: расхождение в высоте страницы ожидаемо,
   расхождение в ширине контейнера или кегле — нет.
2. **Сверить дайджесты снимков.** Они в `SCREENSHOT_INDEX.md`; сами PNG лежат в
   evidence-каталоге задания и в git не входят.
3. **Проверить, что пакет не содержит чужих ассетов** — тест это делает, но
   глазами тоже стоит.
4. **Проверить, что исключения не менялись** после появления оценки кандидата.

## Два блокера, которые замером не закрываются

**1. Диапазоны совместимости.** `compatibility.apiVersionRange`,
`sdkVersionRange`, `seoContractVersionRange` остаются `pending`. Это решение об
архитектуре, а не величина с чужой страницы. Нужен владелец контракта.

**2. Нет утверждённого алгоритма визуального сравнения.** Это главное.
`TEST_INVENTORY.md` фиксирует его отсутствие, в `schemas/reference-pack.schema.json`
полей оценки нет, порог 80 % не описан ни в одном versioned-документе —
он встречается только в текстах заданий.

Пока алгоритма нет, **сравнивать кандидата с этим пакетом нельзя**: токены
измерены, но правила, превращающего их в один процент, не существует.
Назначить веса и порог тем же заданием, которое потом по ним аттестуется,
запрещено — это подгонка.

## Порядок следующих шагов

1. `TEMPLATE-REFERENCE-PACK-AMD-ONLINE-CHECKER-02` — независимая проверка этого
   пакета по списку выше.
2. Отдельное задание: **создать versioned алгоритм визуального сравнения** —
   компоненты, веса, допуски, правило исключений, детерминированный расчёт.
   Его автором не должен быть ни автор пакета, ни автор кандидата.
3. Владелец контракта заполняет диапазоны совместимости.
4. Только после 1–3 имеет смысл повторять визуальный компонент PR #76.
