# Читающее API каталога для мобильного/TV-клиента

Ответ на передачу `ott-app-sandbox` от 2026-10-11
(`docs/handoff/2026-10-11-architect-app-read-api.md`, прочитан локально по пути
`/home/claude/projects/ott-app-sandbox/docs/handoff/`).

Служба: `automation/host/app-read-api.py`. Только GET, только чтение, отдельный
процесс и отдельный порт.

## 1. Что у фабрики уже было и чего не было

Проверено по выложенному коду витрин, а не по памяти.

| возможность | состояние до этой задачи |
| --- | --- |
| каталог и поиск машинно | **нет.** У витрин маршруты `/`, `/healthz`, `/robots.txt`, `/sitemap.xml`, `/sitemap-N.xml`, `/assets/nova.webmanifest`, `/__template_version`, `/poster/…` и страницы. JSON-эндпоинтов каталога нет ни у lords, ни у zona, ни у animedia |
| карточка, сезоны, серии | только HTML-страницы |
| изображения | **есть**: `/poster/<uuid>.webp` — первосторонний прокси витрины (у семейства animedia включён по умолчанию, у lords/zona выключен). Исходные постеры — `poster.cdnvideohub.com` |
| метаданные | **есть в данных**: названия русское и оригинальное, год, жанры, описание, оценки по источникам, внешние id, число серий и доступных серий. Лежат в снимке витрины (`<site>-catalog.json`, `<site>-details.json`) |
| разрешённый источник видео | **нет.** См. §5 |

Поэтому добавлено минимальное дополнение: служба, которая читает ТЕ ЖЕ файлы
снимка и отдаёт их в форме, запрошенной клиентом. Витрины, их рантайм и плееры
не затронуты: это отдельный процесс рядом.

## 2. Адрес и порядок доступа

Служба слушает `127.0.0.1` и наружу выходит через nginx того же домена:

    https://<домен витрины>/api/app/v1/…

Первый источник — **animedia.icu** (8 547 тайтлов, снимок 14 МиБ, свой прокси
постеров). Служба читает `/srv/animedia-icu/data`, память измерена: **108 МиБ**
RSS на полном снимке.

Установка — одной командой владельца (готовый установщик, не пример):

    sudo bash /home/claude/wt-nova-publish-memory-02/automation/host/install-app-read-api.sh

Он ставит юнит `app-read-api-animedia-01.service` — только чтение:
`ProtectSystem=strict`, ни одного `ReadWritePaths`, `ReadOnlyPaths` на каталог
данных, `MemoryMax=512M` (измерено 108 МиБ), `IPAddressAllow=localhost`.
Создаёт ключ клиента `/etc/app-read-api/client-key` (0640 root:claude) в
СВОЁМ каталоге (0710 root:claude — проход только нужной учётной записи) и
**значение не печатает**: передача через файл, см. §2. Добавляет сниппет nginx
`/etc/nginx/snippets/app-read-api-animedia-01.conf` с `location /api/app/v1/` и
одну строку `include` в HTTPS-блок `/etc/nginx/lords/animedia-01.conf`, сняв
копию файла. Существующие маршруты витрины не меняются.

Откат ровно этих изменений:

    sudo bash /home/claude/wt-nova-publish-memory-02/automation/host/install-app-read-api.sh --rollback

### Адрес проверки состояния — внутри префикса

    https://animedia.icu/api/app/v1/healthz        ← этот, ключ не нужен

**Корневой `/healthz` — НЕ наш.** В конфигурации витрины уже стоит
`location = /healthz`, и он ведёт в саму витрину; трогать её маршрут нельзя.
Служба отвечает состоянием по обоим адресам, но наружу отдан только путь внутри
`/api/app/v1/`, и клиент обязан спрашивать именно его.

Как читать ответы на этом адресе — четыре РАЗНЫХ случая, которые раньше
сливались в один:

| что видно | что это значит |
| --- | --- |
| `308` и `Location` с хвостовым слешем, затем `404` и HTML-страница витрины | маршрута нет: служба не установлена. Перенаправление делает сама витрина — она так отвечает на любой неизвестный путь. Измерено 2026-10-10 на `https://animedia.icu/api/app/v1/healthz`: `308 → /api/app/v1/healthz/ → 404`, тело — страница «Страница не найдена — Animedia» (131 КБ) |
| `200` и JSON `{"ready":true,…}` | служба установлена и готова |
| `503` и JSON `{"ready":false,"keyConfigured":false,…}` | служба работает, но ключ клиента на сервере не настроен — данные закрыты |
| `502`/`504` от nginx | маршрут есть, служба не отвечает |
| `401` на путях ДАННЫХ | служба работает, ключ не тот или не прислан |

### Ключ клиента `X-App-Key`

Заголовок `X-App-Key`, значение — ASCII. **Ключ обязателен всегда.** Если файла
ключа на сервере нет или он пуст, служба не отдаёт данные вовсе (401 на любой
путь данных), а состояние отвечает **503** с `ready: false`,
`keyConfigured: false` и названной причиной. Прежняя версия в этом случае
отвечала всем — это было разрешение доступа по недосмотру, и оно устранено до
вывода службы наружу.

#### Где он лежит и почему именно там

    /etc/app-read-api/          0710 root:claude   проход только учётной записи службы
    /etc/app-read-api/client-key 0640 root:claude  сам ключ
    /etc/app-read-api/rotations.log                отметки поворотов, БЕЗ значений

**Почему не вместе с серверными секретами.** Первая попытка установки
2026-10-11 положила ключ в `/etc/site-factory/secrets/` и остановилась:
«учётная запись claude не читает ключ». Причина была не в файле — он был создан
верно, `0640 root:claude`, — а в пути: `/etc/site-factory` имеет права
`0700 root:root`, то есть непроходим ни для кого, кроме root. Выдать группе
проход по этому каталогу значило бы открыть дорогу и к настоящим серверным
секретам, которые там лежат. Клиентский ключ серверным секретом не является,
поэтому у него теперь свой каталог с проходом ровно для нужной учётной записи;
права чужих секретов не менялись вовсе.

Отказ установщика теперь называет составляющую пути, на которой доступ
кончается («каталог … непроходим для claude, права 700, владелец root:root»),
а не общее «не читает ключ».

#### Как значение попадает в приложение

**Значение не печатается ни установкой, ни поворотом.** Напечатанный один раз
ключ 2026-10-11 попал в переписку и тем самым стал раскрытым — «показывается
один раз» защитой не является, потому что вывод терминала копируется.

Передача — через файл, в момент внесения в секрет CI приложения:

    sudo cat /etc/app-read-api/client-key

**Имя файла — `client-key`, через ДЕФИС.** Файла `client.key` с точкой не
существует и никогда не существовало: установщик создаёт
`KEY_FILE="${KEY_DIR}/client-key"`, и то же имя стоит в `--key-file` работающей
службы. Написано здесь отдельной строкой потому, что 2026-10-12 владелец
проверял путь с точкой, получил «KEY_FILE_MISSING» и сделал верный вывод из
неверного замера: ключ есть, а его сочли отсутствующим. Фактическое состояние
на эту дату — файл на месте, 43 байта, `root:claude`, режим `0640`, без
хвостового перевода строки.

Проверить СУЩЕСТВОВАНИЕ, не печатая значение:

    sudo test -s /etc/app-read-api/client-key && echo "ключ на месте и непуст"

Проверить ПРИГОДНОСТЬ, тоже не печатая значение: без ключа API обязан ответить
401, с ключом — 200. Если нужен готовый прогон,
`automation/local/app-api-acceptance.py --key-file /etc/app-read-api/client-key`
делает это и значение не выводит.

Значение не остаётся ни в выводе установки, ни в отчётах, ни в передачах. Поворот
не сохраняет копию прежнего значения: копия раскрытого ключа на диске — тот же
раскрытый ключ, только живущий дольше.

**Это ограниченный клиентский ключ, а не серверный секрет.** Разница
практическая, а не словесная:

* ключ попадает в APK. **Передача через GitHub Secrets не делает его секретным
  после сборки:** в собранном приложении он лежит строкой, и извлечь его может
  любой, у кого есть файл APK. Поэтому ключ не считается тайной и ни одна
  проверка прав на него не опирается;
* что он всё-таки даёт: закрывает путь от случайных обходчиков и чужих
  скриптов, позволяет считать частоту по клиенту (120 запросов в минуту) и
  **отзывать доступ** — ключ меняется одной командой
  `sudo bash …/install-app-read-api.sh --rotate-key` (прежнее значение
  сохраняется рядом с отметкой времени, служба перезапускается, прежние сборки
  перестают получать данные);
* почему этого достаточно: служба отдаёт **тот же каталог, который витрина
  показывает публично** — названия, обложки, жанры, оценки, число серий.
  Ничего, что не видно на сайте, в ответах нет;
* **серверные секреты в приложение не попадают и попадать не должны.** Токены
  провайдера, ключи очереди, доступы Яндекса служба не читает и в ответах не
  упоминает; её файл ключа — отдельный, созданный установщиком только для неё
  (`/etc/app-read-api/client-key`, 0640 root:claude). Когда у
  провайдера появится разрешённый источник видео, подписывать ссылки будет
  СЕРВЕР, и его ключ останется на сервере — в приложение уедет только готовая
  короткоживущая ссылка (п. 5.1, пункты 2 и 3).

Ограничения: 120 запросов в минуту на адрес (сверх — 429 с `Retry-After: 60`),
`Cache-Control: public, max-age=300`, предел страницы 50. Каждый ответ несёт
`X-Catalog-Revision` — по нему клиент видит, что снимок сменился.

## 3. Контракты и примеры (измерены на живых данных)

### `GET /healthz`

```json
{"ok":true,"version":"app-read-api/1","site":"animedia-01","titles":8547,
 "catalogRevision":"38734293c92f1fcff6bd1e38f494824d",
 "catalogBuiltAt":"2026-10-10T11:46:13Z"}
```

### `GET /api/app/v1/search?q=…&cursor=&limit=20`

```json
{"items":[{"contentId":"01915145-2c16-7ba4-8353-42b73d657fdc",
           "slug":"stalnoy-alhimik-bratstvo","type":"SERIES",
           "titleRu":"Стальной алхимик: Братство",
           "originalTitle":"Fullmetal Alchemist: Brotherhood",
           "year":2009,"genres":["аниме","боевик","драма"],
           "synopsis":"Ремейк одноимённого аниме-сериала…",
           "rating":null,
           "artwork":{"posterUrl":"https://poster.cdnvideohub.com/01915145-….webp"},
           "externalIds":[{"namespace":"imdb","value":"1355642"},
                          {"namespace":"kinopoisk","value":"452838"}],
           "addedAt":"2024-11-12"}],
 "nextCursor":"20","total":5}
```

Поиск идёт по русскому И оригинальному написанию. `cursor` — смещение строкой;
`nextCursor: null` означает конец. `rating` остаётся `null`, когда оценки в
снимке нет: нулей не выдумываем.

### `GET /api/app/v1/titles?sort=added&genre=&cursor=&limit=`

Список для главной: та же форма, что у `search`, плюс два добавленных поля.
Маршрут был в службе, но не был описан здесь — пробел закрыт 12.10 по вопросу
разработчика приложения (`APP_TO_FACTORY-002`).

```json
{"rule":"added: порядок по дате добавления в снимок каталога",
 "genre":null,
 "items":[ … тот же объект Title, что у search … ],
 "nextCursor":"20","total":8552}
```

| параметр | поведение |
| --- | --- |
| `sort` | только `added`; любое другое значение — **400** `bad_request`, «sort поддерживает только added: других измеренных порядков у снимка нет» |
| `genre` | приводится к нижнему регистру; пустой — без фильтра |
| `cursor` | смещение числом, отрицательное поднимается до 0; нечисло — 400 |
| `limit` | по умолчанию 20, обрезается сверху пределом страницы |

`rule` в ответе не украшение: правило порядка названо текстом, чтобы клиент не
угадывал смысл `added` и чтобы правило нельзя было поменять молча. `genre` —
эхо применённого фильтра: по нему видно, что параметр понят так, как прислан.

Отказ на неизвестном `sort` сделан по тому же правилу, что `rating: null`:
порядка «по популярности» в снимке нет, данных о просмотрах нет, и выдуманное
правило не появится — иначе клиент получил бы несуществующий порядок и принял
его за настоящий.

Измеренный предел полки по жанру: на снимке `animedia.icu` из 8552 записей
**184 без жанров**, и все 184 — «не спрошены у источника» (покрытие добирается,
`automation/local/genre-coverage-audit.py`). Ряд по жанру поэтому не содержит
части записей, и это свойство снимка, а не дефект API или клиента.

### `GET /api/app/v1/titles/{contentId}`

Тот же объект `Title`. `contentId` — постоянный UUID записи из снимка, он же
ключ редакционных правок, поэтому не меняется при обновлении каталога.

### `GET /api/app/v1/titles/{contentId}/seasons`

```json
[{"seasonId":"01915145-…:s1","contentId":"01915145-…","number":1,
  "episodeCount":64,"availableCount":64,"isSpecial":false}]
```

Нулевой сезон отдаётся с `isSpecial: true`.

**Двоеточие в идентификаторах можно кодировать.** `seasonId` и `episodeId`
несут двоеточие (`<contentId>:s1:e3`), и обе формы адреса равнозначны:

    /api/app/v1/seasons/<contentId>:s1/episodes
    /api/app/v1/seasons/<contentId>%3As1/episodes      — то же самое

Так требует RFC 3986 (§2.2, §6.2.2.2), и это важно для клиентов, чей HTTP-слой
кодирует путь целиком. До 2026-10-11 закодированная форма отдавала 404 —
наблюдение приложения, воспроизведённое на публичном адресе и исправленное.
Закодированный РАЗДЕЛИТЕЛЬ (`%2F`) разделителем не становится: он не делит
сегмент на два, и такой запрос отвергается с 400 — иначе это была бы подмена
маршрута.

### `GET /api/app/v1/seasons/{seasonId}/episodes`

```json
[{"episodeId":"01915145-…:s1:e1","seasonId":"01915145-…:s1",
  "contentId":"01915145-…","displayNumber":"1","order":1001,"available":true}]
```

**Честная оговорка.** В снимке есть ЧИСЛА — сколько серий в сезоне и сколько из
них доступно, — а названий и длительностей отдельных серий нет. Поэтому серии
строятся из этих чисел: `displayNumber` 1…N, `available` по порогу доступных.
Полей `title` и `durationSec` в ответе нет вовсе — вместо выдуманных значений.

### `GET /api/app/v1/episodes/{episodeId}/sources`

```json
{"sources":[],"reason":"NO_SOURCE_CONTRACT_RELEASED",
 "embed":{"kind":"provider-web-component","provider":"cdnvideohub",
          "note":"прямой поток фабрикой не выдаётся…",
          "providerRefs":[{"provider":"mali","sourceId":"7902",
                           "availability":"available"}]}}
```

### `GET /api/app/v1/episodes/movie/sources?contentId={contentId}`

Форма адреса ДЛЯ ФИЛЬМА, то есть для записи без сезонов: у фильма нет
`episodeId`, и тайтл называется параметром. Это форма из задания клиента,
поэтому поддержана как есть. Ответ — тот же объект, что выше:

```json
{"sources":[],"reason":"NO_SOURCE_CONTRACT_RELEASED","embed":{…}}
```

Проверено на живых данных 2026-10-10 (служба на петле, снимок 8 547 тайтлов):
фильм «10 жизней (2024)» — 200 и `NO_SOURCE_CONTRACT_RELEASED`; та же форма с
идентификатором сериала тоже отвечает 200 — различать фильм и сериал обязан
клиент, служба здесь не возражает. Без `contentId` — 400
(`для фильма нужен contentId в запросе`).

`reason` всегда **`NO_SOURCE_CONTRACT_RELEASED`** — постоянное ограничение, а
не временная пустота: прямых ссылок, разрешённых договором для приложения, у
фабрики нет. `embed.providerRefs` показывает, что у записи есть у провайдера
(список может быть пустым). Поле `embed` добавлено сверх запрошенного контракта
и объясняет машинно, почему список пуст; игнорировать его можно.

Перечень серий построен **по числу серий в снимке**, а не по подтверждённой
доступности воспроизведения: `episodeCount` и `availableCount` — числа
каталога. Наличие 64 серий в ответе НЕ означает, что хоть одна из них
воспроизводится в приложении.

### Ошибки

| код | тело | когда |
| --- | --- | --- |
| 400 | `{"error":{"code":"bad_request","message":"q обязателен, от 2 до 100 знаков"}}` | пустой, короткий или слишком длинный `q`; нечисловые `cursor`/`limit` |
| 401 | `{"error":{"code":"unauthorized","message":"нужен заголовок X-App-Key"}}` | ключ задан на сервере и не прислан |
| 404 | `{"error":{"code":"not_found","message":"тайтла нет в снимке"}}` | нет тайтла, сезона или маршрута |
| 429 | `{"error":{"code":"rate_limited","message":"не больше 120 запросов в минуту"}}` + `Retry-After: 60` | превышена частота |

Коды 403 и 410 из запроса клиента служба не возвращает: прав на запись у неё
нет, а истекающих ссылок она не выдаёт, потому что не выдаёт ссылок вовсе.

## 5. Источник видео: остаётся отдельным блокером

Различение, которого требует задача:

* **iframe/веб-компонент сайта.** Витрина подключает скрипт провайдера
  `https://player.cdnvideohub.com/s2/stable/video-player.umd.js` и ставит на
  страницу элемент `<video-player data-publisher-id=… data-title-id=… data-aggregator=…>`.
  Поток запрашивает САМ компонент внутри своего cross-origin кадра. Контракт
  плеера (`knowledge/cdnvideohub/PLAYER_CONTRACT.yaml`) прямо запрещает
  оборачивать его в свой iframe и называет внутренний кадр деталью реализации
  провайдера;
* **прямой поток для нативного плеера.** Его у фабрики нет. В снимке по каждой
  записи лежат только ссылки вида `{"provider":"kp","source_id":"1171952",
  "player_id":null,"availability_status":"available"}` — это идентификаторы у
  провайдера, а не HLS/DASH/MP4. Документированный контент-API провайдера
  (`knowledge/cdnvideohub/content-api.yaml`, база
  `https://public-api.cdnvideohub.com/api/v1/`) содержит эндпоинты
  `titles`, `titles/{id}`, `titles/search`, `titles/filters`,
  `titles/{id}/seasons`, `titles/{id}/seasons/{season}/episodes`, `genres`,
  `countries` — и **ни одного эндпоинта потока или плейлиста**.

Вывод прямой: каталог, поиск, карточки, сезоны, серии и обложки приложение
получает по-настоящему, **воспроизведение — нет**. Это блокер договора, а не
техники, и обойти его нечем: обходить защиту провайдера запрещено и условием ТЗ
клиента, и правилами фабрики.

Что сняло бы блокер: договорённость с провайдером (или другим правообладателем)
о выдаче прямых разрешённых ссылок приложению. Тогда `/sources` отдаёт их с
сервера, секреты остаются на сервере, а форма ответа уже готова — заполнится
массив `sources`, и `reason` исчезнет.

### 5.1. Чего именно не хватает у провайдера — перечень для разговора с ним

Список составлен по замороженному контракту провайдера
(`knowledge/cdnvideohub/content-api.yaml`, `PLAYER_CONTRACT.yaml`): каждая
строка — возможность, которой в документированном API **нет**, и без которой
нативный плеер приложения работать не может. Ни одна из них не обходится
технически с нашей стороны: это предмет договорённости, а не доработки.

| № | Чего нет у провайдера | Зачем это приложению | Что сделаем мы, когда появится |
| --- | --- | --- | --- |
| 1 | **Правовое разрешение** воспроизводить вне их веб-компонента. Контракт плеера прямо называет внутренний кадр деталью реализации и запрещает оборачивать компонент | без этого пункта остальные девять бессмысленны: даже рабочая ссылка не даёт права её играть | фиксируем разрешение в `knowledge/` отдельным источником и снимаем `NO_SOURCE_CONTRACT_RELEASED` |
| 2 | **Эндпоинт выдачи плейлиста** по тайтлу и серии, отдающий HLS-манифест (`application/vnd.apple.mpegurl`) или DASH | ExoPlayer/AVPlayer играет манифест; идентификатора `source_id` ему недостаточно | добавляем серверный вызов в `sources`, заполняем `url` и `container` |
| 3 | **Серверная авторизация** выдачи ссылок (ключ или подпись запроса server-to-server) и срок жизни ссылки | ключ провайдера не должен попадать в APK; ссылка обязана быть короткоживущей | ключ держим в `secret_ref`, клиенту отдаём только готовую ссылку и её `expiresAt` |
| 4 | **Описание защиты контента**: есть ли DRM (Widevine/FairPlay/PlayReady), адрес сервера лицензий, обязательные заголовки | приложение обязано знать это до сборки: DRM меняет плеер и требования к устройству | добавляем в ответ `sources[].drm` с адресом лицензий и заголовками |
| 5 | **Перечень дорожек**: языки звука и субтитров по серии | аниме смотрят с озвучкой или сабами; выбор дорожки — не роскошь | поля `audio[]` и `subtitles[]` в `sources[]` |
| 6 | **Соответствие идентификаторов**: подтверждение, что наш `{"provider":"kp","source_id":"…"}` — тот же ключ, которым запрашивается поток, или эндпоинт сопоставления | иначе ссылку не запросить даже при наличии эндпоинта | берём `source_id` как есть либо вызываем сопоставление перед выдачей |
| 7 | **Признак воспроизводимости**, отличный от каталожной доступности | наш `availability_status: available` означает «есть в каталоге»; это не «играется». Выдавать одно за другое нельзя | отдельное поле `playable` в `sources`, каталожный признак остаётся отдельно |
| 8 | **Нумерация серий от провайдера**, включая серию 0 и спецвыпуски | у нас список серий строится по счётчику из снимка (§3), поэтому серия 0 и спецвыпуски теряются | заменяем счётчик на перечень от провайдера — это же снимает известный дефект нумерации |
| 9 | **Ограничения потока**: гео-доступность, пределы частоты запросов, одновременные сессии | приложение обязано показывать внятный отказ, а не пустой экран | коды и текст отказа в контракте `sources`, клиент показывает причину |
| 10 | **Требования отчётности** (heartbeat, события просмотра), если они есть условием выдачи ссылок | нарушение условий отзовёт доступ уже после выпуска приложения | исполняем отчётность на сервере, не в клиенте |

Пока пунктов 1 и 2 нет, `sources` отдаёт пустой массив и
`NO_SOURCE_CONTRACT_RELEASED` — это постоянное ограничение контракта, а не
временная заглушка. **Число серий в ответе не является доказательством наличия
работающего видео:** список серий строится из каталожных данных и счётчика
снимка, и ни одна его позиция не проверена на воспроизводимость.

## 6. Что требуется, чтобы адрес стал доступен клиенту

Служба проверена на `127.0.0.1`; чтобы она открылась из интернета, нужен root:
юнит + секция nginx `location /api/app/v1/ { proxy_pass http://127.0.0.1:9180; }`
на выбранном домене. Сама служба в сеть не выходит и ничего не меняет.

### 6.1. Что именно меняет установка — измерено на копии боевого файла

| что | как |
| --- | --- |
| служба | новый юнит `app-read-api-animedia-01.service`; существующие юниты не трогаются |
| код службы | копируется в `/usr/local/lib/site-factory/app-read-api-animedia-01.py` (0644 root) вместе с этим контрактом — не в рабочее дерево сессии, оно временное |
| каталог ключа | создаётся `/etc/app-read-api`, 0710 root:claude — проход только учётной записи службы; каталог серверных секретов и его права не трогаются |
| ключ клиента | создаётся `/etc/app-read-api/client-key`, 0640 root:claude; **значение не печатается** |
| сниппет nginx | новый файл `/etc/nginx/snippets/app-read-api-animedia-01.conf` с единственным `location /api/app/v1/` |
| конфигурация витрины | **добавляется ровно одна строка `include`** в HTTPS-блок `/etc/nginx/lords/animedia-01.conf`, перед этим снимается копия `*.before-app-read-api-animedia-01.<метка>` |
| чего установка НЕ делает | не меняет и не удаляет ни один существующий `location`, не трогает TLS, DNS, firewall, витрины, очередь; плееров не касается вовсе — воспроизведение на сайте делает web-компонент провайдера в браузере, серверного маршрута у него нет |

Измерение вставки на КОПИИ боевого файла `animedia-01.conf` (2026-10-10):
добавлено 2 строки (пустая и `include`), число `location` не изменилось (5 → 5),
фигурные скобки сбалансированы, ни одна прежняя строка не исчезла, `include`
оказался внутри блока `listen 443 ssl`. Те же утверждения сторожат проверки
`tests/unit/test_app_read_api_installer.py`.

### 6.1a. Обновление кода службы — тот же установщик

Повторный запуск установщика сравнивает выложенный код с источником и при
различии копирует новый **и перезапускает службу**. Без перезапуска правка
оказалась бы выложенной, но не работающей: `systemctl enable --now` уже
работающую службу не трогает, и это выглядело бы как «исправление не помогло»
(поймано 2026-10-11 при выпуске правки разбора пути). Повтор без изменений
кода перезапуска не делает и говорит об этом.

### 6.2. Приёмка после установки — одной командой

    python3 automation/local/app-api-acceptance.py \
        --base https://animedia.icu --key-file /etc/app-read-api/client-key

Один и тот же прогон годится до установки (`--base http://127.0.0.1:9180`) и
после (`--base https://animedia.icu`): проверки одни, меняется только адрес —
иначе «проверено на петле» незаметно подменяло бы «работает у клиента». Ключ
читается из файла и в вывод не попадает. Проверяется: состояние, отказ без
ключа и с неверным ключом, список главной, поиск, карточка, доля карточек с
обложкой, сезоны, серии и **ожидаемое** пустое `sources` с
`NO_SOURCE_CONTRACT_RELEASED` — внезапно непустой список инструмент считает
расхождением, а не удачей.

Результат прогона на петле против живого снимка 2026-10-10 (8 547 тайтлов):
расхождений 0, код выхода 0; обложки — 9 из 10 карточек выборки (в снимке есть
записи без обложки: 6 из 8 547).
