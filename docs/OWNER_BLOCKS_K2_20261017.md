# Блоки владельца после выпуска K2 — 2026-10-17

Выпуск кода восьми витрин владельца больше НЕ требует: он выполнен из сессии
штатным сценарием (см. ниже «что уже сделано»). Здесь остались две операции,
которые упираются в ограничения, а не в готовность.

Каждый блок отдельно для своей машины: проверка хоста, команды, ожидаемый
результат, откат.

---

## Блок 1. Управляющий сервер: включить суточную доставку каталога

**Зачем.** Приёмщик на узле K2 работает (`k2-catalog-apply.timer`, каждые 15
минут). Вторая половина цепочки — суточная доставка с управляющего сервера —
подготовлена 15.10, но НЕ включена: ссылки в `timers.target.wants` нет, таймер
не запускался ни разу. Из-за этого каталог на восьми витринах простоял с
15.10 11:44 до 17.10 17:34, пока доставку не выполнили вручную.

**Почему это не может сделать сессия.** Профиль сессии не разрешает
`systemctl` ни в каком виде; обходить ограничение профиля запрещено.

**Проверка хоста** (ожидаемые значения — те, что измерены 2026-10-17 18:50 UTC):

```bash
hostname                                     # управляющий сервер, не узел K2
ls -l /var/lib/systemd/linger/claude         # есть: пользовательские юниты живут без сессии
ls -1 ~/.config/systemd/user/k2-catalog-deliver.user.{service,timer}
ls -1 ~/.config/systemd/user/timers.target.wants/   # ссылки k2-catalog-deliver тут НЕТ
grep -n 'WorkingDirectory\|ExecStart' ~/.config/systemd/user/k2-catalog-deliver.user.service
```

`WorkingDirectory` обязан указывать на существующий каталог с ветки, где лежат
`automation/local/k2-deliver-catalog.sh`, `make-k2-publisher.py`,
`run-k2-publisher.py` и `var/ansible/hosts.yml`. Сейчас это
`/home/claude/wt-nova-publish-memory-02`. **В `/srv/site-factory/repo` этих
файлов нет** (проверено 17.10: ни сценариев доставки, ни `var/ansible/`), и
`var/` в git не хранится — значит после слияния ветки туда придётся отдельно
положить `var/ansible/hosts.yml`, иначе таймер включится и будет падать.

**Команды:**

```bash
systemctl --user daemon-reload
systemctl --user enable --now k2-catalog-deliver.user.timer
systemctl --user list-timers k2-catalog-deliver.user.timer --no-pager
```

**Ожидаемый результат:** в `list-timers` одна строка с
`k2-catalog-deliver.user.timer` и ближайшим запуском в 05:20 UTC (плюс
случайная задержка до 5 минут). Ссылка появляется в
`~/.config/systemd/user/timers.target.wants/`.

**Проверка через сутки** (её же делает и сторож, см. ниже):

```bash
journalctl --user -u k2-catalog-deliver.user.service --since '-26h' --no-pager | tail -20
ls -t /home/claude/wt-nova-publish-memory-02/var/k2-data/publish-reports | head -3
```

**Откат:**

```bash
systemctl --user disable --now k2-catalog-deliver.user.timer
systemctl --user list-timers k2-catalog-deliver.user.timer --no-pager   # строки больше нет
```

Откат безопасен: таймер только запускает доставку, доставка идёт во ВХОДЯЩИЙ
каталог узла, а установку делает корневой приёмщик узла со своими проверками
сумм.

## Блок 2. Узел K2: чтение журналов (необязательно)

**Зачем.** Причина 504 установлена и исправлена без журналов (см.
`docs/verification/k2-504-rootcause-20261017.md`). Доступ нужен только если
понадобится разбирать будущие инциденты на узле: сейчас `k2deploy` не состоит
ни в `adm`, ни в `systemd-journal`, поэтому `/var/log/nginx/*.log` и
`journalctl -u nova-*` ему не видны, и сессия это честно отмечает как «не
измерено».

**Проверка хоста:**

```bash
hostname                       # nova-amd-de-1-…, узел K2
id k2deploy                    # групп adm и systemd-journal в списке НЕТ
```

**Команды (только чтение, минимальные права):**

```bash
usermod -aG adm,systemd-journal k2deploy
```

**Ожидаемый результат:** после следующего входа `k2deploy` видит
`/var/log/nginx/error.log` и `journalctl -u nova-lordfilm-group.service`.
Права на запись не добавляются.

**Откат:**

```bash
gpasswd -d k2deploy adm
gpasswd -d k2deploy systemd-journal
```

## Блок 3. Узел K2: предел одновременности в nginx (необязательно, про запас)

**Зачем.** После исправления причины (см. ниже) витрина держит 32
одновременных запроса страницы произведения с максимумом 9.99 с при пределе
nginx 30 с. Предел одновременности сделал бы отказ при всплеске предсказуемым
(503 части запросов вместо 504 всем), но он НЕ требуется для нормальной
работы: порог отодвинут измеренно.

Файлы уже лежат в управляемых источниках (`automation/host/nginx-site/`), и
перед применением их нужно дополнить зоной `limit_conn`. Отдельного блока не
привожу намеренно: это изменение публичного поведения, и без решения владельца
о допустимом числе одновременных соединений цифра была бы выдуманной.

## Что уже сделано без владельца

* **Выпуск кода восьми витрин** — `bash automation/local/k2-release-code.sh
  --release lords-10 … lords-17`. Сценарий проверяет перед первой записью:
  запись в `/srv/<учётка>` и `/srv/<учётка>/releases` (группа витрины и
  setgid), читаемость `config/player.json` текущего выпуска и наличие точной
  строки перезапуска юнита в `sudo -n -l`. При неудаче возвращает прежний
  выпуск и перезапускает службу.
* **Доставка и установка каталога** — выполнены вручную штатным сценарием,
  ревизия `76475e36ed605204`, 65 749 записей, установлено на всех восьми
  17.10 17:34–17:35.
* **Сторож свежести** — `k2_catalog_findings` в суточном цикле
  (`seo_operator/regular.py`): сравнивает возраст снимка поставщика с
  последним прогоном издателя и даёт находку `K2_CATALOG_DELIVERY_STALE`.
  Именно этой проверки не хватало, чтобы заметить невключённый таймер.
