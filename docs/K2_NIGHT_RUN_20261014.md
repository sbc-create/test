## 4. Блокер запуска: publisher_id (и это fail-closed по замыслу)

Пробный запуск `lords-10` на узле (без root, в домашнем каталоге, порт 19125)
остановился до первого запроса:

```
запуск lordfilm.group остановлен до первого запроса:
  — нет …/config/player.json: плеер без publisher_id не заработает
```

Единственная падающая проверка проекта — `activate-scenarios`, и она говорит то
же: «lords-10 не объявляет publisher_id_expected — сверка не проводилась; номер
соседней витрины подставить нельзя (D138: у каждого домена свой)».

**Измеренный факт, который делает решение владельца простым.** В работающей
сети один publisher_id УЖЕ обслуживает несколько домéнов:

| publisher_id | витрины |
| --- | --- |
| `10238` | lords-03, lords-05, lords-06, lords-07 — **четыре** |
| `10252` | animedia-02, animego-04, zona-01 — три |
| `10373` | lords-01 |
| `10378` | lords-02 |

То есть восемь разных номеров не требуются — это измерение, а не
предположение. Какой номер получает каждый домен, решает владелец: подставлять
чужой или выдуманный запрещено и правилом проекта, и заданием. Инструмент для
назначения готов и сам отказывается от тихого разделения:
`automation/local/assign-publisher-id.py --site <id> --publisher-id <N> [--allow-shared]`.

**Где значение живёт.** Паспорт витрины ссылается на
`secret://cdnvideohub/lords/publisher-id`, а в Secret Hub направление `lords`
объявлено с потребителями **lords-01, lords-02, lords-03** и ничем больше: у
всех трёх `publisher_id=есть (0400)`, отпечаток направления
`sha256:3def8c29b51d6c43`, выкат `3/3 применено`. Новых восьми там нет —
значит нужен вход владельца, а не перенос значения.

**Что пускового сценария касается напрямую.** Он ждёт файл
`/home/k2deploy/stage/player/<site>-player.json` и без него останавливается
ДО любых изменений на узле — проверено сухим прогоном:

```
[x] нет /home/k2deploy/stage/player/lords-10-player.json: publisher_id не
    передан, витрина не стартует (D138/D177)
[x] это вход владельца: подставлять чужой или выдуманный номер запрещено
```

## 6. Один блок владельца — всё, что требуется до запуска

Порядок важен: пункты 1–4 готовят узел, 5 даёт данные плеера, 6 запускает
первую витрину, 7–8 открывают домен снаружи.

```bash
# host: k2-zomro-01
set -euo pipefail

# --- 1. Зависимости и каталоги ------------------------------------------
apt-get update
apt-get install -y nginx certbot python3-certbot-nginx python3-venv

# --- 2. Предел журналу СРАЗУ (на основном узле его отсутствие дало 4 ГиБ)

printf '[Journal]\nSystemMaxUse=512M\nSystemMaxFileSize=64M\n' > /etc/systemd/journald.conf.d/50-size-cap.conf
systemctl restart systemd-journald

# --- 3. Учётные записи и каталоги восьми ячеек ---------------------------
# Код — 2775 с группой витрины (выкладку делает k2deploy), данные — 0750 без

for acc in lordfilm-group lordfilm-spb-ru lordfilm-msk-ru lordserial-su lordserial-group lordserial-spb-ru lordserial-msk-ru lordserial-net-ru; do

  install -d -m 2775 -o "$acc" -g "$acc" "/srv/$acc"
  install -d -m 0750 -o "$acc" -g "$acc" "/srv/$acc/data"
  usermod -aG "$acc" k2deploy
done

# --- 4. Юниты и nginx: ставим, ничего не включаем ------------------------
install -m 0644 -o root -g root /home/k2deploy/stage/units/nova-*.service /etc/systemd/system/
systemctl daemon-reload
install -d -m 0755 /etc/nginx/cells /etc/nginx/lords
install -m 0644 /home/k2deploy/stage/cells/lords-1*.robots /etc/nginx/cells/

grep -q 'include /etc/nginx/lords/\*.conf;' /etc/nginx/nginx.conf || \
  sed -i 's|include /etc/nginx/conf.d/\*.conf;|include /etc/nginx/conf.d/*.conf;\n\tinclude /etc/nginx/lords/*.conf;|' /etc/nginx/nginx.conf

# --- 5. Узкие права k2deploy: перезапуск своих витрин и перезагрузка nginx
printf 'k2deploy ALL=(root) NOPASSWD: /usr/sbin/nginx -t, /usr/bin/systemctl reload nginx, /usr/bin/systemctl restart nova-lordfilm-group.service, /usr/bin/systemctl restart nova-lordfilm-spb-ru.service, /usr/bin/systemctl restart nova-lordfilm-msk-ru.service, /usr/bin/systemctl restart nova-lordserial-su.service, /usr/bin/systemctl restart nova-lordserial-group.service, /usr/bin/systemctl restart nova-lordserial-spb-ru.service, /usr/bin/systemctl restart nova-lordserial-msk-ru.service, /usr/bin/systemctl restart nova-lordserial-net-ru.service\n' > /etc/sudoers.d/k2deploy-cells
chmod 0440 /etc/sudoers.d/k2deploy-cells
visudo -c -f /etc/sudoers.d/k2deploy-cells

# --- 6. publisher_id: файлы плеера на узел (значения — от владельца) ----
# По одному файлу на витрину: {"publisher_id": "<номер>", "source_mode": "provider-id"}
install -d -m 0755 -o k2deploy -g k2deploy /home/k2deploy/stage/player

# --- 6б. Первая витрина целиком одной командой --------------------------
# Сценарий сам: проверит память против порога 2000 МиБ, положит данные с
# правами витрины, развернёт выпуск из бандла, подставит player.json,
# установит конфигурацию nginx с проверкой ДО перезагрузки, включит службу,
# дождётся healthz, прогреет, измерит RSS и покажет заголовок индексации.
# При неуспехе откатит: снимет службу и конфигурацию, оставив узел как было.

/home/k2deploy/stage/k2-launch-site.sh lords-10

# --- 7. Что получилось --------------------------------------------------
getent group lordfilm-group
ls -ld /srv/lordfilm-group /srv/lordfilm-group/data
```

## 6а. Регулярное обновление каталога — пробел закрыт

Перенесённый снимок стареет; без цепочки обновления витрины застыли бы на дне
переноса. Цепочка собрана и проверена звено за звеном.

**Совместимый издатель — из действующего кода, без заглушек.** Издатель этой
ветви знает восемь витрин, но не запускается (нет модулей `factory.lords`);
живой запускается, но витрин не знает. Инструмент
`automation/local/make-k2-publisher.py` берёт ЖИВОЙ файл и вставляет в таблицу
`ВИТРИНЫ` восемь записей из реестра ячеек, проверяя, что разница состоит
ТОЛЬКО из добавленных строк: **добавлено 22, убрано 0**. Действующий издатель и
его установленные копии не менялись.

Запуск идёт на живом пакете `factory`: собранная копия лежит в
`var/k2-data/publisher/`, где никакого `factory` нет, поэтому собственная
вставка `sys.path` издателя не перекрывает живой пакет. Именно это и мешало
раньше.

**Полный цикл на изолированном комплекте — прогнан на всех восьми:**

| измерено | значение |
| --- | --- |
| файлов собрано | 16 (8 каталогов + 8 sidecar) |
| элементов | **64 508** — снимок СВЕЖЕЕ перенесённого (было 63 776) |
| ревизия | `66933a38ed60` против `fe166350d2cd` у переноса |
| совпадение наборов между витринами | `parity_pct` **100.0**, у каждой `*_only = 0` |
| производство | «без `--apply` production не изменяется»; наших файлов изменено **0** |
| пик памяти издателя | **1,197 ГиБ**, 281 с на восемь витрин |

**Доставка и приём.** Каталог данных витрины принадлежит ей одной (0750), и
`k2deploy` писать туда не может — ослаблять права ради доставки нельзя.
Поэтому `k2deploy` кладёт комплект во входящий каталог своего дома, а корневой
приёмщик (`k2-catalog-apply.sh` + таймер 15 минут) проверяет и ставит с
правами витрины.

Проверено на деле: для `lords-10` комплект 104 МиБ с суммами доставлен,
`sha256sum -c` на узле **rc=0**, приёмщик принял его проверкой содержимого
(64 508 элементов, ревизии сходятся). Отказы приёмщика проверены отдельно, на
изолированном комплекте: **5 случаев из 5** — годный принят; отвергнуты
неполный набор, битая сумма, чужой `site` внутри файла, пустой каталог.

Единственное недостающее звено — корневой таймер: он в блоке владельца.
