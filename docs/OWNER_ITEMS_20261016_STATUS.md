## 1. B031 (обрезка заголовка): сценарий проверен, выпуск держит МЕСТО НА ДИСКЕ

**Назначение `--no-accept`, как просили проверить.** В
`automation/host/yummy-b016/yummy-b016-release.py` подкоманда `run` делает:
preflight → сборка → резервная копия БД → выкладка `web-biz` → выкладка
`web-org`, причём **приёмка каждой витрины и откат её образа при неуспехе
выполняются всегда**. Флаг `--no-accept` отключает только последний шаг —
приёмку постоянного исправления (`accept`): пауза прогрева, устаревший кеш и
холодный старт через публичный домен, полнота карт, T081. Эту приёмку можно
запустить отдельно подкомандой `accept`. То есть `--no-accept` НЕ отменяет
проверки витрин, он выносит тяжёлую часть в отдельный управляемый шаг.
Рекомендую так и делать: `run --no-accept`, затем `accept`.

**Что уже проверено.** `preflight` пройден (код 0, ни одной мутации): хеши
патчей, базовый compose, закреплённые образы, итоговая конфигурация из ТРЁХ
файлов (база в `wt-yummy-mail-biz` плюс два наложения), монтирования, и
отдельно — что у `web-biz` в итоговой конфигурации `SEO_INDEXING_ENABLED`

**Состояние до выпуска записано** (требование «сохранить режимы

**Блокер, конкретный: свободного места 5,0 ГиБ из 203,3.** Сценарий собирает
по образу на витрину (каждый около 1,5 ГБ плюс кеш сборки). Это тот самый

## 2. B033 (карты сезонов и серий): ваше возражение подтверждено измерением

**Ограничение в 40 тайтлов — да, оно и есть причина.** В
`src/lib/seo/sitemap-catalog.ts` объявлено `const DETAIL_LIMIT = 40`, и
подробности запрашиваются только для первых 40 обойдённых тайтлов; остальные
попадают в карту без подробностей, то есть БЕЗ сезонов и серий.

**Что это даёт на живых картах** (`yummyani7.info`, 16.10 11:22):

| часть карты | адресов |
| --- | ---: |
| `titles.xml` | 8 338 |
| `seasons.xml` | **50** |
| `episodes.xml` | **486** |
| `images.xml` | 8 332 |

При этом сезоны есть у 68,5 % тайтлов (замер линии приложения), то есть у
примерно 5 700 произведений. Сезонов в карте — 50.

**Подготовленный патч `b033-sitemap-fresh-first.patch` охват НЕ расширяет.**
Прочитан: он добавляет упорядочивание (свежие по событиям наблюдателя — в
начало) и дату изменения, но `DETAIL_LIMIT` остаётся, и строка
`titles.slice(0, DETAIL_LIMIT)` не меняется. То есть ваше «перестановка
свежих тайтлов в начало не решает проблему» — буквально так и есть.

**Что нужно вместо этого** (задача линии приложения, не правка одной строки):
постоянный инкрементальный инвентарь — подробности добираются пачками между
прогонами и сохраняются, обновляются по событиям изменения, а карта делится на
части по лимиту адресов. Поднять `DETAIL_LIMIT` до 8 338 «в лоб» нельзя:
каждый тайтл — отдельный запрос к поставщику, и сборка инвентаря превратится в
многочасовую, с риском 504 на самой карте.

Выпуск B033 по вашему указанию держу ОТДЕЛЬНО от B031 — иначе изменение
охвата карт смешается со сравнением заголовков.

Попутно проверено: карты всех трёх арендаторов отвечают 200
(`sitemap.xml`, `seasons.xml`, `episodes.xml`; 0,09–2,77 с). Один замер ранее
дал у `.biz` пустой индекс — это был таймаут моего запроса в момент упора
процессора, а не отказ карты.
