## Шаг 1. Свежая проверенная копия с данными витрин

Места достаточно: свободно 14,83 ГиБ при требовании 11,16 ГиБ. **Ничего не
удаляется.**

```bash
sudo python3 /srv/site-factory/repo/automation/host/backup_cell_data.py --check
sudo systemctl start site-factory-backup.service
sudo systemctl is-active site-factory-backup.service
ls -lt /srv/backups | head -4
sudo cat /srv/backups/$(ls -t /srv/backups | grep verified.json | head -1)
```

**Ожидаемый результат.** Первая команда печатает «витрин в плане: N;
элементов: M» — числа ненулевые. Служба завершается без ошибки
(`is-active` печатает `inactive` для `Type=oneshot` после успешного
завершения — это норма; важен следующий пункт). В `/srv/backups` появляется
пара `host-<штамп>.tar.gz` + `host-<штамп>.verified.json` с сегодняшней датой.
В записи обязаны быть `"restore_verified": true` **и** блок `"cell_data"` с
`sites` ≥ 15 и `items` ≥ 15.

Откуда эти числа. Прогон читает КОРНЕВУЮ копию реестра
(`/usr/local/lib/site-factory-cell/config/site-cells.json`, 0600 root), а она
от 09.10 — то есть старше восьми новых ячеек. Посчитано по рабочему реестру без
партии: витрин 20, элементов плана 46, из них реально существует на диске 21 —
остальные перечислены контрактом как возможные, но у витрины их нет, и это
норма. Поэтому ожидать `items` под сорок нельзя: в первой редакции этого блока
у меня стояло «≥ 40», и владелец остановился бы на успешной копии. Вклад партии
(8 витрин, 24 элемента) появится в копии после слияния ветви и обновления
корневой копии реестра.

**Условие остановки.** Нет новой пары файлов, либо в записи нет
`restore_verified: true`, либо `cell_data.sites` равен нулю — копия не
подтверждена. Прежние копии при этом целы; повторять запуск до разбора причины
не нужно.

**Почему наличие файла проверки — не доказательство.** Запись создаётся только
после того, как сценарий распаковал архив в отдельный временный каталог и
сверил `sha256sum -c` по манифесту, снятому ДО упаковки. Поэтому смотреть надо
на поля внутри записи, а не на существование файла: файл без
`restore_verified: true` означает неудачный прогон.

**Что эта команда НЕ делает:** не удаляет архивы и не меняет срок хранения.

## Шаг 2. Снять блокировку публикаций: перезапустить мост

Измерено: процесс `factory.qwen.mcp` (pid 1499831) стартовал 12.10 17:42:04Z, а
правка «состав накладки собирается из живого файла плюс свои описания» в
`factory/qwen/editorial.py` дерева службы появилась 12.10 22:57:59Z. Процесс
старше правки на 5 ч 15 мин, то есть исполняет прежний код, и затирание чужих
полей ещё возможно. Пауза публикаций на семи витринах держится по этой причине.

```bash
sudo systemctl restart site-factory-mcp.service
systemctl show -p ExecMainStartTimestamp --value site-factory-mcp.service
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/healthz
```

**Ожидаемый результат.** `ExecMainStartTimestamp` — сегодняшний, то есть позже
`12.10 22:57:59 UTC`; `/healthz` отвечает `200`.

**Условие остановки.** Время старта не изменилось или `/healthz` не отвечает —
мост не перезапустился; пауза публикаций остаётся, снимать её нельзя.

После этого шага снятие паузы — уже не root: одна согласованная публикация и

## Шаг 3. Поставить таймер технического SEO

Юниты лежат в дереве SEO-сессии; их пути, пользователь и доступ к очереди
проверены: `ExecStart` указывает на существующий файл (775), `User=claude`,
`Group=claude`, `OnCalendar=*:12/30`, `SuccessExitStatus=0 75`,
`CPUQuota=50%`, `MemoryMax=2G`, `ProtectSystem=strict`,
`ReadWritePaths=/home/claude`; очередь и журнал прогонов читаются и пишутся от
`claude`.

```bash
sudo install -m 0644 -o root -g root \
  /home/claude/wt-portable-site-cell-01/automation/host/editor/seo-tech-run.service \
  /home/claude/wt-portable-site-cell-01/automation/host/editor/seo-tech-run.timer \
  /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now seo-tech-run.timer
systemctl list-timers seo-tech-run.timer --no-pager
```

**Ожидаемый результат.** Таймер в списке, ближайший запуск — в пределах
30 минут (прогоны на :12 и :42).

**Условие остановки.** `daemon-reload` или `enable` вернули ошибку — таймер не
включать повторно, разобраться с юнитом.

**Что будет после включения, и это НЕ неполадка.** В очереди технического SEO
сейчас 90 задач и **ни одной** в состоянии `queued` (blocked 25, session 15,
live_verified 28, verified 17, done 4, released 1). Значит каждый запуск вернёт
«работы нет» с кодом 0 — это штатное ожидание. Полная приёмка (два прогона с
РАЗНЫМИ реальными задачами) станет возможна, когда SEO-сессия положит в очередь
задачи своей зоны; задач ради отчётности никто не создаёт.

## Шаг 6. Маршрут «где смотреть» для приложения «Кинатека»

Подготовленные изменения влиты в рабочую ветвь штатным слиянием (`29cab34`, без
force push), 85 проверок backend пройдены, сухой прогон установщика прошёл все
проверки до изменений. Осталась установка: установщик кладёт код через
`install -o root` и перезапускает юнит.

Зафиксированная версия ДО установки: sha256 `8dc7f32a347df4a0`, 27 832 Б —
побайтово равна версии из git (`4f94542`, файл `automation/host/app-read-api.py`).

```bash
bash /home/claude/wt-nova-publish-memory-02/automation/host/install-app-read-api.sh --dry-run
sudo bash /home/claude/wt-nova-publish-memory-02/automation/host/install-app-read-api.sh
python3 /home/claude/wt-nova-publish-memory-02/automation/local/app-api-acceptance.py --base https://animedia.icu --key-file /etc/app-read-api/client-key
```

**Ожидаемый результат.** Сухой прогон — те же семь «OK» до изменений. Установка
завершается нулём. Приёмка печатает **«расхождений: 0»**, и в ней:
`где смотреть — код 200, status=unknown, reason=NO_AVAILABILITY_SOURCE, offers=0`
и `где смотреть без региона — код 400, code=bad_request`. Прежние маршруты
каталога (состояние, список, поиск, карточка, сезоны, серии, источники) обязаны
остаться на 200 — сейчас они такие и есть.

**Условие остановки.** Приёмка даёт расхождения — откатить версию и не
оставлять службу в промежуточном состоянии. Команды откатa лежат в
`docs/verification/app-offers-route-20261013-install.md`, раздел 4; там же
сказано, почему `--rollback` установщика для этого НЕ годится: он снимает
установку целиком и увёл бы в офлайн всё API каталога, а не версию маршрута.

**Файл предложений не создаётся.** Реального поставщика нет, и `unknown` —
честный ответ контракта, а не недоделка.

## Шаг 5 (по желанию). Выгрузка обхода поисковых роботов

Нужна для вопроса роста: обходят ли роботы домены-дубли. Логи nginx —
`www-data:adm 0640`, и у рабочей учётной записи, как и у SEO-сессии, группы
`adm` нет: читать их мы не можем (проверено, `os.access` → False на всех 107
файлах). Команда только читает и ничего не меняет; секретов в выводе нет.

```bash
sudo zgrep -h -E 'YandexBot|Googlebot' /var/log/nginx/access.log /var/log/nginx/access.log.1 | awk '{print $1}' | sort | uniq -c | sort -rn | head -40
```

**Ожидаемый результат.** Список «число обращений — домен» за двое суток по двум
роботам. Если домен-дубль в списке отсутствует или стоит с единицами
обращений — гипотеза «дубли не обходятся» подтверждается измерением, а не
рассуждением.

**Условие остановки.** `zgrep` не находит файлов или вывод пуст — значит формат
журнала иной; присылать вывод как есть, домен в нём первым полем может не быть.

**Альтернатива без ручной выгрузки:** добавить рабочую учётную запись в группу
`adm` (`sudo usermod -aG adm claude`), и тогда такие выгрузки будут делаться
без владельца. Это расширение доступа, поэтому решение за вами.
