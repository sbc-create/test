## Шаг 1. Свежая проверенная копия с данными витрин

Места достаточно: свободно 14,83 ГиБ при требовании 11,16 ГиБ. **Ничего не
удаляется.**

```bash
sudo python3 /srv/site-factory/repo/automation/host/backup_cell_data.py --check
sudo systemctl start site-factory-backup.service
sudo systemctl is-active site-factory-backup.service
ls -lt /srv/backups | head -4
sudo cat /srv/backups/$(ls -t /srv/backups | grep verified.json | head -1)
```

**Ожидаемый результат.** Первая команда печатает «витрин в плане: N;
элементов: M» — числа ненулевые. Служба завершается без ошибки
(`is-active` печатает `inactive` для `Type=oneshot` после успешного
завершения — это норма; важен следующий пункт). В `/srv/backups` появляется
пара `host-<штамп>.tar.gz` + `host-<штамп>.verified.json` с сегодняшней датой.
В записи обязаны быть `"restore_verified": true` **и** блок `"cell_data"` с
`sites` ≥ 15 и `items` ≥ 15.

Откуда эти числа. Прогон читает КОРНЕВУЮ копию реестра
(`/usr/local/lib/site-factory-cell/config/site-cells.json`, 0600 root), а она
от 09.10 — то есть старше восьми новых ячеек. Посчитано по рабочему реестру без
партии: витрин 20, элементов плана 46, из них реально существует на диске 21 —
остальные перечислены контрактом как возможные, но у витрины их нет, и это
норма. Поэтому ожидать `items` под сорок нельзя: в первой редакции этого блока
у меня стояло «≥ 40», и владелец остановился бы на успешной копии. Вклад партии
(8 витрин, 24 элемента) появится в копии после слияния ветви и обновления
корневой копии реестра.

**Условие остановки.** Нет новой пары файлов, либо в записи нет
`restore_verified: true`, либо `cell_data.sites` равен нулю — копия не
подтверждена. Прежние копии при этом целы; повторять запуск до разбора причины
не нужно.

**Почему наличие файла проверки — не доказательство.** Запись создаётся только
после того, как сценарий распаковал архив в отдельный временный каталог и
сверил `sha256sum -c` по манифесту, снятому ДО упаковки. Поэтому смотреть надо
на поля внутри записи, а не на существование файла: файл без
`restore_verified: true` означает неудачный прогон.

**Что эта команда НЕ делает:** не удаляет архивы и не меняет срок хранения.

## Шаг 3. Поставить таймер технического SEO

Юниты лежат в дереве SEO-сессии; их пути, пользователь и доступ к очереди
проверены: `ExecStart` указывает на существующий файл (775), `User=claude`,
`Group=claude`, `OnCalendar=*:12/30`, `SuccessExitStatus=0 75`,
`CPUQuota=50%`, `MemoryMax=2G`, `ProtectSystem=strict`,
`ReadWritePaths=/home/claude`; очередь и журнал прогонов читаются и пишутся от
`claude`.

```bash
sudo install -m 0644 -o root -g root \
  /home/claude/wt-portable-site-cell-01/automation/host/editor/seo-tech-run.service \
  /home/claude/wt-portable-site-cell-01/automation/host/editor/seo-tech-run.timer \
  /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now seo-tech-run.timer
systemctl list-timers seo-tech-run.timer --no-pager
```

**Ожидаемый результат.** Таймер в списке, ближайший запуск — в пределах
30 минут (прогоны на :12 и :42).

**Условие остановки.** `daemon-reload` или `enable` вернули ошибку — таймер не
включать повторно, разобраться с юнитом.

**Что будет после включения, и это НЕ неполадка.** В очереди технического SEO
сейчас 90 задач и **ни одной** в состоянии `queued` (blocked 25, session 15,
live_verified 28, verified 17, done 4, released 1). Значит каждый запуск вернёт
«работы нет» с кодом 0 — это штатное ожидание. Полная приёмка (два прогона с
РАЗНЫМИ реальными задачами) станет возможна, когда SEO-сессия положит в очередь
задачи своей зоны; задач ради отчётности никто не создаёт.

## Шаг 5 (по желанию). Выгрузка обхода поисковых роботов

Нужна для вопроса роста: обходят ли роботы домены-дубли. Прежняя редакция этого
шага была НЕВЕРНОЙ, и это важнее самой команды.

**Что измерено в настройке nginx.** Для общего `/var/log/nginx/access.log`
своего `log_format` не объявлено нигде, то есть действует встроенный
`combined`:

    $remote_addr - $remote_user [$time_local] "$request" $status
    $body_bytes_sent "$http_referer" "$http_user_agent"

В нём **нет ни `$host`, ни `$server_name`**. Значит по общему журналу
разложить обход по доменам нельзя — ни первым полем, ни любым другим: домена
там просто не записано. Моя прежняя команда с `awk '{print $1}'` дала бы счёт
по IP клиентов и была бы выдана за счёт по доменам.

**Что всё-таки можно.** Свои журналы есть у трёх витрин — им домен даёт имя
файла:

| файл | домен |
| --- | --- |
| `lords-01.access.log` | lordfilm47.space |
| `lords-02.access.log` | lordserial33.biz |
| `lords-03.access.log` | 1lordserials1.online |

```bash
sudo sed -n '1p' /var/log/nginx/access.log
sudo grep -c -E 'YandexBot|Googlebot' /var/log/nginx/lords-01.access.log /var/log/nginx/lords-02.access.log /var/log/nginx/lords-03.access.log
sudo grep -h -o -E 'YandexBot|Googlebot' /var/log/nginx/access.log | sort | uniq -c
```

**Ожидаемый результат.** Первая команда печатает одну строку общего журнала —
по ней видно, что домена в формате нет (это подтверждение, а не догадка).
Вторая даёт число обращений роботов по каждой из трёх витрин. Третья — ОБЩЕЕ
число обращений каждого робота по всем прочим доменам вместе, без разбивки:
большего текущий формат не позволяет.

**Условие остановки.** Если в первой строке домен всё-таки виден — значит
формат переопределён там, где я не нашёл; тогда присылайте строку как есть, и
поле назовём точно, а не на глаз.

**Чтобы разбивка по доменам появилась** (отдельное решение, не часть этого
блока): добавить `$host` в `log_format` общего журнала. Для сравнения — в
`webmaster_verification` он уже есть (`host="$host" server_name="$server_name"`),
то есть приём в сети используется, но только для проверочного журнала.

**Альтернатива без ручной выгрузки:** `sudo usermod -aG adm claude` — после
этого такие выгрузки пойдут без владельца. Расширение доступа, поэтому решение
за вами; сам я его не прошу.

## Шаг 7. B029: карты сайта и переобход в Вебмастере

Просьба SEO-сессии по её аудиту роста (поправка `aecfab9`). Это действие в
интерфейсе Яндекс.Вебмастера, не команда терминала.

Для семи домен — `1lordserials1.online`, `an1mego.site`, `an1meg0.site`,
`zonafilm.cc`, `zonafilm.space`, `yummyani.biz`, `lordfilm47.space` — в
Вебмастере: **добавить `sitemap.xml`** и **запросить переобход главной**.

Основание, измеренное SEO-сессией: у этих домен 0–1 событие появления в поиске
и признак `NO_SITEMAPS` с 10.10 08:06Z, при этом карты сайта отдаются (200,
xml, ссылка в `robots.txt`). То есть карта есть, а Вебмастер о ней не знает.

Отдельно, из той же поправки: признак `DUPLICATE_PAGES` = ABSENT на всех 16
сайтах — склейка дублей срезом 10.10 **не подтверждается**. И Вебмастер
собирался до 11.10 (страницы в поиске, события, до 500 запросов, диагностика в
снимках `analytics-2026-10-09.json` и `-10-10.json`); недоступен он с 11.10, и
это тот же блокер B023, что в конце документа.

**Результат проверяется** по событиям Вебмастера — после восстановления сети
(B023), не раньше.
