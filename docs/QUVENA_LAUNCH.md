# Запуск домена: краткая инструкция

Одна цепочка, одна команда проверки, один способ выкладки. Всё описанное здесь
выполнено и измерено на действующих доменах 27.09.

## Входные данные

Три и только три. Остальное берётся из согласованных конфигураций.

| вход | кто даёт | без него |
|---|---|---|
| домен с записью A на сервер витрин | владелец DNS | цепочка останавливается на `domain_validated` |
| профиль шаблона: какой проверенный выпуск взять образцом | владелец | останов на `template_reserved`; свободных шаблонов в пуле нет |
| `publisher_id` плеера — свой на домен | провайдер плеера | останов на `player_configured`; чужой не копируется |

Счётчик Метрики и проект Topvisor цепочка переиспользует, если они уже есть, и
создаёт, если доступ позволяет. Оба — части выпуска, а не отдельная задача.

## Что делает система

```
python3 automation/host/launch-domain.py --domain <домен>          # показать
python3 automation/host/launch-domain.py --domain <домен> --act    # выполнить выполнимое
```

Порядок этапов и что проверяется после каждого:

1. `domain_validated` — домен разрешается в тот же адрес, что работающая витрина;
2. `site_id_assigned` — запись в реестре ячеек: site_id, порт, учётная запись, юнит;
3. `template_reserved` — профиль шаблона закреплён либо назван источник-выпуск;
4. `player_configured` — свой `publisher_id`, не пересекающийся с чужим;
5. `repo_pushed` — свой репозиторий, рабочая копия, HEAD запушен;
6. `ci_verified` — успешный прогон CI **на этом коммите**;
7. `data_verified` — снимки источника для site_id существуют;
8. `server_staged` — юнит, конфигурация nginx и upstream на месте;
9. `publicly_accepted` — публичный `build-id` совпадает с манифестом
   установленного выпуска.

Девятый этап — единственное доказательство завершённой активации. Переключённый
`current` при процессе со старым кодом его не проходит.

Выкладка выполняется очередью исполнителя:

```
python3 -m factory cell trigger --site <site_id> --commit <sha> \
    --ci-run <номер> --confirm-activation --reason "<зачем>"
```

Исполнитель проверяет происхождение (репозиторий из реестра → разрешённая ветка
→ точный коммит → успешный прогон → digest), поднимает кандидата на порту+1000,
проверяет его ответом и `build-id`, переключает маршрут, **включает службу** и
гасит прежнюю. Откат при неудаче — часть того же прогона.

## Постоянные доступы, без которых цепочка не замкнута

| доступ | где лежит | зачем |
|---|---|---|
| токен GitHub исполнителя | `/etc/site-factory/gh-token` | чтение коммита и прогона CI. Нужен охват всех репозиториев владельца, иначе каждый новый домен требует ручного разблокирования |
| OAuth Метрики | `/etc/site-factory/secrets/yandex_oauth_token` | `metrika:read` — статистика, `metrika:write` — создание счётчиков |
| Topvisor | `/etc/site-factory/secrets/topvisor/{user-id,api-key}` | проекты и позиции |

Секреты получают **службы**, а не сессия: значение приходит через
`LoadCredential` и живёт только на время прогона. Членство в группе-владельце
секрета не нужно и не выдаётся.

Проверить права самого исполнителя, не получая токен:

```
python3 -m factory cell submit --site <site_id> --cell-operation access-check \
    --reason "проверка доступа"
cat /var/lib/site-cells/results/<site_id>-access-<дата>.json
```

## Проверка результата

```
python3 automation/host/domain-state.py                  # все домены одной таблицей
python3 automation/host/metrika-audit.py --domain <домен> # разметка счётчика
node automation/host/metrika-send-check.js --urls '[…]'   # фактическая отправка просмотра
python3 automation/host/check-installed.py                # установленное против пакета
```

Разметка счётчика не доказывает отправку, отправка не доказывает появление
данных в кабинете. Это три разные проверки, и объединять их нельзя.

## Продолжение после сбоя

* повторный запуск цепочки продолжает незавершённое: каждый этап сначала
  проверяет, сделано ли, и только потом делает;
* идентификатор заявки выводится из того, что выкладывается, поэтому повтор той
  же работы не заводит вторую операцию и не создаёт второй репозиторий, счётчик
  или проект;
* откат записывается как откат, а не как успешный выпуск: применёнными
  считаются только исходы `activated | delivered | edited | unchanged | dry-run |
  checked`;
* ошибка прав или конфигурации не повторяется по кругу: заявка получает
  `rejected` с причиной и не переподаётся сама;
* при неоднозначном ответе внешнего API сначала проверяется, был ли объект
  создан, и только потом повторяется создание.

## Чего цепочка не делает намеренно

Не открывает поисковую индексацию, не переключает DNS, не выпускает
сертификаты сверх штатного шага и не создаёт пользовательские данные.
Публикация на домене и открытие индексации — разные решения.
