# Зеркала `www` четырёх живых домен отдают второй сайт: измерение и операция

Запись от 2026-10-15, уточнена в тот же день. Пункт заявлялся 12 октября как
«www-зеркала четырёх доменов отдают 200, `index` и self-canonical». Состояние
перемерено перед просьбой к владельцу: число подтвердилось, СОСТАВ изменился.

Моё первое измерение покрыло 14 доменов и нашло три дубля; SEO-сессия
независимо прошла 17 опубликованных доменов и нашла четвёртый — `an1meg0.site`
— ровно в той тройке, которой у меня не было. Все 14 моих утверждений у неё
совпали. Четвёртый дубль перепроверен здесь своими командами (ниже), и вывод
«дублей три» исправлен: их **четыре**, и дубль действующий.

## Срочность изменилась: сеть открыта к индексации

2 октября все эти домены были ЗАКРЫТЫ (`noindex, nofollow` плюс
`Disallow: /`), и дубль был безвредным. Сейчас открыты и апекс, и www-хост.
Измерено 2026-10-15 своими командами:

```
www.an1meg0.site: код=200 canonical=https://www.an1meg0.site/ meta=index, follow
                  xrobots=index, follow  ссылок_на_тайтлы=127
an1meg0.site:     код=200 canonical=https://an1meg0.site/     meta=index, follow
                  xrobots=index, follow  ссылок_на_тайтлы=127
www.an1mego.site: код=301 → https://an1mego.site/    (норма)
www.animeg0.site: код=301 → https://animeg0.site/    (норма)
```

По сети в целом SEO-сессия измерила 17 открытых из 17 против 4 из 17 две
недели назад. То есть сейчас четыре пары имён отдают один сайт, каждое имя
открыто и указывает canonical на себя — это ровно то условие, при котором в
индекс попадают оба адреса. Пока домены были закрыты, ждать было можно;
теперь нет.

## Что измерено (14 домен моим прогоном, `https://www.<домен>/`, без следования переходам)

| состояние | домены |
| --- | --- |
| **дубль: 200 и canonical на САМ www-хост** | `zonafilm.cc`, `zonafilm12.site`, `lordserials22.info`, `an1meg0.site` (четвёртый — из доменов, которых в моём прогоне не было) |
| 200, но canonical на апекс (сигнал верный, адресов два) | `yummyani7.site`, `yummyani7.info` |
| 308 на апекс — норма | `lordfilm47.space`, `lordserial33.biz`, `1lordserials1.online`, `yummyani.site`, `yummyani.org`, `yummyani.biz` |
| имени `www` в DNS нет вовсе — дубля быть не может | `zonafilm.space`, `animedia.icu`, `animedia.space` |

Дефект подтверждён у **четырёх** домен. Чем он опасен: поисковик
видит два сайта с одинаковым содержимым и сам выбирает, какой считать
основным; у `lordserials22.info` это ещё и домен из партии шести назначений,
то есть страница с плеером доступна по двум адресам.

## Операция владельца (root на `claude-control-01`)

Правильная раскладка в проекте уже есть — её генерирует
`automation/local/stage-k2-cell-artifacts.py` для партии K2: `www` стоит
ОТДЕЛЬНЫМ блоком с `301` на апекс, и путь ACME в нём сохранён (подтверждение
владения именем `www` нужно сертификату). Для четырёх живых домен нужен тот же
блок. Ниже — готовый текст; `<ВИТРИНА>` в имени переменной режима
индексации подставляется по той витрине, которой домен принадлежит
(`$cell_robots_<site_id с подчёркиваниями>`), как в уже установленных файлах.

```nginx
# /etc/nginx/lords/<site_id>-www.conf — www отдельным блоком, 301 на апекс.
server {
    listen 80;
    listen [::]:80;
    server_name www.<домен>;

    server_tokens off;
    add_header X-Robots-Tag $cell_robots_<ВИТРИНА> always;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
        default_type "text/plain";
    }

    location / {
        return 301 https://<домен>$request_uri;
    }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name www.<домен>;

    ssl_certificate     /etc/letsencrypt/live/<домен>/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/<домен>/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    server_tokens off;
    add_header X-Robots-Tag $cell_robots_<ВИТРИНА> always;

    location / {
        return 301 https://<домен>$request_uri;
    }
}
```

Порядок (по одному домену, чтобы отказ не задел соседей):

```bash
# host: claude-control-01, от root
# 1. Убрать имя www из блока апекса, если оно стоит там (именно это и даёт 200).
#    Файл витрины: /etc/nginx/lords/<site_id>.conf — строка server_name.
# 2. Положить блок выше в /etc/nginx/lords/<site_id>-www.conf
# 3. Сертификат обязан покрывать имя www; если он его не покрывает:
certbot certonly --webroot -w /var/www/certbot -d <домен> -d www.<домен> \
    --cert-name <домен> --non-interactive --agree-tos -m <почта владельца>
# 4. Проверка и перезагрузка — в этом порядке:
nginx -t && systemctl reload nginx
```

Проверка результата (моя сторона, без прав):

```bash
python3 automation/local/public-acceptance.py zonafilm.cc zonafilm12.site \
    lordserials22.info an1meg0.site
```
В приёмке теперь есть шаг `www → апекс`: он ждёт `301`/`308` и `Location` на
апекс, и до правки честно показывает расхождение.

## Про пару Yummy

`www.yummyani7.site` и `www.yummyani7.info` отвечают 200, но canonical ведёт
на апекс — поисковику сигнал дан верный, дубля в индексе быть не должно. Это
не дефект того же рода, и в один список с четырьмя выше он не ставится. Привести
их к `301` всё же стоит (два живых адреса вместо одного), но это правка
контура верхнего приложения, а не nginx витрины, и она идёт отдельно от этой
операции.

## Рядом: правило параметрических страниц разошлось

Найдено SEO-сессией при проверке открытых семейств, перепроверено здесь.
`zonafilm.cc` отдаёт `canonical` на сам адрес С ЗАПРОСОМ и `index, follow`, и
с одной страницы каталога ведёт 104 фильтровых ссылки. Правильное поведение
того же рода у `an1meg0.site` и `yummyani7.site`: `canonical` на базовый
каталог и `noindex, follow`. Это отдельный дефект, не зеркала `www`, и он в
зоне SEO-сессии; записан здесь, чтобы при правке `zona` его не пропустили.

## Чего эта запись не делает

Не меняет конфигурацию живых сайтов: правка nginx на управляющем узле — root, и
обходить это нельзя. Не затрагивает работу SEO-сессии: измерение отправлено ей
отдельным сообщением, чтобы правка общих компонентов шла одним порядком, а не
двумя. SEO-сессия правку nginx тоже не вносит и не готовила — живые домены под
root требуют решения владельца, и просьба соседней сессии его не заменяет; она
передаёт владельцу своё измерение со ссылкой на этот файл и берёт на себя
проверку результата по всем 17 доменам после применения.

Независимое измерение соседней сессии:
`reports/SEO-PREFLIGHT-20261002/evidence/www-mirrors-20261015.md`, коммит
`8aafbd9` ветки `claude/seo-preflight-20261002`.
