## 1. `publisher_id`: чей он, где его взять, что к чему привязывать

### Чему он принадлежит

`publisher_id` — номер **издателя по контракту с CDNVideoHub**, поставщиком
потока. Это не наша настройка и не внутренний идентификатор фабрики:
переданный контракт поставщика
(`knowledge/cdnvideohub/PLAYER_CONTRACT.yaml`) объявляет атрибут
`data-publisher-id` со значением «Publisher ID владельца по contract», а
контракт Content API прямо говорит: «Lords обязан работать на собственных
api-token и publisher-id».

Разделение, которое важно не перепутать:

| | что это | где живёт | секрет? |
| --- | --- | --- | --- |
| `publisher_id` | номер издателя в контракте поставщика | три места, см. ниже | **нет** (D138: стоит в разметке страницы) |
| `api_token` | учётные данные доступа к Content API | Secret Hub, направление `lords` | **да**, не покидает хранилища |

Витринам этой партии `api_token` не нужен вовсе: каталог им доставляет
производитель, сами они к Content API не ходят. Нужен только номер издателя.

### Где его взять

Источник один — **кабинет/контракт CDNVideoHub**. Фабрика номер не выдаёт и
выдать не может. Варианта два, и выбор за владельцем:

* **распространить действующий номер направления Lords на новые домены** — если
  контракт позволяет обслуживать этими доменами уже оплаченное размещение;
* **получить у поставщика номер(а) для новых домен** — если контракт привязан к
  перечню домен.

### Восемь разных номеров НЕ требуются

Это измерено 13.10 по действующему реестру, а не предположено:

| номер | сколько домен носит |
| ---: | --- |
| `10252` | **5** — animedia.space, an1mego.site, animeg0.site, an1meg0.site, zonafilm.space |
| `10238` | **2** — 1lordserials1.online, lordserials22.info |
| `10332` | 1 — animedia.icu |
| `10373` | 1 — lordfilm47.space |
| `10378` | 1 — lordserial33.biz |
| `10374` | 1 — zonafilm.cc |
| `10261` | 1 — zonafilm12.site |

Один номер на нескольких доменах в сети уже работает, и механизм этого не
запрещает: `registry.check_publisher_id` отвергает только **отозванные**
поставщиком номера (`10331`, `10333`), проверки на уникальность нет нигде.
Значит для восьми домен может хватить **одного** номера.

Чего нельзя — взять чужой номер молча. Измерено 05.10 на zonafilm.cc: все три
места говорили `10238`, номер пары lords-01, и домену он не принадлежал;
владелец назвал `10374`. Поэтому инструмент требует явного `--allow-shared`,
когда номер уже записан у другого домена, и называет, у какого именно.

### Что к чему привязывать: три места по D177

Привязка нужна в трёх местах, и они обязаны совпадать:

1. **значение** — `/srv/lords/.frontend/player-<site_id>.json` (0600). Отсюда
   привилегированный исполнитель копирует файл в выпуск как
   `config/player.json`; для новой витрины это **единственный** допустимый
   источник (двух других — прежнего выпуска и рабочего каталога — у неё нет);
2. **объявление** — `config/site.json: publisher_id_expected` в репозитории
   витрины. Исполнитель сверяет источник с объявлением и отказывает, если они
   расходятся;
3. **учёт** — `config/site-cells.json: publisher.publisher_id`.

Правка одного места без остальных возвращается следующей выкладкой — это D177,
и это измеренный случай, а не предостережение.

### Что уже проверено и готово

* У всех восьми в репозитории стоит `publisher_id_ref:
  secret://cdnvideohub/lords/publisher-id`, а `publisher_id_expected` — `null`.
  Для исполнителя это означает «плеер нужен», поэтому он и отказывает: ссылка
  есть, значения нет.
* Семейный номер в паспорта восьми ячеек **не скопирован** сознательно (D177).
* Инструмент назначения готов и проверен 13 проверками:

```bash
# сухой прогон: ничего не меняет, печатает, что изменится
python3 automation/local/assign-publisher-id.py --site lords-10 --publisher-id <НОМЕР>

# запись во все три места сразу, с проверкой согласия после записи
python3 automation/local/assign-publisher-id.py --site lords-10 --publisher-id <НОМЕР> --apply

# если номер решено разделить с уже существующим доменом
python3 automation/local/assign-publisher-id.py --site lords-10 --publisher-id <НОМЕР> --apply --allow-shared
```

Инструмент отвергает негодную форму, отозванный номер и совместное
использование без флага — всё это **до** первой записи. Номер не попадает ни в
вывод, ни в текст отказа.

### Что нужно от владельца — ровно одна строка

> Номер издателя для восьми домен: `<НОМЕР>` — один на все восемь
> **или** по домену: lordfilm.group=…, lordfilm.spb.ru=… и так далее.

Больше ничего. Запись в три места, коммит, пуш и проверку CI я делаю сам: root
для этого не нужен (каталог `/srv/lords/.frontend` принадлежит рабочей учётной
записи — проверено).

## 2. Резервное копирование: почему стоит и как вернуть

### Почему стоит — измерено, а не предположено

| проверено | результат |
| --- | --- |
| таймер установлен и включён | да: `/etc/systemd/system/site-factory-backup.timer` и ссылка в `timers.target.wants` |
| живой сценарий свежий | да: `/srv/site-factory/repo/.../site-factory-backup.sh`, 249 строк, прежнее исправление прав на consumer-файлы на месте |
| свежесть копий | **последний архив 29.09, 14 суток назад**; до него пропуск между 24 и 29 сентября |
| свободно на `/srv` | **7,08 ГиБ из 203 ГиБ (занято 96,5 %)** |
| требование политики места | **11,2 ГиБ** |

Политика места (`backup-space-precheck.sh`) считает так: сценарий держит на
диске одновременно staging, архив и распакованную копию для доказательства
восстановления; при одной файловой системе требование складывается и выходит
`3,6 × staging`. Нижняя оценка staging — сжатый архив от 29.09, 3,10 ГиБ
(сжатие размер не увеличивает). Прогон политики на этих числах:

```
код 1
недостаточно места: рабочий каталог и каталог бэкапов на одной файловой системе,
им вместе нужно 11.2 GB (архив + распакованная копия для доказательства
восстановления + итоговый архив + запас 20%), свободно 7.1 GB; staging 3.1 GB
```

Это **штатный отказ**, а не поломка: он задуман так, чтобы не портить
последнюю подтверждённую копию ради новой. Но дальше — замкнутый круг:

> копирование не идёт, потому что диск занят старыми копиями;
> старые копии не удаляются, потому что удержание (`backup-retention.sh`)
> выполняется ТОЛЬКО в конце успешного прогона.

Арифметика круга: 9 архивов держат 21,59 ГиБ (7 подтверждённых и 2 сироты без
записи о проверке), а удержание настроено на `KEEP=14` — то есть удалять ему
пока нечего. Прогон удержания с `KEEP=3` оставит три архива и освободит
**14,20 ГиБ**: свободно станет около 21,3 ГиБ при требовании 11,16 ГиБ.

При этом `KEEP=14` на этом диске недостижим в принципе: 14 архивов по ~3,1 ГиБ
это 43 ГиБ плюс 11,2 ГиБ рабочего места, а всего свободного даже после удаления
всех копий будет около 33 ГиБ. Это решение владельца, и оно названо в шаге 2.3.

### Что уже сделано без владельца

Данные ячеек теперь входят в копию. До 13.10 сбор шёл по `/srv/sites/`, а
каталоги данных ячеек живут в `/srv/<учётная запись>/data` — другой путь, и в
архив не попадала ни одна из 28 ячеек: оценки, комментарии и опубликованные
правки редактора восстановить было бы нечем.

Берётся не весь каталог, и это тоже измерено: данные ячеек весят 1,81 ГиБ, а
невосстановимая их часть — 25,74 МиБ (1,39 %); остальное заново положит
производитель. Состав берётся из **контракта данных самой витрины**
(`data_contract.user_writable`), поэтому витрина, добавленная завтра, попадёт в
копию сама. Проверено в изоляции: план даёт 28 витрин и 70 элементов,
собралось 21 элемент на 16 витрин, 111 МиБ, ни одного снимка каталога (прочее
не собралось под обычной учётной записью по правам — это и подтверждает, что
бэкап обязан идти от root). Проверки: `tests/unit/test_backup_covers_cell_data.py`,
11 passed, включая четыре на побег из каталога данных.

Запись о проверке теперь называет покрытие числом (`cell_data.sites`,
`.items`, `.kib`): архив `0600` и запись `0640 root:root`, заглянуть внутрь
снаружи нечем, и «данные ячеек в копии» иначе пришлось бы принимать на слово.

### Проверка восстановления в изолированном месте — уже встроена

Отдельный инструмент не нужен: сценарий это и делает, и только после этого
считает копию подтверждённой.

1. считает SHA-256 всех файлов staging **до** упаковки;
2. пакует архив;
3. распаковывает его в **отдельный временный каталог** (`$WORK/restore`);
4. сверяет `sha256sum -c` по манифесту источника; расхождение — отказ;
5. сверяет, что файлов восстановилось не меньше, чем было;
6. только теперь пишет `host-<штамп>.verified.json` с
   `restore_verified: true` и `restore_method: "extract to temp dir +
   sha256sum -c against source manifest"`.

Прогон без этой записи считается неудачным, чем бы ни закончились шаги:
`site-factory-health.sh` датирует последнюю хорошую копию только по этим
файлам.

Сверх этого в сети есть недельное доказательство восстановления базы —
`site-factory-restore-proof.timer` (воскресенье 05:00 UTC,
`tests/tools/restore_proof.py`). Оно про базу стенда, не про архив хоста, и
одно другое не заменяет.

## 3. SERVER TERMINAL — только то, что действительно требует владельца

Общее правило для всех шагов: **останавливаться на первом несовпадении с
ожидаемым результатом и не переходить к следующему шагу.** Ни одна команда
ниже не принимает секретных значений.

### Шаг 2.1. Разблокировать место под копии

Поимённый список на 13.10 15:3x (посчитан по правилам самого удержания):

| архив | дата | ГиБ | подтверждён | решение |
| --- | --- | ---: | --- | --- |
| host-20260916T032201Z | 16.09 | 1,95 | да | удалить |
| host-20260917T032259Z | 17.09 | 2,04 | да | удалить |
| host-20260918T032210Z | 18.09 | 2,13 | да | удалить |
| host-20260919T032107Z | 19.09 | 2,22 | да | удалить |
| host-20260920T032157Z | 20.09 | 2,31 | да | **оставить** |
| host-20260921T032227Z | 21.09 | 2,40 | да | **оставить** |
| host-20260923T032424Z | 23.09 | 2,67 | да | **оставить** |
| host-20260924T032059Z | 24.09 | 2,76 | **нет** | удалить вторым проходом |
| host-20260929T032303Z | 29.09 | 3,10 | **нет** | удалить вторым проходом |

Два самых свежих архива — БЕЗ записи о проверке, то есть доверять им нечем.
Удалять их сразу всё же не нужно: сначала появится свежая подтверждённая копия,
и только потом они уйдут. Поэтому проход первый гасит правило сирот высоким
порогом возраста.

```bash
# проход первый: только четыре самых старых ПОДТВЕРЖДЁННЫХ; сироты не трогаем
sudo SITE_FACTORY_BACKUP_KEEP=3 SITE_FACTORY_BACKUP_ORPHAN_MIN_AGE_HOURS=100000 \
  bash /srv/site-factory/repo/automation/host/backup-retention.sh /srv/backups
df -h /srv
ls -la /srv/backups | head -20
```

**Ожидаемый результат:** удалены четыре набора от 16–19 сентября,
освобождается **8,34 ГиБ**; свободно становится около **15,1 ГиБ** при
требовании 11,16 ГиБ. В `/srv/backups` остаются три подтверждённых набора
(20, 21, 23 сентября) и два неподтверждённых архива (24 и 29 сентября).

Почему `KEEP=3`, а не `2`: в удержании есть пол `KEEP_FLOOR=3`, и ниже трёх
подтверждённых наборов оно не опускается ни при каком `KEEP`. С `KEEP=2`
результат был бы тот же, но ожидание в пакете разошлось бы с поведением.

**Условие остановки:** свободного стало меньше 12 ГиБ — значит место занято не
копиями, и запускать бэкап бессмысленно; разбираться надо с тем, что занимает
диск, а не с копиями.

### Шаг 2.2. Обновить сценарий бэкапа на хосте и сделать свежую копию

Правка данных ячеек лежит в ветви `claude/nova-publish-memory-02`; живой
сценарий — отдельная копия в `/srv/site-factory/repo`, и она обновляется
переносом, а не слиянием ветви.

```bash
# 1) перенести два файла в живую копию
sudo install -m 0755 -o claude -g claude \
  /home/claude/wt-nova-publish-memory-02/automation/host/site-factory-backup.sh \
  /srv/site-factory/repo/automation/host/site-factory-backup.sh
sudo install -m 0644 -o claude -g claude \
  /home/claude/wt-nova-publish-memory-02/automation/host/backup_cell_data.py \
  /srv/site-factory/repo/automation/host/backup_cell_data.py

# 2) проверить план сбора данных ячеек (ничего не меняет)
sudo python3 /srv/site-factory/repo/automation/host/backup_cell_data.py --check

# 3) свежая копия с доказательством восстановления
sudo systemctl start site-factory-backup.service
systemctl status site-factory-backup.service --no-pager | tail -5

# 4) запись о проверке
sudo cat /srv/backups/$(ls -t /srv/backups | grep verified.json | head -1)
```

**Ожидаемый результат:** шаг 2 печатает «витрин в плане: 28; элементов: 70»
(числа растут вместе с сетью). Шаг 3 завершается нулём. В записи о проверке:
`"restore_verified": true` и блок `"cell_data"`, где `sites` **не меньше 20** и
`items` **не меньше 60**.

**Условие остановки:** в записи `cell_data.sites: 0` — значит перенесённый
сценарий не тот или план не построился; архив при этом не считается
подтверждённым, и прежняя копия остаётся на месте.

### Шаг 2.2a. Проход второй: убрать неподтверждённые архивы

Только ПОСЛЕ того, как свежая копия получила `restore_verified: true`.

```bash
sudo bash /srv/site-factory/repo/automation/host/backup-retention.sh /srv/backups
df -h /srv
```

**Ожидаемый результат:** уходят два архива без записи о проверке (24 и 29
сентября, 5,86 ГиБ), остаются свежая копия и три подтверждённых набора.

**Условие остановки:** если свежей подтверждённой копии ещё нет — второй проход
не запускать: он снимет неподтверждённые архивы, и самой новой копией останется
23 сентября.

### Шаг 2.3. Решение об удержании копий

`KEEP=14` на этом диске недостижим: 14 × 3,1 ГиБ = 43 ГиБ плюс 11,2 ГиБ
рабочего места. Нужно одно из двух, и это решение, а не команда:

* оставить `SITE_FACTORY_BACKUP_KEEP=4` постоянно (четверо суток истории
  вместо четырнадцати) — тогда в юнит добавляется
  `Environment=SITE_FACTORY_BACKUP_KEEP=4`;
* либо выделить под `/srv/backups` отдельный том и оставить 14.

Скажите, какой вариант, — правку юнита подготовлю я.

### Шаг 3.1. Поднять восемь витрин на хосте

Делается **после** назначения номера издателя (раздел 1) и зелёного CI. По
одной витрине; порядок — сначала по одному представителю каждого профиля
(`lords-10`, `lords-13`), остальные шесть после их приёмки.

```bash
sudo bash /home/claude/wt-nova-publish-memory-02/automation/host/launch-new-site.sh --site lords-10 --dry-run
sudo bash /home/claude/wt-nova-publish-memory-02/automation/host/launch-new-site.sh --site lords-10
```

**Ожидаемый результат:** созданы учётная запись `lordfilm-group`, каталоги
`/srv/lordfilm-group/{current,releases,data}`, юнит
`nova-lordfilm-group.service`; `curl -s localhost:9125/healthz` отвечает строкой, начинающейся с
`{"ok": true`.

Нюанс, замеченный сухим прогоном и важный до запуска: **шаг 1 сценария ставит
юниты СРАЗУ ВСЕМ ячейкам реестра**, а не только названной. То есть один прогон
создаст файлы юнитов и для `lords-08`, `lords-09`, и для всех восьми новых —
сухой прогон перечисляет их построчно («поставил бы»), а существующие не
трогает («уже есть, не трогаю»). Это безопасно: `install-cell-units.py` только
записывает файлы и делает `daemon-reload`, он ничего не включает и не
запускает. Шаги 2–4 (nginx, сертификат, недельный снимок) касаются только
названной витрины.

Порты у всех восьми различаются и не пересекаются с действующими: 9125–9129,
9133–9135 плюс кандидатные 10125–10135 — проверено по всей сети из 33 ячеек.

**Условие остановки:** `healthz` не отвечает или юнит не поднялся — витрина
остаётся незапущенной, остальные семь не трогаем.

### Шаг 3.2. nginx и сертификат

```bash
sudo bash /srv/site-factory/repo/automation/host/install-site-nginx.sh --site lords-10 --dry-run
sudo bash /srv/site-factory/repo/automation/host/install-site-nginx.sh --site lords-10
sudo nginx -t
sudo bash /srv/site-factory/repo/automation/host/install-site-tls.sh --site lords-10
```

Ключ именно `--site`, не позиционный аргумент: проверено по заголовкам обоих
сценариев. Оба понимают `--dry-run`.

**Ожидаемый результат:** `nginx -t` печатает `syntax is ok` и `test is
successful`; certbot выдаёт сертификат на `lordfilm.group` **и**
`www.lordfilm.group`. Проверено сухим прогоном после правки реестра: шаг
печатает `-d lordfilm.group -d www.lordfilm.group`. Оба имени есть в зоне
(измерено авторитетным запросом), поэтому запрос пройдёт; у lords-09, где
`www` в зоне нет, его и не объявляли — иначе certbot провалил бы запрос целиком
и не выдал сертификата даже на apex. После установки
`https://lordfilm.group/` отвечает 200 своим сертификатом, а
`https://www.lordfilm.group/` — 301 на apex.

**Условие остановки:** `nginx -t` не прошёл — **не перезагружать nginx**:
блок 443 со ссылкой на несуществующий сертификат роняет и соседние витрины.
Файл TLS подключается только после выдачи сертификата.
