### Почему четыре суток никто не узнал причину

Строка 85 прежней редакции сценария:

```bash
ansible … -m copy -a "src=$box/ dest=/home/k2deploy/stage/incoming/$site/ …" \
    >/dev/null || { echo "[x] доставка не удалась"; exit 1; }
```

**Вывод ansible уходил в `/dev/null`** — у единственного шага, на котором стоит
вся цепочка, и причина отказа уничтожалась вместе с ним. В журнале поэтому
остаются только «комплект собран» и «не удалась», без единого слова о том,
почему. Это дефект инструмента, а не узла: MOD-136, исправлен в этой же смене
(вывод пишется в `$work/<site>-copy.log`, последние 25 строк печатаются, копия
переживает уборку ящика — `var/k2-data/last-copy-failure.log`).

**Что из этого НЕ следует.** Причина отказа ansible по-прежнему не названа: её
нет ни в одном сохранившемся журнале, а проверить связь с узлом из моей сессии
нельзя — произвольный `ansible`/`ssh` в цели запрещён, и обходить запрет я не
буду. Это установленное внешнее ограничение, а не недоделанная работа.

## Почему «успешная доставка» сама по себе ничего не закрывает

Проверка «доставлено и сверено» в сценарии подтверждает только совпадение
сумм ЯЩИКА на узле. Она ничего не говорит ни о том, разобрал ли комплект
приёмщик, ни о том, какое поколение данных витрина отдаёт после этого. Поэтому
признаком закрытия задачи считается стадия 5 — дата свежайшей карточки
витрины, — а не отчёт о доставке. Это тот же принцип, что в приёмке карты:
доказательство живёт на публичной стороне, а не в журнале инструмента.
