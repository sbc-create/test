получает конфигурацию через `docker compose config --format json` и
останавливается на любом несовпадении формы ДО изменений.

## Почему переноса alias недостаточно

В Compose **имя сервиса само является именем в DNS сети проекта**. Пока прежний
сервис называется `site-factory-mcp`, это имя разрешается в него независимо от
списка `aliases`; выдача того же имени мосту даёт два адреса на одно имя, и
примерно половина вызовов уходит в прежний пустой реестр. Отсюда порядок:

1. прежний сервис переименовывается в `site-factory-mcp-legacy`; образ,
   `container_name`, томa и healthcheck сохраняются — данные не затрагиваются;
2. лишний alias, равный имени сервиса, из него убирается;
3. зависимости переводятся на новое имя **с сохранением** `condition:
   service_healthy` и `required: true` — проверено разрешённой конфигурацией
   самого compose;
4. ссылки вида `http://site-factory-mcp:9000` в переменных других сервисов
   переводятся на `site-factory-mcp-legacy`: их поведение остаётся прежним, на
   мост переходит только коннектор;
5. сервис `site-factory-mcp` создаётся заново — это канал SSH к мосту.

URL коннектора при этом не меняется.

## Доставка пакета на srv-qwen

Файла пакета на srv-qwen НЕТ и предполагать его наличие нельзя: путь
`/srv/site-factory/indexing-operator-2026-10-03/…` — это каталог прогона на
claude-control-01. Канала передачи файлов туда тоже нет:

- ключ канала несёт `command="/bin/false"` и `permitopen="127.0.0.1:9000"` —
  возможен только проброс на порт моста, `scp`/`sftp` исключены;
- обратного доступа (фабрика → srv-qwen) нет: `inventory/ssh-hosts.yaml`
  содержит `hosts: []`;
- мост отдаёт только инструменты MCP в режиме чтения; расширять его поверхность
  ради доставки файла нельзя.

Поэтому пакет едет ВНУТРИ инструкции: gzip + base64 одним блоком, а SHA-256
распакованного файла подтверждает версию.

    размер : 42415 байт
    SHA-256: 083647f974d210b03caddfc3402257e1c01d9a04837b92de17f94f62b1af225e
    место  : /opt/qwen/site-factory/connect-site-factory-bridge.sh

Проверено исполнением ровно того конвейера, который попадёт в терминал
(heredoc → `base64 -d` → `gzip -dc` → `tee`): доставленный файл совпадает по
SHA-256, проходит `bash -n`, `--help` отвечает кодом 0. Вложение и инструкция
лежат рядом с пакетом: `connect-site-factory-bridge.sh.b64`,
`DELIVERY-TO-SRV-QWEN.md`.

## Единый пакет для администратора

`automation/srv-qwen/connect-site-factory-bridge.sh` (копия — в каталоге
прогона `/srv/site-factory/indexing-operator-2026-10-03/`).

| шаг | содержание |
| --- | --- |
| 0 | права на конкретные пути, docker, compose, валидность ИСХОДНОГО файла, имя проекта по метке работающего контейнера |
| 1 | разбор фактической конфигурации: сеть, aliases, зависимости с условиями, ссылки на имя |
| 2 | канал: ключ и закреплённый `known_hosts` на месте (печатается только отпечаток), образ доступен, клиент HTTP внутри контейнера Open WebUI найден |
| 3 | резервная копия: файл, разрешённая конфигурация, `ps`, сеть, перечень инструментов прежнего ответчика |
| 4 | точечная правка: переименование, зависимости, ссылки, блок моста |
| 5 | проверка новой конфигурации ДО применения: `config -q` плюс инварианты, включая «имя принадлежит только мосту» |
| 6 | применение: снятие прежнего контейнера, замена файла, запуск только нужных сервисов, пересоздание тех, где была ссылка |
| 7 | приёмка: `system_readiness`, `list_registered_sites`, `get_registered_site` ИЗ контейнера Open WebUI, сверка host, версии, источника, отпечатка, 23 сайтов и контрольного домена |
| 8 | имя `site-factory-mcp` в работающей сети принадлежит ровно одному контейнеру |
| при отказе | возврат файла из копии, снятие контейнеров моста и переименованного сервиса, подъём прежнего, сообщение о владельце имени |

Команды: `--check` (без изменений), без аргументов (полный проход),
`--rollback` (возврат из последней копии).

| проверка | способ | результат |

| правка на фактической форме | настоящий `docker compose config -q` и `--format json` | валидна; зависимость `{"site-factory-mcp-legacy": {"condition": "service_healthy", "required": true}}` |
| многострочная команда SSH | исполнена в контейнере с подставным `ssh` | ssh получает 18 аргументов нужного состава; `apk` не вызывается, если `ssh` есть |
| пакет целиком | `automation/local/mock-srv-qwen-package.py` — макет той же формы, настоящий `docker compose` | 18 проверок без сбоев; найдены и исправлены два настоящих дефекта (см. ниже) |

Макет нашёл то, чего не видно чтением:

1. **имя проекта Compose.** Пакет полагался на неявное имя (каталог файла). Если
   стек создан с `-p`, `COMPOSE_PROJECT_NAME` или ключом `name:`, `stop`/`rm`
   уходят в другой проект, а `up` упирается в занятое `container_name`. Теперь
   имя проекта берётся из метки `com.docker.compose.project` работающего
   контейнера, а несколько проектов с тем же сервисом — остановка.
2. **осиротевший контейнер моста при откате.** Он носит имя сервиса в DNS и при
   `restart: unless-stopped` поднимается снова, давая после возврата состояния
   то самое двойное разрешение. Откат теперь снимает контейнеры моста и
   переименованного сервиса и печатает, кому принадлежит имя.

## НЕ ПРОВЕРЕНО

- **приёмка из контейнера Open WebUI** (`system_readiness`,
  `list_registered_sites`, `get_registered_site` через
  `http://site-factory-mcp:9000/mcp`): требует srv-qwen. Доступа нет —
  `inventory/ssh-hosts.yaml` содержит `hosts: []`, srv-qwen в inventory
  отсутствует, прямой `ssh` профилем запрещён. Выполняется шагом 7 пакета.
- **вызов инструмента непосредственно в сессии Qwen** (не HTTP, а работа
  модели с инструментом): не подтверждён. HTTP 200 и `healthy` приёмкой не
  считаются; подтверждением будет ответ инструмента в сессии с
  `host=claude-control-01` и 23 сайтами.
- **полная конфигурация `/opt/qwen/compose.yaml`**: известны только отдельные
  факты и конец вывода.
- **настоящий туннель из контейнера моста**: в макете канал заведомо
  недоступен; проверяется шагами 6–7 пакета на srv-qwen.

## Границы

Подключение в режиме только чтения **не является** готовностью к выпуску
сайтов: пишущий инструмент не объявлен, разрешения выпуска и владельца
выставляются отдельно и вручную. Открытие production-доменов для индексации
этим заданием не предусмотрено и не выполнялось.
