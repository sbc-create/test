# Задачи поддержки (вне основной итерации)

Владелец 23.10: «MOD148 и обработку повреждённой резервной копии оставь
отдельными задачами поддержки. Снимки приёмки должны перестать попадать в
каждый новый выпуск.» Здесь они и лежат — с измеренным состоянием, критерием
и тем, чьё решение требуется. В очередях домéнов их нет: они не про домены.

## 1. MOD-148 — снимки приёмки возвращаются с каждой выкладкой

**Состояние измерено 23.10.** Каталог релиза — это полная выкладка
репозитория на коммите, и снимки лежат внутри потому, что они ЗАКОММИЧЕНЫ:
`artifacts/evidence/products/*/screenshots`,
`artifacts/evidence/release/live-acceptance`, `.../preview-screenshots`.
Следствие: 147 изображений в каждом из 12 каталогов релизов `lords-tooling` и
55 в каждом из двух `animeg0-site`. Уборка это не лечит — копии возвращаются
при следующей выкладке.

**Сторож уже показывает нарушение числом.**
`screenshot-retention-guard.py --list <опись>` по итоговой описи 23.10:
ПРЕВЫШЕНО, 5 817 снимков, 2,48 ГиБ против потолка 2,0; четыре каталога релизов
сверх предела 20 снимков. Прогон занимает секунды, если дать ему готовую опись.

**Критерий закрытия** (он же ответ на «снимки должны перестать попадать в
выпуск»): полноразмерные наборы не отслеживаются git-ом — в репозитории
остаются опись и уменьшенный образец на каталог прогона; сторож по `/srv` даёт
ИСПРАВНО; проверка прогоняется ПОСЛЕ выкладки нового релиза, а не только после
уборки. Чистка истории git в критерий НЕ входит.

**Чьё решение.** Владельца: (а) перестать коммитить наборы — правило и
инструменты готовы; (б) отдельно — чистить ли историю. Пока (б) не сделано,
каждая выкладка несёт прежние 147 файлов, но НОВЫЕ наборы добавляться
перестанут. Правило уже применено к себе: в этой копии git держит 163
изображения на 11,9 МиБ, из них 1,5 МиБ — 335 образцов снятых наборов вместо
2,2 ГиБ самих наборов.

## 2. Повреждённая резервная копия — учитывается отдельно, не чинится

**Состояние измерено 23.10** (`backup-generation-audit.py`): поколений 24,
ГОДНЫХ 20. Повреждён ровно один файл —
`lords-06-details.json.before.daily-20261023T033423Z`, 122 880 байт, хвост не
закрывает структуру (жертва ENOSPC того же прогона).

**Что из этого следует.** Восстановление возможно и без него: двенадцать
суточных поколений 11.10–22.10 полны (13 витрин из 13, по 1,15–1,24 ГиБ),
ближайшая полная точка — `daily-20261022T033207Z`. Значит обрезанный файл
мешает не восстановлению, а УБОРКЕ: `backup-retention.py --keep-days 7`
отказывается работать, пока он лежит в каталоге, и поэтому срок хранения не
применён, а копии продолжают расти на 1,14 ГиБ в сутки.

**Чего делать НЕ надо** (прямо отклонено владельцем 23.10): копировать живой
JSON поверх исторического `before.daily` — это подменило бы снимок на момент
прогона сегодняшними данными и испортило бы саму точку восстановления.
Предложение снято и повторяться не будет.

**Чьё решение.** Владельца, и выбор из трёх: пометить файл и исключить из
проверки срока хранения; перенести в отдельный каталог разбора; удалить как
заведомо непригодный. Любой из трёх разблокирует срок хранения.

**Критерий закрытия:** `backup-retention.py --keep-days 7` строит план без
строки «УДАЛЕНИЕ НЕ ВЫПОЛНЯЕТСЯ», и после применения срока свободного места
остаётся больше 5 ГиБ, а `backup-generation-audit.py` показывает годных
поколений не меньше трёх.

## Почему это не в основной итерации

Ни одна из двух не блокирует развитие сайтов: место на диске освобождено
(19,97 ГиБ), доставка каталогов работает, пользовательские сценарии восьми
витрин K2 проверены. Обе задачи — про гигиену хранения, и обе ждут одного
решения владельца каждая.
