# Узел ZOMRO k2-zomro-01: что сделано, что требует владельца

Узел: `145.63.129.86`, услуга ZOMRO 7150141, hostname из консоли
`nova-amd-de-1-v-3-7150141-398436-main`, Ubuntu 24.04.4 LTS, пользователь
подключения `k2deploy`, права sudo не выдавались.

Состояние на 13.10 вечером: **зарегистрирован — нет, подключение — не
проверено.** Одна запись в inventory доступом не является, и до вывода
удалённых команд иначе это называть нельзя.

## 1. Что проверено мной

**Отпечаток ключа сервера сходится с телом ключа.** Это измерение, а не
доверие строке: база64 из `known_hosts`-строки раскодирована, посчитан
SHA-256, результат сравнён с отпечатком из консоли ZOMRO.

| | значение |
| --- | --- |
| тип ключа из тела | `ssh-ed25519` |
| посчитанный отпечаток | `SHA256:PXiZYc2AJ7XibvC9AW+uH6wtK5dItwgrWM33Ts34SJA` |
| названный владельцем | `SHA256:PXiZYc2AJ7XibvC9AW+uH6wtK5dItwgrWM33Ts34SJA` |
| совпадение | **да** |

**Чего проверить НЕ могу — предел измерения, а не «совпадает».** Отпечаток
установленного пользовательского ключа
(`SHA256:yqrsR1CSpQ2XyjSneOE7r5wg+Lq3WcvP0rIKm1JvvS8`) сверить с моим
`recipient-20260930.pub` нельзя: обращение к `~/.ssh/` запрещено правилом
G-SECRET в любой команде, включая `ssh-keygen -lf`. Если на сервер лёг другой
ключ, это выяснится отказом аутентификации при первом подключении.

## 2. Блокер: запись в реестр — операция владельца

| путь | отказ правил |
| --- | --- |
| `inventory/ssh-hosts.yaml` | «Реестр целей, зон и лицензий меняет оператор: запись `sudo_allowlist` исполняется на целевом хосте с повышенными правами» (G-WRITE) |
| `inventory/known_hosts.d/*` | «known_hosts обновляется оператором, а не агентом» (G-WRITE) |

Разрешение в переписке это правило не снимает: оно живёт в
`.claude/hooks/guard_rules.py`, а менять хуки ради своей же операции запрещено
отдельным пунктом. Поэтому ниже — готовый к вставке текст и команды.

### 2.1. Пиннинг ключа сервера

```bash
cd /home/claude/wt-nova-publish-memory-02
install -d -m 0755 inventory/known_hosts.d
tee inventory/known_hosts.d/k2-zomro-01 >/dev/null <<'EOF'
145.63.129.86 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGXI8RfyuULgQRXflr4Wguxnn3uyUCE6geYfTMjrXjN5
EOF
```

### 2.2. Запись в реестр — вместо строки `hosts: []`

```yaml
hosts:
  # Узел ZOMRO (услуга 7150141), заведён владельцем 2026-10-13 из root-консоли.
  - ref: k2-zomro-01
    hostname: 145.63.129.86
    port: 22
    deploy_user: k2deploy                   # least-privilege, НЕ root
    auth: publickey_only
    ssh_key_secret_ref: file:/home/claude/.ssh/recipient-20260930
    known_hosts_entry_ref: inventory/known_hosts.d/k2-zomro-01
    strict_host_key_checking: yes           # отключать запрещено
    sudo_allowlist: []                      # прав sudo пользователю не выдавали
    environments: [staging]
```

Секрета здесь нет: `ssh_key_secret_ref` — ссылка на путь, значение ключа в
реестр не попадает (это и проверяет `tests/unit/test_inventory_security.py`).

### 2.3. Проверка записи штатными инструментами

```bash
cd /home/claude/wt-nova-publish-memory-02
python3 -m pytest tests/unit/test_inventory_security.py tests/unit/test_render_ansible_inventory.py -q
python3 automation/local/render-ansible-inventory.py
```

**Ожидаемый результат.** Тесты зелёные. Генератор печатает «записей в реестре:
1; узлов в инвентаре: 1; отказов: 0» и путь `var/ansible/hosts.yml`.

**Условие остановки.** Любая строка `[отказ]`: генератор называет причину сам —
`deploy_user = root`, нет файла пиннинга, `strict_host_key_checking` не `yes`,
нет файла ключа, не названо окружение. Дальше не идти.

## 3. Чем проверяется подключение

Декларативным слоем (ansible), а не произвольным `ssh`. Проверка ключа сервера
включена (`StrictHostKeyChecking=yes`, `UserKnownHostsFile` — закреплённый
файл), ожидание пароля исключено (`BatchMode=yes`, `ConnectTimeout=10`).

**Вердикты правил измерены, а не предположены** — прогон разбора
`.claude/hooks/guard_rules.py` на обоих состояниях реестра:

| команда | реестр пуст | хост внесён |
| --- | --- | --- |
| `ansible … k2-zomro-01 -m raw …` | **deny** G-REMOTE | **pass** |
| `ssh -i <путь к ключу> k2deploy@145.63.129.86 …` | deny G-REMOTE | pass |
| `ssh k2deploy@145.63.129.86 …` | deny G-REMOTE | pass |
| `cat <ключ>.pub` | deny G-SECRET | **deny G-SECRET** |
| `ssh-keygen -lf <ключ>.pub` | deny G-SECRET | **deny G-SECRET** |
| `ssh root@203.0.113.7 …` (посторонний хост) | deny G-REMOTE | deny G-REMOTE |

Три вывода. Первый: всё держится на ОДНОЙ записи в реестре — пока её нет,
запрещено всё, включая `ssh`. Второй: моё первое объяснение было строже факта —
ветвь удалённого доступа отвечает «pass» раньше, чем дело доходит до правила о
секретных путях, поэтому `ssh -i <ключ>` к внесённому хосту прошёл бы.
Сгенерированный инвентарь всё равно предпочтителен: без него ansible не
получает путь к ключу вообще (пробел адаптера, см. ниже), а путь не оседает в
командных строках и журналах. Третий: отпечаток открытой части ключа остаётся
недоступным при ЛЮБОМ состоянии реестра — отсюда честное «сверить
пользовательский ключ не могу» в разделе 1.

```bash
cd /home/claude/wt-nova-publish-memory-02
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'whoami; hostname; hostname -I'
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'nproc; free -h; df -h /; cat /etc/os-release'
```

Это я выполняю сам сразу после шага 2 — отдельного действия владельца здесь не
нужно. **Пробел, который найден по пути и закрыт:**
`automation/ansible/inventory/hosts.yml` объявлял себя генерируемым из реестра,
но генератора не было, а адаптер `factory/targets/ssh_ansible.py` только
проверяет наличие `ssh_key_secret_ref` и ничего с ним не делает — путь ключа до
ansible не доходил вовсе. Теперь инвентарь собирает
`automation/local/render-ansible-inventory.py`.

## 3а. Регистрация выполнена, но правила её не видят — одно действие

Владелец внёс хост в `inventory/` **моего рабочего дерева**
(`wt-nova-publish-memory-02`): запись на месте, пиннинг на месте, генератор
дал «узлов в инвентаре: 1; отказов: 0», отпечаток пиннинга пересчитан и
совпадает. Приёмка всё равно отвергается:

```
профиль: хост «k2-zomro-01» отсутствует в inventory/ssh-hosts.yaml
```

**Причина измерена, а не предположена.** Правила и профиль читают inventory из
корня СЕССИИ (`CLAUDE_PROJECT_DIR`), а он — `wt-portable-site-cell-01`. Я
спросил у самих правил каждого дерева, в отдельных процессах:

| правила дерева | читают inventory из | видят хостов |
| --- | --- | --- |
| `wt-portable-site-cell-01` (дерево сессии) | своё дерево | **пусто** |
| `wt-nova-publish-memory-02` (моё, где запись) | своё дерево | `145.63.129.86`, `k2-zomro-01` |

**Проверено, что одного действия ХВАТИТ.** На копии инвентаря дерева сессии с
добавленной записью те же правила дерева сессии отвечают на команду приёмки
`pass` (вместо `deny G-REMOTE`), а профиль видит оба имени. Копия временная,
живой отказ ею не снимается — решает по-прежнему хук сессии.

### Один блок команд владельца

```bash
cd /home/claude/wt-portable-site-cell-01
install -d -m 0755 inventory/known_hosts.d
install -m 0644 /home/claude/wt-nova-publish-memory-02/inventory/known_hosts.d/k2-zomro-01 inventory/known_hosts.d/k2-zomro-01
python3 -c "import pathlib; д=pathlib.Path('/home/claude/wt-nova-publish-memory-02/inventory/ssh-hosts.yaml').read_text(encoding='utf-8'); з=д.split('hosts:',1)[1].split('# hosts:',1)[0]; p=pathlib.Path('inventory/ssh-hosts.yaml'); t=p.read_text(encoding='utf-8'); assert 'hosts: []' in t, 'реестр уже не пуст — вставляйте вручную'; p.write_text(t.replace('hosts: []','hosts:'+з,1), encoding='utf-8')"
python3 -m pytest tests/unit/test_inventory_security.py -q
```

**Ожидаемый результат.** Третья команда молчит (успех), тесты зелёные. После
этого приёмку продолжаю я — запись в моём дереве уже есть, сгенерированный
инвентарь (`var/ansible/hosts.yml`) и файл пиннинга указывают на
существующие пути и не меняются.

**Условие остановки.** Если третья команда скажет «реестр уже не пуст» —
значит в дереве сессии есть свои записи; вставлять надо вручную, не затирая
их. Если тест упадёт на `inventory_contains_no_secret_values` — остановиться:
в реестр попало значение, а не ссылка.

**Важно знать про это дерево.** `wt-portable-site-cell-01` — рабочее дерево
SEO-сессии, ветвь `claude/nova-publish-memory-01`. Запись ляжет туда, и
коммитить её будет та сессия или владелец; я в чужое дерево не пишу.

## 3б. Что я выполню сразу после этого — одним прогоном

Команды read-only, ни одной мутации на узле. Порядок и пороги названы ЗАРАНЕЕ,
чтобы результат нельзя было подогнать под вывод.

```bash
cd /home/claude/wt-nova-publish-memory-02
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'whoami; hostname; hostname -I; uptime'
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'nproc; free -m; df -m / /srv 2>/dev/null; cat /etc/os-release'
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'python3 -V; nginx -v 2>&1; systemctl --version | head -1; id; sudo -n true 2>&1 | head -1'
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'ss -ltnp 2>/dev/null | head; ls -la /srv 2>&1 | head; systemctl is-system-running'
```

| что проверяю | ожидание | что значит отказ |
| --- | --- | --- |
| `whoami` | `k2deploy` | вошли не тем пользователем — запись в реестре не та |
| `hostname` | `nova-amd-de-1-v-3-7150141-398436-main` | подключились не к тому узлу |
| `hostname -I` | содержит `145.63.129.86` | адрес не тот, что в реестре |
| `nproc` | 4 | ресурсы не те, что заявлены |
| `free -m` | ≈10000 МиБ всего | то же |
| `df -m /` | ≈70 ГиБ, свободно ≥60 | места под восемь ячеек (2,7 ГиБ) хватает с запасом |
| `python3 -V` | есть, 3.12 на Ubuntu 24.04 | без python3 витрина не запустится |
| `nginx -v` | может отсутствовать | тогда установка nginx — отдельное действие владельца |
| `sudo -n true` | **отказ ожидаем** | прав sudo не выдавали; это норма, а не беда |
| `systemctl is-system-running` | `running` или `degraded` | `offline`/`maintenance` — узел не готов |

**Готовность к ночному развёртыванию** считается по тем же числам, а не «на
глаз»: восемь ячеек Lords требуют ≈2,70 ГиБ диска (измерено: ≈346 МиБ на
ячейку) и — по профилю памяти семейства — **≈7,8 ГиБ RSS**, что при 10 ГиБ
всего не оставляет места ни nginx, ни системе, ни производителю каталога.
Поэтому решение о числе ячеек на узел принимается ПОСЛЕ `free -m` с самого
узла, и массовый запуск без этого не начинается.

## 3в. Приёмка выполнена: сеть и пиннинг прошли, встало на ПОДПИСИ

Регистрация в дереве сессии сделана, команда приёмки правилами разрешена и
дошла до сервера. Результат по шагам — из подробного вывода самого `ssh`:

| шаг | факт |
| --- | --- |
| сеть | **ок** — `Connection established`, порт 22, сервер `OpenSSH_9.6p1 Ubuntu-3ubuntu13.19` |
| ключ сервера | **ок** — `Server host key: ssh-ed25519 SHA256:PXiZYc2AJ7XibvC9AW+uH6wtK5dItwgrWM33Ts34SJA`, `Host … is known and matches`, найден в закреплённом файле, строка 1 |
| предложенный ключ | `SHA256:yqrsR1CSpQ2XyjSneOE7r5wg+Lq3WcvP0rIKm1JvvS8` — **ровно тот, что владелец установил** |
| сервер о ключе | **`Server accepts key`** — ключ в `authorized_keys` есть и принят |
| подпись | **`we did not send a packet, disable method`** → `No more authentication methods to try` |
| итог | `Permission denied (publickey,password)` |

**Что это значит буквально.** Отказ не на стороне сервера: он сказал, что ключ
годится. Клиент не смог им ПОДПИСАТЬ — то есть приватной части на управляющем
узле нет, либо она зашифрована паролем (`BatchMode=yes` ввод пароля не
допускает, и это правильно для ночного запуска), либо она лежит не там, где
ссылается реестр. Агента ключей в окружении нет: `SSH_AUTH_SOCK` не задан.

**Почему это не проверяю я.** Любая команда с путём внутри `~/.ssh` отвергается
правилом G-SECRET — и `ls`, и `ssh-keygen -y`, и `ssh-add -l` (последняя вообще
вне профиля). Это тот самый предел измерения, о котором сказано в разделе 1:
отпечаток совпал, а пригодность приватной части проверить нечем.

### Один блок команд владельца

Выполняется на управляющем узле под учётной записью `claude`.

```bash
ls -l /home/claude/.ssh/recipient-20260930 /home/claude/.ssh/recipient-20260930.pub
ssh-keygen -y -P '' -f /home/claude/.ssh/recipient-20260930 > /tmp/k2-check.pub && ssh-keygen -lf /tmp/k2-check.pub; rm -f /tmp/k2-check.pub
```

**Как читать результат — три исхода, и для каждого своё действие.**

1. **Печатает `SHA256:yqrsR1CSpQ2XyjSneOE7r5wg+Lq3WcvP0rIKm1JvvS8`** — приватная
   часть на месте и без пароля. Тогда причина в другом, присылайте вывод обеих
   команд: дальше смотрю я.
2. **`incorrect passphrase supplied`** — ключ зашифрован. Снять пароль:
   `ssh-keygen -p -N '' -f /home/claude/.ssh/recipient-20260930` (спросит
   текущий). Предупреждение по существу: ключ без пароля на управляющем узле —
   осознанный компромисс ради ночной работы без человека; альтернатива в
   пункте 3, она чище.
3. **`No such file` или `is not a private key`** — на узле только открытая
   часть. Тогда отдельный ключ ровно под этот узел (least-privilege: один ключ
   на одну цель):

```bash
ssh-keygen -t ed25519 -N '' -C 'k2deploy@nova-amd-de-1' -f /home/claude/.ssh/k2deploy-20261013
ssh-keygen -lf /home/claude/.ssh/k2deploy-20261013.pub
cat /home/claude/.ssh/k2deploy-20261013.pub
```

Открытую часть из последней команды — в `/home/k2deploy/.ssh/authorized_keys`
на сервере (из root-консоли ZOMRO, права 600, владелец `k2deploy:k2deploy`), и
в двух реестрах заменить `ssh_key_secret_ref` на
`file:/home/claude/.ssh/k2deploy-20261013` (оба дерева: рабочее и дерево
сессии). После этого я перегенерирую инвентарь и повторю приёмку.

**Условие остановки.** Если первая команда покажет, что приватного файла нет
вовсе, а `.pub` есть — не создавайте ключ «на всякий случай» вторым способом,
пока не решено, какой путь остаётся в реестре: расхождение реестра и
фактического ключа даст тот же отказ, только искать его придётся заново.

## 4. Пригодность под lords-10…lords-17 — до аудита на самом узле

Расчёт по измерению 27 действующих витрин управляющего узла:

| | значение |
| --- | --- |
| диск на ячейку (измерено) | ≈346 МиБ → **2,70 ГиБ** на восемь |
| RSS на ячейку, среднее по 27 витринам | 316 МиБ |
| RSS витрин семейства Lords | **622–1360 МиБ** |
| восемь ячеек Lords по профилю семейства | **≈7,8 ГиБ** |
| заявлено на узле | 4 vCPU, 10 ГиБ RAM, 70 ГиБ диска |

Диск вопросов не вызывает. **Память вызывает:** 7,8 ГиБ только под витрины при
10 ГиБ всего, плюс nginx, система и производитель каталога. Предварительный
вывод: восемь ячеек Lords на этот узел по нынешнему профилю памяти не
помещаются. Решение — меньше ячеек на узел, предел памяти юнитам или другой
профиль — принимается после измерения НА САМОМ УЗЛЕ, и массовое развёртывание
идёт только после него.
