# Узел ZOMRO k2-zomro-01: что сделано, что требует владельца

Узел: `145.63.129.86`, услуга ZOMRO 7150141, hostname из консоли
`nova-amd-de-1-v-3-7150141-398436-main`, Ubuntu 24.04.4 LTS, пользователь
подключения `k2deploy`, права sudo не выдавались.

Состояние на 13.10 вечером: **зарегистрирован — нет, подключение — не
проверено.** Одна запись в inventory доступом не является, и до вывода
удалённых команд иначе это называть нельзя.

## 1. Что проверено мной

**Отпечаток ключа сервера сходится с телом ключа.** Это измерение, а не
доверие строке: база64 из `known_hosts`-строки раскодирована, посчитан
SHA-256, результат сравнён с отпечатком из консоли ZOMRO.

| | значение |
| --- | --- |
| тип ключа из тела | `ssh-ed25519` |
| посчитанный отпечаток | `SHA256:PXiZYc2AJ7XibvC9AW+uH6wtK5dItwgrWM33Ts34SJA` |
| названный владельцем | `SHA256:PXiZYc2AJ7XibvC9AW+uH6wtK5dItwgrWM33Ts34SJA` |
| совпадение | **да** |

**Чего проверить НЕ могу — предел измерения, а не «совпадает».** Отпечаток
установленного пользовательского ключа
(`SHA256:yqrsR1CSpQ2XyjSneOE7r5wg+Lq3WcvP0rIKm1JvvS8`) сверить с моим
`recipient-20260930.pub` нельзя: обращение к `~/.ssh/` запрещено правилом
G-SECRET в любой команде, включая `ssh-keygen -lf`. Если на сервер лёг другой
ключ, это выяснится отказом аутентификации при первом подключении.

## 2. Блокер: запись в реестр — операция владельца

| путь | отказ правил |
| --- | --- |
| `inventory/ssh-hosts.yaml` | «Реестр целей, зон и лицензий меняет оператор: запись `sudo_allowlist` исполняется на целевом хосте с повышенными правами» (G-WRITE) |
| `inventory/known_hosts.d/*` | «known_hosts обновляется оператором, а не агентом» (G-WRITE) |

Разрешение в переписке это правило не снимает: оно живёт в
`.claude/hooks/guard_rules.py`, а менять хуки ради своей же операции запрещено
отдельным пунктом. Поэтому ниже — готовый к вставке текст и команды.

### 2.1. Пиннинг ключа сервера

```bash
cd /home/claude/wt-nova-publish-memory-02
install -d -m 0755 inventory/known_hosts.d
tee inventory/known_hosts.d/k2-zomro-01 >/dev/null <<'EOF'
145.63.129.86 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGXI8RfyuULgQRXflr4Wguxnn3uyUCE6geYfTMjrXjN5
EOF
```

### 2.2. Запись в реестр — вместо строки `hosts: []`

```yaml
hosts:
  # Узел ZOMRO (услуга 7150141), заведён владельцем 2026-10-13 из root-консоли.
  - ref: k2-zomro-01
    hostname: 145.63.129.86
    port: 22
    deploy_user: k2deploy                   # least-privilege, НЕ root
    auth: publickey_only
    ssh_key_secret_ref: file:/home/claude/.ssh/recipient-20260930
    known_hosts_entry_ref: inventory/known_hosts.d/k2-zomro-01
    strict_host_key_checking: yes           # отключать запрещено
    sudo_allowlist: []                      # прав sudo пользователю не выдавали
    environments: [staging]
```

Секрета здесь нет: `ssh_key_secret_ref` — ссылка на путь, значение ключа в
реестр не попадает (это и проверяет `tests/unit/test_inventory_security.py`).

### 2.3. Проверка записи штатными инструментами

```bash
cd /home/claude/wt-nova-publish-memory-02
python3 -m pytest tests/unit/test_inventory_security.py tests/unit/test_render_ansible_inventory.py -q
python3 automation/local/render-ansible-inventory.py
```

**Ожидаемый результат.** Тесты зелёные. Генератор печатает «записей в реестре:
1; узлов в инвентаре: 1; отказов: 0» и путь `var/ansible/hosts.yml`.

**Условие остановки.** Любая строка `[отказ]`: генератор называет причину сам —
`deploy_user = root`, нет файла пиннинга, `strict_host_key_checking` не `yes`,
нет файла ключа, не названо окружение. Дальше не идти.

## 3. Чем проверяется подключение

Декларативным слоем (ansible), а не произвольным `ssh`. Проверка ключа сервера
включена (`StrictHostKeyChecking=yes`, `UserKnownHostsFile` — закреплённый
файл), ожидание пароля исключено (`BatchMode=yes`, `ConnectTimeout=10`).

**Вердикты правил измерены, а не предположены** — прогон разбора
`.claude/hooks/guard_rules.py` на обоих состояниях реестра:

| команда | реестр пуст | хост внесён |
| --- | --- | --- |
| `ansible … k2-zomro-01 -m raw …` | **deny** G-REMOTE | **pass** |
| `ssh -i <путь к ключу> k2deploy@145.63.129.86 …` | deny G-REMOTE | pass |
| `ssh k2deploy@145.63.129.86 …` | deny G-REMOTE | pass |
| `cat <ключ>.pub` | deny G-SECRET | **deny G-SECRET** |
| `ssh-keygen -lf <ключ>.pub` | deny G-SECRET | **deny G-SECRET** |
| `ssh root@203.0.113.7 …` (посторонний хост) | deny G-REMOTE | deny G-REMOTE |

Три вывода. Первый: всё держится на ОДНОЙ записи в реестре — пока её нет,
запрещено всё, включая `ssh`. Второй: моё первое объяснение было строже факта —
ветвь удалённого доступа отвечает «pass» раньше, чем дело доходит до правила о
секретных путях, поэтому `ssh -i <ключ>` к внесённому хосту прошёл бы.
Сгенерированный инвентарь всё равно предпочтителен: без него ansible не
получает путь к ключу вообще (пробел адаптера, см. ниже), а путь не оседает в
командных строках и журналах. Третий: отпечаток открытой части ключа остаётся
недоступным при ЛЮБОМ состоянии реестра — отсюда честное «сверить
пользовательский ключ не могу» в разделе 1.

```bash
cd /home/claude/wt-nova-publish-memory-02
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'whoami; hostname; hostname -I'
ansible -i var/ansible/hosts.yml k2-zomro-01 -m raw -a 'nproc; free -h; df -h /; cat /etc/os-release'
```

Это я выполняю сам сразу после шага 2 — отдельного действия владельца здесь не
нужно. **Пробел, который найден по пути и закрыт:**
`automation/ansible/inventory/hosts.yml` объявлял себя генерируемым из реестра,
но генератора не было, а адаптер `factory/targets/ssh_ansible.py` только
проверяет наличие `ssh_key_secret_ref` и ничего с ним не делает — путь ключа до
ansible не доходил вовсе. Теперь инвентарь собирает
`automation/local/render-ansible-inventory.py`.

## 4. Пригодность под lords-10…lords-17 — до аудита на самом узле

Расчёт по измерению 27 действующих витрин управляющего узла:

| | значение |
| --- | --- |
| диск на ячейку (измерено) | ≈346 МиБ → **2,70 ГиБ** на восемь |
| RSS на ячейку, среднее по 27 витринам | 316 МиБ |
| RSS витрин семейства Lords | **622–1360 МиБ** |
| восемь ячеек Lords по профилю семейства | **≈7,8 ГиБ** |
| заявлено на узле | 4 vCPU, 10 ГиБ RAM, 70 ГиБ диска |

Диск вопросов не вызывает. **Память вызывает:** 7,8 ГиБ только под витрины при
10 ГиБ всего, плюс nginx, система и производитель каталога. Предварительный
вывод: восемь ячеек Lords на этот узел по нынешнему профилю памяти не
помещаются. Решение — меньше ячеек на узел, предел памяти юнитам или другой
профиль — принимается после измерения НА САМОМ УЗЛЕ, и массовое развёртывание
идёт только после него.
