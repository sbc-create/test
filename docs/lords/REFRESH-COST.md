# Куда уходят семь часов цикла

Вход для `SITE-ENGINE-02B`. Замерено на живом хосте 30 августа 2026 года, не
оценено.

## Разбор цикла

| Этап | Время | Зависит от |
| --- | --- | --- |
| выборка каталога по трём витринам | 11–15 мин | размера каталога и скорости источника |
| рендер и публикация одной витрины | 2 ч 22 мин | размера каталога |
| три витрины | 7 ч 08 мин | |

Каталог — 53 116 записей, релиз одной витрины — около 1,6 ГБ и порядка 61 тысячи
страниц.

## Главная находка: рендер выполняется всегда

Идентификатор релиза считается **от содержимого уже собранной витрины**:

```bash
release="$(find "$staging" -type f -print0 | sort -z \
           | xargs -0 sha256sum | sha256sum | cut -c1-12)"
target="${runtime}/releases/${release}"
...
if [ "$current" = "$target" ]; then
  log "${site}: каталог не изменился, релиз ${release} уже работает"
```

Проверка «каталог не изменился» стоит **после** сборки. Значит, при неизменном
каталоге цикл всё равно тратит два с половиной часа на витрину, чтобы в конце
получить тот же хеш и ничего не опубликовать. Экономится только копирование
1,6 ГБ и переключение ссылки.

Наблюдалось прямо: прогон 18:42 UTC получил `FRESH, записей 53116` по всем трём
витринам — каталог не изменился ни на запись — и всё равно начал полный рендер
`lords-01`, релиз которого собран из этого же каталога сорок минут назад.

**Проверка предсказания опровергла его.** Я записал было, что рендер прошёл
впустую, увидев в 21:13 неизменившийся список релизов. Это была поспешность:
проверка попала в момент между сборкой и публикацией. Через минуту появился
новый релиз `55d57e36b76f`, и сравнение с прежним показывает, что работа была не
холостой:

| Что сравнивалось | Результат |
| --- | --- |
| страниц было / стало | 61 318 / 61 328 |
| появилось страниц | 12 (в основном `/genres/drama/page/71…75/`) |
| исчезло страниц | 2 |
| изменилось содержимым | 52 из 300 общих страниц выборки (≈17 %) |

Причина: каждый прогон дообогащает 300 карточек из `detail` и проверяет 400 на
воспроизводимость потока (`ENRICH_BUDGET`, `PLAY_BUDGET`). Число записей в
каталоге то же, но содержимое витрины растёт — появляются жанры, страны,
описания, и вместе с ними новые страницы жанровых листингов.

Поэтому утверждение «неизменный каталог означает холостой рендер» **неверно**,
пока обогащение не насыщено. Верно другое, и это по-прежнему следует из кода:
решение о публикации принимается только после полной сборки, а значит, случай
действительно ничего не меняющего прогона обойдётся в те же два с четвертью
часа. Такой случай наступит, когда обогащение дойдёт до конца каталога.

## Что из этого следует для 02B

**Проверять изменение до дорогой работы, а не после.** Но отпечатка одного лишь
каталога для этого мало — и это уточнение к моему же первому предложению.
Содержимое витрины зависит ещё от состояния обогащения и от проверки
воспроизводимости, которые растут с каждым прогоном. Предварительное сравнение
должно учитывать все три источника: каталог, обогащение, воспроизводимость.
Отпечаток по ним троим отсекает сборку целиком в те прогоны, когда не изменилось
ничего, — а такие наступят, как только обогащение насытится.

**Перерисовывать затронутое, а не весь каталог.** Выход одной серии меняет
страницу тайтла, полку новых серий и одну-две страницы листинга — не 61 тысячу
страниц. Инкрементальный рендер приводит стоимость обновления в соответствие с
величиной изменения.

**Разделить свежесть и полноту.** Полный обход нужен для полноты и может идти
раз в сутки. Свежесть новых серий требует минут, а не часов, и должна
обеспечиваться отдельным быстрым путём.

Пока это не сделано, восьми- и десятичасовые пределы остаются подпорками:
серия, вышедшая через пять минут после начала цикла, доедет до витрины через
семь часов независимо от величины предела.

## Смежное: публикация атомарна — прежнее утверждение было ошибочным

Я записал здесь, что `ln -sfn` выполняется как `unlink` плюс `symlink` и потому
оставляет окно без ссылки. **Это неверно.** Проверка системных вызовов
опровергает:

```
$ strace -e trace=symlinkat,unlinkat,renameat ln -sfn b current
symlinkat("b", AT_FDCWD, "current")     = -1 EEXIST (File exists)
symlinkat("b", AT_FDCWD, "CumdNavt")    = 0
renameat(AT_FDCWD, "CumdNavt", AT_FDCWD, "current") = 0
```

GNU coreutils 8.32 сам создаёт ссылку под временным именем и переставляет её
через `renameat(2)` — ту самую атомарную операцию, которую я предлагал
«внедрить». Окна нет.

Испытание подтверждает: 400 переключений при шести параллельных читателях,
11 021 обращение к ссылке, ноль случаев её отсутствия.

Утверждение держалось на чтении кода сценария и знании, что `ln -f` *может*
делать unlink, — но не на проверке того, что он делает здесь. Это ошибка
рассуждения по аналогии вместо измерения.

## Сколько карточек на витрине и почему не 53 116

Замерено на `lords-01`, релиз `d4296e961e19`.

| Величина | Записей |
| --- | --- |
| в кэше каталога | 53 116 |
| уникальных адресов после разрешения столкновений | 52 909 |
| карточек на диске | 52 412 |

Недостача в 704 карточки распадается на две части **разной природы**, и путать
их нельзя.

### 497 — так и задумано

Все 497 имеют тип контента `anime`, которого нет среди активных типов
`lords-01`: витрина публикует `movies`, `series` и `animation`. Страницы
строятся из `catalog.of_types(kinds)`, где `kinds` берутся из плана сайта.
Аниме — предмет порталов Yummy, и его отсутствие здесь правильно.

Отсюда следствие для приёмки: **ожидать 53 116 страниц на витрине неверно**.
Проверять нужно, что все тайтлы активных типов получили страницы. Сравнение с
сырым числом записей дало бы ложную недостачу и увело бы от настоящей.

### 207 — дефект

`seen` в `catalog_from_live` ключуется **исходным** слагом, а суффиксная форма в
нём не регистрируется:

```python
count = seen.get(title.slug, 0)
seen[title.slug] = count + 1
if count:
    title = replace(title, slug=f"{title.slug}-{count + 1}")
```

Второй тайтл с именем «Агент времени» получает адрес `agent-vremeni-2`. Тот же
адрес принадлежит настоящему тайтлу «Агент времени 2», и `by_slug` оставляет
одного из двух. Так теряются 207 записей — 0,4 % каталога.

Починка: регистрировать в `seen` итоговый слаг и повторять суффиксацию, пока
адрес не станет свободным. Правка вне разрешения, выданного на два systemd-юнита,
поэтому записана в план `SITE-ENGINE-02B`, а не сделана.
