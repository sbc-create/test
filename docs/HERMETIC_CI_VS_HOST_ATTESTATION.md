# Герметичный CI и аттестация хоста

Версия документа: `ci-host-split/1.0.0`
Ветка: `claude/fleet-core-003-r2` (PR #77)
Исходный прогон CI: run `35142243172` — 7/8 стадий, 15 failed, 4267 passed, 14 errors.

## Различение

Обязательная проверка PR (`Verify (schemas, lint, tests)` → `./scripts/verify.sh`)
проверяет **воспроизводимые программные контракты**: то, что верно в любом клоне
репозитория на любой машине. Она не обращается к `/srv/site-factory`, не требует
живых systemd-юнитов, боевых баз, реальных доменов и фиксированных портов,
использует `tmp_path`, изолированные БД, управляемые процессы с readiness и
обязательным teardown, и не зависит от порядка тестов.

Факты о живом флоте проверкой кода не являются. Они устанавливаются явно
запускаемым host-контуром:

```bash
HOST_ATTESTATION_CONTROL_HOST=1 bin/host-attest --candidate-sha <40 hex>
```

Команда выпускает машиночитаемое свидетельство
(`schemas/host-attestation.schema.json`), привязанное к точному candidate SHA и
моменту измерения. Без допуска она не притворяется успехом: выпускает
свидетельство с вердиктом `BLOCKED` и завершается кодом 2.

Коды возврата: `0` — PASS, `1` — FAIL, `2` — BLOCKED, `3` — неверный вызов.

## Ворота релиза

`factory/site_engine/attestation/gate.py` останавливает production-выкат
(`factory/pipeline.py`, до единой мутации), если свидетельство:

| Отказ | Код |
| --- | --- |
| отсутствует | `HOST_ATTESTATION_MISSING` |
| протухло (старше 24 ч) | `HOST_ATTESTATION_STALE` |
| относится к другому дереву | `HOST_ATTESTATION_SHA_MISMATCH` |
| неполно | `HOST_ATTESTATION_INCOMPLETE` |
| содержит failed/blocked обязательную проверку | `HOST_ATTESTATION_CHECK_FAILED` |
| снято не на control host | `HOST_ATTESTATION_NOT_CONTROL_HOST` |
| повреждено, время без зоны, вердикт не из данных | `HOST_ATTESTATION_MALFORMED` |

`BLOCKED` блокирует наравне с `FAIL`: «не смотрели» — не «всё хорошо».

Ворота проверяются герметично на синтетических свидетельствах —
`tests/unit/test_host_attestation_gate.py`, — включая параметризацию по каждой
обязательной проверке по отдельности. Что их отсутствие останавливает конвейер,
проверяется в `tests/unit/test_production_gates.py`.

Граница герметичности сама по себе является проверяемым контрактом:
`tests/unit/test_hermetic_ci_boundary.py` разбирает код всех `tests/**/test_*.py`
и падает, если в них появится обращение к данным флота или к каноническому порту.

## Открытый пункт

`tests/credentials/test_secret_boundary.py:131` вызывает
`POL.одобрить()` с самодельным набором `cs-1`, которого нет ни в одном
хранилище. Служба подписи читает каноническое состояние сама — в этом её смысл —
и честно отвечает `404` (в CI до правки эфемерности было `500`). Тест устарел
вместе с переходом на подпись по ссылке; дефект в тесте, а не в коде.

Правка требует изменения файла под каталогом `tests/credentials/`, закрытым
deny-правилом `Read(./**/credentials)` в `.claude/settings.json`. Правило
написано под файлы учётных данных, а каталог тестов совпал с ним побочно.
Профиль UNATTENDED_SAFE запреты не снимает, `Edit(.claude/**)` тоже запрещён.

Дефект внесён коммитом `f402676` («служба подписи перестала заверять
присланное») на этой же ветке: он снял у службы возможность подписывать
присланное тело, но этот вызывающий не обновил. На `main` теста в таком виде
нет, поэтому закрыть его — часть этого PR, а не отдельная задача.

### Требуемая правка

Заменить самодельный `набор` на набор, реально существующий в том хранилище,
которое читает служба подписи. `эфемерный_signer` задаёт `CHANGESET_DB`, поэтому
`store.открыть()` без аргумента попадает ровно туда:

```python
from factory.site_engine.changeset import store as S

соед = S.открыть()                       # CHANGESET_DB задан эфемерным signer
создано = S.создать(
    соед,
    {"resource_type": <род ресурса>, "resource_id": "r",
     "operation_type": "update", "target_site_ids": ["s1"],
     "idempotency_key": "credentials-revocation",
     "correlation_id": "credentials-revocation",
     "requested_change": {"canonical_domain": "s1.invalid"}},
    producer_service="templates", actor_id="service:templates",
    actor_type="SERVICE")
cid = создано["changeset_id"]
# набор обязан дойти до состояния с планом: одобрять нечего, пока plan_hash пуст
...                                      # как в tests/tplr2/_путь.py::довести_до_approved
набор = S.получить(соед, cid)
запись = POL.одобрить(набор, approver_id="human:owner", ...)
```
