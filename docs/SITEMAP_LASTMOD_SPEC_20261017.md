# Даты в карте сайта: что именно менять (задание владельца 17.10)

Запись от 2026-10-17, 08:55 UTC. Владелец разрешил довести до выпуска две
правки дат — индекса карты и страниц сезонов и серий — на пяти витринах
(`yummyani.site`, `.org`, `.biz`, `yummyani7.site`, `yummyani7.info`) через
ответственную линию приложения и штатный выпуск. Здесь — требования, разбор
причин по коду и мера приёмки. Код правит линия приложения в своём дереве;
выпуск и приёмку ведёт линия выпусков.

## Требования владельца, дословно по смыслу

1. `lastmod` страницы отражает **подтверждённое существенное обновление её
   содержимого**;
2. `lastmod` в `sitemap-index` отражает **изменение соответствующего файла
   карты**;
3. **дата эфира остаётся характеристикой произведения** — в содержимом
   страницы, не в `lastmod`;
4. при отсутствии достоверной даты обновления **необязательный `lastmod`
   опускается**; массовая подстановка сегодняшней даты или даты запуска сайта
   запрещена;
5. прежде сохранённые ошибочные значения — проверить;
6. проверка только диапазона годов недостаточна: неизменённая страница
   сохраняет дату при повторном запросе **и при перезапуске**, а существенное
   изменение получает обновление.

То есть у страниц сезонов и серий сломаны обе стороны сразу: часть адресов

тайтла. Первое — не дата обновления, второе — массовая подстановка.

## Причины по коду

* **`src/lib/seo/sitemap-detail-order.ts::detailRecord`**
  `at = observed.episodes.get(`${slug}:${key}`) ?? dateMs(episode.airDate, now)`
  — при отсутствии наблюдения берётся дата эфира, и она же попадает в
  хранилище подробностей;
* **`src/lib/seo/sitemap-inventory.ts::dated(at, modified)`** отдаёт это
  значение в `lastModified` сезона и серии, а при `at <= 0` подставляет дату
  тайтла — отсюда 77 % одинаковых дат;
* **`src/lib/seo/sitemap-inventory.ts::lastmod(title, fallback)`** при
  отсутствии `title.updatedAt` возвращает `fallback`, то есть константу
  `SEO_CONTENT_UPDATED_AT = 2026-08-21`;
* **`src/lib/seo/sitemap.ts::sitemapIndexXml`** объявляет всем частям
  `sitemapLastModified()` — ту же константу.

## Что делать (предлагаемое решение)

### A. Страницы: дата только подтверждённая, иначе её нет

* `SitemapUrlRecord.lastModified` становится **необязательным**
  (`Date | undefined`). Запись XML к этому готова: `sitemapUrlsetXml` уже
  опускает `<lastmod>`, когда значения нет (`lastmod ? … : null`), менять
  писатель не требуется;
* **страница произведения**: `title.updatedAt`, если он есть и разбирается;
  иначе `lastmod` **опускается** (сейчас — константа);
* **страницы сезона и серии**: только **время наблюдения** появления
  содержимого (`observed.episodes`, `observed.seasons` из журнала наблюдений);
  иначе `lastmod` **опускается**. Дата эфира в `lastmod` не используется
  никогда;
* сезон: максимум по НАБЛЮДЁННЫМ сериям сезона; если наблюдений нет — дата
  опускается.

### B. Прежде сохранённые значения: без сброса хранилища

Хранилище подробностей `seo:sitemap-detail:v1` хранит тройки
`[сезон, серия, at]`, где `at` — уже испорченная дата. Сбрасывать ключ
**нельзя**: вместе с ним потеряется достигнутое покрытие (сейчас
`covered` 4 656 и 4 434 на `.biz`/`.org`, 800 на обоих `yummyani7`), а
владелец требует покрытие сохранить. Поэтому:

* номера сезонов и серий из хранилища продолжают использоваться — это и есть
  покрытие;
* **поле `at` из хранилища перестаёт использоваться как дата**: дата берётся
  из журнала наблюдений на этапе сборки инвентаря. Так старые значения
  обезвреживаются без единой записи в хранилище;
* при следующем штатном обновлении записи (`detailRecord`) поле `at` можно
  писать только когда наблюдение есть, иначе `0` — это снимает конфликт на
  будущее, но ждать переписывания всех записей для исправления карты не нужно.

### C. Индекс: дата изменения ФАЙЛА карты, устойчивая к повторному запросу

* рядом с инвентарём хранится по каждой части **дайджест её содержимого**
  (список адресов и их дат) и **время, когда дайджест последний раз
  изменился**;
* индекс объявляет частью именно это время. Перестройка, не изменившая часть,
  дату **не двигает** — отсюда устойчивость к повторному запросу и к
  перезапуску (значение лежит в Redis рядом с инвентарём, срок хранения тот
  же);
* если времени нет (холодный старт, пустое хранилище) — `lastmod` в индексе
  **опускается**, а не подставляется константой;
* время перестройки (`BUILT_KEY`) как дата индекса — допустимо лишь как
  промежуточный вариант; он нарушает требование 6, потому что двигает дату
  при каждой перестройке, даже если часть не изменилась. Поэтому в выпуск
  идёт вариант с дайджестом.

## Мера приёмки (проверка только годов недостаточна)

Проверять по адресам, а не по сводке:

1. **границы интервала с двух сторон**: ни одного `lastmod` позже текущего
   времени и ни одного раньше даты создания витрины; в частях `seasons` и
   `episodes` — ноль дат старше 2010 года;
2. **нет массовой подстановки**: доля самой частой даты в части `episodes`
   ниже 20 % (сейчас 77,3 %); число различных дат растёт;
3. **устойчивость к повторному запросу**: тот же адрес, два запроса с
   интервалом ≥5 минут — `lastmod` совпадает дословно;
4. **устойчивость к перезапуску**: после `docker restart` контейнера —
   `lastmod` того же адреса совпадает с дозапусковым значением;
5. **реакция на изменение**: у страницы, по которой в журнале наблюдений
   появилось новое наблюдение, дата обновляется, и дата соответствующей части
   в индексе сдвигается; у не изменившихся частей дата индекса остаётся
   прежней;
6. **индекс не старше содержимого**: дата части в индексе не раньше
   свежайшей достоверной даты внутри неё и не позже текущего времени;
7. **сохранено**: число адресов в частях не упало, деление частей на месте,
   `publisher_id`, `canonical`, режим индексации и ноль ошибок записи кеша.

Пункты 3–5 — ровно то, чего не покрывает проверка диапазона годов, и ровно то,
на чём владелец настоял.
