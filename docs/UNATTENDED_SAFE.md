# Профиль UNATTENDED_SAFE

Постоянный режим работы фабрики: обычная разработка и штатный выкат идут без
подтверждений, обязательные стоп-сигналы остаются на месте. Профиль включён для
всех сессий репозитория — он задан в основном `.claude/settings.json`, а не в
локальном файле сессии и не в `settings.unattended.json`, который применяется
только при явной передаче через `--settings`.

`bypassPermissions` не используется: в облачном Claude Code он недоступен, а
`disableBypassPermissionsMode: "disable"` в настройках закрывает его насовсем.
Автономность достигается решениями хуков, а не отключением проверок.

## Где живёт решение

| Слой | Файл | Что делает |
| --- | --- | --- |
| Запреты фабрики | `.claude/hooks/guard_rules.py` | `deny` по правилам G-*. Вердикт окончателен. |
| Запреты оператора | `seo_operator/guardrails.py` | `BLOCKED_PATTERNS`, production-поверхности. |
| Профиль | `seo_operator/unattended.py` | Умеет **только** `allow`. Ни одного запрета не отменяет. |
| Хуки | `.claude/hooks/guard_bash.py`, `guard_write.py`, `seo_operator/hookguard.py` | Отдают решение Claude Code. |
| Модель разрешений | `seo_operator/permission_model.py` | Складывает правила настроек и решения хуков — как это делает Claude Code. |
| Матрица | `tests/unit/test_permission_matrix.py` | Проверяет итог всех слоёв, а не отдельное правило. |

Порядок разрешения: `deny` в настройках → решение хука (`deny` или `allow`)
→ `allow` в настройках. Запрет в настройках сильнее любого разрешения хука,
поэтому список `deny` — последняя линия, и он только пополняется.

**У проектных хуков ровно два исхода: `allow` и `deny`.** Исхода `ask` больше
нет: профиль работает без человека, и на неотвечающем терминале подтверждение —
не защита, а зависание без записи причины. Всё, что раньше уходило на
подтверждение, теперь отвечает «нет» сразу и называет условие, а сам отказ
дописывается в `var/log/unattended-denials.jsonl` — раз человека не спрашивают,
отчёт обязан уметь показать, что именно было запрещено и почему.

Запреты при этом не ослаблены: списки в разделе «Что по-прежнему останавливает
работу» действуют полностью. Инвариант закреплён тестами
`tests/unit/test_unattended_no_prompts.py`: штатный цикл проходит без единого
`ask`, опасные операции отвечают `deny` и попадают в журнал.

## Как разбирается команда

Разбор синтаксический, а не по подстроке:

1. команда режется на сегменты по `&&`, `||`, `;`, `|`, `|&` и переводу строки
   с учётом кавычек;
2. тела heredoc отделяются: `cat > file <<EOF` пишет данные, а не исполняет их;
   heredoc, который читает интерпретатор, разбирается как код;
3. у сегмента снимаются перенаправления — `2>&1`, `>out.log`, `&>/dev/null`, `< in`;
4. снимаются присваивания и обёртки: `VAR=1`, `env FOO=2`, `timeout 300`, `nice`,
   `nohup`, `command`, `flock`, `setsid`, `stdbuf`;
5. `xargs` распаковывается отдельно: его флаги и их значения отбрасываются, а
   классифицируется команда, которую он запустит;
6. остаток классифицируется по первой программе.

Разрешение выдаётся, только если рутинен **каждый** сегмент. Один непонятный
сегмент снимает разрешение со всей команды: безопасная команда не ручается за
то, что к ней приписали через `&&`.

Поэтому `git status --short; timeout 300 git push origin claude/... 2>&1 | tail -3`
выполняется без подтверждения, а `git status && /usr/local/bin/unknown` — нет.

Если составная команда всё же уходит на подтверждение, её следует разбить на
несколько разрешённых команд, а не останавливать работу.

## Что выполняется автономно

**Репозиторий.** Чтение, создание, правка, перемещение и форматирование файлов
внутри репозитория; рабочие каталоги и временные файлы внутри проекта; поиск,
анализ и сравнение.

**Инструменты.** `pytest`, `ruff`, `mypy`, `npm`/`pnpm`/`yarn`/`npx`, Playwright,
`tsc`, `eslint`, `prettier`, `php`, `composer`, `docker`, `docker compose`,
`make`, `ansible-lint`, `shellcheck`; установка зависимостей проекта
(`npm ci`, `pip install -r`, `composer install`, `uv pip install`).

**Git.** `status`, `diff`, `log`, `show`, `ls-tree`, `merge-base`, `grep`,
`name-rev`, `whatchanged`, `ls-remote`, `rev-parse`, `fetch`, `add`, `commit`,
создание и переключение рабочих веток, `merge`, `rebase`, `cherry-pick`,
`revert`, `tag`; обычный `git push` **только** в ветку `claude/*`; проверка
remote SHA.

**GitHub.** Чтение через штатные инструменты (`mcp__github__get_*`, `list_*`,
`search_*`), создание и обновление pull request, работа с review-тредами.

**Сайты.** Анализ переданного референса по `inventory/reference-sources.yaml`,
разработка CMS, шаблонов, страниц и SEO-структуры, генерация sitemap, robots,
canonical, pagination, schema.org и метаданных, тестирование desktop и mobile,
скриншоты и отчёты, сохранение сайта в собственном каталоге и site manifest.

**Серверы — после внесения цели в inventory.** `ssh`, `scp`, `rsync`, `ansible`
и `ansible-playbook` к хостам из `inventory/ssh-hosts.yaml`; DNS по зонам из
`inventory/dns-zones.yaml`; внешние запросы к хостам из
`inventory/network-allowlist.yaml`; HTTP к стенду `127.0.0.1`.

Разрешение даёт запись в реестре, а не форма команды. Реестры сейчас пусты:
хосты, зоны и контракты интеграций не переданы. Пустая запись означает
`BLOCKED_INPUT`, а не «разрешено всё», поэтому та же команда, что разрешена на
утверждённой цели, закрыта на любой другой.

## Production

Выкат на утверждённую цель — штатная операция и не требует отдельного вопроса,
если одновременно выполнены условия. Статически проверяются:

| Условие | Где проверяется |
| --- | --- |
| Цель в inventory и `production_capable` | `inventory/targets.yaml` |
| Домен связан с этим site manifest | `domain`, `canonical_url` пакета |
| Пакет не `fixture` | `fixture: false` |
| Передана авторизация владельца | `production_authorized: true` |
| Подтверждены права и передан rights manifest | `content_source.rights_*` |
| Бэкап делается и проверяется | `backup_policy.before_mutation`, `restore_test` |
| Релиз атомарный и откатываемый | `rollback_policy.keep_releases`, `auto_rollback_on_smoke_failure` |
| Есть health-check | `monitoring_policy.health_endpoint`, `checks` |

Условия «секреты не попали в лог и git», «все обязательные тесты прошли» и
«изменение отражено в audit log» профиль не проверяет и выполненными не
объявляет: их обеспечивает сам конвейер во время работы (`factory.redaction`,
ворота `factory/pipeline.py`, `factory/audit.py`), и без них выкат не
состоится. Разрешение снимает лишний вопрос перед воротами, а не сами ворота.

Невыполненное условие возвращает команду человеку и называется в тексте отказа:
`операция над production — цель «stage-1» отсутствует в inventory/targets.yaml`.

## Что по-прежнему останавливает работу

Всегда запрещено:

- `git push --force`, `-f`, `--force-with-lease`, `+refs/`;
- переписывание опубликованной истории: `reset --hard`, `filter-branch`, интерактивный rebase;
- удаление веток: `branch -D`, `push --delete`, рефспек `:ref`;
- прямой push в `main`/`master`;
- удаление репозитория, сервера, виртуальной машины, production-базы, бэкапов, DNS-зоны;
- массовое удаление вне каталога проекта;
- перенос домена другому владельцу, покупка доменов и любые платные действия;
- раскрытие, печать, коммит и передача секретов; чтение `.env`, ключей и токенов;
- подключение к SSH-хостам и работа с зонами вне inventory;
- удаление журнала аудита (`var/audit/`, `*.jsonl`) и затирание его перенаправлением;
- выключение бэкапа, отката и health-check правкой пакета из команды;
- ослабление branch protection (`branches/*/protection`, `enforce_admins=false`);
- обход guard и permission rules: `--dangerously-skip-permissions`,
  `bypassPermissions`, `--no-verify`, снятие хуков;
- скрытое исполнение: `curl | bash`, `base64 | bash`, произвольный `eval`;
- публикация контента без подтверждённых прав и rights manifest.

Отвечает `deny` и пишет в журнал отказов: production с невыполненным условием,
неизвестный инструмент, попытка отредактировать саму защитную машинерию
(`.claude/hooks/`, `settings.json`), `AskUserQuestion` и поиск по интернету,
который нельзя ограничить хостом.

Выкат на стенд подтверждения **не** требует. Окружение определяется флагом
`--environment`, а при его отсутствии — полем `environment` пакета, поэтому
штатная форма `python3 -m factory deploy --site pilot-local` из
`tests/run-all.sh` проходит сама. Нечитаемый пакет и команда без `--site`
считаются боевыми: не знать, куда метит команда, — не то же самое, что знать,
что она безопасна.

## Что осталось за оператором

Две вещи агент изменить не может и не должен — их правит человек вручную:

1. **`.claude/settings.json`.** Список `permissions.ask` (`Bash(git push *)`,
   `python3 -m factory deploy|rollback`) фактически не срабатывает, пока хук
   отвечает `allow` или `deny`, но остаётся в файле как мёртвая ветка. Его
   следует перенести в `allow`/`deny` по существу, а `defaultMode` выставить в
   нужный режим. Правка защитной конфигурации тем же агентом, которого она
   ограничивает, снимала бы защиту её собственным механизмом (правило G-WRITE).
2. **`.claude/hooks/pretooluse-guard.sh`.** Резервная ветка «guard недоступен»
   до сих пор отвечает `ask`. Это единственный оставшийся `ask` в контуре, и он
   срабатывает только когда сам guard не запустился. Заменять его на `deny`
   имеет смысл вместе с решением, что делать с неработающим guard'ом.

## Чего разбор команд не закрывает

Профиль читает команды. Поля пакета правятся ещё и редактором, а разбор команд
там бессилен, поэтому восстановимость держится инвариантом:
`tests/unit/test_production_gates.py::test_site_packages_keep_recovery_enabled`
падает, если в любом пакете выключены `backup_policy.before_mutation`,
`restore_test`, `rollback_policy.auto_rollback_on_smoke_failure`,
`keep_releases` или `monitoring_policy.health_endpoint`/`checks`. Осознанное
отключение остаётся возможным — оно требует изменить тест, то есть пройти через
ревью, а не через тихую правку одной строки.

Событие хука `PermissionRequest` в замороженной документации Claude Code
(SRC-CC-HOOKS) не описано, проверить его вживую в CLOSED_WORLD нельзя, поэтому
профиль реализован целиком на `PreToolUse` — его достаточно: решение выдаётся до
вызова инструмента. Запись — в `knowledge/UNKNOWNS.md`.

## Как расширять

Новая рутинная программа добавляется в набор профиля **вместе со строкой в
матрице** `tests/unit/test_permission_matrix.py`. Правило без строки в матрице
считается отсутствующим: матрица гоняет настоящую цепочку правил и хуков и
ловит случай «правило есть, а решение не выдаётся».

Ложное срабатывание защиты чинится в самой защите вместе с regression-тестом, а
не обходится. Так починены случаи, перечисленные в
`tests/unit/test_guard_false_positives.py`.
