# Открытые блокеры фабрики

Живой список того, что не закрыто. Запись остаётся здесь, пока блокер не снят:
проверка, которая не выполнялась, не должна выглядеть как пройденная.

Формат: что не работает, чем это подтверждено, что блокирует, что нужно для
снятия.

## PC-SITE-D — контракт плеера на site-d-series не проверен

**Статус:** открыт.
**Подтверждение:** задание `site-d-series-create-20260823T060816Z-0c5a63`,
артефакт `artifacts/verify/site-d-series/site-d-series-create-20260823T060816Z-0c5a63/player-contract.json`:

```json
{"pages": 3, "players_rendered": 0, "status": "skipped",
 "reason": "ни на одной странице серии плеер не отрисован"}
```

Проверены три страницы серий (`/catalog/dvenadcat-pisem/season-1/episode-1..3/`).
Плеер не найден ни на одной, поэтому ворота `player-contract` записали
`skipped`, а не `passed`: ноль отрисованных плееров — это непроведённая
проверка, а не «нарушений нет».

**Что блокирует:** `DONE` для `site-d-series` и любой выкат этого сайта на
production. Слияние программного контура он не блокирует — код фабрики и
оператора от него не зависят.

**Что нужно для снятия:** разобраться, почему на странице серии не появляется
элемент плеера в стенде site-d-series (маршрут, данные `videoRef` или условие
показа), затем прогнать `python3 -m factory verify --site site-d-series` и
получить `status: executed` с ненулевым `players_rendered`.

**Чего делать нельзя:** понижать критичность ворот, объявлять `skipped`
успехом или проверять контракт на другом сайте вместо этого.

## XBROWSER-FLAKE — firefox нестабилен на этом хосте под нагрузкой

**Статус:** открыт.
**Подтверждение:** три полных прогона с `FACTORY_ALL_BROWSERS=1` на
`claude-control-01` (4 vCPU). Каждый раз ровно один тест firefox падает по
таймауту 45 с на `page.goto`, каждый раз — другой:

| Прогон | Условия | Итог | Упавший тест |
| --- | --- | --- | --- |
| 1 | воркеры по умолчанию | 86/88 | `/lekcii/page/2/` (таймаут) + 401 на `/lekcii/page/999/` |
| 2 | после правки учётных данных | 87/88 | `unavailable-video` (таймаут) |
| 3 | `workers: 2` | 78/79 на момент остановки | `/search/` (таймаут) |

Ошибка 401 из первого прогона — отдельный, уже устранённый дефект
(см. `playwright.config.js`). Оставшиеся таймауты к нему не относятся.

Что проверено и **не** объясняет проблему:
- сервер стенда отдаёт корректные статусы: `curl` даёт 200/404/410 на тех же
  адресах, а `/410/ → /lekcii/page/999/ → /lekcii/page/2/` проходит одинаково
  во всех трёх движках;
- стенд не сериализует запросы: четыре параллельных запроса выполняются за
  0.01 с против 0.04 с последовательных, то есть однопоточность `php -S`
  здесь ни при чём;
- упавший тест в одиночку проходит за 2.4 с — то есть дефекта страницы нет;
- chromium и webkit не падают ни разу.

**Что блокирует:** только заявление «приёмка проходит на трёх движках». Ничего
другого: штатный прогон репозитория идёт на Chromium, и он зелёный.

**Что нужно для снятия:** либо более просторный хост под кросс-браузерный
прогон, либо разбор, почему именно firefox упирается в 45-секундный таймаут при
`load1` около 6 на 4 ядрах.

**Чего делать нельзя:** добавлять `retries`. Повтор превратил бы и настоящую
нестабильность страницы в зелёный статус, а отличить её от этой перестало бы
быть возможным.

## HEADLESS-AUTH — `claude -p` на сервере не авторизован

**Статус:** открыт.
**Подтверждение:** `claude -p --bare --settings .claude/settings.json "ok"` на
`claude-control-01` возвращает `{"is_error": true, ..., "result": "Not logged in · Please run /login"}`.
Интерактивная сессия при этом работает: учётные данные существуют, но headless-запуск
их не подхватывает.

**Что блокирует:** запуск оператора по расписанию как Claude-сессии — и Routine,
и резервный вариант из `docs/seo-operator/automation-policy.md`. Не блокирует
ничего из того, что выполняется без Claude: таймеры `site-factory-health`,
`site-factory-backup`, `site-factory-selfcheck` и `site-factory-seo-dryrun`
работают, потому что вызывают Python и shell напрямую.

**Что нужно для снятия:** владелец выполняет авторизацию для headless-режима на
самом сервере. Токен в чат не передаётся и в репозиторий не попадает.

**Чего делать нельзя:** извлекать учётные данные интерактивной сессии из
`~/.claude/.credentials.json` и подставлять их в headless-запуск.

## SANDBOX-NOTE — `settings.unattended.json` теперь применим на сервере

**Статус:** информационный, действия не требует.
**Подтверждение:** `bwrap --version` → 0.6.1, `kernel.unprivileged_userns_clone = 1`,
пробный `bwrap --unshare-all` завершается успешно.

Комментарий в `.claude/settings.unattended.json` говорит, что `bubblewrap`
отсутствует, и это верно для контейнера сессии. На `claude-control-01` он
установлен и работает, поэтому профиль с `sandbox.failIfUnavailable: true`
здесь запускается, а не останавливается на старте. Сам файл не правился:
`.claude/**` закрыт deny-правилом.

## LORDS-TIMER-DEAD — автоматическое обновление каталога не запустится само

**Статус:** открыт. Требует одной команды владельца; сам выполнить не могу —
запуск юнита есть изменение production, запрещённое условиями текущей задачи.

**Подтверждение:**

```
systemctl is-active  lords-content-refresh.timer  -> inactive
systemctl is-enabled lords-content-refresh.timer  -> enabled
NextElapseUSecRealtime                            -> пусто (никогда)
```

Таймер включён при загрузке, но не запущен сейчас, и следующего срабатывания у
него нет. Соседние таймеры (`yummy-episode-watcher`, `yummy-watchdog`,
`site-factory-health`) активны — то есть дело в этом юните, а не в systemd.

Неактивен он с 13:45 UTC 2026-08-30 — момента, когда рядом появился drop-in
`interval.conf`, поднявший шаг с 10 до 120 минут. Правка интервала, судя по
всему, прошла без последующего `systemctl start` таймера. Журнал юнита пуст,
поэтому утверждать наверняка, кто и чем его остановил, не могу; проверяемый
факт — что он неактивен с этого времени.

**Чем это грозит.** Ровно тем, ради чего вся автоматизация и делалась: каталог
перестаёт обновляться, а витрины продолжают отвечать HTTP 200. Именно так на
трёх публичных доменах месяцами стоял каталог тридцатипятичасовой давности.
Последний успешный обход — 2026-08-30T13:10:03Z.

**Что нужно для снятия:**

```
sudo systemctl start lords-content-refresh.timer
systemctl list-timers lords-content-refresh.timer   # обязана появиться строка со временем
```

**Чего делать нельзя:** считать «enabled» достаточным. Включённый при загрузке
и запущенный сейчас — разные вещи, и различие здесь стоит суток свежести.

**Смежное.** Служба в этот раз была прервана по `TimeoutStartSec=3h`: полный
рендер одной витрины занимает около двух с половиной часов, а витрин три.
Первая (`lordfilm47.space`) успела получить полный каталог — 61 318 страниц,
каталог до страницы 2193. Две другие остались на прежних релизах и отвечают
200. Чтобы полный каталог доехал и до них, таймаут придётся поднять до
семи-восьми часов.

## LORDS-SCHEDULE-SOURCE — расписание Lords не на чем строить

**Статус:** открыт, ждёт решения владельца.

**Подтверждение:** публичный API поставщика не отдаёт дат выхода серий. В
карточке тайтла нет `updated_at`, маршрут со списком эпизодов отсутствует
(404), а сезон сообщает только `{number, name, episodes_count,
available_episodes_count}`. Даты, которые можно было бы поставить в
расписание, взять неоткуда.

**Что блокирует:** блок расписания на трёх витринах Lords. Сейчас он говорит
ровно то, что известно, и не обещает несуществующих дат — это осознанное
поведение, а не заглушка.

**Что нужно для снятия:** решение владельца об источнике дат — либо
разрешённый внешний источник с подтверждёнными идентификаторами (как это уже
сделано для оценок), либо явное указание, что расписание строится только по
наблюдениям.

**Чего делать нельзя:** выводить дату из момента нашего наблюдения и выдавать
её за дату выхода; угадывать расписание по номеру серии.

## Переданные владельцем данные, которых нет

Не блокеры кода, а отсутствующие входные данные. Полный машинный список —
`docs/INPUT_REQUEST.md` (`python3 -m factory input-request`).

| Чего нет | Что это закрывает |
| --- | --- |
| Домены и цели выката | production для всех сайтов |
| SSH-хосты в `inventory/ssh-hosts.yaml` | удалённый выкат, backup на цели |
| DNS-зоны в `inventory/dns-zones.yaml` | cutover, выпуск SSL |
| Контракты CDNVideoHub, CMS, VK, аналитики и хосты в `inventory/network-allowlist.yaml` | живые источники, health-check боевого сайта |
| Лицензия DLE (`dle_license_ref`) | production для DLE-пакетов |
| Права на контент и rights manifest | публикацию контента |
| `production_authorized: true` в manifest | production в принципе |

Пустая запись в реестре означает `BLOCKED_INPUT`, а не «разрешено всё».
