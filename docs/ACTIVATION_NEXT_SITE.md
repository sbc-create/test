# Активация zonafilm.space — предварительная проверка и решение владельца

Следующий сайт очереди. Ниже — одна команда предварительной проверки; она
**ничего не меняет** и её результат заранее известен: она упрётся в замок
направления. Что с ним делать — решение владельца, см. последний раздел.

## Шаг 1. Предварительная проверка (ничего не меняет)

```bash
cd /home/claude/wt-portable-site-cell-01 && \
sudo /home/claude/wt-portable-site-cell-01/.venv/bin/python -m factory cell activate \
  --site zona-01 \
  --commit 25f6808a8388e83391389af4e25f02773401ca8a \
  --expect-digest sha256:abcb74f173705af04edae5f79f57e7215a5c9751a23e3af2de97178fb23ca5be
```

`cd` обязателен: из другого каталога `python -m factory` подхватывает другую
копию пакета, в которой команды `cell` нет. Проверено запуском.

Команда без `--confirm-activation` только проверяет. Она соберёт артефакт из
названного коммита, сверит digest и **запустит `deploy/activate.sh --dry-run`** —
то есть дойдёт до настоящих предусловий сценария, а не остановится перед ними.

### Что она напечатает

Ожидаемый результат — отказ на замке направления:

```json
{
  "status": "dry-run-failed",
  "exit_code": 1,
  "stderr": "в замке /srv/lords/.frontend/.deploy.lock нет pid владельца — снимать его автоматически нельзя",
  "digest": "sha256:abcb74f173705af04edae5f79f57e7215a5c9751a23e3af2de97178fb23ca5be",
  "build_id": "25f6808a8388-zona-01"
}
```

`status: "dry-run-failed"` здесь означает «проверка сделала свою работу»:
она нашла препятствие до того, как что-либо изменилось.

Проверено без root тем же сценарием (`SITE_REQUIRE_ROOT=0`): вывод совпадает,
каталог `/srv/zonafilm-space` не создан, собственный замок не взят — сухой
прогон не создаёт его по построению.

## Шаг 2. Решение о замке — за вами

```
/srv/lords/.frontend/.deploy.lock   владелец claude:claude, mtime 2026-09-19 22:42 (81 ч)
{"site": "zona-01", "head": "88cd272f30b86f9adc97d6fd33f8250e2dfb06f4",
  "at": "20260919T224255Z-88cd272f-nova"}
```

Pid в замке отсутствует, поэтому сценарий отказывается считать его брошенным
(решение D136: возраст не доказывает смерть владельца). Эта сессия замок не
создавала и не снимает.

Свидетельство, которое стоит взвесить: zona-01 после этой даты выкладывался
дважды — `releases/zona-01-fca1d54eeeb7` (22.09 12:24) и
`releases/zona-01-a0209877e1db` (22.09 14:52, на него указывает
`sites/zona-01/current`). Прогон, взявший замок, завершился задолго до них.

Два пути, оба ваши:

1. **Снять замок** — `sudo rm -f /srv/lords/.frontend/.deploy.lock`, затем шаг 3.
2. **Оставить** и решить, относится ли общий замок направления к операции,
   которая в общий каталог только читает. Сценарий активации пишет в
   `/srv/zonafilm-space/{app,data}` и трогает службу; в `/srv/lords/.frontend`
   он не пишет. Соседний терминал пришёл к такому же выводу для своего
   обновления. Менять семантику замка перед самой выкладкой я не стал.

## Шаг 3. Активация (только после решения по замку)

Та же команда плюс `--confirm-activation`:

```bash
cd /home/claude/wt-portable-site-cell-01 && \
sudo /home/claude/wt-portable-site-cell-01/.venv/bin/python -m factory cell activate \
  --site zona-01 \
  --commit 25f6808a8388e83391389af4e25f02773401ca8a \
  --expect-digest sha256:abcb74f173705af04edae5f79f57e7215a5c9751a23e3af2de97178fb23ca5be \
  --confirm-activation
```

Сделает: учётную запись `zonafilm-space`, каталоги `/srv/zonafilm-space/{app,data}`,
распаковку проверенного артефакта, копию секрета плеера и снимков каталога,
остановку и снятие с автозапуска `nova-zona-01.service`, установку и запуск
`nova-zonafilm-space.service` на том же порту 9120, проверку `/healthz` и
откат при неудаче.

nginx, DNS, TLS и режим индексации не затрагиваются: конфигурация уже указывает
на `127.0.0.1:9120`.
