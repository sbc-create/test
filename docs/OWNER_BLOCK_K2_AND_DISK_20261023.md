## Шаг 1. Освободить место образами docker — 12,86 ГБ, данных не касается

```bash
docker image prune -a --force --filter "until=168h"
```

Удаляются только образы, **не занятые ни одним контейнером** и старше семи
суток. Проверка — до и после:

```bash
docker system df
python3 -c "import shutil; u=shutil.disk_usage('/'); print(f'свободно {u.free/2**30:.2f} ГиБ')"
```

Ожидается: `RECLAIMABLE` у образов падает с 12,86 ГБ, свободное место растёт на
столько же. **Откат:** невозможен для удалённых слоёв, поэтому фильтр
`until=168h` и `-a` без `--volumes` обязательны — образы работающих витрин под
фильтр не попадают (активных 16 из 68). Если нужен нулевой риск, сначала
`docker image prune --force` без `-a`: уберёт только висячие слои.

## Чего этот блок не делает

* **не удаляет 215 рабочих копий** в `/home` и временные каталоги сессий в
  `/tmp` (13 ГБ): в копиях может быть незакоммиченная работа других линий, и
  решение по ним — отдельное. Моя собственная причина роста уже убрана правкой
  `pytest.ini` (хранить один прогон, только при провале);
* **не открывает индексацию** восьми витрин K2: у них `open_authorized: false`
  и `noindex, nofollow` по решению владельца (D209);
* **не включает и не меняет таймеры**;
* **не трогает `/srv/backups`** (19 ГБ хостовых архивов 21–29 сентября) — срок
  их хранения отдельное решение;
* **не обещает, что доставка пройдёт.** Исправленная редакция гарантирует
  другое: причина отказа сохранится в журнале, а отказ одной витрины не лишит
  каталога остальных семи.

## Почему шаги 1–5 не выполнены сессией

Профиль `UNATTENDED_SAFE` отказывает на любой файловой операции вне
репозитория — проверено попыткой сделать резервную копию шага 5: «no allow rule
matched … профиль: файловая операция вне репозитория». Изменение образов docker
и исполняемого слоя общей службы в профиль тоже не входит. Всё, что можно было
сделать чтением, сделано: суммы сверены, синтаксис проверен, готовность
доставки подтверждена (нехваток 0), источник для шага 3 проверен на
разбираемость и размер.
