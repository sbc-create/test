## Шаг 1. Освободить место образами docker — 12,86 ГБ, данных не касается

```bash
docker image prune -a --force --filter "until=168h"
```

Удаляются только образы, **не занятые ни одним контейнером** и старше семи
суток. Проверка — до и после:

```bash
docker system df
python3 -c "import shutil; u=shutil.disk_usage('/'); print(f'свободно {u.free/2**30:.2f} ГиБ')"
```

Ожидается: `RECLAIMABLE` у образов падает с 12,86 ГБ, свободное место растёт на
столько же. **Откат:** невозможен для удалённых слоёв, поэтому фильтр
`until=168h` и `-a` без `--volumes` обязательны — образы работающих витрин под
фильтр не попадают (активных 16 из 68). Если нужен нулевой риск, сначала
`docker image prune --force` без `-a`: уберёт только висячие слои.

удаление резервной копии и запись в снимок постоянных данных — его решение.

**Оговорка о способе проверки, чтобы на него не опирались шире, чем он даёт.**
Целость проверяется по хвосту файла: последний значащий символ должен
закрывать структуру. Это ловит обрыв записи — ровно случай 23.10 — и НЕ
доказывает, что остальное содержимое верно. Полный разбор JSON включается
ключом `--full` и стоит часы чтения на 1,2 ГиБ поколение.

**И ещё одна оговорка, уже про мою собственную меру.** Первая редакция
проверки объявила негодными шесть поколений 11–16.10 с признаком «хвост не
разбирается как UTF-8». Это была ЛОЖНАЯ тревога моего кода: окно в 4096 байт
отсчитывается от конца и может начаться посреди многобайтового символа.
Проверено на файле: он кончается `…"source": "canonical-snapshot/1.0.0"}`,
то есть цел. Исправлено отбрасыванием ведущих байтов окна; после правки те же
шесть поколений — ГОДНЫ.

  двумя вопросами, только чтением:

  | состояние | копий | вес |

  возвращаются РЕШЕНИЕМ: слить или объявить брошенными. Решение не моё и не
  может быть автоматическим;
* **не открывает индексацию** восьми витрин K2: у них `open_authorized: false`

## Почему шаги 1–5 не выполнены сессией

Профиль `UNATTENDED_SAFE` отказывает на любой файловой операции вне
репозитория — проверено попыткой сделать резервную копию шага 5: «no allow rule
matched … профиль: файловая операция вне репозитория». Изменение образов docker
и исполняемого слоя общей службы в профиль тоже не входит. Всё, что можно было
сделать чтением, сделано: суммы сверены, синтаксис проверен, готовность
доставки подтверждена (нехваток 0), источник для шага 3 проверен на
разбираемость и размер.

Разовая уборка дала девять суток. Прирост ~1,2 ГБ в сутки, то есть к 10.11

**Чем мерить объём журнала — и это не придирка.** Две меры одного предмета
расходятся в тринадцать раз, и обе «правильные» для своего вопроса:

| мера | результат | что на самом деле отвечает |
| --- | ---: | --- |
| `du -sh /var/log/journal` | **4,1 ГБ** | сколько занято на диске |
| `journalctl --disk-usage` без прав | **320,1 МБ** | сколько journald может ПРОЧИТАТЬ этой учётной записью |

Причину установила линия аудита, я проверил и получил точное совпадение: в
каталоге журнала 61 файл общим объёмом 4 128,0 МиБ, из них моей учётной записи
читаемы 31 файл — ровно **320,0 МиБ**, то есть те самые 320,1 М, которые
печатает `journalctl`. Ни моя учётная запись, ни её не входят в `adm` и
`systemd-journal`.

**Следствие для этого блока:** объём мерить `du` по каталогу — она работает при
любых правах, — а `journalctl --disk-usage` использовать ТОЛЬКО от root и
только вместе с той же мерой до и после. Иначе проверка «до» и проверка
«после» дадут несравнимые числа, и предел покажется ненужным: 320 МБ его не
требуют, а 4,1 ГБ — это треть всего свободного места на разделе.

**Главный довод за предел — работающий случай, а не предположение:** на узле K2
`SystemMaxUse=512M` стоит с 14.10, и за двенадцать суток журнал там проблемой
не стал и диагностику не отнял. Это снимает единственное серьёзное возражение
против предела.

### Что подготовлено (и ничего не удалено)

План удержания посчитан: `--keep-days 7` освободил бы **девять наборов, 9
суток, ≈10,8 ГБ** (`artifacts/evidence/publish-backups-plan-20261026.txt`).

постоянных данных витрин, и правило прямое — выпуск их только читает.

Расписание готово: `automation/host/publish-backups-retention.{service,timer}`
(06:40Z, вне суточного публикатора в 03:3xZ и сбора кабинета в 05:00Z). Юнит
по умолчанию **считает план и пишет отчёт, не удаляя ничего**; строка с
`--apply --keep-days N` лежит рядом закомментированной — это единственное, что
нужно поменять, когда срок будет назван.

credentials. Дата перенесена в сам инструмент (`backup-retention.py --out-dir`).
