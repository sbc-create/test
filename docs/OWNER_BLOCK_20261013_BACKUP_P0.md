# P0: безопасный повторный запуск резервного копирования

Происшествие 13.10: прогон заполнил системный раздел (`/dev/vda1` 204 ГиБ,
осталось 424 МиБ) на сборе `$REPO/var/` в `/tmp/tmp.7AGWgdx5OP/stage/factory-var/`.
Разбор и исправление — в этом документе; числа измерены, а не оценены.

**Ничего не удаляется этим блоком**: ни архивы, ни `publish-backups`, ни срок
хранения. Где нужно решение — оно названо решением.

---

## 1. Остановка подтверждена, временные данные убраны

| проверено | факт |
| --- | --- |
| процессы бэкапа, `rsync`, упаковки | **ни одного** |
| `/tmp/tmp.7AGWgdx5OP` | **отсутствует** — штатная уборка (`trap … EXIT`) сработала |
| временные каталоги владельца root в `/tmp` | **ноль** |
| `tmp.*` рабочей учётной записи | 117 каталогов, вместе **2,9 МиБ** — остатки прочих сессий, не бэкапа; по маске не удаляются |
| свободно на разделе | **14,84 ГиБ** из 203,3 (было 424 МиБ) |
| осиротевшие архивы | `host-20260924T032059Z` (2,76 ГиБ) и `host-20260929T032303Z` (3,10 ГиБ) — без записи о проверке, от прежних прогонов; **сохранены** |

Точечная уборка каталога остановленного прогона не требуется: его уже нет.
Принадлежность проверялась до любых действий — по владельцу и по времени.

## 2. Почему 11,16 ГиБ оказалось мало

Две причины, обе мои.

**Оценка была неверна по построению.** Я считал «нужно 3,6 × staging», подставляя
за staging размер СЖАТОГО архива — 3,10 ГиБ. Источники в несжатом виде:

| источник | ГиБ | файлов |
| --- | ---: | ---: |
| `$REPO/var/` | **25,10** | 100 649 |
| `/srv/sites/` | 1,91 | 38 664 |
| `/etc/nginx/sites-available/` | 0,00 | 10 |
| `/etc/site-factory/`, хранилище Secret Hub | не читаются рабочей учётной записью | — |
| **итого** | **27,00** | ≈139 тыс. |

Внутри `var/` (25,10 ГиБ) почти всё — одна запись:

| `var/lords/…` | ГиБ | файлов | свежайший |
| --- | ---: | ---: | ---: |
| **`publish-backups`** | **23,15** | **588** | 1,6 сут |
| `detail-cache` | 0,31 | 61 450 | 0,6 сут |
| `arc005-backups` | 0,15 | 4 | 29,1 сут |
| остальные 13 записей | < 0,15 каждая | | |

`publish-backups` — суточные копии «до публикации» файлов `*-details.json`, по
**110–115 МиБ каждая**, 588 штук. Сжатие такого материала ~8,7×, поэтому архив
и выглядел на 3,10 ГиБ при 27 ГиБ источников: **нижняя граница была выдана за
величину**.

**Проверка стояла ПОСЛЕ сбора.** Она брала `du` уже собранной копии — то есть
защищала упаковку и распаковку, но не сам сбор. Диск заполнялся раньше, чем
проверка получала управление.

## 3. Пик по этапам и исправленная проверка

Что одновременно лежит на диске (S — источники, A — архив, B — git bundle):

| этап | занято |
| --- | --- |
| сбор | S |
| манифест сумм | S |
| упаковка | S + A |
| **освобождение собранной копии** (новое) | A |
| проверочное восстановление | A + S |
| git bundle во временном каталоге | + B |

**Пик = S + A + B.** Пока собранная копия жила до конца прогона, пик был
2S + A + B. На измеренных числах: **32,41 ГиБ вместо 59,41**.

Требование = пик + запас 20 % + **резерв работающим сайтам 5 ГиБ** (раздел
общий: на нём витрины, их данные и журналы; бэкап не вправе занимать последние
гигабайты) = **43,89 ГиБ**. Свободно 14,84 → **прогон откажет до первой
записи**, и это теперь штатный отказ, а не заполненный диск.

Исправлено в коде (перенесено и в живую копию `/srv/site-factory/repo`, суммы
совпадают):

* `backup-preflight-space.sh` — политика на числах ДО сбора;
* собранная копия освобождается сразу после упаковки;
* уборка по сигналу `INT TERM HUP`, а не только по `EXIT`;
* одна политика на оба рубежа (прежние 3,6 × staging просили бы 97 ГиБ);
* `--completeness` — обязательный состав вместо порога количества.

## 4. Полнота состава действующих витрин

Порог «витрин не меньше N» проверкой состава не является: он зелёный и тогда,
когда выпала именно та витрина, чьи данные невосстановимы. Поэтому проверка
спрашивает про КАЖДУЮ публичную ячейку.

**Разобран пропуск animedia-01.** В её паспорте не было `runtime.data_dir`,
поэтому действующая витрина `animedia.icu` в план сбора не попадала вовсе.
Каталог `/srv/animedia-icu/data` записан по измерению: его называют два
работающих процесса витрины (читающее API приложения и обновлятель данных), и
в нём 14 файлов `animedia-01-*`.

**Поправка к этому же разделу: «покрыто 29» было завышено на десять.** Проверка
полноты считала покрытой витрину, у которой каталог ОБЪЯВЛЕН в паспорте, но на
диске ещё не создан, — а это все десять незапущенных (`lords-08`, `lords-09` и
восемь новых). Перемерено после правки:

| состояние | витрин |
| --- | ---: |
| покрыто (каталог есть на диске и попал в план) | **19** |
| ещё не запущены (каталог объявлен, данных пока нет — терять нечего) | **10**, поимённо |
| пробелов | **0** |

Разница важна в двух местах. Во-первых, «собрано элементов N из плана M» в
журнале прогона теперь объяснено: расхождение на десять — не потеря, и
проверка прямо это печатает. Во-вторых, случай «витрина `live`, а каталога на
диске нет» прежде попадал в покрытые молча; теперь это названный пробел с
указанием статуса. Доказано подменой: на прежней версии такая запись давала
«покрытых 1, пробелов 0», на новой — «покрытых 0, пробелов 1».

**Пять каталогов без объявленного контракта** — animedia-02, animego-02,
animego-03, lords-06, lords-07. Они покрыты, но грубо: берётся весь каталог
данных минус поставляемые снимки. Это не пробел копии, а пробел ОБЪЯВЛЕНИЯ:
контракт `data_contract.user_writable` живёт в репозитории каждой витрины, и
объявить его — отдельная задача по этим пяти репозиториям, не правка бэкапа.

Начало этой задачи измерено, чтобы её не начинали с нуля и не скопировали
чужой контракт по аналогии.

| измерено | факт |
| --- | --- |
| контракт у соседей того же семейства | **нет ни у одного**: animedia-01, animedia-02, animego-02, animego-03, lords-06, lords-07 — `data_contract` не объявлен, копировать неоткуда |
| состав каталога данных | animedia-02 — 19 файлов, animego-02 и animego-03 — по 14, lords-06 и lords-07 — по 2 (`catalog` и `details`) |
| кто пишет | в этом семействе запись идёт помощником `записать_атомарно(путь, …)`, чтение — `прочитать(путь, …)`; writer определяется по вызову, а не по упоминанию имени |
| **`{site}-details.json` витрина ПИШЕТ САМА** | `automation/<домен>-update.py` правит его атомарно (через переменную `файл`), а не только читает |

Последняя строка — причина не копировать контракт семейства Lordfilm: там
`{site}-details.json` объявлен `delivered`, то есть доставка его заменяет. Для
animedia это означало бы выбросить то, что дописал обновлятель витрины. Какие
именно поля он дописывает и восстановимы ли они производителем — измерять надо
по его коду, этого я не делал.

**Чего не хватает для объявления** (по каждому из шести файлов состояния:
`admission`, `episode-events`, `episode-state`, `episode-sync`,
`freshness-overlay`, `freshness-state`, плюс `details.nums`, `popular`,
`ratings-top`, `schedule`, `update-state`): writer по коду и ответ, восстановим
ли файл производителем. Пока ответа нет, грубое покрытие «весь каталог минус
поставляемое» ОСТАЁТСЯ — оно безопаснее точного, но неверного контракта:
лишний файл в копии стоит места, пропущенный стоит данных.

**Отдельный названный пробел:** корневая копия реестра
(`/usr/local/lib/site-factory-cell/config/site-cells.json`), из которой читает
прогон, от **09.10**. Правка `animedia-01` и восемь новых ячеек в неё пока не
попали. Проверка `--completeness` теперь это печатает отдельной строкой, а не
молчит. Обновление корневой копии — своя привилегированная операция
(`install-executor-narrow.sh` с пакетом и digest), и в этот блок она не входит.

## 5. Блок команд владельца

```bash
sudo python3 /srv/site-factory/repo/automation/host/backup_cell_data.py --completeness
sudo bash /srv/site-factory/repo/automation/host/site-factory-backup.sh --preflight-only
df -h /
```

Вторая команда заменила прежнюю с числами, измеренными днём. Числа живут своей
жизнью — `publish-backups` растёт суточными копиями, свободное место меняется
(14,83 ГиБ в 18:50 → 14,19 в 20:50), — а повторять в документе перечень из пяти
источников значило бы завести второй список, который разойдётся с первым.
`--preflight-only` измеряет ровно свои источники, прогоняет ровно свою политику
и выходит ДО первой записи.

**Ожидаемый результат.** Первая команда печатает три числа: «покрыто **19**»,
«ещё не запущены: **10**» поимённо и «пробелов нет» — либо ПОИМЁННЫЕ пробелы
(ожидается строка про корневую копию от 09.10, потому что команда читает
именно её, а не рабочий реестр). Вторая печатает арифметику и завершается
**кодом 1**: «нужно 43.89 GiB … свободно 14.83 GiB». Это подтверждение, что
защита работает.

Обе команды читают копию сценариев в `/srv/site-factory/repo` — ту, откуда
запускается юнит. Она синхронизирована с ветвью: суммы SHA-256 трёх файлов
(`backup_cell_data.py`, `site-factory-backup.sh`, `backup-preflight-space.sh`)
совпадают, проверено после правки полноты.

**Условие остановки.** Если вторая команда завершилась нулём при свободном
меньше 43,89 ГиБ — политика не та, что я проверял; дальше не идти.

### Раздел тает и без бэкапа: найдена единственная повторяющаяся утечка

Свободное место за два часа ушло с **14,83 ГиБ** (18:50) до **14,19** (20:50) —
0,3 ГиБ в час. Это не бэкап (он не запускался) и не `publish-backups` (её
свежайшие файлы 40-часовой давности). Измерено обходом файлов от 50 МиБ,
изменённых за 6 часов:

| что | размер | темп |
| --- | ---: | --- |
| `/var/log` целиком | **6,27 ГиБ** | |
| из них `/var/log/journal` | **4,01 ГиБ** | **6 файлов по 128 МиБ за 6 часов ≈ 128 МиБ/ч, ≈3 ГиБ/сут** |
| из них `/var/log/nginx` | 1,13 ГиБ | общий `access.log` 216 МиБ, `yummyani.site` 154 МиБ за сутки |
| `/var/log/syslog` | 442 МиБ | пишется сейчас |

**Причина названа: у журнала нет предела.** В `/etc/systemd/journald.conf`
только заголовок `[Journal]`, все строки закомментированы — значит действует
умолчание «до 10 % раздела», то есть около **20 ГиБ**. Журнал просто идёт к
этому потолку.

**Второе: `syslog` вращается РАЗ В НЕДЕЛЮ.** В `/etc/logrotate.d/rsyslog` —
`weekly`, `rotate 4`, и ни одного `maxsize`. При 0,4 ГиБ в сутки это около
3 ГиБ на файл к моменту вращения, плюс четыре хранимых. Для сравнения, у nginx
и у самой фабрики — `daily`, `rotate 14`, `compress`.

**Чего я измерить не смог.** Кто именно пишет 128 МиБ в час — моей учётной
записи видно 0,1 МиБ/ч (919 записей `site-factory-mcp.service`, в среднем
118 Б). Остальное принадлежит юнитам, чьи записи рабочей учётной записи
закрыты, и `journalctl --disk-usage` показывает мне 320 МиБ вместо
фактических 4,01 ГиБ. Назвать виновника можно только от root:

```bash
sudo journalctl --disk-usage
sudo journalctl --since '-60 min' -o json --output-fields=_SYSTEMD_UNIT,MESSAGE | python3 -c "
import sys, json, collections
объём, число = collections.Counter(), collections.Counter()
for с in sys.stdin:
    try: з = json.loads(с)
    except ValueError: continue
    u = з.get('_SYSTEMD_UNIT') or '—'; m = з.get('MESSAGE') or ''
    if isinstance(m, list): m = bytes(m).decode('utf-8','replace')
    объём[u] += len(m); число[u] += 1
for имя, б in объём.most_common(8):
    print(f'{имя:44} {б/2**20:8.2f} МиБ/ч, записей {число[имя]}')
"
```

**Что это даёт по месту** (решение ваше, я ничего не удаляю):

| действие | освободит | остановит |
| --- | ---: | --- |
| предел журналу `SystemMaxUse=512M` + применить сейчас | ≈3,5 ГиБ | ≈3 ГиБ/сут |
| `syslog`: `daily` + `maxsize 100M` | до 0,4 ГиБ сразу | рост до 3 ГиБ на файл |

```bash
sudo install -d -m 0755 /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=512M\nSystemMaxFileSize=64M\n' | sudo tee /etc/systemd/journald.conf.d/50-size-cap.conf
sudo systemctl restart systemd-journald
sudo journalctl --vacuum-size=512M
df -h /
```

**Ожидаемый результат.** `--vacuum-size` печатает поимённо удаляемые архивные
файлы журнала и итог «Vacuuming done, freed …»; свободное место растёт
примерно на 3,5 ГиБ. **Условие остановки:** если `journalctl --disk-usage`
после этого больше 512 МиБ — предел не применился, причину искать до
продолжения.

Это не заменяет освобождение ≈29 ГиБ под бэкап: журнал даёт около четырёх из
них. Но это единственная НАЙДЕННАЯ повторяющаяся утечка, и без неё раздел
продолжит таять независимо от бэкапа.

### Запуск бэкапа — только после решения о месте

Нужно освободить **≈29 ГиБ**. Что это может быть (решение ваше, я не удаляю):

| кандидат | ГиБ | чем является |
| --- | ---: | --- |
| `var/lords/publish-backups` | 23,15 | 588 суточных копий `*-details.json` «до публикации»; сам файл восстанавливается производителем. Это **не** бэкап хоста и не его retention |
| осиротевшие архивы 24.09 и 29.09 | 5,86 | без записи о проверке, доверять им нечем; по вашему указанию сохранены |
| `/srv/backups` целиком | 17,9 | три подтверждённых набора + два зеркала репозитория; удалять нельзя |

После освобождения:

```bash
sudo systemctl start site-factory-backup.service
sudo cat /srv/backups/$(ls -t /srv/backups | grep verified.json | head -1)
df -h /
ls -d /tmp/tmp.* 2>/dev/null | head -3
```

**Критерии завершения — все пять, не часть:**

1. появилась пара `host-<штамп>.tar.gz` + `.verified.json` с сегодняшней датой;
2. в записи `"restore_verified": true` — распаковка в отдельный каталог и сверка
   `sha256sum -c` по манифесту прошли;
3. в записи блок `"cell_data"` с ненулевыми `sites` и `items` (состав, а не
   порог: сверять с выводом `--completeness`);
4. временных данных не осталось: каталогов `tmp.*` владельца root нет;
5. свободного места осталось не меньше резерва 5 ГиБ.

**Только после этого — вернуть таймер:**

```bash
sudo systemctl enable --now site-factory-backup.timer
systemctl list-timers site-factory-backup.timer --no-pager
```

**Важно про таймер.** Его можно включать и ДО освобождения места: с
исправлением очередной запуск в 03:20 UTC теперь откажет до первой записи и
оставит прежние копии целыми, а не заполнит раздел. Включение после успешного
прогона — порядок, а не необходимость.
