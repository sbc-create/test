# Подключение нового домена

Порядок для домена, который владелец уже приобрёл и передал фабрике. Фабрика
доменов **не покупает** и не продлевает; появление домена — вход, а не результат
работы конвейера.

Ввод самого сайта описан в [`NEW_SITE.md`](NEW_SITE.md), выкат — в
[`DEPLOY.md`](DEPLOY.md). Здесь только то, что относится к домену: реестры, DNS,
TLS и cutover.

## 0. Что должно быть передано

Пока хотя бы одного пункта нет, статус — `BLOCKED_INPUT`, и это не обходится
значением по умолчанию.

| Что | Куда попадает | Кто вносит |
| --- | --- | --- |
| Сам домен и подтверждение владения | `domain`, `canonical_url` пакета | владелец |
| DNS-зона, провайдер, scoped-токен | `inventory/dns-zones.yaml` | **человек** (файл закрыт deny-правилом) |
| Цель выката | `inventory/targets.yaml` | человек |
| SSH-хост цели (для удалённого выката) | `inventory/ssh-hosts.yaml` | **человек** (закрыт deny-правилом) |
| Лицензия DLE на домен второго уровня | `inventory/dle-licenses.yaml` | **человек** (закрыт deny-правилом) |
| Права на контент | `content/rights-manifest.yaml` пакета | владелец |
| `production_authorized: true`, `authorized_by`, `authorized_at` | манифест сайта | владелец |

Три файла реестра закрыты `deny Edit(...)` в `.claude/settings.json` намеренно:
список SSH-хостов, DNS-зон и лицензий не расширяется агентом. Это не препятствие,
которое нужно обойти, — это точка, где решение принимает человек.

## 1. Внести домен в реестры

```bash
# после того как человек добавил записи — проверить, что они резолвятся
python3 -m factory validate --site <site_id>
```

`validate` называет каждое незаполненное поле и статус, который оно вызывает.
Догадки не подставляются: отсутствующая зона даёт `BLOCKED_ACCESS` с именем
записи, которой не хватает.

## 2. Поднять origin и убедиться, что он отвечает

Домен ещё никуда не указывает — сайт проверяется по адресу цели.

```bash
python3 -m factory build  --site <site_id>
python3 -m factory deploy --site <site_id> --environment staging
python3 -m factory verify --site <site_id>
```

Staging закрыт Basic-авторизацией и `X-Robots-Tag: noindex` до любой отдачи,
включая `robots.txt` и `sitemap.xml`. Один `robots.txt` защитой не считается.

## 3. TLS

Сертификат выпускается **до** переключения DNS, иначе первый же запрос по новому
домену придёт на origin без сертификата.

Порядок зависит от способа валидации:

- **DNS-01** — работает до cutover, потому что не требует, чтобы домен уже
  указывал на этот сервер. Предпочтительный вариант.
- **HTTP-01** — требует, чтобы домен уже резолвился на origin, то есть
  выполняется только после cutover и оставляет окно без сертификата.

Порт 80 на хосте открыт, порт 443 открыт. Выпуск и продление — обычная
инфраструктурная задача хоста; срок действия отслеживает health-check
(`site-factory-health`, предупреждение за 21 день).

## 4. Cutover DNS

Отдельный журналируемый шаг. Выполняется, только когда **все** условия верны
одновременно:

| Условие | Чем подтверждается |
| --- | --- |
| origin отвечает и здоров | `factory verify` зелёный, health-endpoint отвечает |
| конфигурация веб-сервера верна | `nginx -t` из привилегированного прогона |
| сертификат готов и покрывает домен | срок действия и SAN проверены |
| canonical указывает на этот домен | `canonical_url` пакета совпадает с доменом |
| план отката готов | `rollback_policy` заполнен, предыдущий релиз существует |
| TTL заранее понижен | иначе откат DNS будет длиться сутки |

Токен ограничен зоной и типами записей (`scope: zone_records_only`). Фабрика не
расширяет список зон и не трогает записи вне `allowed_names`.

**Понизь TTL заранее.** За сутки до cutover TTL ставится в 300 секунд. Откат
DNS с TTL 86400 — это не откат, а сутки недоступности.

## 5. Проверка после переключения

```bash
python3 -m factory verify     --site <site_id>
python3 -m factory seo-report --site <site_id>
```

Что должно совпасть, иначе — откат:

- домен отдаёт **этот** сайт, а не соседний из того же портфеля;
- `canonical`, `sitemap.xml` и `robots.txt` называют новый домен;
- staging-авторизация с production-домена **не** требуется, а сам staging
  по-прежнему закрыт;
- `X-Robots-Tag: noindex` на production **снят**, на staging остался;
- нет cross-site утечки: страницы одного сайта не отдают контент другого.

## 6. Откат cutover

```bash
python3 -m factory status   --site <site_id> --json    # зафиксировать состояние ДО
python3 -m factory rollback --site <site_id> --environment production
python3 -m factory verify   --site <site_id>
```

Откат DNS — возврат прежней записи в зоне. Откат кода не откатывает базу: если
релиз содержал миграцию, сначала восстанавливается БД из бэкапа этого релиза и
восстановление подтверждается сравнением, и только затем открывается трафик
([`ROLLBACK.md`](ROLLBACK.md)).

После отката — `/incident-report`.

## Чего делать нельзя

- Покупать или продлевать домен, переносить его другому владельцу.
- Менять DNS-записи вне зон из `inventory/dns-zones.yaml` и вне `allowed_names`.
- Переключать DNS до готового сертификата и проверенного origin.
- Считать зелёный staging разрешением на production: нужен
  `production_authorized: true` и флаг `--allow-production`.
- Публиковать контент без подтверждённых прав и rights manifest.
