# Инструкции по инцидентам

Каждый разбор построен одинаково: как замечается, как подтверждается, что делать,
как откатиться. Сценарии взяты из происходившего на этой системе, а не придуманы.

Общее правило: **HTTP 200 не означает исправность**. Самая дорогая авария здесь
выглядела как полностью здоровый сайт — код 200, страница отдаётся, каталог пуст.
Поэтому проверки должны смотреть на содержимое, а не на код ответа.

---

## 1. Пустой каталог при коде 200

**Как замечается.** `automation/host/yummy-catalog-content-check.sh` считает
карточки на витрине и считает пустой каталог аварией. Переменные:
`CATALOG_CHECK_HOSTS`, `CATALOG_CHECK_MIN_TITLES`, `CATALOG_CHECK_TIMEOUT`,
`CATALOG_CHECK_REPORT`.

**Как подтверждается.**

```bash
redis-cli -n 0 dbsize    # витрина site
redis-cli -n 1 dbsize    # org
redis-cli -n 2 dbsize    # biz
systemctl status redis-server
```

Ноль ключей при живом Redis — каталог не построен. Redis в цикле перезапуска —
причина ниже по стеку.

**Что делать.** Сначала поднять Redis (см. п. 5), затем перестроить индекс:
`systemctl start yummy-catalog-index`. Проверить все три витрины, а не одну:
базы раздельные, и авария бывает частичной.

**Откат.** Не требуется — данные восстанавливаются перестроением из источника.

---

## 2. Контент устарел

**Как замечается.** Свежесть падает при живых службах: страницы отдаются,
новые серии не появляются. `GET /api/v1/ingestion/status` показывает состояние
обхода; `GET /api/v1/sites/{siteId}/coverage` — полноту каталога.

**Как подтверждается.**

```bash
systemctl list-timers | grep yummy
journalctl -u yummy-episode-watcher --since "-2h" | tail -40
```

Отдельно проверить, что таймер не просто «активен», а недавно **отработал**:
активный таймер при падающей службе выглядит нормально.

**Что делать.** Запустить обход заданием, а не руками:

```bash
curl -X POST .../api/v1/sites/{siteId}/jobs \
  -H 'Authorization: Bearer ops' -H 'Idempotency-Key: refresh-1' \
  -d '{"action":"refresh"}'
```

Ключ идемпотентности обязателен: при таймауте повтор не создаст второе задание.

---

## 3. Задание застряло

**Как замечается.** `GET /api/v1/jobs/{jobId}` показывает стадию `processing`
дольше ожидаемого, либо `queue.counts()` показывает рост `processing`.

**Как подтверждается.** Задание переходит `inbox → processing` атомарным
переименованием, поэтому «застряло» означает, что исполнитель умер после захвата.
Проверить блокировку сайта: `factory.locks.is_locked(site_id, environment)`.

**Что делать.** `factory.queue.requeue_stale(max_age_seconds, max_attempts)`
возвращает просроченные в `inbox`. После `MAX_ATTEMPTS = 3` задание уходит в
`quarantine` — это не ошибка механизма, а отказ повторять то, что трижды не вышло.
Карантин разбирается вручную: повторять четвёртый раз без изменения причины
бессмысленно.

**Чего не делать.** Не удалять файл задания из `processing`, чтобы «оживить»
очередь: пропадёт след того, на чём именно оно встало.

---

## 4. Поставщик недоступен

**Как замечается.** Обход завершается ошибками авторизации или таймаутами;
каталог не обновляется, но и не пустеет.

**Как подтверждается.** Токен поставщика доставляется **файлом секрета** и
экспортируется точкой входа контейнера. Поэтому `docker exec ... env` покажет
пустое значение, хотя токен есть: смотреть надо `/proc/1/environ` внутри
контейнера. Пустота в `env` сама по себе не доказывает отсутствия токена —
на этом легко потерять час.

**Что делать.** Убедиться, что деградация частичная: витрина продолжает отдавать
уже загруженное. Не запускать массовую переиндексацию во время недоступности
поставщика — она вытеснит рабочий кэш неполными данными.

---

## 5. Отказ кэша (Redis)

**Как замечается.** Симптом — п. 1. Причина — Redis не поднимается или падает в
цикле.

**Как подтверждается.**

```bash
redis-cli ping
journalctl -u redis-server --since "-30m" | tail -30
```

**Что делать при повреждении AOF.** Сначала снять копию, затем чинить **копию**,
и только убедившись в результате — оригинал. Порядок именно такой: проверка
`redis-check-aof --fix` на копии сама усекает повреждённый хвост, и если копия
была единственной, исходное состояние потеряно безвозвратно. Это уже происходило.

**Откат.** Восстановление из резервной копии; при потере хвоста зафиксировать
объём потерянных данных в отчёте, а не умолчать о нём.

---

## 6. Отказ одной витрины

**Как замечается.** Одна витрина недоступна, соседние отвечают.

**Как подтверждается.** У витрин раздельные учётные данные, базы и контейнеры,
поэтому отказ одной — норма изоляции, а не начало общей аварии. Проверить, что
соседние действительно здоровы, прежде чем трогать общее.

**Что делать.** Выкладка и откат — поштучные. `deploy/staging/deploy.sh`
(репозиторий yummyani) принимает вторым аргументом одну витрину: `site`, `org`
или `biz`. Одновременная выкладка на весь массив запрещена (ADR-001).

**Откат.** `deploy/staging/rollback.sh` проверяет возраст резервной копии и
отказывается откатываться на устаревшую: порог `ROLLBACK_MAX_AGE_H`
(по умолчанию 24), осознанное согласие — `ROLLBACK_ACCEPT_DATA_LOSS=1`.
Измеренное время восстановления одной витрины — 3 секунды.

---

## 7. Расхождение версий контрактов

**Как замечается.** Управляющий вызов отвергается с `422` по полю, которое
вызывающий считает допустимым.

**Как подтверждается.** Перечни допустимых действий и областей прав
импортируются в описание OpenAPI **из кода проверок**, поэтому описание не может
разойтись с поведением. Расхождение означает, что вызывающий читает старую копию
описания. Сверить: `GET /api/v1/health` возвращает версию.

**Что делать.** Перечитать описание из работающей службы, а не из сохранённого
файла. Изменения контракта — только добавлением новой версии, не правкой
существующей.

---

## Чего в наблюдаемости пока нет

Честный перечень, чтобы на него не рассчитывали: метрик и трассировок нет,
порогов и автоматических предупреждений нет, ограничение частоты управляющего
API считается в памяти процесса и при нескольких экземплярах кратно их числу.
Обнаружение перечисленного выше опирается на таймеры, журнал операций и ручную
проверку.

## Пороги и предупреждения

Метрики отдаются по `GET /api/v1/metrics` (право `read`) в текстовом формате
Prometheus. Счётчики живут в памяти процесса и обнуляются при перезапуске,
поэтому осмысленна скорость роста, а не абсолютное значение.

| Показатель | Порог | Что означает |
|---|---|---|
| `site_engine_queue_items{stage="quarantine"}` | > 0 | задание трижды не удалось; повтор без разбора причины бесполезен |
| `site_engine_queue_items{stage="processing"}` | не убывает 15 мин | исполнитель умер после захвата задания (п. 3 инструкций) |
| `site_engine_queue_items{stage="inbox"}` | растёт 30 мин | задания ставятся быстрее, чем исполняются |
| `rate(site_engine_control_refusals_total{code="rate_limited"})` | > 0 | сорвавшийся цикл автоматики |
| `rate(site_engine_control_refusals_total{code="version_conflict"})` | всплеск | двое правят одну конфигурацию одновременно |
| `rate(site_engine_control_requests_total{status="5xx"})` | > 0 | внутренняя ошибка: смотреть журнал процесса |
| `site_engine_sites` | изменилось неожиданно | профиль добавлен или потерян мимо процедуры |
| `site_engine_admin_sessions` | необычно много | сессии не завершаются либо доступ шире ожидаемого |

Отсутствие ряда `site_engine_control_requests_total` на свежем процессе —
не авария: счётчик появляется с первым наблюдением. Ноль означал бы «запросов
не было», отсутствие означает «ещё не мерили». Панели следует строить так, чтобы
она это различала.

Чего метрики не покрывают: свежесть контента и полноту каталога измеряются
читающими маршрутами (`/api/v1/ingestion/status`, `/api/v1/sites/{id}/coverage`)
и функциональной проверкой каталога, а не счётчиками процесса. Счётчик не
заметит, что витрина отдаёт 200 с пустым каталогом, — это остаётся задачей
`yummy-catalog-content-check.sh`.
