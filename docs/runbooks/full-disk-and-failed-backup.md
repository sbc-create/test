# Runbook: диск заполнен, бэкап не подтверждается

**Назначение.** Восстановить подтверждаемость бэкапа control-host и вернуть
`site-factory-health` в зелёное состояние.
**Владелец.** Направление host-automation (`automation/host/`).
**Последняя проверка.** 2026-09-03, на реальном отказе (см. «Разбор» ниже).

## Инварианты, которые здесь защищаются

1. Существование архива не является доказательством восстановления. Подтверждён
   только тот бэкап, у которого есть `host-<stamp>.verified.json`.
2. `site-factory-health` датирует последний хороший бэкап **исключительно** по
   этим записям. Архив без записи для здоровья хоста не существует.
3. Упавший прогон не имеет права ухудшать положение следующего.
4. Предыдущая подтверждённая копия не трогается, пока новая не подтверждена.

## Симптом

`site-factory-health.service` падает каждые 15 минут, `site-factory-backup.service`
в состоянии `failed`.

```
systemctl status site-factory-backup site-factory-health --no-pager
tail -1 /var/log/site-factory/health.log | python3 -m json.tool
```

Код выхода health равен числу алертов, а не 0/1. `exit 2` — два алерта.

## Разбор: как это выглядело 2026-09-03

Два алерта health были **одним** событием, а не двумя проблемами:

```
{"check": "disk_root", "status": "alert", "used_pct": 90, "threshold_pct": 80}
{"check": "backup", "status": "alert", "age_hours": 34, "threshold_hours": 30,
 "latest": "/srv/backups/host-20260902T032255Z.verified.json"}
```

Цепочка:

1. Диск дошёл до 90 %.
2. Бэкап собрал staging, упаковал архив на 1.13 GB и на шаге доказательства
   восстановления распаковывал его во второй каталог. Распаковка упала:
   `tar: ... Cannot create symlink ...: No space left on device`, далее
   `BACKUP FAILED: архив не распаковывается`.
3. Запись `.verified.json` создаётся только после успешной сверки — не появилась.
4. Health увидел, что последней подтверждённой копии 34 часа при пороге 30.

Отказ произошёл на последнем шаге, но был предсказуем на первом.

## Диагностика: три вопроса по порядку

**1. Место действительно кончилось или кончилось только у бэкапа?**

```
df -h /
sudo journalctl -u site-factory-backup -n 40 --no-pager | grep -i "no space\|FAILED"
```

**2. Есть ли осиротевшие архивы?** Архив без пары `.verified.json` — продукт
упавшего прогона:

```
cd /srv/backups
for a in host-*.tar.gz; do
  [ -e "${a%.tar.gz}.verified.json" ] || echo "СИРОТА: $a"
done
```

**3. Кто на самом деле занял диск?** Порядок именно такой — сначала самые
крупные потребители, а не самые заметные:

```
sudo du -x -d1 / | sort -rn | head
sudo du -x -d2 /var | sort -rn | head
docker system df
```

На этом хосте 2026-09-03 распределение было: `/var/lib/containerd` 25.0 GB
(37 % диска), `/srv/backups` 9.7 GB, `/srv/lords` 6.8 GB. Крупнейший потребитель
не имел отношения к бэкапу — вывод по одному лишь `/srv/backups` был бы неверен.

## Освобождение места — по возрастанию риска

**Безопасно и обратимо (build cache пересоберётся):**

```
docker builder prune -f
```

2026-09-03 это дало 2.382 GB.

**Безопасно при проверке пути (осиротевший архив упавшего прогона):** удаляется
только `host-*.tar.gz` без парного `.verified.json` и **старше суток** — порог
защищает архив прогона, который идёт прямо сейчас. С 2026-09-03 это делает сам
`automation/host/backup-retention.sh`, вручную не нужно.

**Требует решения владельца:** неиспользуемые образы одноразовых стендов.
Проверять, что образ не занят контейнером и не является rollback-целью:

```
docker ps --format '{{.Image}}' | sort -u
docker images --format '{{.Repository}}:{{.Tag}}\t{{.CreatedSince}}'
```

Образы с тегом `rollback-*` и текущий рабочий тег не трогать никогда.

## Возврат в зелёное

```
sudo systemctl start site-factory-backup
sudo journalctl -u site-factory-backup -f
```

Успехом считается **не** нулевой код возврата, а появившийся файл:

```
ls -lt /srv/backups/host-*.verified.json | head -1
sudo systemctl start site-factory-health
tail -1 /var/log/site-factory/health.log | python3 -m json.tool
```

`alerts: 0` — состояние восстановлено.

## Что мешает отказу повториться

* `automation/host/backup-retention.sh` — удаляет осиротевшие архивы старше
  суток, пока остаётся хотя бы одна подтверждённая копия. Прежде такой архив не
  удалялся никогда и каждый провал приближал следующий.
  Тест: `tests/unit/test_backup_retention_prunes_orphan_archives.py`.
* `automation/host/backup-space-precheck.sh` — отказывает **до** упаковки, если
  места не хватит на архив и распакованную копию. Учитывает, что рабочий каталог
  и каталог бэкапов могут лежать на одной файловой системе: тогда требования
  складываются, а не проверяются порознь.
  Тест: `tests/unit/test_backup_space_precheck.py`.

## Чего делать нельзя

* Удалять `*.verified.json`, чтобы «почистить» — это стирает единственное
  доказательство восстановления и мгновенно состарит health.
* Удалять последнюю подтверждённую копию ради места.
* Исключать `/var/lib/site-factory-secret-hub` из бэкапа, чтобы прогон
  «прошёл»: без шифрованного хранилища восстановление consumer-файлов
  невозможно, и архив будет только выглядеть полным. Скрипт падает на этом
  намеренно.
* Считать зелёный `systemctl status` доказательством. Доказательство — файл
  `.verified.json` и `alerts: 0` в health.
