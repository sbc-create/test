# Управление массивом сайтов через Control API v1

Документ для того, кто управляет витринами программно. Описывает, что можно
сделать, чего нельзя и как понять, что произошло.

## Включение

Два выключателя, независимых друг от друга. Оба выключены по умолчанию.

| Переменная | Что включает |
|---|---|
| `SITE_ENGINE_API_ENABLED` | чтение (11 маршрутов GET) |
| `SITE_ENGINE_CONTROL_WRITES` | запись (задания, настройки, инвалидация) |
| `SITE_ENGINE_CONTROL_TOKENS` | токены и их права |

Формат токенов — `токен=область,область|токен=область`. Разделитель между
токеном и правами — знак равенства, потому что имена областей сами содержат
двоеточие:

```
SITE_ENGINE_CONTROL_TOKENS='ops=read,jobs:write,cache:write|robot=read,jobs:write'
```

Опечатка в имени области не игнорируется — сборка падает с перечнем неизвестных
областей. Молча выданное не то право хуже отказа.

При выключенной записи записывающие маршруты отвечают `404`. Это не ошибка
настройки: ответ `403` подтверждал бы, что маршрут существует.

## Области прав

| Область | Что разрешает |
|---|---|
| `read` | состояние заданий |
| `jobs:write` | ставить задания по сайту |
| `config:write` | менять обратимые настройки |
| `cache:write` | планировать инвалидацию кэша |
| `audit:read` | читать журнал операций |

Выдавайте наименьший достаточный набор. Автоматике, которая только
переиндексирует, нужны `read` и `jobs:write` — и ничего больше.

## Правило первого вызова: сначала `dryRun`

Каждая изменяющая операция принимает `"dryRun": true`. В этом режиме запрос
проходит всю проверку и возвращает, что именно произошло бы, но ничего не меняет.

```bash
curl -X PATCH .../api/v1/sites/yummyani-site/settings \
  -H 'Authorization: Bearer ops' -H 'Content-Type: application/json' \
  -d '{"changes": {"keep_releases": 8}, "dryRun": true}'
```

```json
{"dryRun": true, "currentVersion": "sha256:…", "noop": false,
 "diff": {"keep_releases": {"before": 5, "after": 8}},
 "correlationId": "cid-…"}
```

Поле `currentVersion` из ответа передайте в боевой запрос как `expectedVersion`.
Если за это время конфигурацию изменил кто-то ещё, вы получите `409`, а не
тихую перезапись чужой правки.

## Операции

### Поставить задание

`POST /api/v1/sites/{siteId}/jobs` — право `jobs:write`.
Допустимые действия: `reindex`, `refresh`, `enrich`, `verify`. Список закрытый:
свободное поле означало бы выполнение произвольного действия по HTTP.

Ответ `202` с идентификатором задания. Состояние — `GET /api/v1/jobs/{jobId}`:
поле `stage` (`inbox`, `processing`, `done`, `failed`, `quarantine`) и
`terminal`, показывающее, окончено ли задание.

### Изменить настройку

`PATCH /api/v1/sites/{siteId}/settings` — право `config:write`.

Меняются только обратимые настройки ядра: `keep_releases` (2…20),
`cache_policy` (числа 0…86400), `feature_flags` (логические). Вложенные словари
**дополняются**, а не заменяются целиком — иначе правка одного ключа тихо стёрла
бы соседние.

Отклоняются намеренно, с причиной в ответе: `domains`, `canonical_host`,
`site_type`, `indexing_enabled`, `seo_enabled`, `locale`, `timezone`, `theme`,
`render_mode`. Это не пробел в реализации. Такие изменения проходят через ревью
и выкладку, где у них есть автор и откат.

Ответ `422` перечисляет **все** нарушения сразу, а не первое.

### Сбросить кэш

`POST /api/v1/sites/{siteId}/cache/invalidate` — право `cache:write`.
Область: `homepage`, `shelves`, `catalog`, `title`. Для `title` список `keys`
обязателен и непуст: пустой список при точечной области — это «сбрось всё» под
видом точечной операции, и почти всегда это ошибка вызывающего.

Операция ставится в очередь (`202`) и исполняется рабочим процессом.
Управляющий слой не ходит в хранилище витрины сам.

## Повторы и таймауты

Передавайте `Idempotency-Key` на каждой изменяющей операции. Повтор того же
запроса с тем же ключом вернёт прежний ответ с полем `idempotentReplay: true` и
не выполнит действие второй раз.

Тот же ключ с **другим** телом даст `409 idempotency_key_reused`. Так и задумано:
это другой запрос под уже использованным ключом.

При таймауте не меняйте запрос — повторите его с тем же ключом.

## Как понять, что произошло

Каждый ответ, включая отказы, содержит `correlationId`. Передайте свой через
заголовок `X-Correlation-Id`, если хотите связать вызов со своими журналами.

Журнал: `GET /api/v1/audit` (право `audit:read`), фильтры `siteId` и `limit`.
В журнал попадают и отказы — с кодом причины и идентификатором токена.
Сам токен в журнал не пишется, только его устойчивый отпечаток.

Запись об изменении настройки содержит `diff` с полями `before` и `after`,
а также версии до и после. Журнал отвечает на вопрос «что стало другим», а не
только «кто-то менял».

## Коды ответов

| Код | Значение | Что делать |
|---|---|---|
| `401` | токен отсутствует или не распознан | проверить заголовок `Authorization: Bearer` |
| `403` | у токена нет нужной области | в ответе указано, какой именно |
| `404` | маршрута или сайта нет; либо запись выключена | проверить `SITE_ENGINE_CONTROL_WRITES` |
| `409` | конфликт версии, занятый сайт, повтор ключа с другим телом | перечитать состояние, не повторять вслепую |
| `422` | настройка вне списка, вне диапазона или отклонена намеренно | смотреть `problems` |
| `429` | превышен предел частоты | 30 запросов в минуту на токен |

Предел частоты считается в памяти процесса: при нескольких экземплярах он
кратен их числу. Ограничение задумано против сорвавшегося цикла автоматики.

## Чего этот API не делает

Не выкладывает и не откатывает релизы, не трогает базы данных витрин, не
управляет контейнерами и не меняет оформление. Выкладка остаётся поэтапной
процедурой с канареечной витриной — одновременная выкладка на весь массив
запрещена (ADR-001).
