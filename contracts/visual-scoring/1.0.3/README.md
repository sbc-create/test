# visual-scoring/1.0.3 — расчёт визуального соответствия

Неизменяемая версия. Числа этого каталога не меняются: правка любого веса,
допуска или порога требует нового каталога `1.1.0` или `2.0.0`.

## Что изменилось относительно 1.0.2

Независимый аудит (PR #81, статус `NEEDS_CONTRACT_REPAIR`) подтвердил
конфликт приоритета правил в `component_assignment.order`. С 1.0.1 правило
`^.*_sticky$` → `geometry` было дописано в конец списка `order`, внутри той же
записи `geometry`, что и остальные геометрические шаблоны. Реализация
`assign_component()` (`factory/visual_scoring.py`) брала **первое по порядку
массива** правило, чей хоть один шаблон совпал, — не самое специфичное. Любой
`*_sticky`-токен, чей префикс до `_sticky` совпадал с более общим префиксным
шаблоном какого-то другого компонента, стоящего в списке раньше `geometry`,
перехватывался этим более общим компонентом:

| Имя токена | Ожидалось (семантика 1.0.1) | Фактически под 1.0.2 | Перехватывающий шаблон |
| --- | --- | --- | --- |
| `cards_sticky` | `geometry` | `cards_media` | `^cards_.*$` |
| `media_sticky` | `geometry` | `cards_media` | `^media_.*$` |
| `border_sticky` | `geometry` | `colors` | `^border_.*$` |
| `surface_sticky` | `geometry` | `colors` | `^surface_.*$` |
| `type_sticky` | `geometry` | `typography` | `^type_.*$` |
| `viewport_sticky` | `geometry` | `responsive` | `^viewport_.*$` |
| `required_block_sticky` | `geometry` | `structure_order` | `^required_block_.*$` |

Конфликт не завязан на `header_sticky`: `header_sticky` под 1.0.2 продолжал
резолвиться верно только потому, что ни один более ранний в списке шаблон с
ним не совпадал — совпадение было случайностью конкретного имени, а не
свойством правила.

Исправление: `component_assignment.order` допускает необязательное целое поле
`priority` у каждой записи (по умолчанию `0`). Если несколько записей
совпадают с одним именем токена, побеждает запись с наибольшим `priority`, а
не первая по позиции в массиве. `^.*_sticky$` → `geometry` вынесен в
отдельную запись с `"priority": 100`, что делает его победителем независимо от
того, где эта запись физически расположена в `order`. Правила без явного
`priority` (все правила 1.0.0-1.0.2 и большая часть правил 1.0.3) остаются
равны между собой — для них тай-брейком остаётся позиция в массиве, то есть
их результат воспроизводится побитово так же, как и раньше. Механизм общий:
любое будущее правило, которому нужно не быть перехваченным более общим
шаблоном другого компонента, объявляет свой `priority`, без правки кода.

Отдельно исправлен дефект совместимости среды из того же аудита:
`check_compatibility()` падал `TypeError` при отсутствующем (`None`)
`environment_manifest` эталонной стороны вместо честного
`BLOCKED_COMPATIBILITY_MISMATCH`. Это правка кода (`factory/visual_scoring.py`),
применяется одинаково ко всем версиям контракта и не требует отдельного
каталога — числа, пороги и политика совместимости не менялись. Подробности —
`CHANGELOG.md`.

Что не менялось: все матрицы весов, числовые допуски, пороги
80.00 / 70.00 / 65.00, требование `evidence_completeness_required = 100`,
правило округления, одиннадцать hard-fail, `component_applicability` из 1.0.2
(`cards_media` на `catalog`/`not_found`) и anti-fitting правила — перенесены
без изменений. Ни одно из ранее закреплённых сопоставлений имя → компонент не
изменило результат. Схема результата правки не потребовала.

## Как назначается компонент токена (с учётом priority)

Для каждого правила `order`, чей хоть один `name_patterns` совпал с именем
токена по `re.match`, берётся его `priority` (по умолчанию `0`). Побеждает
правило с наибольшим `priority`; при равенстве — правило, встречающееся в
массиве `order` раньше (тот же «первое совпадение по порядку», что был
единственным механизмом в 1.0.0-1.0.2). Явное поле `token.component` сильнее
любого шаблона. Токен, не попавший ни в одно правило, получает `UNASSIGNED`:
он не отбрасывается тихо, а снижает `evidence_completeness`.

Действующий с 1.0.1 семантический принцип не изменился: булев токен положения
sticky-элемента (имя оканчивается на `_sticky`) относится к `geometry` —
теперь это гарантировано `priority: 100` независимо от префикса имени и от
позиции записи в `order`.

## Применимость компонента к поверхности (scope-aware, из 1.0.2)

`component_applicability` решает: применим ли компонент X к обязательной
поверхности Y. По умолчанию — да (`REQUIRED`). Список `not_applicable` умеет
только сужать охват явной записью `{component, surface, reason}`; отсутствие
записи или неизвестное имя поверхности не расширяют исключение — они дают
`REQUIRED`, то есть остаются fail-closed. Эта версия наследует ровно те же две
пары, что и 1.0.2: `cards_media`/`catalog` и `cards_media`/`not_found`.

## Зачем контракт существует отдельно от проверки

Reference pack `amd.online` завершился статусом `BLOCKED_SCORING_CONTRACT_MISSING`
и был прав: токены измерены, а правила, превращающего их в один процент, в
репозитории не было. Порог «80 %» встречался только в текстах заданий и ни в
одном versioned-документе.

Назначить веса и порог тем же заданием, которое затем по ним аттестуется, —
подгонка, а не измерение. Поэтому контракт написан до появления оценки
кандидата, его автор не является ни автором пакета, ни автором кандидата, и ни
одно число здесь не выведено из результатов PR #80, PR #81 или PR #76.

## Что подаётся на вход

| Вход | Требование |
| --- | --- |
| reference pack | неизменяемый, с зафиксированным полным SHA коммита |
| candidate pack | тот же набор поверхностей и ширин |
| токены | `name`, `value`, `unit`, `surface`, `viewport`, `method`, `evidence` |
| исключения | объявлены до сравнения, с причиной и provenance |
| дайджесты снимков | записанные и заново наблюдаемые значения |
| environment manifest | обе стороны, полностью заполненный |

Токен без `method` или `evidence` не имеет provenance. Вручную вписанное
значение provenance не имеет по определению и вызывает hard-fail.

Отсутствующий (`None`/незаполненный) `environment_manifest` любой из сторон
недоказуем так же, как запрещённое значение (`any`/`latest`/`*`/`pending`) —
он не подставляется значением другой стороны, чтобы сравнение прошло, а
честно даёт `BLOCKED_COMPATIBILITY_MISMATCH`.

## Матрицы весов

Поверхности: `home` 25, `catalog` 20, `collection_hub` 20, `title` 25,
`not_found` 10.
Ширины: `390` 30, `768` 30, `1440` 40.
Компоненты: структура и порядок блоков 30, геометрия 30, типографика 15,
цвета и границы 10, карточки и медиа 10, отзывчивость 5.

Каждая матрица проверяется вычислительно на сумму 100 при загрузке. Опечатка в
числах валит загрузку, а не смещает оценку молча.

## Как считается балл

**Числовые параметры.** Относительное отклонение `|кандидат − эталон| / |эталон|`.
До 5 % включительно — 100 баллов. От 5 % до 25 % — линейное снижение
`100 × (0,25 − отклонение) / 0,20`. От 25 % — 0. Эталонный ноль не делится:
совпадение с нулём даёт 100, любое иное значение — 0.

**Цвета.** CIEDE2000 в пространстве CIELAB, осветитель D65, наблюдатель 2°.
Точное совпадение нормализованного hex или имени токена — 100 без вычислений.
ΔE00 до 1,0 — 100. От 1,0 до 5,0 — линейное снижение. От 5,0 — 0.

**Перечисления, флаги, наличие и порядок.** Совпадение — 100, иначе 0.

**Отсутствующее измерение.** 0, если оно не было исключено заранее или не
`NOT_APPLICABLE` по `component_applicability`.

**Лишний токен кандидата.** Не участвует в расчёте и не может поднять оценку.

## Агрегация

`токен → компонент → ячейка (surface × viewport) → surface → overall`.

Токены внутри компонента равновесны. Компонент в ячейку входит по весу
компонента (после перераспределения), ячейки в surface — по весу ширины,
surfaces в общий балл — по весу поверхности. Порядок обхода задаётся
сортировкой, а не порядком поступления.

Промежуточные значения не округляются. Округляется только отчётное значение —
до двух знаков, полубанковским правилом. Пороги сравниваются с уже округлённым
отчётным значением.

## Когда разрешена сертификация

`VISUAL_CERTIFIED` требует одновременно:

* overall ≥ 80.00;
* каждая обязательная поверхность ≥ 70.00;
* каждая ширина в агрегате ≥ 65.00;
* пустой список hard-fail;
* полнота evidence ровно 100 %;
* checker не совпадает с автором пакета;
* checker не совпадает с автором кандидата;
* выполнено хотя бы одно сравнение.

## Hard-fail

Сертификация запрещена независимо от среднего балла при: отсутствии
обязательной поверхности или ширины; расхождении дайджеста; измерении без
provenance; изменении evidence после начала проверки; появлении горизонтальной
прокрутки; отсутствии или недоступности обязательного блока; перекрытии
основного контента; совпадении checker с автором пакета или кандидата;
изменении контракта после просмотра результата; применении незаявленного
исключения.

## Совместимость

Диапазон берётся только из доказанного манифеста, lockfile или конфигурации CI.
Недоказуемый диапазон закрепляется текущей проверенной версией; `any`, `latest`,
`*` и `pending` запрещены и отвергаются схемой результата. Отсутствующий
`environment_manifest` одной из сторон недоказуем так же, как запрещённое
значение.

| Параметр | Значение | Источник |

## Результат

Машиночитаемая форма — `schemas/visual-scoring-result.schema.json`.
Статусы и их приоритет: `BLOCKED_SCORING_CONTRACT_MISSING` →
`BLOCKED_INDEPENDENCE_VIOLATION` → `BLOCKED_COMPATIBILITY_MISMATCH` →
`BLOCKED_EVIDENCE_INCOMPLETE` → `VISUAL_REJECTED` → `VISUAL_CERTIFIED`. Эта
версия не меняет `decide()` и её приоритет статусов.

## Как применять

```python
from factory.visual_scoring import Identity, compare, load_contract

contract = load_contract("1.0.3")
result = compare(
    reference_tokens=..., candidate_tokens=..., contract=contract,
    checker=Identity("checker-01", "INDEPENDENT_CHECKER"),
    pack_author=Identity("templates-01", "TEMPLATES"),
    candidate_author=Identity("candidate-01", "TEMPLATES_CANDIDATE"),
    reference_environment=..., candidate_environment=...,
    declared_exclusions=..., baseline_exclusions_digest=...,
    digest_checks=...,
)
```

Единая точка входа существует затем, чтобы независимый checker не собирал
расчёт заново: собранный вручную конвейер разойдётся с контрактом в мелочи, и
разойдётся в удобную сторону.

## Чего контракт не делает

Он не выносит вердикт по конкретному кандидату и не запускает проверку. Ни
один тест этой версии не использует данные пакета `amd.online`.

Эта версия закрывает конфликт приоритета правил `component_assignment` для
`*_sticky`-имён (регрессия от 1.0.1/1.0.2, найденная независимым аудитом
PR #81) и делает `check_compatibility()` устойчивой к отсутствующему
`environment_manifest` эталонной стороны. Численные пороги сертификации
кандидата эта версия не меняет и не смягчает.
