# DNS и Cloudflare для zonafilm.cc

Команда:

```bash
python3 automation/host/zonafilm-cc-dns-probe.py \
  --domain zonafilm.cc \
  --expect-ns paris.ns.cloudflare.com --expect-ns piers.ns.cloudflare.com \
  --expect-a 45.131.182.225
```

Полный вывод — [`zonafilm-cc.json`](zonafilm-cc.json). Exit code 0,
`verdict = DELEGATED_NO_RECORDS`.

## Что доказано

| Проверка | Результат | Чем подтверждено |
| --- | --- | --- |
| Делегация на ожидаемые NS | **MATCH** | серверы `.cc` (192.42.173.30 и ещё три) отвечают `paris.ns.cloudflare.com`, `piers.ns.cloudflare.com`; те же два имени независимо возвращают 1.1.1.1, 8.8.8.8, 9.9.9.9, 208.67.222.222 |
| Конфликтующие или устаревшие NS | **нет** | все пять источников дали один и тот же набор из двух имён, третьего имени не назвал никто |
| Зона существует в Cloudflare | **да** | оба назначенных NS отвечают авторитетно (AA=1) на SOA: `zonafilm.cc SOA paris.ns.cloudflare.com dns.cloudflare.com`, TTL 1800 |
| Зона активна | **да** | неактивная зона не обслуживалась бы назначенными ей NS авторитетно; запросы дают NOERROR, а не REFUSED |
| A/AAAA apex | **отсутствуют** | NOERROR + пустая секция ответа + SOA в authority = NODATA: имя есть, адреса нет |
| A/AAAA/CNAME `www` | **отсутствуют** | NXDOMAIN на всех трёх типах от обоих авторитетных серверов |
| Dangling records | **нет** | NXDOMAIN на `www` означает, что записи нет вовсе; висящего CNAME на чужой origin не существует |
| IPv4/IPv6 согласованы | **тривиально** | нет ни одной записи ни одного семейства, рассогласовать нечего |
| Чужие записи, которые будут затронуты | **нет** | в зоне `zonafilm.cc` не обнаружено ни одной A/AAAA/CNAME записи |

## Origin

`45.131.182.225` — не догадка. Два независимых источника на этом же хосте:

1. `config/directions/lords.json` → `origin_ipv4`, и те же адреса в `a_apex`
   каждого из трёх доменов Lords;
2. живой DNS: `zonafilm.space` (соседняя витрина того же семейства, тот же
   реестр, тот же nginx) резолвится в `45.131.182.225`.

## Чего сделать нельзя и почему

Запись A для `zonafilm.cc` не создана, и создать её эта сессия не может:

* `inventory/dns-zones.yaml` содержит `zones: []`, то есть ни одна зона фабрике
  не передана. Файл закрыт `deny Edit` намеренно — расширение списка зон
  является решением человека, а не выводом агента;
* в Secret Hub нет учётных данных Cloudflare: `python3 -m factory secrets status`
  перечисляет только `api_token`/`publisher_id` CDNVideoHub по направлениям
  `yami`, `lords`, `amedia`;
* в окружении нет ни одной переменной `CF_*`/`CLOUDFLARE_*`, на диске нет ни
  одного файла токена (единственное совпадение по имени —
  `/etc/fail2ban/action.d/cloudflare.conf`, это шаблон действия fail2ban).

Статус: **`BLOCKED_EXTERNAL_CREDENTIAL`** — ровно на шаге создания записи.
Делегация при этом завершена, поэтому остальная работа не останавливается:
контур поднимается и проверяется по Host-заголовку и TLS SNI на самом origin,
как это уже делается для соседних витрин.

## Что останется сделать владельцу

Одно действие в панели Cloudflare зоны `zonafilm.cc`:

```
A    zonafilm.cc       45.131.182.225   proxy: DNS only (серое облако)
A    www.zonafilm.cc   45.131.182.225   proxy: DNS only (серое облако)
```

`DNS only` — не предпочтение, а совпадение с принятой схемой: в
`config/directions/lords.json` все домены направления объявлены как
`"mode": "dns-only"`. Proxy-режим Cloudflare добавил бы собственный кэш поверх
витрины и собственный сертификат, и тогда `X-Robots-Tag: noindex`, отданный
origin, зависел бы от политики кэширования CDN — ровно тот риск «случайного
открытия индексации через CDN-кеш», который задание требует исключить.
