# Приёмка 1.2.11 как шаблона для новых сайтов

Продолжение стадии ANIMEDIA-TEMPLATE-PORT-SPACE-02. Перенос 14 исправлений не
трогался; здесь закрыты пять оставшихся вопросов приёмки.

## 1. Путь от шаблона до нового сайта

**Генератор** — `automation/host/animedia_release_build.py`. Другого пути у
семейства нет: `automation/host/provision-site.py` раскладывает готовый
статический срез и к рантайму Animedia отношения не имеет, а машинерия ячеек
(`factory/cell`, `docs/PORTABLE_SITE_CELL.md`) живёт только в ветке
`claude/portable-site-cell-01` и в эту линию не влита.

**Откуда берётся версия.** Из `config/animedia/TEMPLATE_VERSION.json` дерева
той ветки, на которой запущен сборщик. Fail closed на четырёх границах:

| отказ | условие |
| --- | --- |
| `ветка вне контура` | ветка не начинается на `claude/animedia-` |
| `нет файла версии шаблона` | нет `config/animedia/TEMPLATE_VERSION.json` |
| `рантайм не объявляет версию X` | строки версии нет в исходнике рантайма |
| `дерево грязное` / `артефакт не совпадает` | сборка не из зафиксированного кода |

**Какая ветка что отдаёт** (проверено `git show <ветка>:…`):

| ветка | версия |
| --- | --- |
| `origin/main` | файла версии нет — сборка откажет |
| `origin/claude/animedia-template-fix-01` | 1.2.10 |
| эта ветка | **1.2.11** |

Отсутствие изменений в `main` неработоспособности не доказывает: источник
сборки для семейства — ветка `claude/animedia-*`, и сборщик на `main` не
работает по устройству, а не по недосмотру.

**Манифест витрины больше не пишется руками.** Сборщик умеет
`--emit-manifest ПУТЬ --profile ПРОФИЛЬ` и выводит манифест из ЭТОЙ сборки:
`build_id`, `artifact_sha256`, `source_commit`, `design_version`, `profile`
из объявленных выбираемых вариантов. Профиль вне списка — отказ.

## 2. Идентификация экземпляра

`build_id`/`release_id` брались только из манифеста витрины, который пишется
отдельно от сборки. После пересборки витрина называла прежний выпуск — так
стенд прошлой стадии сообщал `release_id` первой сборки, исполняя пятую.

Теперь паспорт выпуска читается из `RELEASE.json`, лежащего рядом с
исполняемым артефактом. `/healthz` отдаёт:

| поле | что означает |
| --- | --- |
| `build_id`, `release_id` | выпуск по `RELEASE.json`, иначе по манифесту |
| `release_identity_source` | `release.json` или `manifest` |
| `manifest_build_id` | что об этом говорит манифест |
| `identity_match` | сходятся ли релиз, манифест и цифра артефакта |

Состояние ЗАГРУЖЕННЫХ данных (а не файла на диске):
`catalog_digest_loaded`, `details_digest_loaded`, `catalog_items_loaded`,
`details_entries_loaded`, `catalog_loaded_at`, `snapshot_reloads` и сводный
`snapshot_up_to_date`. Проверено на стенде: после записи файла
`snapshot_up_to_date` становится `false` и возвращается в `true` только после
перечитывания, вместе с новой `catalog_revision`.

Закреплено проверками: выпуск по релизу, расхождение манифеста и релиза, запуск
из дерева без релиза, цифры загруженных снимков у каталога и подробностей.

## 3. Воспроизведение видео

Издатель взят из УЖЕ СУЩЕСТВУЮЩЕЙ разрешённой конфигурации
(`/srv/lords/.frontend/player-animedia-02.json`), указанной стенду явной
переменной `LORDS_PLAYER_CONFIG`. Умолчанием для новых доменов это не
становится: имя файла плеера выводится из имени снимка каталога, у витрины
`animedia-new` это `player-animedia-new.json`, и его нет — плеер молчит.
Закреплено проверкой: даже когда рядом лежит `player-animedia-01.json`, новая
витрина остаётся без плеера, а не подбирает соседний ключ.

Воспроизведение подтверждено тремя признаками сразу:

* провайдер отдал плейлист `…/player/sv/playlist?pub=…` и поток
  `…/player/sv/video/16087215463088` — коды 200;
* провайдер прислал `started` и `timeupdate`;
* `currentTime` у `<video>` вырос (0 → 1,8 с за три приращения,
  `paused:false`, `readyState:4`); на прогоне без преролла — на элементе
  контента длительностью 300 с.

Витрина засчитала просмотр маячком `/event/play`. Переход между сериями
открывается, на соседней серии плеер подключается.

Две ловушки, на которых проверка давала ложный отказ: `<video>` живёт в КАДРЕ
провайдера (не в документе витрины и не в теневом корне), и провайдер пускает
преролл, во время которого основное видео стоит на 0,08 с `paused:true`.

## 4. Вес превью подборок

Замеры и границы — `docs/animedia/REQUEST_POSTER_DOWNSCALE.md`. Коротко:
превью показывает **6,0 % площади оригинала** (681 кБ), но та же неисправность
стоит **4795 кБ** на карточках каталога; главная весит 5,16 МБ на компьютере и
2,95 МБ на телефоне. Механизма уменьшения нет ни у провайдера (замороженный
контракт знает только адрес и `fetch_images: false`), ни у витрины (рантайм
импортирует только стандартную библиотеку — проверено разбором AST). Правка
требует новой зависимости рантайма и решения владельца; чужой компонент из
этой ветки не правился.

Читаемые названия, пропорции обложек, заглушки записей без постера и обе темы
проверены на свежем экземпляре — 224 проверки в браузере.

## 5. Закреплённые зависимости

`factory/animedia/community.py` побайтово равен передаточному файлу
закреплённого коммита `da20a290` (sha256 `f82555e8…`, 52743 байта). Все девять
имён, которые шаблон берёт у модуля, в 2.1 есть. Версия расчёта
(`main-score/1.0`) в шаблоне не зашита ни строкой, ни константой — в разметку
она попадает из поля «формула» объекта оценки, возвращённого модулем.
Обработчик данных о хранилище сообщества не знает вовсе. Версия не поднимается:
более новой передачи, чем 2.1, в репозитории нет.
