# Lords shared template — второй реальный цикл ремонта (PR #76, слой factory/lords/**)

Эта папка — evidence владельца **общего** слоя (`factory/lords/**`, общие
visual measurement tools, общие Lords contracts/schemas, generic Lords
profiles), а не Animedia-профиля. Предыдущие два прохода
(`artifacts/evidence/templates/animedia-portal/visual-candidate-repair/`,
коммиты `8678861` и `74ad40c`) чинили и измерительный инструмент, и реальные
дефекты вёрстки, но были закоммичены под именем `templates(animedia-portal)`
и писали в Animedia-специфичную evidence-папку. Эта папка — продолжение той
же работы над PR #76, но со стороны владельца общего шаблона и без записи в
чужое (Animedia) дерево evidence.

Кандидат для измерения — тот же `sites/animedia-preview` (`blueprints/lords/
profiles/animedia-portal.yaml`), но **не изменён**: он используется только
как read-only тестовый стенд для общего шаблона (как и в первых двух
проходах), а не как предмет правки. Список изменённых файлов ниже содержит
только общий слой.

## Найденный и исправленный реальный общий дефект

**`.site-nav{flex:1 1 auto}` даёт вторую строку шапки на всех поверхностях
с формой поиска в шапке.** Первый проход (README `.../animedia-portal/
visual-candidate-repair/README.md`, п.3) выровнял брейкпоинт скрытия
тумблера и появления инлайн-меню — это устранило перенос там, где его
измеряли (страница без `.header-search`, т.е. главная). Но `flex-basis:
auto` берёт гипотетическую ширину `.site-nav` из полного, несвёрнутого
содержимого списка меню (несмотря на `overflow-x:auto` у вложенного `ul`) —
и на **всех остальных четырёх поверхностях** (`catalog`, `collection_hub`,
`title`, `not_found`), где в шапке рядом есть `.header-search`
(`_header_search()` в `factory/lords/render.py`, форма скрыта только на
главной), этой ширины хватает, чтобы целиком вытолкнуть форму поиска на
вторую строку шапки.

Измерено `tests/tools/measure_candidate_tokens.js` на кандидате (5×3, живой
`python3 -m factory lords-preview --site animedia-preview --serve`):

| surface | 390 | 768 (до → после) | 1440 (до → после) |
| --- | --- | --- | --- |
| home | 61 | 98.56 → 61 | 61 → 61 |
| catalog / collection_hub / title / not_found | 125.8 | 152.25 → 61 | 110.25 → 61 |

Правка — `factory/lords/theme.py`, блок `@media (min-width: 640px)`:
`.site-nav{flex:1 1 auto}` → `.site-nav{flex:1 1 0%}`. `flex-basis:0%` отдаёт
гипотетическую ширину нулю; `.site-nav` встаёт в общую строку и получает
через `flex-grow` только реально свободное место, список внутри остаётся
прокручиваемым при нехватке места (`.site-nav ul{overflow-x:auto}`,
не тронуто). Перенос исчезает на всех пяти поверхностях разом, а не только
на той, что без формы поиска.

`tests/unit/test_candidate_visual_coverage.py::TestHeaderBreakpointStaysOnePassage`
проверял старое значение (`flex:1 1 auto`) буквально по тексту исходника —
обновлён на `flex:1 1 0%` и дополнен тестом, явно запрещающим `auto`
вернуться (регрессия того же класса, что и найденная).

### Компромисс со score — сознательный, не подгонка

`geometry` для `(catalog, 1440)` в контракте считает относительное
отклонение от эталонных 90px: было 110.25px (откл. 0.225), стало 61px
(откл. 0.322) — дальше от конкретного числа `amd.online`. Держать перенос
строки ради этой доли балла значило бы чинить число вместо дефекта — прямо
запрещено этим циклом. Полная разбивка — `scoring-summary.json
.header_geometry_fix_effect`.

## Профильные блокеры (не эта ветка — для Animedia writer)

### 1. `header_sticky` — кандидат `true` на всех 15 ячейках, эталон `false` на всех 15

Источник в общем слое — `factory/lords/theme.py:472-476`
(`.site-header{position:sticky;...}`), общий для всех профилей (lords-general/
curated/genre/new, zona-cinema, animedia-portal). Это не баг: рендерится
ровно так, как написано, и sticky-шапка — обычный, часто желаемый паттерн.
Несовпадение — то, что `amd.online` в реальности НЕ держит шапку прилипающей,
а этот общий шаблон — держит везде. Менять поведение для всех профилей ради
одного эталона недопустимо (тот же принцип «не подгоняй число под один
кандидат»). Если продукту Animedia нужно точное визуальное соответствие
`amd.online`, это профильная настройка: либо принять расхождение как
осознанное отличие дизайна, либо запросить у владельца общего слоя
конфигурируемый профильный флаг (`layout.header_sticky` или аналог) —
это отдельный запрос на фичу в общий слой, не тихая правка сейчас.

- Файл (профильный слой, не трогать этой веткой):
  `blueprints/lords/profiles/animedia-portal.yaml`.
- Токен: `header_sticky` (surface: `catalog`, `collection_hub`, `home`,
  `not_found`, `title`; viewport: `390`, `768`, `1440` — все 15 ячеек).
- Ожидаемое исправление (для Animedia writer / владельца профиля, не для
  этой ветки): принять расхождение осознанно **или** завести запрос к
  владельцу `factory/lords/**` на профильный флаг для `position: sticky`
  шапки.

### 2. `type_h3_font_size` / `type_h3_font_weight` — кандидат не совпадает с эталоном по абсолютному значению

Эталон (`amd.online`, PR #80): `14px` / `500` на всех измеренных ячейках.
Кандидат: `.card__title{font-size:.92rem;font-weight:600}`
(`factory/lords/theme.py`) — не подогнан под 14px намеренно, это общий
дизайн-токен шаблона, используемый всеми профилями. Приводить это конкретное
число к 14/500 в общем слое значило бы тюнинговать общий CSS под одну
Animedia-референс-пару — тот же принцип, что и с `header_sticky`.

- Файл (профильный слой, не трогать этой веткой):
  `blueprints/lords/profiles/animedia-portal.yaml` (профильные theme-токены,
  если шаблон их для этого экспонирует) **или** отдельный запрос к владельцу
  общего слоя на профильный override `--card-title-size`/`--card-title-weight`,
  если такого рычага в профиле сейчас нет.
- Токен: `type_h3_font_size` (эталон 14px, кандидат ≈14.7px при обычном
  16px root — см. примечание ниже), `type_h3_font_weight` (эталон "500",
  кандидат "600"). Surface: `home`/`catalog`/`title` (везде, где есть
  карточки с `<h3>`).
- Ожидаемое исправление: профильная задача, не эта ветка.

**Побочное наблюдение, не исправлено в этом цикле (за рамками найденного
дефекта, требует отдельного решения владельца дизайн-системы):**
`.card__title{font-size:.92rem}` резолвится от `<html>`, у которого в
`factory/lords/theme.py` НЕТ явного `font-size` — используется implicit
UA-default браузера (в этом окружении Chromium 151 даёт 16px). `<body>`
при этом явно объявляет `font-size:14px` («Базовый кегль референсов —
14px», комментарий в theme.py) — то есть весь `rem`-масштаб шаблона неявно
завязан НЕ на задекларированную дизайн-базу, а на implicit UA default,
потенциально чувствительный к настройкам доступности/локали браузера.
Подтверждено дважды детерминированным повтором в этой сессии (639/639
токенов побитово совпали), но НЕ подтверждено против того окружения, что
дало более ранние 17.66px для того же токена — увязать с конкретной
причиной не удалось. Не исправлено намеренно: смена базы `rem` меняет
визуальный масштаб КАЖДОГО элемента на `rem` во ВСЕХ профилях
(lords-general/curated/genre/new, zona-cinema, animedia-portal), а не
только чинит этот один токен — решение по конкретному значению базы
(14px? 16px?) выходит за рамки «исправь реальный дефект» этого цикла и
требует владельца дизайн-системы, а не одностороннего решения этой ветки.
