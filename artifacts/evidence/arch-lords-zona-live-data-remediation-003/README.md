# Восстановление живых данных Lords и Zona (003)

Ветка `claude/arch-lords-zona-live-data-remediation-003`, предшественник
`c69eadd9` (`arch-lords-data-contract-backfill-002`).

## Что было сломано

Публичный рендерер (`lords-frontend.py`) берёт оценки, описания и постеры
только из бокового файла `{site}-details.json`. Этот файл собирался из
`detail-cache`, который покрывает треть каталога. Оценки, которые поставщик
отдаёт в списке каталога, до страницы не доходили: на витрине это выглядело
как «КП — IMDb —» у записи, для которой источник оценку вернул.

Проверено на живых доменах до работы: на главной Lords **0 из 48** карточек
показывали оценку.

## Чего в источнике нет

Оставшиеся пустыми оценки — это отсутствие значения у поставщика, а не потеря
по дороге. Проверено поимённо: у 12 карточек главной Zona поставщик отдаёт 0
оценок Кинопоиска и 1 IMDb — ровно столько и показано. Выдумывать
отсутствующие значения запрещено, и ни одно не выдумано.

## Документированные исключения

| причина | lords-01 | zona-01 |
|---|---|---|
| `ambiguous_slug` — один slug у поставщика принадлежит нескольким произведениям | 121 | 15 |
| `no_id_mapping` — slug не связан ни с одним идентификатором | 3 | 2 |

Неоднозначные slug'и **не** разрешаются наугад. Выбрать любой из двух
идентификаторов значит однажды показать чужое произведение под знакомым
адресом — снаружи это выглядит как работающая страница и потому не будет
замечено. `WRONG_ENTITY_COUNT=0` именно поэтому.

## Боевой отказ и откат (произошёл, устранён)

Первая полная раскатка Lords уронила витрину: `/`, `/catalog/`, `/new/`
начали отдавать **502**, `/healthz` при этом оставался 200.

* Причина: рендерер читает сезоны как `сезон["n"]` — по индексу, без `get`.
  Каноническая проекция проносила сырую форму поставщика
  (`number`/`episodes_count`). Значения были верные, форма — чужая.
* Действие: немедленный откат к образу до задачи. SHA-256 после отката совпал
  с исходным (`a58f9d73…`), все маршруты вернулись в 200 за один перезапуск.
* Исправление: `сезоны_рендерера()` приводит обе формы к `{n, eps, avail}`, а
  `проверить_контракт_рендерера()` прекращает прогон **до** записи при любом
  нарушении формы, которую шаблон читает по индексу.
* Новая ступень: `--staging-out` собирает файл вне production, после чего
  настоящий рендерер поднимается на свободном порту и проверяется. Проверки
  формы ловят известные способы уронить витрину, прогон рендерера — ещё и
  неизвестные.

Отказ и откат оставлены в evidence (`incident-rollout-lords-01-failed.json`)
намеренно: раскатка, у которой нет доказанного отката, отличается от
раскатки, у которой он есть, только тем, что его ещё не пробовали.

## Порядок, которым это выкачено

Для каждой витрины отдельно: сухой прогон → черновик вне production → прогон
настоящего рендерера на свободном порту → резервная копия → канарейка из 6
представительных записей → публичная проверка канарейки → полная раскатка →
перезапуск только своего сервиса → публичная проверка.

Канарейки: запись только с КП, только с IMDb, с обеими, с описанием, с
постером и привязкой к источнику, и контрольная, которая измениться не должна
(`chas-rasplaty-2` для Lords, `medvezhya-shkura` для Zona). Обе контрольные
остались неизменными.

`public-verification.json`, три независимых прохода:

* `/healthz`, `/`, `/catalog/`, `/new/` — 200 на обеих витринах;
* по 100 случайных title-страниц каждой витрины — 200, без soft-404;

`image/webp` (проверено на обеих витринах). Шаблон не изменялся.
