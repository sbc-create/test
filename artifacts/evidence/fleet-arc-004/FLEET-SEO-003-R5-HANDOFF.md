# FLEET-SEO-003.R5 — как повторить R4 без доступа к общему хранилищу

## Что произошло в R4

Прогон работал по общему Changeset Store и оставил там 12 строк
(4 предложения + 4 набора + 4 цели) и 8 зависимых записей ящика. Вины
исполнителя в этом меньше, чем кажется: путь к базе берётся из
`CHANGESET_DB`, а при отсутствии переменной **молча подставляется общий**.
Тихое значение по умолчанию и есть причина.

Очистка не выполнена и выполняться вами не должна: права на общее хранилище
у SEO нет и не появится. Точный перечень и порядок — в
`R4-OWNER-CLEANUP-RUNBOOK.md`, применяет его владелец Changeset Store.

## Что исправлено в CORE

**1. Идемпотентность больше не зависит от случайности.**

Было: `proposal_id = uuid4()` попадал в `requested_change`, а контур
сравнивает повторы именно по этому полю. Два логически одинаковых запроса
с одним ключом оказывались несравнимы — второй получал 409 вместо повтора.
После аварии между созданием набора и вставкой предложения повтор упирался
в тот же ложный конфликт, а набор оставался сиротой.

Стало: идентификатор выводится из намерения —
`sha256(requester_service \0 idempotency_key)`. Пара уже уникальна в
таблице, поэтому новых столкновений не возникает. `requested_change` несёт
только каноническое намерение клиента; серверных значений в нём нет.

**2. Запись стала настоящей транзакцией.**

Соединение открывается с `isolation_level=None` — в режиме автофиксации, где
`with соединением` транзакции **не открывает**. Прежнее утверждение о «одной
транзакции» было неверным: предложение и набор фиксировались по отдельности.
Добавлен явный `BEGIN IMMEDIATE` (`store.транзакция`), и теперь авария между
ними откатывает обе записи.

**3. Появилась защита от работы по общему хранилищу.**

`factory/site_engine/changeset/isolation.py`:

```python
from factory.site_engine.changeset import isolation as I

окр = I.эфемерное_окружение(врем_каталог)   # 7 переменных, все в своём каталоге
I.требовать_эфемерное(окр["CHANGESET_DB"])  # отказ, если это общее хранилище
```

Отказывает по четырём признакам, каждый проверен отдельно:

| признак | случай |
|---|---|
| `dsn` | путь буквально равен общему |
| `realpath` | символическая ссылка на общий файл |
| `inode` | другое имя того же файла |
| `directory` | любой файл в каталоге общего хранилища |
| `unset` | путь не задан — подстановки по умолчанию не будет |

`эфемерное_окружение` возвращает **словарь**, а не правит окружение процесса:
правка на месте переживает прогон и достаётся следующему.

## Требования к прогону R5

1. **Своё хранилище на каждый запуск.** Каталог из `mkdtemp`, семь
   переменных из `эфемерное_окружение`, ни одного значения по умолчанию.
2. **Fail-closed до первого запроса.** `требовать_эфемерное` вызывается
   перед поднятием службы, а не после. Отказ — остановка прогона, не
   предупреждение.
3. **Никакого отката на общее хранилище.** Ни при отсутствии переменной, ни
   при ошибке создания каталога, ни в обработчике исключений.
4. **Уборка при любом исходе** — успех, отказ, прерывание. Каталог удаляется
   в `finally`; эфемерный сервер поднимается с `PR_SET_PDEATHSIG`, иначе
   убитая обвязка оставляет его сиротой (так уже было в CORE-002).
5. **Сверка общего хранилища до и после: дельта 0.** Сравнивать не счётчики,
   а точные множества идентификаторов — одинаковое число получится и после
   записи с удалением.
6. **Три focused suite целиком**, `failed=0`, `skipped=0`, `xfailed=0`.
7. **`PRODUCTION_MUTATIONS=0`, `LIVE_QWEN_CALLS=0`.**

Образец прогона, который всё это уже делает, — `tests/arc_seo/run_arc003.py`:
он поднимает свой экземпляр Control API, выбирает свободный порт через
операционную систему и сверяет канонические хранилища до и после.

## Что учесть про одобрение

Стадия `approve` обращается к службе подписи, которая читает **каноническое**
состояние. На эфемерных наборах она отказывает с
`план опирается на версию реестра 100, действующая 32` — и отказывает
правильно. Направлять её на свои данные нельзя. Поэтому R5, как и ARC-003,
доказывает `approve`/`apply` как **заблокированные без одобрения**, а
исполнимость адаптера — его собственным полным циклом.

Двадцать одна проверка в `tests/changeset` падает по этой же причине и на
развёрнутом релизе тоже. Это предсуществующее состояние контура одобрения, не
ваш дефект и не следствие этих правок.
