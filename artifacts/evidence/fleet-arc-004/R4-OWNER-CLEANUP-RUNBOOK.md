# Очистка следов SEO R4 в общем Changeset Store

Ничего не удалено. Это описание того, что предстоит сделать **владельцу
Changeset Store** после отдельного подтверждения. Архитектор права на
удаление не имеет и его не брал.

## Что обнаружено

`/srv/site-factory/changeset-store/changesets.sqlite3`

| таблица | строк | из них от R4 |
|---|---|---|
| `seo_content_proposal` | 4 | 4 |
| `changeset` | 4 | 4 |
| `changeset_target` | 4 | 4 |
| `changeset_outbox` | 8 | 8 (зависимые, уже опубликованы) |
| `changeset_transition` | 0 | — |

**12 ключевых строк** = 4 + 4 + 4. Именно это число назвал SEO. Ящик —
зависимые записи сверх двенадцати.

До прогона R4 хранилище было пустым: отпечаток production от 12 сентября
(`artifacts/evidence/fleet-arc-003/production-before.json`) фиксирует
`changeset: {"changesets": 0}`. Чужих и ранее существовавших записей в этих
таблицах нет — удалять нечего, кроме следов R4.

## Чем доказано происхождение

Каждое из четырёх предложений несёт **шесть независимых признаков**, а
требовалось два:

1. `model_version` содержит `fake_shadow` — настоящая модель такого не даёт;
2. `prompt_version = seo-r4-prompt/1.0.0` — называет прогон прямо;
3. ключ идемпотентности начинается с `probe-` или `s2-`;
4. `correlation_id` начинается с `corr-probe-` или `corr-s2-`;
5. время: два всплеска 03:14:06–07 и 03:16:10–11 тринадцатого сентября;
6. витрины `demo-books` (non-production, DRAFT) и `synthetic-http-b4e4f1`
   (test, DRAFT) — ни одна не входит в девять production ACTIVE.

`UNKNOWN_PROVENANCE` — ноль. `PREEXISTING_LEGITIMATE` — ноль.

## Чего делать нельзя

```sql
-- ЗАПРЕЩЕНО: снесёт всё, включая будущие законные записи
DELETE FROM seo_content_proposal;
DELETE FROM changeset WHERE resource_type = 'seo.content.proposal';
DELETE FROM changeset WHERE status = 'PROPOSED';
DELETE FROM changeset WHERE created_at < '2026-09-14';
```

Любое условие вместо перечня идентификаторов однажды совпадёт с чужой
записью, и узнают об этом уже после удаления.

## Что именно удалять

Точный перечень — `r4-cleanup-manifest.json`, 20 строк с неизменяемыми
идентификаторами. Порядок продиктован внешними ключами: сначала то, что
ссылается, потом то, на что ссылаются.

```
1. seo_content_proposal  по proposal_id   (4 строки)
2. changeset_target      по (changeset_id, site_id)  (4 строки)
3. changeset_outbox      по seq           (8 строк)
4. changeset             по changeset_id  (4 строки)
```

## Порядок действий владельца

1. **Остановить процесс контура**, иначе он может писать во время очистки:
   ```
   sudo systemctl stop site-factory-changeset-worker
   ```
2. **Снять проверенную копию** штатным средством, а не `cp`:
   ```
   python -m factory.site_engine.changeset.backup cycle
   ```
   Вердикт восстановления обязан быть `PASS`. Без него дальше не идти.
3. **Применить манифест** — только по идентификаторам из файла, по одной
   строке, в указанном порядке, внутри одной транзакции.
4. **Проверить итог**: все четыре таблицы обязаны стать пустыми
   (`verification_after` в манифесте).
5. **Запустить процесс обратно** и убедиться, что он поднялся:
   ```
   sudo systemctl start site-factory-changeset-worker
   systemctl is-active site-factory-changeset-worker
   ```

## Журнал аудита не трогать

Восемь событий, `ledger_seq` 115–122, остаются на месте. Журнал только на
добавление, и удаление разрушило бы цепь хешей — то самое свойство, ради
которого журнал существует. Если события нужно вывести из рабочих решений,
для этого есть логический карантин CORE-002:
`audit.event_set.quarantined.v1` со ссылкой на манифест. Это отдельное
решение и отдельная задача.

## Почему следы вообще появились

Прогон R4 работал против общего хранилища вместо своего. Корень — не
небрежность исполнителя: путь к базе берётся из `CHANGESET_DB`, а при
отсутствии переменной подставляется общий. Тихое значение по умолчанию и
есть причина. Требования к повторному прогону (fail-closed при совпадении с
общим путём) описаны в `FLEET-SEO-003-R5-HANDOFF.md`.
