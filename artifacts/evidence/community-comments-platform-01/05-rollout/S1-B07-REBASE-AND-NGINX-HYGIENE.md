## 4. Почему nginx блокировал выкладку и что теперь мешает этому повторяться

Apply не дошёл до первой мутации: он останавливался на собственной проверке
include-гигиены. Файл доказательства `stage1-apply-evidence.txt` обрывается на
заголовке `== nginx include hygiene` — дальше ничего не записано.

Причина — `/etc/nginx/lords/animedia-01.conf.before-comments-stage1`, который
записала **прежняя** версия apply. Это тупик: чтобы файл убрать, нужен root, а
root держал именно тот скрипт, который из-за файла отказывался стартовать.

Почему бэкап рядом с конфигом вообще опасен:

```
include /etc/nginx/sites-enabled/*;    # фильтра расширения нет вовсе
include /etc/nginx/lords/*.conf;       # фильтр есть, но только по суффиксу
```

Копия рядом грузится как второй `server`-блок. Это источник уже имеющихся на
хосте предупреждений `conflicting server name` (они принадлежат Yummy, записаны
и не исправляются).

Исправлено структурно, а не соглашением. Правила вынесены в
`automation/host/nginx_backup_hygiene.sh` и подключаются **обоими** скриптами:

* `nginx_backup_path()` — единственный способ назвать бэкап. Отказывает на любом
  `BACKUP_DIR` внутри `/etc/nginx` и на имени, которое не является простым
  именем файла. Записать бэкап в include-каталог теперь нельзя — не «не нужно».
* `nginx_quarantine()` — переносит посторонний файл харнесса в `$BACKUP_DIR` под
  именем `<имя>.quarantined.<UTC>` с разрешением коллизий. **Никогда не удаляет**:
  это чья-то копия для отката, и плоха в ней не суть, а местоположение.
* `nginx_assert_clean()` — отказ, если после переноса что-то осталось.
* Rollback отказывается восстанавливать vhost из бэкапа, лежащего внутри
  `/etc/nginx`: иначе откат зависел бы от дефекта, который призван устранить.
* Чужие `*.bak.*` не трогаются.

Заодно закрыты два дефекта, найденные при правке: `[ -f "$VHOST" ] && cp …`
отдельной строкой при `set -e` завершал скрипт молча, а `find … -name A -o -name B`
без скобок навешивал неявный `-print` только на последний шаблон.

## 7. Что не сделано и почему

**Выкладка не выполнена. Статус — `BLOCKED_ACCESS`, не «не успел».**

`sudo` отклоняется профилем сессии (`[factory-guard G-PRIV]`), а
`inventory/ssh-hosts.yaml` содержит `hosts: []` — ни хоста, ни `sudo_allowlist`.
По `.claude/rules/infrastructure.md` значения, которого нет в inventory, не
существует. `bypassPermissions` по CLAUDE.md не используется. Это та же
причина, что зафиксирована в `PILOT_READY.json` от 12:44.

Поэтому **не выполнены** и требуют владельца:

* перенос `/etc/nginx/lords/animedia-01.conf.before-comments-stage1` — файл
  по-прежнему на месте, `root:root`, 1951 байт, `/srv/site-factory/var/comments/backups/`
  пуст. Переносить его вручную больше не нужно: apply сделает это сам, под root,
  первым же шагом и с сохранением файла;
* `nginx -t`, повторный apply, перезагрузка nginx;
* живая проверка: главная, каталог, страница тайтла, плеер, UX, видимость
  комментариев только владельцу, тестовый комментарий и премодерация, закрытый
  доступ для обычного посетителя, noindex/canonical, неизменность animedia.space.

Команда владельца — одна:

```bash
sudo bash /home/claude/wt-community-comments-platform-01/automation/host/animedia-comments-stage1-apply.sh
```

Скрипт сам: перенесёт посторонний файл в хранилище бэкапов, сверит базу адаптера
с объявленным релизом, проверит noindex до любой мутации, и при любом отказе
живой проверки откатит **только** изменения комментариев (trap по счётчику
мутаций). Откат вручную:

```bash
sudo bash /home/claude/wt-community-comments-platform-01/automation/host/animedia-comments-stage1-rollback.sh --full
```

База комментариев `/srv/site-factory/var/comments/comments.sqlite` не удаляется
ни на одном уровне отката.
