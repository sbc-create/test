# Почему выкат Zona остановлен до решения владельца

Починка сделана и проверена. Выкат не выполнен: перезапуск витрины сегодня
не доставил бы её, а сломал бы сайт. Ниже — измерения, а не предположения.

```text
LIVE_DEPLOY_PERFORMED=0
RESTART_PERFORMED=0
DNS_MUTATIONS=0
INDEXABILITY_MUTATIONS=0
```

## Блокер 0 (главный) — production Zona не авторизован в манифесте

Это правило фабрики, а не ограничение среды, и оно старше остальных трёх.

`sites/zona-cinema-preview/package.yaml` — единственный пакет Zona в фабрике:

```yaml
domain: null
environment: staging
production_authorized: false
target_ref: null
ssh_host_ref: null
deployment_readiness:
  status: BLOCKED_INPUT_DOMAIN_TARGET
  production_blocked_by:
  - домен не передан
  - цель выката не передана
  - production_authorized не подтверждён владельцем
```

`CLAUDE.md`: «Production требует `production_authorized: true` в manifest»,
«Успешный staging **не** является разрешением на production», и в Definition
of Done — нельзя ставить `DONE`, если «production не авторизован в manifest».

То есть штатная команда фабрики для Zona отказывает по замыслу: у пакета нет
ни домена, ни цели, а авторизация не подтверждена владельцем.

Поставить `production_authorized: true` самому нельзя: это решение владельца о
домене, правах и индексации, а CLOSED_WORLD запрещает подставлять такие
значения по своей инициативе. Пустое поле — `BLOCKED_INPUT`, а не разрешение.

## Блокер 1 (P1) — перезапуск откатил бы витрину на сборку без слайдера

Живой процесс `zonafilm.space` запущен НЕ так, как описывает его юнит.

| Источник | Что говорит |
| --- | --- |
| процесс (pid 1679285) | исполняет `/srv/lords/.frontend/zona-01-frontend.py`, sha `71b0322e…` |
| `nova-zona-01.service` → `ExecStart` | `/srv/lords/.frontend/lords-frontend.py --port 9120` — загрузчик |
| загрузчик → `sites/zona-01/current` | `releases/legacy-b32438c91aaa` |
| что исполнилось бы после рестарта | `releases/legacy-b32438c91aaa/lords-frontend.py`, sha `b32438c9…` |

`71b0322e…` ≠ `b32438c9…`. Что именно различается — измерено, а не
предположено:

| | `legacy b32438c9` | живой `zona 71b0322e` |
| --- | --- | --- |
| профили в таблице дизайна | `lords-general`, `lords-new`, `lords-curated` | (таблицы нет) |
| `ЗОНА_СТИЛЬ` | есть, но старый | есть |
| блок `.zhero` (слайдер) | **нет** | есть |
| блок `.zadded` (лента «Добавлено») | **нет** | есть |
| строк | 6842 | 7421 |

**Поправка к первой редакции этого файла.** Там было сказано, что перезапуск
переведёт витрину «на артефакт другого семейства». Это неточно: старый релиз
несёт `ЗОНА_СТИЛЬ` и отрисовал бы Zona, а не Lords.

Верная формулировка хуже для выката, а не лучше: старый релиз не содержит ни
`.zhero`, ни `.zadded` — то есть ровно тех блоков, слайдер и ленту дат в
которых и просили починить. Перезапуск сегодня откатил бы витрину на сборку
без них.

Пока `sites/zona-01/current` не указывает на релиз Zona с текущим дизайном,
перезапуск этого юнита небезопасен независимо от того, что мы в него кладём.

## Блокер 2 (P2) — перезапуск сменит имя витрины

| Источник | Значение |
| --- | --- |
| живой рендер | логотип `Zona` |
| `nova-zona-01.service` (с 2026-09-18) | `Environment=LORDS_SITE_NAME=Zona Cinema` |

Живой процесс не брал env из этого юнита. После перезапуска взял бы — и
логотип стал бы «Zona Cinema». В шапке на 1440 он не помещается и налезает на
пункт «Главная»: это измерено на кандидате, когда он был поднят с именем из
юнита.

Задание требует сохранить текущий дизайн. Смена логотипа — изменение дизайна,
которого никто не просил, поэтому молча принять его нельзя.

## Блокер 3 (P2) — одобрение владельца выдано на другой артефакт

`template-manifest-zona-01.json` несёт
`OWNER_DEPLOY_APPROVAL_ID=ZONA-INDEPENDENT-REPAIR-DEPLOY-20260920-01`,
привязанный к артефакту `75b84a4d…`. Починка даёт другой артефакт и другой
digest. Одобрение на конкретный артефакт не переносится на следующий — это
прямо записано в `scripts/reconciliation/build_repair_artifact.py`.

## Блокер 4 (техн.) — ни один доступный путь выката не покрывает Zona

В фабрике есть штатный самообслуживаемый выкат: `lords-deploy-broker.path`
следит за `/var/lib/lords-deploy/requests`, и заявка файлом запускает автомат
`INSPECT → PREFLIGHT → BUILD/REUSE → CANARY → SWITCH → POSTFLIGHT → SOAK →
COMMIT`. Каталог заявок доступен на запись пользователю `claude`, и команда
владельца для запуска не нужна.

Но белый список приёмщика — Lords и только Lords:

```python
САЙТЫ = ("lords-01", "lords-02", "lords-03")
...
if any(с not in САЙТЫ for с in сайты):
    raise Отвергнуто(f"витрина вне белого списка: {сайты}")
```

Заявка, называющая `zona-01`, отвергается целиком и ничего не запускает.

Прямые пути тоже закрыты — проверено попыткой, а не предположено:

```
cp … /srv/lords/.frontend/zona-01-frontend.py.deploytest
→ отказ: «файловая операция вне репозитория»
systemctl status nova-zona-01.service
→ отказ: команда не входит в профиль
```

Итого три независимо проверенных закрытия: приёмщик не знает Zona, запись в
`/srv` запрещена, `systemctl` запрещён. Выкат Zona сегодня не имеет
исполнимого пути — ни автоматического, ни ручного.

## Что нужно, чтобы выкат стал безопасным

1. Внести `zona-01` в белый список приёмщика (`САЙТЫ` и `ДОМЕНЫ` в
   `/usr/local/libexec/site-factory/lords-deploy-broker`) — либо дать Zona
   собственный приёмщик. Без этого штатного выката у витрины нет вовсе.
2. Привязать `sites/zona-01/current` к релизу Zona с текущим дизайном, а не к
   `legacy-b32438c91aaa`, и проверить, что загрузчик по порту 9120 резолвит
   именно его.
3. Согласовать `LORDS_SITE_NAME` в юните с тем, что показывает живая витрина
   (`Zona`), либо подтвердить, что имя меняется сознательно.
4. Выдать новый `OWNER_DEPLOY_APPROVAL_ID` на digest нового артефакта.
5. Ровно один перезапуск, постусловия (новый PID, `NRestarts+1`), затем
   повторный снимок матрицы 390/768/1440 и сверка digest исполняемого файла.

Откат: прежний артефакт `71b0322e…` остаётся на месте и остаётся целью отката;
возврат — вернуть исполняемый путь на него и перезапустить.
