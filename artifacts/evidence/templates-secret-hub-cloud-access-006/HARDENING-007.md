# SECRET-HUB-ROOT-BOUNDARY-HARDEN-007 — закрепление границы root

Секретов здесь нет: только пути, коммиты, хеши кода и имена unit'ов. Ни одна
операция этой работы не открывала файл секрета.

## Область оказалась шире пяти юнитов

Задание называет пять. Транзитивная проверка всей цепочки исполнения — не
только `ExecStart`, но и интерпретатор, `PYTHONPATH`, `WorkingDirectory`,
каталог инструментов, `EnvironmentFile`, шебанг и элементы `PATH` — нашла
**13 root-юнитов из 27**, и **5 из них получают расшифрованные credentials**.

Полный отчёт: `audit-before-hardening.json` (144 нарушения).

### Самое важное: уязвим сам Secret Hub

```
site-factory-secret-hub.service
  ExecStart=/opt/site-factory-secret-hub/venv/bin/python -m factory.secret_hub serve   ← интерпретатор root-owned
  PYTHONPATH=/srv/site-factory/repo        ← владелец claude, режим 0775
  WorkingDirectory=/srv/site-factory/repo  ← то же
  LoadCredential=secret_hub_master_key:…
```

Root-процесс, держащий мастер-ключ и все расшифрованные значения, импортирует
пакет `factory` из каталога, которым владеет агент. Подменив
`factory/secret_hub/service.py`, учётная запись `claude` исполняет свой код
внутри процесса, который по проекту единственный имеет доступ к секретам.

Проверка `SO_PEERCRED` в хабе работает как задумано. Она просто не на этом
пути: граница обходится не через API хаба, а через его собственный `PYTHONPATH`.

Это делает вывод прошлого отчёта точнее: дело не в «соседних службах с
доступными на запись скриптами», а в том, что **весь контур исполняет код из
каталога агента**, и хаб — не исключение из этого, а самый дорогой его случай.

### Поправка к прошлому выводу

В прошлом отчёте `lords-content-refresh.service` назван образцом правильного
закрепления. Это неверно, и ошибка существенная:

```
ExecStart=/srv/site-factory/lords-tooling/releases/0b0722f3…/…/lords-content-refresh.sh
```

Путь закреплён, но `/srv/site-factory` **принадлежит `claude`**. Владелец
каталога переименует `lords-tooling` и подставит своё дерево — права на сами
файлы при этом не нужны. Вдобавок у того же юнита
`FACTORY_PYTHON=/srv/site-factory/repo/.venv/bin/python`, а `.venv` — ссылка в
`/home/claude/work-test/.venv`, то есть интерпретатор тоже агентский.

Отсюда требование к месту закрепления: **ни один родительский каталог не
принадлежит агенту**. Поэтому закреплённый рантайм ставится в `/opt`, а не в
`/srv/site-factory`.

### Бандл воспроизводим

Три независимые сборки дали один и тот же `sha256`. Это условие проверяемости:
владелец может пересобрать бандл из тех же коммитов и сравнить хеш. Фиксируются
владелец, группа, права, порядок файлов и mtime; `gzip -n` убирает имя и время
из заголовка.

Провенанс записан **по файлам**: у каждого из 168 файлов свой `sha256` и
коммит, из которого он взят. Файл без провенанса обрывает сборку.

### Расхождение с рабочей копией хоста

`automation/host/nova-daily-refresh.sh` в момент сборки **не совпадал** с
отсмотренным коммитом `2bb47de` — и сменился дважды за время работы: другая
сессия правит его прямо сейчас.

Закрепляется версия из коммита. Закреплять байты, которые никто не смотрел,
означало бы оставить root на непроверенном коде — то есть сделать ровно то, от
чего мы уходим. Расхождение записано обоими хешами в `dist/release.json`
(`host_divergences`) и требует явного признания при сборке
(`--accept-host-divergence`), иначе сборка отказывает.

**Действие владеющей сессии:** закоммитить свою правку, после чего бандл
пересобирается. Иначе после установки будет исполняться не то, что лежит на
хосте сегодня.

То же касается `lords-canary-apply.sh`: рабочая копия в
`/home/claude/wt-release-03` разошлась с коммитом `f47b63a`; закрепляется
версия коммита.

## Почему тест зелёный, хотя хост ещё не исправлен

Тесты разделены на два рода, и разница между ними существенная:

* **контракт поставки** (16 проверок) — над файлами ветки, зелёные всегда:
  полнота охвата, наличие вектора у каждого юнита, отсутствие путей кода в
  каталогах агента, закреплённый `PATH`, совпадение хеша бандла, покрытие
  юнитов с credentials, и самопроверки аудита (он обязан уметь падать);
* **состояние хоста** (2 проверки) — SKIPPED с причиной, пока
  `/opt/site-factory/runtime/current` не существует. Текст пропуска говорит
  прямо: «ещё не исправлено», а не «исправно», и ссылается на находку.

Красный тест в ветке не оставлен. Дефект от этого не спрятан: он описан
находкой, измерен `audit-before-hardening.json`, и обе проверки станут
обязательными в ту же минуту, когда транзакция выполнится — установщик
вызывает тот же аудит десятым шагом и откатывается, если он не зелёный.

## Что транзакция не трогает

Шаблоны, каталоги, контент, SEO, плеер, DNS, TLS и **значения credentials**.
Ни одного `LoadCredential` не добавляется и не убирается; значения не читаются,
не перевыпускаются и не перемещаются. Меняются только пути, по которым root
берёт **код**. Пути к данным (`FACTORY_REPO`, `LORDS_ARTIFACT_ROOT`) оставлены
прежними намеренно: данные root читает и пишет по назначению, код он исполняет
— разница именно в этом.
